binary64 用 1 位符号、11 位指数与 52 位存储尾数（加 1 位隐含位）表示一个数值，共 53 位有效二进制位。可精确表示的值是形如 `m * 2^e` 的有理数，其中 `m` 的位宽不超过 53；其余值被舍入到最近的可表示值。判据是有效位数量：`2**100` 可以精确表示，`2**53 + 1` 不能。

binary64 是一个格式规范，哪些语言的哪个类型用它要逐个确认。Python 的 `float` 是 binary64；多数语言的 `double` 与 SQL 的 `REAL` 在常见实现中也是，但 SQL 的浮点类型语义由各引擎定义，JSON 的 `number` 不规定二进制布局（它只约束十进制语法与一个互操作的有效数字下限），十进制类型根本不是二进制浮点。因此「两边都是 binary64 就语义一致」不成立——跨系统传递数值要对每个系统分别确认类型、精度与舍入规则，关键数值用可检验的表示（字符串、定标整数）承载。

每次运算对结果舍入一次，加法不满足结合律，改变运算顺序会改变结果；十进制小数通常在二进制下无限循环，字面量写入时已经产生一次舍入。比较浮点结果应该用容差比较（`math.isclose`）或比较差值，不用相等比较；`inf` 与 `nan` 是格式的一部分，NaN 与任何值比较都为假，含 NaN 的排序与去重不可靠。

需要精确十进制或有理数时用另外的表示：`decimal.Decimal`、`fractions.Fraction` 或整数最小单位。用浮点存储金额并期望对账精确，或用浮点作计数器、索引以致超过 2^53 后相邻整数不再可分，都会得到错误结果。
