## 目的

本课解释数据变更语句的语义：它们如何改变表的状态，失败时状态停在哪一步，以及一个变更序列怎样被整体撤销。

查询可以从数据推导结论，变更语句改变后续推理的前提。生产事故中，数据被改坏的影响面比查询写错大得多，而状态转移的可推理性是判断改动是否安全的基础。本课使用夹具 <LabRef id="sql.orders.basic" />，变更语句都用前后查询呈现。

## 模型

- `INSERT` 增加行，`UPDATE` 修改匹配行的指定列，`DELETE` 删除匹配行。三者都接受 `WHERE` 子句决定匹配范围。
- 影响行数等于匹配到的行数。没有 `WHERE` 时条件恒真，语句匹配全表。
- **语句级原子性**：一条语句要么整体生效，要么整体不生效。约束在语句末尾检查，任一行违反约束会让整条语句回滚，已处理的行不会留下。
- **事务**（transaction）：把多条语句作为一个整体提交或撤销。`BEGIN` 开始，`COMMIT` 提交，`ROLLBACK` 撤销。事务失败时整个事务的效果都不存在，这是比语句级更强的恢复边界。
- `INSERT ... ON CONFLICT (key) DO UPDATE` 表达「键已存在则更新」，在一条语句里完成判定与写入，避免「先查询再写入」之间的窗口。
- `RETURNING` 让变更语句返回被影响的行，用于确认写入内容而不必再查询一次（SQLite 3.35 起支持）。
- 隔离与并发下的可见性属于事务与隔离级别的范围，本课只处理单连接上的状态转移。

## 定向变更与全表变更

```sql run id="sql.mut.update" fixture="sql.orders.basic"
UPDATE orders SET status = 'shipped' WHERE order_id = 1003;

SELECT order_id, status FROM orders WHERE order_id IN (1002, 1003) ORDER BY order_id;

UPDATE orders SET status = 'pending';

SELECT status, COUNT(*) AS orders FROM orders GROUP BY status ORDER BY status;
```

第一条语句只匹配订单 1003，影响一行，`WHERE` 之外的订单保持不变。第二条没有 `WHERE`，六行全部被改写成 `pending`，分组统计只剩一组。

两条语句形状相同，效果相差整个表。这类缺陷的形态是结果看起来合理：状态分布「变成了一种」，过程中没有错误或异常。

## 删除与引用完整性

```sql run id="sql.mut.delete" fixture="sql.orders.basic"
DELETE FROM order_items WHERE order_id = 1001;

SELECT order_id, COUNT(*) AS line_items
FROM order_items
GROUP BY order_id
ORDER BY order_id;

DELETE FROM orders WHERE order_id = 1002;
```

第一条删除了订单 1001 的两行订单行，影响行数是 2，其余订单行不变。第二条试图删除仍被订单行引用的订单 1002，被外键约束拒绝：`on_delete` 默认为 `NO ACTION`，删除被引用行会直接失败，不会静默留下悬空引用。

删除一个对象时有两个选择：先删引用它的行（自底向上），或让约束负责拒绝并在应用层处理失败。选哪一种取决于引用的生命周期。

## 写入即判定

```sql run id="sql.mut.upsert" fixture="sql.orders.basic"
INSERT INTO customers (customer_id, email, full_name, country, referral_code)
VALUES (4, 'barbara@example.com', 'Barbara Liskov', 'GB', 'REF-BAR')
ON CONFLICT (customer_id) DO UPDATE SET country = excluded.country;

SELECT customer_id, email, country FROM customers WHERE customer_id = 4;
```

`ON CONFLICT` 指定冲突目标为主键，冲突时执行更新，`excluded` 指代本次尝试插入的那一行，因此可以引用它提供的值。结果是一行被影响，4 号客户的国家从 `US` 变为 `GB`。

先 `SELECT` 再决定插入还是更新需要两次往返，两次之间的时间窗里另一个写入者可能插入同一行。`ON CONFLICT` 把判定与写入放进一条语句，由数据库在同一时刻完成。

## 返回受影响的行

```sql run id="sql.mut.returning" fixture="sql.orders.basic"
UPDATE orders
SET status = 'shipped', discount_cents = 100
WHERE order_id = 1003
RETURNING order_id, status, discount_cents;
```

`RETURNING` 让变更语句直接给出被影响行的内容，省掉「更新后再查询」的往返，也让写入结果与读取结果之间不再有窗口。

## 语句原子性与事务

下面五个单元格共享同一个具名 session 的连接，按顺序观察一个变更序列被逐步撤销的过程。

```sql run id="sql.tx.begin" session="orders-tx" fixture="sql.orders.basic"
BEGIN;

SELECT order_id, status, discount_cents
FROM orders
WHERE order_id IN (1002, 1003)
ORDER BY order_id;
```

```sql run id="sql.tx.update" session="orders-tx"
UPDATE orders SET status = 'shipped' WHERE order_id = 1003;
```

```sql run id="sql.tx.failed" session="orders-tx"
UPDATE orders
SET status = 'cancelled', discount_cents = -5
WHERE order_id = 1002;
```

```sql run id="sql.tx.visible" session="orders-tx"
SELECT order_id, status, discount_cents
FROM orders
WHERE order_id IN (1002, 1003)
ORDER BY order_id;
```

```sql run id="sql.tx.rollback" session="orders-tx"
ROLLBACK;

SELECT order_id, status, discount_cents
FROM orders
WHERE order_id IN (1002, 1003)
ORDER BY order_id;
```

第二个单元格把订单 1003 的状态改为 `shipped`，影响一行。第三个单元格尝试把订单 1002 的状态改为 `cancelled` 并把折扣设为 −5，被 `CHECK` 拒绝；这条语句同时修改两列，失败之后两列都没有留下痕迹，这就是语句级原子性——它不能被拆成「一半生效」。

第四个单元格显示：1003 的改动仍在（属于事务内尚未提交的改动），1002 保持原值。第五个单元格执行 `ROLLBACK`，事务内的改动全部撤销，1003 回到 `pending`。

由此得到两个恢复边界：语句级失败恢复该语句，事务级撤销恢复该事务内的全部语句。需要两者都成立时，把变更语句放进事务里。

## 具名 session 与重置

```sql run id="sql.session.before" session="orders-demo" fixture="sql.orders.basic"
SELECT COUNT(*) AS orders_before FROM orders;
```

```sql run id="sql.session.insert" session="orders-demo"
INSERT INTO orders (order_id, customer_id, placed_on, status, discount_cents)
VALUES (1007, 2, '2026-03-05', 'pending', NULL);

SELECT COUNT(*) AS orders_after_insert FROM orders;
```

```sql run id="sql.session.after" session="orders-demo"
SELECT COUNT(*) AS orders_in_later_cell FROM orders;
```

默认情况下每个可运行单元格使用独立连接，因此单元格之间的写入不会互相影响。显式声明同一个 session 名之后，连接在该页面的运行时里保持存活：第三个单元格能看到第二个单元格插入的行。

「重置 session」会重建该 session 的连接并重新应用夹具，计数回到 6。这条约定让「变更后的状态可以观察、也可以还原」成为课程的默认前提，单元格之间的依赖不会隐藏在页面的执行历史里。

## 边界与失败情形

- **缺少 `WHERE`**：`UPDATE` 与 `DELETE` 在没有 `WHERE` 时匹配全表，这是最常见的破坏性变更。写变更语句时先单独运行它的 `WHERE` 条件确认匹配范围。
- **约束在写入时才检查**：外键、`CHECK`、`UNIQUE` 都在语句执行时判定，因此数据是否满足约束只能在写入时确认，静态审查代码看不出来。
- **隐式提交**：多数引擎在执行 DDL 时隐式提交当前事务。把 DDL 与数据变更放在同一个事务里会让「整体回滚」失效，这一点在模式变更时需要核对具体引擎的行为。
- **长事务**：事务保持打开会占用锁并阻止回收旧版本，把交互式等待放进事务是常见的资源事故来源。
- **非确定性变更**：`UPDATE ... FROM` 或多个匹配行的表达式求值顺序可能影响结果，涉及同一行的多次更新应显式写出顺序。
- **影响行数为 0**：条件没有匹配是正常结果，应用层需要区分「没有匹配」与「执行失败」，否则会把无效操作记成成功。

## 生产后果

- 破坏性变更的防护来自流程：先在事务里执行并检查影响行数，确认之后再提交。
- 变更与查询共用一个连接时，未提交的改动对同一连接可见、对其他连接不可见。这个差别决定了并发程序观察到的结果。
- 应用需要依据影响行数判断操作是否生效：删除返回 0 行通常意味着并发修改或条件写错。
- 数据修复脚本应可重复执行：`ON CONFLICT` 与条件化的 `WHERE` 让脚本在部分执行后仍能得到同一结果。

## 小结

- `INSERT`、`UPDATE`、`DELETE` 的状态转移由匹配条件决定，影响行数等于匹配行数，缺少 `WHERE` 时匹配全表。
- 语句级原子性保证失败的语句不留部分结果，两列的修改同时生效或同时不生效。
- 事务把多条语句作为一个整体提交或撤销，`ROLLBACK` 恢复事务开始时的状态。
- `ON CONFLICT` 在一次写入里完成存在性判定，避免先查后写的窗口。
- 具名 session 让单元格之间显式共享连接，重置它会重新应用夹具。
- 变更语句的影响行数是判断操作是否生效的依据，也是破坏性操作的即时反馈。
