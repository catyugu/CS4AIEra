## 目的

本课解释 SQL 中 <Term id="null-logic">NULL 三值逻辑</Term> 的语义，以及它如何让过滤条件、聚合与约束的表现偏离直觉。

`WHERE` 子句只保留谓词为真的行，而 NULL 参与的比较不产生真或假，只产生未知。由此产生的结果是行静默消失、`NOT IN` 静默返回空集、聚合忽略 NULL 输入、`CHECK` 拦不住 NULL。查询返回空集时，必须能判断这是「确实没有这样的数据」还是「谓词求值为未知」。

本课使用夹具 <LabRef id="sql.orders.basic" />。`customers.country` 与 `orders.discount_cents` 允许为空，其余列由约束保证非空。

## 模型

布尔表达式有三个真值：`TRUE`、`FALSE`、`UNKNOWN`。`WHERE` 保留结果为真的行，假与未知都被丢弃。

| 表达式 | 结果 |
| --- | --- |
| `NULL = NULL` | `UNKNOWN` |
| `NULL = 1` | `UNKNOWN` |
| `NULL IS NULL` | `TRUE` |
| `NOT UNKNOWN` | `UNKNOWN` |
| `TRUE OR UNKNOWN` | `TRUE` |
| `FALSE OR UNKNOWN` | `UNKNOWN` |
| `TRUE AND UNKNOWN` | `UNKNOWN` |
| `FALSE AND UNKNOWN` | `FALSE` |

未知会传播：由 `AND`、`OR` 组合的谓词只要含有未知且其余部分不足以决定结果，整体就是未知。`OR` 的左侧为真时整体为真，`AND` 的左侧为假时整体为假——这两条短路规则是唯一能让未知被吸收的情形。

`IS NULL` 与 `IS NOT NULL` 是谓词：它们判定「值是否存在」，对 NULL 给出确定结果。三值逻辑表达的是「值未知」，与「值等于空字符串」或「值等于零」完全不同。

## 比较运算不覆盖 NULL

```sql run id="sql.null.comparison" fixture="sql.orders.basic"
SELECT customer_id, full_name, country
FROM customers
WHERE country = 'GB'
ORDER BY customer_id;

SELECT customer_id, full_name, country
FROM customers
WHERE country <> 'GB'
ORDER BY customer_id;
```

第一条返回英国客户。第二条返回两位美国客户，国家未知的那一行没有出现：`NULL <> 'GB'` 求值为未知，被 `WHERE` 丢弃。

`country = 'GB'` 与 `country <> 'GB'` 的并集不覆盖全部行，原因是同一行在两种谓词下都得到未知。想表达「不是英国」并包含国家未知的客户，必须显式补上分支：

```sql run id="sql.null.complete-filter" fixture="sql.orders.basic"
SELECT customer_id, full_name, country
FROM customers
WHERE country IS NULL OR country <> 'GB'
ORDER BY customer_id;
```

`IS NULL` 与 `IS NOT NULL` 的并集覆盖全部行，因此它们是编写「互斥且完备」过滤条件的工具。检查一个过滤条件是否完备，用这两条互补谓词判断。

## NOT IN 与未知

`NOT IN` 是三值逻辑最容易造成静默错误的地方。

```sql run id="sql.null.not-in-literal" fixture="sql.orders.basic"
SELECT order_id, discount_cents
FROM orders
WHERE discount_cents NOT IN (200, 500)
ORDER BY order_id;

SELECT order_id, discount_cents
FROM orders
WHERE discount_cents NOT IN (200, 500, NULL)
ORDER BY order_id;
```

第一条返回两条 `discount_cents = 0` 的订单，`discount_cents` 为空的两条订单被未知排除。第二条在列表里加入一个 NULL 之后返回空集：`x NOT IN (200, 500, NULL)` 等价于 `NOT (x = 200 OR x = 500 OR x = NULL)`，对任何值，`x = NULL` 都是未知；当 `x` 不等于前两个值时，整条 `OR` 链是未知，取反仍是未知，行被丢弃。

子查询产生的 NULL 有同样的效果：

```sql run id="sql.null.not-in-subquery" fixture="sql.orders.basic"
SELECT order_id, discount_cents
FROM orders
WHERE discount_cents NOT IN (
    SELECT discount_cents FROM orders WHERE customer_id = 1
)
ORDER BY order_id;
```

客户 1 的两条订单折扣分别是 500 与 NULL，子查询的结果集含 NULL，于是整条查询返回空集，而「折扣不同于客户 1 的订单」在数据上是存在的。子查询的列可以为空时，`NOT IN` 的语义就不再是「不属于这个集合」。

表达「不存在」用 `NOT EXISTS`。它只判断子查询是否产生行，不把值代入比较：

```sql run id="sql.null.not-exists" fixture="sql.orders.basic"
SELECT c.customer_id, c.full_name
FROM customers AS c
WHERE NOT EXISTS (
    SELECT 1 FROM orders AS o WHERE o.customer_id = c.customer_id
)
ORDER BY c.customer_id;

SELECT c.customer_id, c.full_name
FROM customers AS c
WHERE c.customer_id NOT IN (SELECT o.customer_id FROM orders AS o)
ORDER BY c.customer_id;
```

两条查询返回同一个结论：4 号客户没有订单。第二条之所以在这里成立，是因为 `orders.customer_id` 被声明为 `NOT NULL`，子查询不可能产生 NULL。同一个写法换到可空列上就会静默返回空集，这就是「`NOT IN` 是否安全取决于列的约束」的含义。

## 聚合忽略 NULL

```sql run id="sql.null.aggregates" fixture="sql.orders.basic"
SELECT
    COUNT(*)                  AS rows_total,
    COUNT(country)            AS rows_with_country,
    COUNT(*) - COUNT(country) AS rows_without_country
FROM customers;

SELECT
    COUNT(*)            AS orders,
    SUM(discount_cents) AS discount_sum,
    AVG(discount_cents) AS discount_avg,
    MAX(discount_cents) AS discount_max
FROM orders;
```

`COUNT(*)` 数行数，`COUNT(column)` 只数该列非空的行，两者之差就是该列为空的行数。`SUM`、`AVG`、`MAX` 忽略空值输入：折扣合计 700 只由三个非空值产生，`AVG` 的分母是 3，因此平均值高于「把 NULL 当作零」的口径。

业务指标的分母由此确定。报表口径必须写明 NULL 的处置方式，否则同一个字段在不同查询里含义不同。

## 分组与排序

```sql run id="sql.null.grouping" fixture="sql.orders.basic"
SELECT country, COUNT(*) AS customers
FROM customers
GROUP BY country
ORDER BY country;
```

`GROUP BY` 把所有 NULL 归入同一组：分组使用「是否同一组」的等价关系，因此三个国家值（未知、GB、US）产生三组。这一点与 `WHERE` 中的比较不矛盾——两处处理的是不同的问题：过滤判断谓词真假，分组判断行是否属于同一类。

NULL 在排序中的位置由引擎决定：

```sql run id="sql.null.ordering" fixture="sql.orders.basic"
SELECT order_id, discount_cents
FROM orders
ORDER BY discount_cents, order_id;

SELECT order_id, discount_cents
FROM orders
ORDER BY discount_cents DESC, order_id;
```

SQLite 把 NULL 视为小于任何值，于是升序时排在最前、降序时排在最后。这是方言行为：PostgreSQL 的默认行为相反，标准 SQL 也不规定。跨引擎的报表要么显式写出 NULL 的处置，要么把 NULL 转换成参与排序的显式值。

## 约束在 NULL 上的保证范围

`CHECK` 只在结果为假时拒绝写入，而含 NULL 的表达式得到未知：

```sql run id="sql.null.check" fixture="sql.orders.basic"
SELECT COUNT(*) AS orders_before FROM orders;

INSERT INTO orders (order_id, customer_id, placed_on, status, discount_cents)
VALUES (1007, 1, '2026-03-05', 'paid', -1);
```

负的折扣被 `CHECK` 拒绝。

```sql run id="sql.null.check-null" fixture="sql.orders.basic"
INSERT INTO orders (order_id, customer_id, placed_on, status, discount_cents)
VALUES (1007, 1, '2026-03-05', 'paid', NULL);

SELECT order_id, discount_cents FROM orders WHERE order_id = 1007;
```

同一个约束对 NULL 不做判定：`CHECK` 求值为未知，约束不算被违反。要禁止这一列出现 NULL，必须再加 `NOT NULL`。

结论汇总：`NOT NULL` 排除空值，是其余约束实际生效的前提；`CHECK` 只拒绝明确为假的取值；`UNIQUE` 允许任意多行 NULL；外键列上的 NULL 表示「没有引用对象」，不触发参照完整性检查。

## 边界与失败情形

- **`IS DISTINCT FROM`**：部分引擎提供把 NULL 当作普通值比较的运算符，用于表达「确实不同」。SQLite 没有这个运算符，只能用 `IS NULL` 分支或 `COALESCE` 模拟。
- **`COALESCE` 与默认值**：`COALESCE(x, 0)` 让 NULL 参与运算，代价是「未知」与「零」在结果里不再可区分。用于展示可以，用于计数与均值会改变口径。
- **`NOT NULL` 的添加**：对既有数据加 `NOT NULL` 时，先回填再改约束，否则迁移失败。
- **`COUNT(DISTINCT)` 忽略 NULL**：去重计数同样不计空值，与 `COUNT(*)` 的差异需要显式说明。
- **`ORDER BY` 中的 NULL**：位置由引擎决定，跨引擎结果的顺序可能不同。
- **`NOT IN` 的可空列**：子查询列可空时改写成 `NOT EXISTS`，这是从语义出发的必要改动，不是风格偏好。

## 生产后果

- 应用层用空字符串或 0 表示缺失时，三值逻辑不再能区分「未知」与「空」。这类混淆会一直传播到报表与对账，且无法在查询层修复。
- 聚合的分母决定指标含义。平均值、比率与转化率的口径必须写清 NULL 的处置。
- 生成式工具常写出 `NOT IN (SELECT ...)` 形式的排除查询，在可空列上静默返回空结果，看起来像「没有数据」。
- 过滤条件成对检查：`=` 与 `<>` 覆盖不到 NULL，写入审查清单可以避免这一类缺陷进入生产。

## 小结

- NULL 表示未知；任何与它的比较得到未知，`WHERE` 丢弃未知的行。
- `IS NULL`、`IS NOT NULL` 是谓词，对 NULL 有确定结果，且两者互补覆盖全部行。
- 列表或子查询中出现 NULL 会让 `NOT IN` 返回空集；表达「不存在」用 `NOT EXISTS`。
- 聚合忽略 NULL 输入，`COUNT(*)` 与 `COUNT(column)` 的含义不同。
- `GROUP BY` 把 NULL 归入同一组；`ORDER BY` 中 NULL 的位置由引擎决定。
- `NOT NULL`、`CHECK`、`UNIQUE` 对 NULL 的保证各不相同，需要逐条核对。
