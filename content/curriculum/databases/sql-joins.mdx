连接的语义是：它由两个关系组合出新的关系，结果的行数由匹配对的数量决定，与两侧各自的行数无关。

连接的基数（cardinality）是后续索引与查询计划的输入，也是报表重复计数这类生产事故的来源。读一个连接查询时要能说出：它保留哪些行，一行可能匹配几行，条件里的 NULL 会怎样。

本课使用夹具 <LabRef id="sql.orders.basic" />。

## 连接的语义与匹配对

- `A JOIN B ON p` 的语义模型是：先取 `A` 与 `B` 的全部组合，再保留 `p` 为真的组合，最后按 `SELECT` 选择列。执行方式由优化器决定，与写法无关。
- **内连接**只保留匹配对；**左外连接**保留左表全部行，未匹配处在右表列上填 NULL；**反连接**保留没有匹配的左表行，用 `NOT EXISTS` 或 `LEFT JOIN` 加 `IS NULL` 表达。
- 结果行数等于匹配对的数量。连接条件不是候选键等式时，一行可以匹配多行，行数放大。
- 连接条件里的 NULL 参与比较得到未知，因此含 NULL 的行不匹配任何行，包括另一个 NULL。
- `ON` 是连接的匹配条件，参与生成连接结果；`WHERE` 在连接结果之上过滤。对左外连接，把右侧表的条件写进 `WHERE` 会丢弃由 NULL 扩展出来的行，效果退化为内连接。

## 内连接与左外连接

```sql run id="sql.join.inner-left" fixture="sql.orders.basic"
SELECT c.customer_id, c.full_name, COUNT(o.order_id) AS orders
FROM customers AS c
JOIN orders AS o ON o.customer_id = c.customer_id
GROUP BY c.customer_id
ORDER BY c.customer_id;

SELECT c.customer_id, c.full_name, COUNT(o.order_id) AS orders
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.customer_id
GROUP BY c.customer_id
ORDER BY c.customer_id;
```

内连接只给出有订单的三位客户。左外连接多出一行：4 号客户没有订单，未匹配处 `o.order_id` 为 NULL，`COUNT(o.order_id)` 数非空值，于是得到 0。这里必须用 `COUNT(o.order_id)`：`COUNT(*)` 会把 NULL 扩展行也数进去，得到 1。

选择哪一种取决于问题：「有订单的客户」用内连接，「每个客户的订单数」用左外连接。选错的表现是报表里整类对象消失，且不报错。`LEFT JOIN` 保留左表，`RIGHT JOIN` 保留右表；SQLite 从 3.39 起才支持 `RIGHT` 与 `FULL OUTER JOIN`，早期版本需要用交换表顺序或联合查询表达。在连接结果上计数或求金额会把一匹配多的行计入多次，按正确粒度先聚合再连接可以避免。

## 基数：结果行数由匹配对决定

```sql run id="sql.join.fanout" fixture="sql.orders.basic"
SELECT COUNT(*) AS order_rows FROM orders;

SELECT COUNT(*) AS matching_pairs
FROM orders AS a
JOIN orders AS b ON a.status = b.status;
```

`status` 不是候选键：`paid` 有两条、`shipped` 一条、`pending` 两条、`cancelled` 一条，匹配对数量是 4 + 1 + 4 + 1 = 10，六行的表与自身连接产生十行。

连接条件的形状决定了这个数字：等式两侧都是候选键时最多一对一；一侧是候选键、另一侧可重复时是一对多；两侧都可重复时是多对多，行数按乘积增长。判断一次连接的规模，先判断这三类中的哪一类。没有连接条件时得到两表的笛卡尔积，行数是两侧行数的乘积，它偶尔用于生成组合，在数据量稍大时就是资源事故。同一张表连接多次时必须用别名区分，否则列名有歧义，无法表达「自己与自己不同行」的条件。没有索引时，一侧的每一行都要扫描另一侧，成本随两侧行数相乘，这是查询计划要处理的问题。

## 未匹配的行

```sql run id="sql.join.unmatched" fixture="sql.orders.basic"
SELECT o.order_id, o.status, COUNT(oi.product_id) AS line_items
FROM orders AS o
LEFT JOIN order_items AS oi ON oi.order_id = o.order_id
GROUP BY o.order_id
ORDER BY o.order_id;
```

两张订单没有任何订单行，左外连接为它们生成 NULL 扩展行，`COUNT(oi.product_id)` 得到 0。用内连接写同一个查询，这两行会消失——这正是「没有订单行的订单丢了」这类缺陷的形态，在业务上常表现为总量对不上。

## 条件写在 ON 还是 WHERE

```sql run id="sql.join.on-vs-where" fixture="sql.orders.basic"
SELECT c.customer_id, COUNT(o.order_id) AS paid_orders
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.customer_id AND o.status = 'paid'
GROUP BY c.customer_id
ORDER BY c.customer_id;

SELECT c.customer_id, COUNT(o.order_id) AS paid_orders
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.customer_id
WHERE o.status = 'paid'
GROUP BY c.customer_id
ORDER BY c.customer_id;
```

第一条把 `o.status = 'paid'` 放在 `ON` 里：它只影响哪些组合算匹配，左表全部行仍然保留，因此四位客户都在结果里，其中两位的计数为 0。

第二条把同一个条件放在 `WHERE` 里：未匹配的行在右表列上是 NULL，`NULL = 'paid'` 为未知，被 `WHERE` 丢弃，连没有订单的客户也一起消失，结果退化为内连接。同一个条件换一个位置，语义从「每位客户的已付订单数」变成「有已付订单的客户数」。

过滤右侧表时把条件写进 `ON` 以保留左表全部行，是左外连接的常规用法；写进 `WHERE` 说明你要的其实是内连接。多表连接的书写顺序不决定语义，优化器可以选择任意执行顺序，同一组表的连接结果相同而执行代价可以相差很大。

## 反连接

```sql run id="sql.join.anti" fixture="sql.orders.basic"
SELECT c.customer_id, c.full_name
FROM customers AS c
WHERE NOT EXISTS (
    SELECT 1 FROM orders AS o WHERE o.customer_id = c.customer_id
)
ORDER BY c.customer_id;

SELECT p.product_id, p.name
FROM products AS p
WHERE NOT EXISTS (
    SELECT 1 FROM order_items AS oi WHERE oi.product_id = p.product_id
)
ORDER BY p.product_id;

SELECT c.customer_id, c.full_name
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL
ORDER BY c.customer_id;
```

三种写法得到两个答案：没有订单的客户（4 号）与从未被订购的商品（4 号）。第三种写法依赖 `orders.order_id` 非空：被引用的主键永远有值，因此 NULL 扩展行只可能来自未匹配。如果连接列本身可为空，这个写法会把「匹配到一行但该列为空」误判成未匹配，`NOT EXISTS` 没有这个问题。

`NOT EXISTS` 只判断子查询是否产生行，不做值比较，因此不受 NULL 影响；`NOT IN` 在子查询列可为空时返回空集，这一点在 <CrossRef id="db.sql.null-semantics" /> 中演示。

## NULL 不可连接

```sql run id="sql.join.null-on" fixture="sql.orders.basic"
SELECT a.customer_id AS left_id, b.customer_id AS right_id
FROM customers AS a
JOIN customers AS b ON a.country = b.country
ORDER BY left_id, right_id;
```

国家为 NULL 的客户没有与自己匹配：`NULL = NULL` 求值为未知。结果里只有 GB 与 US 的组内组合（1-1、2-2、2-4、4-2、4-4），共五行。

用可空列做连接键在语义上就意味着「未知不等于未知」，业务上常常不是想要的。处理方式要么在连接条件里显式补齐（`a.country = b.country OR (a.country IS NULL AND b.country IS NULL)`），要么把缺失值在写入时就规范成一个真实值。连接列类型不一致时，SQLite 按类型亲和性比较，可能给出跨类型相等的匹配，其他引擎会隐式转换或报错，连接键的类型因此是模式设计的一部分。可空列上的连接与 `NOT IN` 是两类静默空的来源：结果集偏小，且没有任何异常。

## 小结

- 连接的语义模型是笛卡尔积加谓词过滤，结果行数由匹配对数量决定。
- 内连接只保留匹配对，左外连接保留左表全部行并在未匹配处填 NULL，反连接保留没有匹配的左表行。
- 在左外连接里计数用 `COUNT(右侧列)`，否则会把 NULL 扩展行数进去。
- 右侧表的过滤条件写在 `ON` 里保留左表全部行，写在 `WHERE` 里退化为内连接。
- NULL 不匹配任何值，包括另一个 NULL；可空列不能直接承担连接键的语义。
- 反连接用 `NOT EXISTS` 表达最稳妥，`LEFT JOIN` 加 `IS NULL` 依赖连接列非空。
