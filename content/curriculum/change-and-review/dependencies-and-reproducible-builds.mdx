一个项目的运行结果可能由源码、第三方依赖、编译工具和配置共同决定。只复制源码到另一台机器，未必能得到相同的程序：依赖版本、目标平台或构建选项都可能不同。

## 依赖声明与依赖锁文件

直接依赖是项目主动使用的包，传递依赖是这些包继续使用的包。包管理工具根据声明解析它们，选择具体版本并取得内容。

依赖声明可以允许一段版本范围，<Term id="lockfile">依赖锁文件</Term>则记录已选定的依赖图。以 npm 为例，`package-lock.json` 保存确切依赖树和完整性等信息，见 [npm 锁文件](https://docs.npmjs.com/cli/v11/configuring-npm/package-lock-json/)。

`npm ci` 按锁文件进行干净安装，声明与锁文件不一致时失败，见 [npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci/)。因此，一次依赖升级通常要同时审查声明和锁定结果，再验证应用实际调用的功能。

## 构建输入与可复现构建

构建工具读取源码、依赖与配置，生成后续运行或部署所需的文件。例如，前端构建输出 HTML、脚本和样式，本地编译项目则生成目标文件、库和可执行文件。

| 输入 | 在构建中的作用 |
| --- | --- |
| 源码 | 规定程序行为 |
| 依赖与工具版本 | 提供所用接口并执行转换 |
| 目标平台与构建选项 | 决定生成哪类文件和功能 |
| 配置与资源 | 提供端点、页面内容等输入 |

要重新生成相同的产物，应记录源码提交、锁定的依赖、工具链、目标平台和构建选项。若构建读取本机配置或环境变量，它们也是实际输入。例如构建时写入的 API 地址不同，即使源码和锁文件相同，生成的前端文件也可能不同。

可复现构建进一步要求，在相同源码、构建说明和定义的环境下生成逐字节相同的指定产物，见 [Reproducible Builds 定义](https://reproducible-builds.org/docs/definition/)。实际项目可以据此核对构建来源；功能是否正确仍由测试检查。

## 构建时配置与运行时配置

前端构建可以把 API 地址直接写入脚本。发布后，浏览器读取的是这些文件；生产机器再改变环境变量，不会改写已经生成的字节。

服务端则可以在启动时从环境变量或配置文件取得数据库地址。修改配置后是否立即生效，取决于程序是在启动时读取，还是支持重新加载。

公开前端配置与服务端秘密应分开。写进前端文件的值会交给使用者；凭据的保存位置见 <CrossRef id="security.passwords-and-secret-lifecycle" />。

## 依赖升级与验证

升级依赖后，应从更新后的声明和锁文件重新安装，再执行构建与相关测试。若测试仍使用旧的缓存产物，测试通过就无法证明新依赖组合可用。

检查报告应关联到实际测试的源码提交、构建环境和产物。部署时使用经过检查的文件，可以避免测试版本与上线版本发生偏离。

## 练习

两次构建使用相同源码和锁文件，一次读到本机配置中的测试 API 地址，另一次使用生产地址。找出不同输入，并说明怎样让构建者明确选择它。

前端文件在测试环境构建，复制到生产后仍访问测试 API。配置是在何时生效的？应重新准备哪份文件，或者怎样改变应用读取配置的设计？
