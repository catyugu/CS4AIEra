两个构建都使用同一个源码提交，一个能运行，一个启动失败。构建是把源码转换为可运行或可部署文件的过程，结果称为制品。源码相同，还没有说明它们使用相同依赖、编译器等工具、配置或外部输入。

## 依赖声明与解析结果分开保存

项目可以声明允许某个库的一段版本范围。这个库也可能依赖其他库，这些间接引入的库称为传递依赖。包管理工具要沿着依赖关系选择实际版本，并取得对应内容。范围允许的版本随发布变化，单凭范围不能固定每次安装结果。

<Term id="lockfile">锁文件</Term>记录已选定的依赖图及相关获取信息。以 npm 为例，`package-lock.json` 描述确切依赖树，包含版本与完整性等信息，见 [npm：package-lock.json](https://docs.npmjs.com/cli/v11/configuring-npm/package-lock-json/)。锁文件应与依赖声明一起审查：新增一个直接依赖，还可能带来多个传递依赖和安装过程。

`npm ci` 是按锁文件进行干净安装的具体机制；依赖声明与锁文件不一致时失败，不通过改写锁文件继续安装。影响依赖树的安装选项也需与生成锁文件时一致，见 [npm：npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci/)。这些机制说明如何约束解析结果，不构成整个运行环境相同的证明。

## 构建是源码加输入的计算

构建可以读取工具版本、系统库、文件路径、当前时间和环境变量。如果制品含构建时间，重复构建就可能生成不同字节；本机有未跟踪配置文件时，提交到仓库的源码也没有包含全部输入。

| 输入 | 可能改变的结果 | 需要记录或约束的信息 |
| --- | --- | --- |
| 编译器、运行时、包管理工具 | 语义、依赖解析或生成代码 | 版本与必要选项 |
| 操作系统和本地库 | 可加载的二进制或系统行为 | 平台及依赖条件 |
| 构建配置与环境变量 | 端点、功能开关和资源路径 | 必需项、类型与生效阶段 |
| 时间、网络下载和生成数据 | 制品内容 | 固定输入或明确消除依赖 |

“能重新构建”说明流程可以再次运行；**可复现构建**要求在相同源码、构建说明与定义的环境条件下产生逐字节相同的指定制品，见 [Reproducible Builds：定义](https://reproducible-builds.org/docs/definition/)。它帮助检查制品与来源是否匹配，但制品相同也可能同样包含缺陷。

## 配置在哪个阶段生效

前端构建可能把端点地址直接写入静态脚本。部署机器随后改变环境变量，不会自动改写已经生成的字节。服务端启动配置则可能在进程启动时读取；修改后是否重新加载由程序的契约决定。

配置需要区分公开值与秘密。前端构建产物交给用户，写入其中的令牌不能继续被当成服务端秘密。构建时能够读取秘密，也意味着依赖安装和构建工具可能取得它们；能力范围见 <CrossRef id="security.permissions-dependencies-and-audit" />。

配置差异还改变边界：本地地址可以指向本机服务，部署到浏览器后 `localhost` 指向访问者自己的机器；文件路径存在于开发机，不证明容器或发布目录里也存在。审查时应追踪配置在哪里解释，以及路径和地址属于哪一个进程环境。

## 升级依赖需要验证真实使用路径

一份新的锁文件固定了新的解析结果，验证仍要检查应用真正调用的接口、失败行为和支持平台。版本声明的兼容性质有助于缩小检查范围，不能排除实现缺陷或应用依赖未承诺行为的情况。

如果只运行缓存中的旧构建，新的依赖可能完全没有参与验证。结果应记录实际工具版本、安装来源和制品身份；对于发布而言，还要避免把“测试过一个制品”替换成“部署前重新构建另一个制品”。

## 练习

一次依赖升级只改变了锁文件，代码没有修改。团队以“源码一样”为由，仅检查应用能否启动。这个验证覆盖了哪些事实？面对应用实际使用的接口、安装脚本和支持平台，应该补充哪些证据？

前端静态文件在测试环境构建，随后复制到生产机器；生产机器设置了不同 API 环境变量，浏览器仍访问测试地址。解释变量可能在哪个阶段被读取，并说明验证应检查哪份实际制品。
