一次修改新增了缓存，正常样例更快，测试也通过。审查不能停在“用了缓存”或“减少了查询次数”，而要追踪新返回路径依赖了什么状态，省略了什么判断。

## 缓存命中时，还会检查所有者吗

下面是一份针对 Python 文档读取函数构造的有效 diff。行首 `-` 表示删除，`+` 表示加入，没有符号的行提供上下文；`---` 和 `+++` 标识改动前后的文件，`@@` 标识对应行的片段。

```diff
--- a/documents.py
+++ b/documents.py
@@ -1,7 +1,12 @@
+cache = {}
+
 def read_document(store, user_id, document_id):
+    if document_id in cache:
+        return cache[document_id]
     document = store.get(document_id)
     if document is None:
         return None
     if document["owner"] != user_id:
         raise PermissionError("not allowed")
+    cache[document_id] = document["body"]
     return document["body"]
```

`store` 是按文档编号保存记录的映射，`get` 在编号不存在时返回 `None`。原函数对已存在记录检查所有者，再返回正文。新增路径先按编号查缓存，命中后直接返回，未经过所有者检查。

若所有者先读过文档，缓存已有内容，其他用户的后续读取就走新增路径。缺陷来自返回路径跨过权限判断，不来自字典查询本身。只用相同用户反复读取的性能测试，不会发现这项行为变化。

审查者需要阅读调用方、状态位置和失败规则，而不必把每行都改写成自己的风格。若同一份改动还涉及前端提示、数据库与测试，可以按需求连接它们：客户端提供哪些信息，服务器相信哪些信息，状态由谁保存，失败后调用方得到什么。

## 缓存键正确仍不代表状态永远正确

把用户编号加入缓存键，解决了上述不同用户共用一个结果的问题。文档归属或共享权限以后还可能变化；缓存的结果也有时间范围。权限变更后如何验证、失效或重新检查，必须来自当前契约。

若缓存放在某个页面里，页面刷新就可能丢失；若放在某个服务进程里，多实例也可能各有一份。为了满足跨进程或跨重启要求，需要检查实际状态位置，不能仅从变量名推断保证。

这也是对 Agent 生成改动的判断方式：让它实现缓存、生成测试和列出调用方，可以减少操作工作；哪些用户有权读取、允许结果旧多久，以及必须检查哪些行为，仍需由需求方决定。

## 怎样核对“更快”和“权限没变”

| 改动说明 | 可以核对的结果 |
| --- | --- |
| 读取更快 | 用实际数据规模和命中率测量整个请求耗时 |
| 修改不会重复 | 同标识并发请求、响应丢失和重启后，数据库仍只有一次业务修改 |
| 权限没有改变 | 所有者、其他用户和已被撤销权限的用户，分别取得或被拒绝读取 |
| 超时处理完整 | 等待按期限结束，已经产生的修改可以查到并按约定处理 |

对“自动重试”的修改尤其要追踪效果。重试会新增执行路径；可能失败的调用需要保留失败语义与总预算，不能把捕获异常后再次调用当成可靠函数。保证与反例见 <CrossRef id="networks-and-web.latency-timeouts-and-retries" />。

测试应覆盖改变的条件，判据来自独立要求，见 <CrossRef id="debugging-and-observability.test-criteria" />。一份失败轨迹、数据库实际状态或浏览器行为，可能比“所有单元测试通过”的一句话更能说明某项系统要求。

## 把缺陷写成可以复现的问题

缺陷报告应给出输入、操作步骤、实际结果、预期结果及影响，让审查者能复现问题，并判断它是否阻塞合入或发布。例如“缓存命中时在所有者检查之前返回；所有者读取后，另一用户使用相同编号也能取得正文”。这比“缓存设计不安全”更容易验证和修正。

修复后需要重新检查相关路径，并确认结果关联到最终版本。需求不明确时，应说明分歧对应的实际行为：权限撤销是否立即生效、过期内容最多允许多旧、重复标识保存多久。这些决定没有一个能从代码格式或已有测试数量中推出。

## 所有者改变以后，再读一次

下面把用户加入缓存键。服务要求文档转移所有者之后，原所有者立即失去读取权限。先判断这份实现满足什么、遗漏什么，再运行追踪状态；若修改，检查每条返回路径在什么时刻使用当前权限。

```python run id="change-and-review.reviewing-diffs-and-evidence.cached-permission"
cache = {}
documents = {7: {"owner": "Ada", "body": "private"}}

def read_document(user_id, document_id):
    key = (user_id, document_id)
    if key in cache:
        return cache[key]
    document = documents[document_id]
    if document["owner"] != user_id:
        raise PermissionError("not allowed")
    cache[key] = document["body"]
    return document["body"]

print("before:", read_document("Ada", 7))
documents[7]["owner"] = "Lin"
print("after:", read_document("Ada", 7))
```

另一个改动报告只写“增加三次重试，失败率下降”。为了判断是否可以合入，需要补充哪些操作效果、失败条件和时间范围？哪些是实现者可以代为收集的事实，哪些是需求方必须决定的允许行为？
