测试全部通过，发布之后服务却无法连接数据库。验证管道执行了已有的检查，实际部署还依赖环境配置、网络和数据状态。发布需要把经过验证的对象与运行中的对象对应起来。

## 管道重复判据，并保存对应关系

<Term id="continuous-integration">持续集成</Term>（CI）通过自动化构建与检查提供改动反馈。流程可以分为依赖安装、静态检查、测试、打包和验证制品等任务；任务之间的依赖要反映实际数据流，例如打包依赖构建结果，部署依赖验证通过的制品。

GitHub Actions 的工作流以事件触发任务，任务可以顺序或并行运行，并通过依赖关系安排先后，见 [GitHub：工作流、任务与执行器](https://docs.github.com/en/actions/get-started/understand-github-actions)。这是一个具体平台的组织方式；课程关心的是任务检查什么、使用哪些输入和产出什么证据。

| 对象 | 必须能追踪到的信息 |
| --- | --- |
| 源码 | 固定提交及是否混入其他修改 |
| 验证运行 | 工具版本、配置和判据结果 |
| 发布制品 | 构建输入及制品标识 |
| 部署实例 | 制品、运行配置和数据版本 |

如果测试通过之后重新构建，环境输入可能改变，验证对象与部署对象便不再天然相同。可以把同一份制品逐步推广到不同环境，同时对各环境配置单独验证。测试真实边界与替身的分工见 <CrossRef id="debugging-and-observability.isolation-and-properties" />。

## 验证代码也有权限边界

来自外部贡献的改动可能修改测试和构建脚本。执行这些脚本就是执行尚未信任的代码；让它取得发布密钥，会把发布能力交给它。通常的验证任务应使用所需的最少权限，并把需要秘密的发布步骤放在适当的信任条件下。

第三方自动化组件也属于执行的依赖。固定可验证身份、限制令牌权限和避免把不可信输入拼成脚本，是管道中的具体控制；相关条件见 [GitHub：安全使用工作流](https://docs.github.com/en/actions/reference/security/secure-use)。日志自动遮盖秘密也不能替代对脚本实际输出的检查。

## 进程存在不等于可以接流量

**部署**把某份制品及配置放到执行环境中；**发布**让它开始承担用户可见的行为。一个进程可以已经启动，却仍未加载配置或完成初始化。就绪检查应判断是否可以处理所需请求，不能只检查“进程还在”。

滚动发布逐步替换实例，在过渡期内新旧版本共存。需要验证共同使用的数据格式、协议和配置均兼容；以 Kubernetes Deployment 为例，滚动更新安排逐步建立和替换副本，回退记录针对工作负载模板，见 [Kubernetes：Deployment 更新与回退](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)。它没有替应用恢复数据库中的业务数据。

小范围发布可以减少一个缺陷立即影响全部用户的机会，但必须定义观察的结果、持续时间和停止条件。没有请求量的十分钟“无报错”，不能证明常用路径正常。错误率、尾延迟和关键业务结果需要与已有版本、当前负载及统计范围一起解释。

## 恢复需要匹配程序、配置与数据

恢复旧制品之前，应检查它能否读取当前数据、理解当前消息，以及在当前配置下启动。迁移阶段与回退窗口见 <CrossRef id="change-and-review.compatibility-and-migration" />。如果新版本已经发出重复单据或错误通知，回退只能停止继续发生，既有结果还需要识别和处理。

| 变化 | 换回旧程序是否足够 |
| --- | --- |
| 纯计算缺陷，数据格式未变 | 还需检查已产生的错误结果 |
| 新格式仅增加兼容字段 | 取决于旧程序的读取契约与配置 |
| 已删除旧程序必需的数据 | 不能只靠换程序恢复 |
| 外部付款或消息已发送 | 需要业务补偿或对账规则 |

恢复方案可以是换回兼容的旧版本，也可以是向前发布修复并修正数据。选择要考虑已产生效果、恢复所需时间和额外风险；“保留了旧镜像”只是保存了一个对象，并没有证明使用它仍然安全。

## 练习

一个发布候选在独立测试数据库里通过全部测试，生产部署缺少新的必需配置。应在哪个阶段检查这项条件？哪些检查可以在发布前进行，哪些需要观察实际实例？

新版本已经把历史数据换成旧程序不能读取的格式，但发布平台能一键回退工作负载。审查这份回退能力的范围，并说明恢复决定还需要哪些状态信息。
