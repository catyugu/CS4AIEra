书目导出合入主分支后，团队要把这一版交给用户。在开发机器上下载成功只是其中一次观察。交付时还要核对主分支合入后的源码、将要部署的文件，以及应用连接生产环境后能否实际导出。

## 从提交到发布包

<Term id="continuous-integration">持续集成</Term>（CI）会在提交或合并请求等事件触发后执行约定的检查。合并后可以针对新的提交再走一遍构建与验证。

| 交付环节 | 书目应用的输入与输出 |
| --- | --- |
| 安装 | 取指定提交，按锁文件安装前端依赖 |
| 测试 | 运行 CSV 编码测试和测试数据库中的导出用例，记录提交和结果 |
| 构建 | 生成浏览器脚本与服务端发布文件，保存为带有版本标识的包 |
| 产物验证 | 用该发布包运行应用，检查下载路径并记录文件摘要 |
| 部署 | 取验证过的同一份包送入目标环境，按环境提供配置 |

提交标识说明源码版本，文件摘要用来核对实际部署的包。若上生产前重新构建，新的产物也要重新核对。工作流如何定义触发条件和任务，见 [GitHub Actions 工作流](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflows)。

## 上线验证

部署把程序装到目标环境。发布则让用户开始使用新版功能。一次发布可以先部署新包、核对实际运行结果，再让用户访问新的导出入口。

在指定账户下打开书目列表，选择用于验证的分类并下载。读回文件，检查标题行、首尾编号和预期条数。这个操作经过浏览器、下载接口、数据库查询和 CSV 编码。若页面可打开但下载失败，可以从浏览器的请求状态和后端日志找出失败发生在哪一步。

例如生产环境中，服务进程已启动，导出却返回错误。若日志显示书目查询时数据库连接超时，应从运行该服务的环境检查数据库地址和网络连接。CI 使用的测试数据库响应正常，只解释了测试环境中通过的那条路径。

## 回退程序与数据

假如新前端把下载请求发到了不存在的路径，而数据格式沿用旧版，团队可以撤下新包，恢复上一份已验证的包，再走一遍下载操作。代码在 Git 中留下相应修复或撤销提交，发布记录则应写清实际部署了哪一份包。

若这次交付还改变了价格存储，就要按 <CrossRef id="change-and-review.compatibility-and-migration" /> 核对线上数据。如果旧列已停用或出现了只能用分表示的价格，应保留能读取现有数据的版本并修复下载路径。发布前预留兼容期，可以给运行中的系统留下更多恢复选择。
