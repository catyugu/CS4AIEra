需求已经明确，怎样知道实现满足它？测试把一组输入和初始状态交给程序，再将实际行为与预期结果比较。预期结果应来自需求，而不是抄写实现当前算出的值。

## 把一项规则变成检查

假设库存操作的规则是：购买数量必须为正整数；库存足够时扣减并返回新库存；不足时拒绝，库存不变。

先从最小的函数检查开始。下面的实现故意留有缺陷，单元格暂时只检查一次正常购买：

```python run id="change-and-review.software-testing.stock"
def buy(stock, quantity):
    if quantity > stock:
        raise ValueError("not enough stock")
    return stock - quantity


assert buy(3, 2) == 1
print("normal purchase passed")
```

`assert` 后的条件为假时抛出 `AssertionError`，让错误自动显现，见 [Python assert](https://docs.python.org/3/reference/simple_stmts.html#the-assert-statement)。通过这一条检查，只知道库存 3、购买 2 时返回了预期值。

根据要求再选一些输入：

| 初始库存 | 数量 | 预期行为 | 检查的规则 |
| --- | --- | --- | --- |
| 3 | 2 | 返回 1 | 正常扣减 |
| 3 | 3 | 返回 0 | 恰好耗尽库存 |
| 3 | 4 | 拒绝 | 库存不足 |
| 3 | 0 | 拒绝 | 数量必须为正 |
| 3 | -1 | 拒绝 | 不能反向增加库存 |
| 3 | 1.5 | 拒绝 | 数量必须为整数 |

这张表来自业务规则。无需枚举所有整数，也已经能检查几类不同边界。

## 验证拒绝行为

把下面的检查代码追加到第一个单元格中。它要求程序抛出 `ValueError`；如果程序正常返回，就主动报告测试失败：

```python
try:
    buy(3, -1)
except ValueError:
    pass
else:
    raise AssertionError("negative quantity was accepted")
```

`try` 的 `else` 在没有异常时运行。本例会发现 `buy(3, -1)` 返回 4，违反正数规则。现在已有一个能重复触发问题的输入。修复参数检查后再次运行，确认正常购买与拒绝路径都符合要求。

留下这条检查，就形成回归测试：以后修改代码时，自动确认同一种错误没有重新出现。测试自身也要校验；可以暂时恢复有缺陷的函数，确认这条检查确实失败。

## 状态和副作用也要检查

真实购买会修改数据库并创建订单。仅检查返回“成功”不够，还应查询剩余库存、订单数量和请求编号。

对于拒绝路径，比较操作前后的记录，确认没有留下半笔购买。对于重试，重复使用同一个操作标识，确认记录数没有增加。每个测试应从明确的初始数据开始，避免依赖其他测试先做过什么。

测试框架负责组织用例、收集断言失败和汇总结果。理解输入、执行、核对这三个步骤之后，再学习具体框架的写法就有了基础。

## 不同范围的测试

单元测试检查较小的独立部分，例如上述库存函数；集成测试检查部分之间的合作，例如后端与真实数据库；端到端测试从用户入口走通操作，例如在浏览器提交购买，再检查结果。

它们能发现不同的问题。函数测试发现负数未被拒绝，数据库测试发现事务没有回滚，浏览器测试则可能发现按钮没有发出请求。检查范围越大，准备环境和定位原因通常也越费力，应按改动涉及的路径选择组合。
