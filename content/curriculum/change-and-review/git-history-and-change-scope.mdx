同一个项目的两组改动从共同版本出发，分别发展，再合到一起。Git 用提交记录版本，用分支名标识当前发展到哪里。先看一段这样的历史：

```text
A ── B ── C ───── M  main
     └── D ── E ──┘
              topic
```

线连接父提交和后继提交，历史从左向右发展。A 到 M 是提交标记，`main` 和 `topic` 是分支名；主分支与功能分支在 B 之后分别修改代码，M 是合并后的提交。要审查功能分支引入的改动，需要找到它开始分开的版本，再与分支结果比较。

## 提交保存快照，分支记录位置

一次<Term id="commit">提交</Term>记录项目文件的快照，以及父提交、作者和说明等信息。快照表示这次提交时各文件的内容；父提交表示它从哪些已记录版本发展而来。提交有由内容计算的标识，分支名则是可以移动的引用，指向某个提交。Git 在内部使用内容对象和树对象保存这些记录，具体对象模型见 [Pro Git：Git 对象](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)。

因此“验证了 main 分支”不够精确：分支可能在验证之后前进。结果应该关联到当时的提交标识，必要时还包括未提交修改。

| 位置 | 保存的内容 | 对审查的含义 |
| --- | --- | --- |
| 工作区 | 当前可以编辑的文件 | 可以包含未记录的修改与新文件 |
| 暂存区（index） | 准备写进下次提交的状态 | 可以只包含工作区修改的一部分 |
| 提交快照 | 某次记录的项目树 | 固定的比较对象 |
| 分支引用 | 当前指向的提交 | 名称可以保持，指向可以改变 |

工作区里的修改不一定都进入暂存区，暂存内容也可能在工作区后续编辑后保持旧值。测试当前工作区通过，不自动证明刚提交的快照与它相同。

## 共同起点与三方合并

图中 A 到 B 是共享历史，M 有 C 和 E 两个父提交。

B 是 C 与 E 的<Term id="merge-base">合并基点</Term>。B 到 E 的快照差异表示功能分支引入的变化，B 到 C 则表示主分支的变化。C 与 E 直接比较得到的是两个结果之间的差异，含义不同。这张图中的共同起点只有一个。更复杂历史中的基点选择由 Git 的规则决定，见 [Git：merge-base](https://git-scm.com/docs/git-merge-base)。

三方合并综合共同起点与两边结果。当变化不能自动结合时，需要人工处理冲突；没有文本冲突也可能存在语义冲突。例如一边把接口的时间单位改成秒，另一边新增一个仍按毫秒解释的调用方，文件不同也能形成错误组合。合并结构见 [Pro Git：分支与合并](https://git-scm.com/book/en/v2/Git-Branching-Basic-Branching-and-Merging)。

若主分支只是功能分支头的祖先，整合可以只让主分支引用前进，这叫快进（fast-forward），不必产生新的合并提交。是否出现合并节点，由历史关系与整合策略决定，不能把每次整合都画成同一个形状。

## 撤销源码不会撤销外部效果

可以创建新提交，撤销先前提交引入的代码变化，同时保留共享历史；Git 的 revert 表达这种安排，见 [Git：revert](https://git-scm.com/docs/git-revert)。改写已有历史则生成不同提交并改变引用，已经使用旧历史的协作者必须处理分叉。

两者都只操作仓库里的记录。如果某个版本已经写入新的数据库格式、发出邮件或公开了文件，撤销代码不会自动恢复这些效果。恢复运行中的系统还需要检查数据、配置、部署制品和已经产生的外部动作。

审查范围因此要同时说明：比较哪个基准与哪个结果，是否包含未提交修改，以及哪些外部状态变化需要与源码一起评估。一份 diff 展示源码差异，却不是整个运行系统的快照。

## 练习

在开头的图中，E 的测试全部通过，M 也没有文本冲突。一份审查只比较 C 与 E，并把其中所有差异都当作功能分支新增的改动。这个比较会混入什么内容，漏掉什么背景？要验证合并结果，应把检查关联到哪个提交？

一个文件修改后被暂存，作者又修改了同一个文件。当前工作区测试通过，随后提交时没有重新暂存。仅凭这份测试结果能否确认提交通过检查？说明还需要核对的两份状态。
