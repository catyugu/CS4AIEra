生成报告需要几十秒。可以让一次 HTTP 请求一直等到报告完成，也可以先返回任务编号，让用户稍后查询结果。后一种安排把提交和计算分开，用户取得编号后就能关闭页面，后台继续处理。

## 从提交到取得报告

沿用上一课的报告应用，现在为它增加工作进程（worker），专门执行耗时计算。API 将待处理工作的消息交给队列，工作进程空闲时取出任务。数据库保存任务记录，对象存储保存输入和报告。

假设输入文件已经上传，应用为这次报告分配编号 17：

| 步骤 | 程序的动作 | 用户能查到的状态 |
| --- | --- | --- |
| 1 | API 保存任务编号、输入引用和参数，再把编号送入队列 | 待处理 |
| 2 | API 返回任务编号和查询地址 | 待处理，可以关闭原页面 |
| 3 | 工作进程取出任务，开始计算 | 处理中 |
| 4 | 工作进程保存报告和结果引用 | 已完成，可以打开报告 |

计算失败时，任务记录保存失败状态和原因。客户端凭同一个编号查询，就能知道任务在等候、处理中，还是已经有了结果。HTTP 的 `202 Accepted` 状态码可以表示已接纳但尚未完成的工作，见 [RFC 9110：202 Accepted](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3)。

消息可以只携带任务编号，工作进程再从数据库找到输入文件和参数。因此，继续计算所需的信息要保存在后台能取得的位置，不能只留在即将关闭的浏览器页面里。

## 工作进程怎样报告处理完成

工作进程完成任务后，向队列发送消费确认，队列便可以移除这条消息。在支持重新投递的队列中，工作进程若在确认前退出，未确认的任务可以交给另一个进程继续处理。

这也带来重复的可能：工作进程已经保存报告，却在确认之前退出，另一个进程还会收到同一任务。因而处理任务时，要能按编号识别已有结果。重试与恢复见 <CrossRef id="software-systems.delivery-and-recovery" />。

这里的确认由工作进程发出。API 把任务送入队列时，也可以收到队列的接收确认；它只表示队列收到了任务，此时计算可能还没开始。两种确认分别连接发送方、队列和处理方，见 [RabbitMQ：发布确认与消费确认](https://www.rabbitmq.com/docs/confirms)。

## 队列让计算稍后进行

API 接收请求，工作进程执行计算，两者可以按各自的速度运行。多个工作进程也可以同时取任务，因此提交次序不一定等于完成次序。

队列允许暂时积压，但处理能力仍有限。持续进入的工作超过完成能力，就要等待更久；<CrossRef id="software-systems.capacity-and-backpressure" /> 会计算这种情况。下一课先检查正常流程中哪些交接可能失败。

## 练习

任务 17、18、19 依次进入队列，两个工作进程各处理一项。17 需要 30 秒，18 需要 2 秒，19 需要 1 秒，忽略交接开销。写出一种领取与完成次序，说明页面应按什么编号关联进度和结果。

API 返回编号后，输入文件仍只在用户浏览器的内存里。用户关闭页面，工作进程才开始处理。找出缺少的信息交接，并调整保存顺序。
