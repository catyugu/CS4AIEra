生成一份报告需要几十秒。若请求一直等到结束，浏览器需要保持等待，应用也要保留这次请求的资源。可以先接纳任务、返回任务标识，由工作进程稍后执行；这使“已接纳”成为一个必须单独兑现的承诺。

## 用户先拿到任务标识，再查询结果

任务队列保存待处理工作，生产方把任务送入队列，消费方取出任务执行。先进先出队列的基本操作见 <CrossRef id="data-algorithms-and-scale.queues-stacks-and-priority-queues" />；跨进程队列还需要规定消息保留与确认规则。

任务标识让客户端后续查询同一项工作。可以约定状态为“待处理、处理中、已完成、已失败”；每个状态说明已知事实，而不是仅用一个布尔值表示“没结束”。

| 可观察结果 | 可以推出什么 |
| --- | --- |
| API 返回接纳结果 | API 已承担契约规定的后续责任 |
| 消息服务确认发布 | 按服务及配置约定，消息已被接收 |
| 工作进程取到消息 | 处理可以开始，结果尚未确认 |
| 报告与结果记录完成 | 查询可以报告完成，并提供有效结果引用 |

HTTP `202 Accepted` 表示请求已接纳但处理尚未完成，并不保证最终一定成功，见 [RFC 9110：202 Accepted](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3)。应用需要另外说明查询入口、任务保留时间与最终失败如何展示。

## 发布确认与消费确认分别确认什么

RabbitMQ 将发布确认与消费确认分开：发布确认涉及生产方与消息服务，消费确认涉及消息服务与消费方，两者并不相互替代，见 [RabbitMQ：发布确认与消费确认](https://www.rabbitmq.com/docs/confirms)。

如果工作进程刚取到任务就确认消费，随后计算失败，消息服务可能已经删除消息。若等业务效果完成后才确认，效果完成与确认之间的崩溃又可能导致重复投递。调整确认时机，会改变失败窗口，不能单靠“打开确认”推出端到端恰好完成一次。

对可靠接纳，还要区分队列与消息的持久性。例如 RabbitMQ 的持久队列属性与消息持久标记是不同设置，见 [RabbitMQ：队列持久性](https://www.rabbitmq.com/docs/queues#durability)。具体故障下消息是否保留，由队列类型、消息设置和确认语义共同决定。

## 队列改变执行关系，也增加等待

同步请求直接把用户等待与执行绑定；后台任务让 API 与工作进程按不同速度运行，工作进程也可以单独扩容。但是队列中的任务仍要等待实际处理容量。

单一发布通道的消息次序，不等于多个工作进程的完成次序。任务 A 先进入队列却执行得慢，任务 B 后进入却先完成；若 B 必须使用 A 的结果，需要明确记录依赖并检查 A 已完成，不能仅依赖入队先后。RabbitMQ 的并行消费和重新投递也会影响实际观察到的顺序，见 [RabbitMQ：消息顺序](https://www.rabbitmq.com/docs/queues#message-ordering)。

任务内容最好保存继续执行所需的稳定信息，例如输入对象键、操作标识和参数版本。只保存一份会随时变化的记录编号，意味着工作进程稍后读取的内容可能已经与接纳时不同；究竟需要最新内容还是接纳时快照，应由任务契约规定。

报告要求使用用户提交时的数据，队列消息却只含数据集编号。用户提交后又修改了数据，工作进程才开始读取。它会处理哪一份？消息或存储记录中需要增加什么，才能找回提交时的内容？
