生成报告需要几十秒。可以让一次 HTTP 请求一直等到报告完成，也可以先返回任务编号，让用户稍后查询结果。后一种安排把“提交任务”和“取得报告”分成了两次交互。

## 从提交到取得报告

沿用 <CrossRef id="software-systems.responsibilities-and-state" /> 的报告应用：数据库保存任务记录，对象存储保存文件，工作进程负责计算。任务队列保存待处理工作；生产方把任务送进去，消费方取出任务执行。

先看没有故障的一次执行。假设输入已经上传，应用为这次报告分配编号 17：

| 步骤 | 执行者的动作 | 用户此时能查到什么 |
| --- | --- | --- |
| 1 | API 保存输入引用和参数，发布任务 17 | 待处理 |
| 2 | API 返回任务编号和查询地址 | 可以凭编号查询，不必保持原请求 |
| 3 | 工作进程取出任务，记录开始处理 | 处理中 |
| 4 | 工作进程读取输入，生成并保存报告 | 仍在处理，结果还未登记完整 |
| 5 | 工作进程保存报告引用和完成状态 | 已完成，可以打开报告 |

计算无法完成时，任务记录也可以进入“已失败”，并提供失败原因。客户端反复查询同一个编号，就能区分等待、计算、成功和失败。HTTP `202 Accepted` 适合表达接纳了尚未完成的工作，含义见 [RFC 9110：202 Accepted](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3)。

这里的队列让 API 和工作进程可以按各自的速度运行。多个工作进程可以共同取任务，浏览器关闭后也不必停止已经交给后台的计算。任务能否跨重启继续，取决于输入、任务记录和消息实际保存在哪里。

## 消息里需要带什么

消息可以只携带任务编号，由工作进程从数据库读取输入引用与参数。也可以直接携带这些信息。无论采用哪一种方式，工作进程都要能找回这次提交要求处理的那份输入。

假设用户提交数据集 8 后又修改了它。消息只带 `dataset_id = 8`，工作进程稍后读取到的就可能是修改后的内容。若报告要求使用提交时的数据，需要保存不可变的输入副本或版本，并让任务指向它。若需求就是处理最新数据，也应明确这一选择。

队列的取出次序也不决定完成次序。A 先入队却计算得慢，B 后入队却先完成；若 B 依赖 A 的结果，就要记录依赖，在 A 完成后才允许 B 开始。

## 队列怎样知道消息可以删除

工作进程取到消息后，消息服务需要知道它是否还要保留这项工作。消费确认就是消费方向消息服务报告“这条消息已经处理，可以结束本次投递”。

如果工作进程一取到消息就确认，随后在计算中退出，消息可能已被删除，任务却没有完成。若完成后才确认，工作进程又可能在保存结果之后、发送确认之前退出。消息服务随后重新投递，另一个进程就会再次遇到任务 17。

| 退出位置 | 已留下的结果 | 恢复时要处理的问题 |
| --- | --- | --- |
| 取到消息后，计算前 | 尚无报告 | 未确认消息需要重新交给工作进程 |
| 报告与完成记录已保存，确认前 | 已有报告 | 重复处理应识别已有结果 |
| 消费确认之后 | 消息可以移除 | 完成结果应已可查询 |

重复任务怎样复用结果，见 <CrossRef id="software-systems.delivery-and-recovery" />。

生产方也需要知道发布是否被消息服务接收。这称为发布确认，发生在 API 与消息服务之间；消费确认发生在工作进程与消息服务之间。RabbitMQ 对两者的说明见 [发布确认与消费确认](https://www.rabbitmq.com/docs/confirms)。取得发布确认时，工作进程可能还没开始计算。

消息服务重启后是否保留消息，还取决于持久性设置。例如 RabbitMQ 的队列持久性与消息持久标记是不同设置，见 [RabbitMQ：队列持久性](https://www.rabbitmq.com/docs/queues#durability)。保存任务与发布消息之间的故障，留到 <CrossRef id="software-systems.delivery-and-recovery" /> 讨论。

## 队列里的等待也计入完成时间

用户取得编号后，任务仍可能等待很久。工作进程每秒处理 10 项而持续收到 12 项时，增加的任务会积压。队列用于暂存和分配工作，处理能力与等待时间的计算见 <CrossRef id="software-systems.capacity-and-backpressure" />。

接纳任务时，应告诉用户在哪里查询、结果保留多久，以及最终失败怎样显示。这样用户关闭原页面后，仍有办法知道这项工作的结局。

## 追踪一次中断

报告要求使用用户提交时的数据。任务 17 保存了数据集编号，工作进程尚未读取时，用户修改了数据集。工作进程随后生成报告、保存完成记录，却在确认消息前退出。

这份报告使用了哪一版输入？重新投递后，另一个进程应先检查什么？怎样调整任务保存的信息，才能让重做与第一次处理使用同一份数据？

<details>
<summary>参考推理</summary>

若编号始终定位到可变的当前数据，第一次报告可能已用了修改后的版本。再次读取还可能得到更新的版本。任务应保存提交时的输入副本或不可变版本引用，以及相应参数。重新投递时先按任务编号检查完成记录；已有有效结果时复用它，再确认消息。若尚未完成，则使用任务保存的同一版输入继续计算。

</details>
