上午九点，三个用户同时提交报告。处理每份报告要读取表格、统计数据、生成 PDF。应用让接收请求的 API 继续响应用户，让空闲的工作进程（worker）领取等待中的任务。两者之间由消息队列传递工作。

## 生产者、消息队列与消费者

| 组件 | 在报告应用里负责什么 |
| --- | --- |
| API | 接纳提交、建立数据库记录、安排发送任务编号，也负责回答进度查询 |
| 消息队列 | 保存等待投递的消息，把编号分发给工作进程 |
| 工作进程 | 根据编号读任务记录和原始表格，生成 PDF，保存结果并更新状态 |

例如，工作进程收到消息 `{"task_id": 17}` 后，先到数据库获取生成参数和表格的对象键。任务仍在等待时，它领取任务开始计算。报告保存、完成状态提交后，它向队列确认消息。这样，数据库能回答“这份报告现在怎样了”，而队列负责让后台程序知道“有哪些工作要做”。

## 消息确认与重新投递

领取任务表示工作进程开始处理，确认消息表示队列可以结束这次投递。对提供重投的队列，进程若在确认前退出，消息可以由另一进程再次取得。确认应安排在业务结果提交之后。提交与确认之间也可能失败，因此接手者要检查该任务编号是否已有结果。具体恢复过程见 <CrossRef id="software-systems.delivery-and-recovery" />。

## 排队与并行执行

工作进程都在忙时，新消息在队列中等待，用户仍可查询已接纳的任务。若其他资源有余量，增加工作进程可以同时处理更多份报告。领取顺序和完成顺序可能不同，用户凭任务编号查询对应的结果。

## 练习

假设任务 17、18、19 按此顺序分发给两个空闲的工作进程，每个进程一次处理一项。三个任务分别需要 30 秒、2 秒和 1 秒，忽略交接时间。写出它们的开始和完成时刻。页面应当用什么信息把任务与下载地址对应起来？
