一份报告要等半分钟，网页每秒查一次进度。在下一次状态变化之前，每次查询都会读到相同的值。如果页面允许晚几秒显示新进度，API 可以暂存最近查到的状态，减少重复的数据库查询。

## 缓存命中与按需填充

API 校验访问权限后，用任务编号查询缓存。找到仍在有效期内的记录叫**命中**，可以直接返回。没有找到有效记录叫**未命中**，这时 API 读数据库，把任务状态填入缓存，再返回给网页。

## 缓存失效与读取要求

当工作进程将任务 17 改为“已完成”时，数据库已经保存新状态，缓存可能仍返回“处理中”。应用可以给条目设有效期，也可以在数据库提交后主动删除条目。这两种做法都会使缓存条目<Term id="cache-invalidation">失效</Term>。有效期从填入时算起。下面是一种可能的交错。

| 次序 | 操作 | 缓存 |
| --- | --- | --- |
| 1 | 查询未命中，从数据库读到「处理中」 | 空 |
| 2 | 工作进程提交「已完成」，然后清除缓存 | 空 |
| 3 | 第一步的查询按旧结果填入缓存 | 处理中 |

这次旧值来自清除后的一次迟到写入，会留到到期或下一次清除。

普通轮询可以容忍短暂延迟。用户取消任务时，是否成功应由数据库的条件更新决定，响应直接返回操作结果。如果取消后刷新页面也要求看到这次修改，相应查询可以绕过缓存，读取已应用该次更新的数据库节点。读路径的选择取决于操作者拿到旧结果后会怎样行动。

## 练习

假设 10:00:00 查询任务 17 时缓存未命中，API 查到“处理中”，以三秒有效期写入缓存。10:00:01 数据库记录变成“已完成”。应用采用到期失效，忽略数据库和 API 的处理时间。10:00:02 和 10:00:04 的轮询分别从哪里读到什么状态？
