两个 API 实例共同查询同一个数据库，任务列表的读请求继续增加。团队给数据库加了一个只读副本，让部分查询由副本处理。用户取消了另一份报告的任务 23。服务已经确认取消成功，刷新却看到“等待执行”。这次查询直接访问数据库，没有经过缓存。

## 写入怎样传到副本

<Term id="replication">复制</Term>让多个节点维护同一份数据。本例由主节点接收写入，再将修改传给只读副本。采用异步复制时，主节点可以先确认提交，副本稍后应用该修改。见 [PostgreSQL 18：流复制](https://www.postgresql.org/docs/18/warm-standby.html#STREAMING-REPLICATION)。

| 次序 | 主节点的任务状态 | 副本的任务状态 |
| --- | --- | --- |
| 提交取消前 | 等待执行 | 等待执行 |
| 主节点确认取消，副本尚未应用 | 已取消 | 等待执行 |
| 副本应用这次修改 | 已取消 | 已取消 |

刷新请求在第二行的时间点读副本，便会得到旧状态。沿着这次请求排查时，可以记录 API 实际选中的读取节点，核对对应副本是否已经应用这次更新。

## 哪些读取要求看到刚才的写入

在报告应用里，一条读取<Term id="consistency">一致性</Term>要求是，用户提交取消后，随后的查询应看见自己的修改。可以让这类查询访问仍在服务的主节点，或等副本应用这次修改后再读。直接读主节点会增加主节点的读负载，等待副本会增加查询延迟。仪表盘允许短暂滞后，汇总查询可以交给延迟在可接受范围内的副本。

## 主节点失效后还能找回什么

主节点可能在确认写入后、传播完成前失效。若此时切换到尚未收到修改的副本，任务 23 的取消结果可能丢失。同步复制可以要求某个副本达到规定的接收、持久保存或应用阶段，再确认写入；等待条件会影响写入的时延和可用性。见 [PostgreSQL 18：同步复制](https://www.postgresql.org/docs/18/warm-standby.html#SYNCHRONOUS-REPLICATION)。

副本跟随主节点更新，误删除也会传播。若要恢复删除前的状态，就需要保留能够还原到相应时刻的备份。

## 练习

用户取消任务 23 后立即打开详情页，同时团队看板每隔一分钟刷新一次任务统计。为两个读操作选择适合的节点，说明副本落后时页面可能显示什么。
