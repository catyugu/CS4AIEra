网页允许上传数据并生成报告。浏览器可以读取文件、预览字段，甚至完成部分计算；服务器也可以处理同一份数据。放在哪里做，取决于结果由谁使用、规则由谁保证，以及页面关闭后是否还需要继续完成。

## 先画数据与决定怎样经过组件

一个需要后台生成报告的应用，可以有下面的结构：

```text
browser ──> application API ──> database
   │              │
   │              └──> task queue ──> worker
   │                                     │
   └────────────> object storage <────────┘
```

浏览器预览文件并提交请求；API 检查是否接纳任务；数据库保存任务状态与报告元数据；工作进程取任务并生成内容；对象存储保存原始文件与报告字节。图中的箭头是数据或调用关系，每一条都需要相应契约；部署时这些组件也可能分布在不同进程与机器。

<Term id="object-storage">对象存储</Term>的对象键与数据库记录如何关联，见 <CrossRef id="persistence.caches-and-object-storage" />。将两个组件画在一起，不会使它们的更新自动成为一次共同提交。

## 预览与权威判断可以分别存在

浏览器先检查必需字段，可以提前反馈并减少无效上传。若服务器的报告计算要求这些字段有效，服务器仍要按自己的规则验证收到的数据：请求可以来自另一种客户端，浏览器中的检查也可能没有执行。服务器只能依据实际收到的信息作出接纳决定。

反过来，若数据始终由当前使用者在本地查看，结果无需上传、共享或后台继续计算，浏览器执行可以满足需求，并减少数据离开设备的次数。独立于服务端的本地计算与“浏览器负责保证服务器收到的所有数据都合法”，是两项不同要求。

计算放在客户端，要考虑设备能力、页面生命周期与代码分发；放在服务器，要考虑上传成本、资源容量、运行权限与数据处理责任。比较应先写出需求，再按这些条件判断，不能仅从“前端”或“后端”的名称推导优劣。

## 每份状态都需要位置与寿命

同一个任务可以有多种状态：

| 状态 | 合适的位置与寿命 | 丢失后的后果 |
| --- | --- | --- |
| 尚未提交的输入与预览 | 当前浏览器页面 | 关闭页面可能丢失；是否允许由产品决定 |
| 某次请求的中间计算 | 处理该请求的进程内存 | 进程退出后要重新计算或报告中断 |
| 已接纳的任务及其结果引用 | 持久数据库 | 用户重新打开页面仍能查询；丢失会破坏接纳承诺 |
| 已生成的报告内容 | 约定保留期的内容存储 | 引用还在但内容丢失，报告不能打开 |
| 可重建的查询结果缓存 | 应用内存或缓存服务 | 未命中后重新计算或读取权威数据 |

权威状态是作出业务判断时以之为准的记录。缓存可以复制权威数据，<Term id="cache-invalidation">缓存失效</Term>负责停止复用不再合适的结果。若恢复缓存时找不到其他来源，它已经承担了原始记录的责任，不能仍以“丢了再算”解释。

## 无状态服务仍然使用状态

这里把“不要求同一个请求序列必须回到原来的进程，必要业务状态在外部可取得”的服务称为无状态服务。进程仍然有内存、连接与临时数据；“无状态”描述的是跨请求的必要状态依赖。

若任务进度只保存在接纳请求的进程内存里，另一个进程无法回答查询，原进程退出也会丢失进度。把必要状态放在可共同访问的持久位置，可让另一个实例接续查询；同时新增了存储访问、并发更新与存储不可用时的处理责任。

某些服务确实需要保留进程内状态，例如一条持续连接的会话。要说明怎样分配连接、实例退出后怎样恢复，而不是把所有状态都移出进程来满足一个名称。

## 练习

报告服务的需求是：“提交成功后，即使浏览器关闭或接纳请求的进程重启，任务仍能完成；任意服务实例都能查询进度。”方案把输入上传到对象存储，任务标识与进度存进 API 进程的字典，队列只保存该标识。

分别追踪浏览器关闭、API 进程重启、查询落到另一个实例时还能取得哪些信息。应当移动哪份状态，才能兑现需求？移动后新增了哪些需要处理的失败？
