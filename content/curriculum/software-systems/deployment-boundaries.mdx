开发时，应用与数据库都在一台机器上，数据库地址写成 `localhost`。部署后，应用运行在一个容器，数据库在另一个容器。相同的字符串现在指向应用自己的网络环境，数据库连接可能因此失败。

## 部署需要还原程序的运行条件

部署一份程序，需要准备执行它的进程、依赖、配置、可访问的文件与网络端点。源代码没有变，工作目录、权限、监听地址或外部服务地址改变，都可能改变行为。

容器将应用及其运行环境打包，并提供相应隔离。它仍运行进程，并依赖宿主机资源；进程内存的生命周期见 <CrossRef id="program-execution.processes-and-kernel" />。程序将数据存进内存，不会因为被放入容器就获得持久性。

## 每个地址都需要一个观察位置

下面是 Docker Compose 配置片段；应用镜像需由项目提供，并且应用实际监听容器内的 `0.0.0.0:8000`。片段只展示端口和数据库主机的约定：

```yaml
services:
  api:
    ports:
      - "8080:8000"
    environment:
      DB_HOST: db
  db:
    volumes:
      - database-data:/var/lib/postgresql
volumes:
  database-data:
```

默认 Compose 网络中，服务可以通过服务名称找到彼此，见 [Docker Compose：网络](https://docs.docker.com/compose/how-tos/networking/)。应用使用 `db`，表达的是同一网络中的数据库服务；从宿主机上的客户端访问 API，则使用宿主机地址与发布端口 8080。

`8080:8000` 把主机端口映射到容器端口。发布端口与应用监听是两个条件：若应用只在容器内部的回环地址监听，端口映射不能代替它接受来自容器网络接口的连接。监听地址的含义见 <CrossRef id="networks-and-web.addressing-and-listening" />。

Docker 发布端口未指定主机地址时，通常会向所有主机网络接口发布；需要限定主机本地访问时，可以明确写 `127.0.0.1:8080:8000`，见 [Docker：端口发布与映射](https://docs.docker.com/engine/network/port-publishing/)。配置应与实际访问需求一致。

## 配置与文件各有自己的来源

环境变量让同一份程序使用不同服务地址或资源配置，但变量必须进入实际运行进程。开发终端里设置过变量，不证明部署平台创建的进程也继承了它；变量名拼对，也不证明值指向可达服务。普通配置与密钥还需要采用各自合适的分发方式。

相对路径从进程的工作目录解释。开发时写 `data/input.csv`，部署后目录可能没有这个文件，也可能不可写。需要明确文件是随程序分发的只读资源、上传输入、临时结果，还是必须跨部署保留的业务数据。

Docker 卷与容器生命周期分离，可以在容器删除后继续保存卷中的数据，见 [Docker：卷](https://docs.docker.com/engine/storage/volumes/)。卷并不自动提供备份：它仍可能被删除、损坏或随存储设备失效。挂载位置也要与实际数据库版本的存储目录一致，上面的配置片段不能替代镜像的运行要求。

## “进程存在”不足以说明能够工作

应用进程启动成功，仍可能连不上数据库或无法读取输入。可以分开检查“进程是否仍在运行”和“当前是否能接收并完成某类请求”。若把任何外部依赖短暂失败都当作必须重启进程，重启可能销毁当前请求，却无法修复外部服务。

部署检查应沿真实路径进行：调用入口能否访问应用，应用能否访问数据库与内容存储，工作进程能否取得任务。逐项检查的位置不同；从宿主机成功连接数据库，不能直接证明容器内的应用也能连接。

## 练习

配置将主机 8080 映射到 API 容器 8000。应用日志显示监听 `127.0.0.1:8000`，数据库地址是 `localhost:5432`，数据库运行在另一个容器。上传内容写到 `./uploads`，没有卷或外部内容存储。

分别从浏览器请求、应用读取数据库、容器被替换三个事件追踪后果。哪些改动涉及网络地址，哪些涉及数据寿命？如果健康检查只是发现进程存在，这些问题能被它区分吗？
