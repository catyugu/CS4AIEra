开发时，应用和数据库在同一台机器。部署时，应用移到另一台服务器，原来的 `localhost`、相对路径和环境变量都可能指向不同位置。要让同一份程序继续工作，需要重建完整的运行条件。

## 部署一个可工作的应用

部署后，报告应用需要一个请求入口、应用进程、后台工作进程，以及它们能访问的数据库和文件存储。进程可以在同一台机器，也可以分布运行。

| 运行条件 | 必须确定什么 |
| --- | --- |
| 程序与依赖 | 目标平台能执行哪些产物，所需运行时和库在哪里 |
| 启动方式 | 启动哪个程序，以什么身份、工作目录和参数运行 |
| 配置 | 数据库地址、资源位置和功能选项从哪里读取 |
| 网络 | 谁监听什么地址，哪些调用方能够连接 |
| 数据 | 哪些文件随程序替换，哪些必须继续保存 |
| 进程管理 | 退出后谁发现、怎样重新启动 |

程序文件相同，并不保证这些条件也相同。服务端启动配置在运行时读取；前端构建已经写进脚本的值，则要检查实际发布文件，见 <CrossRef id="networks-and-web.development-and-deployment" />。

## 地址与路径属于执行环境

`127.0.0.1` 只接受相应环境中的本地连接。应用只在回环地址监听时，远程浏览器不能直接连接它。反向代理可以在对外入口接收请求，再访问本机应用端口。

数据库若在另一台机器，应用要使用那台机器可访问的地址。应从应用所在环境检查连接，而非只在开发机上验证。地址的基础见 <CrossRef id="networks-and-web.addressing-and-listening" />。

相对路径从进程工作目录解释。`./uploads` 在开发目录里存在，换一个启动目录就可能找不到；将上传文件放进会被替换的发布目录，又可能在下次部署时丢失。可执行文件、只读资源、临时文件和持久业务数据应分别安排位置。

## 容器打包运行环境

容器镜像可以打包应用及所需文件，容器运行时提供可配置的文件系统、进程和网络隔离。容器中的程序仍使用宿主机资源，退出后内存状态也会消失。

两个容器使用独立网络环境时，各自的 `localhost` 不会指向对方。容器内监听端口和主机对外发布的端口也可能不同。持久数据可通过卷或外部服务保留，其寿命应与替换应用分开，见 [Docker：网络](https://docs.docker.com/engine/network/)与[数据卷](https://docs.docker.com/engine/storage/volumes/)。

容器是一种部署方式。理解进程、地址、文件和配置之后，再阅读具体容器配置，就能判断每项设置承担什么工作。

## 检查是否能完成真实工作

启动成功后，可以先请求一条已有报告，确认入口可达、数据库连接正常、当前程序能解释记录；再读取一份报告文件，检查内容存储和权限。后台工作进程还应能够取得一项测试任务，保存并查询结果。

存活检查判断进程是否仍在运行；就绪检查判断它是否可以接收所需工作。外部数据库暂时不可用时，应用可以停止接纳依赖它的新任务，并报告原因。反复重启应用不能修复外部连接本身。

## 练习

部署记录写着：进程已启动，API 监听 `127.0.0.1:8000`，公网入口直接指向主机 8000；数据库实际在另一台机器，配置仍是 `localhost`；上传文件存在本次发布目录。

分别追踪浏览器访问、读取数据库和替换发布目录的后果。为每个问题选择正确的检查位置，再设计一组上线后能够发现它们的实际操作。
