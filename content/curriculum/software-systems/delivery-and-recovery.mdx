前面的正常过程是：API 保存任务并送入队列，工作进程计算并保存结果，再向队列确认。进程可能在任意两步之间退出。恢复程序需要根据留下的记录，决定继续哪一步。

## 部分失败与组件状态

部分失败是某些组件或它们之间的通信失败，其他组件仍继续运行。例如 API 已把任务 17 保存到数据库，随后发送消息时超时。数据库记录已经存在，消息是否接收仍未知。超时的含义见 <CrossRef id="networks-and-web.latency-timeouts-and-retries" />。

| 中断位置 | 已知事实 | 需要恢复的工作 |
| --- | --- | --- |
| 保存任务后，尚未发送 | 数据库有任务，队列没有 | 继续发送 |
| 消息已接收，确认未返回 | 数据库有任务，发送方不确定队列状态 | 查询或重发，并识别重复 |
| 计算结果已提交，消息确认未发送 | 数据库有结果，队列可能重投 | 复用原结果，再确认 |

每个组件只完成自己的动作。数据库提交、消息发送和文件上传分别改变各自系统的状态。恢复前要核对每一步是否已经执行。

## 任务标识与重复处理

任务 17 的各次尝试都使用同一个编号。工作进程收到任务时，先读保存的状态。已取消就结束处理，已完成就复用结果，待处理则按条件转为处理中并计算。处理中任务可为每次尝试保存编号和处理期限，由执行者定期续期。期限届满时，另一执行者通过条件更新登记新尝试。提交结果时也要核对尝试编号与期限，防止已经过期的执行者覆盖现有结果。允许重新投递的队列可能多次送来同一消息，这属于<Term id="delivery-semantics">投递语义</Term>，例如 [Amazon SQS 标准队列](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues-at-least-once-delivery.html)允许重复投递。

两个处理者可能同时读到“未完成”。保存结果时，可以用任务编号的唯一约束识别重复，并把结果与完成记录放在同一事务中。一个处理者提交成功后，另一个按唯一约束冲突重新读取原结果。

| 数据库事务 | 重投后怎样处理 |
| --- | --- |
| 尚未提交 | 没有完成记录，可以重新计算 |
| 已提交，尚未确认队列消息 | 找到原结果，复用并确认 |

这样，即使计算重复执行，数据库仍可只保存一份对应任务的业务结果。唯一约束与事务分别见 <CrossRef id="persistence.relations-keys-and-constraints" /> 和 <CrossRef id="persistence.transactions-and-recovery" />。

## 待发送记录与故障恢复

为了找回保存后尚未发送的任务，API 可以在保存任务的同一个数据库事务中写入一条待发送记录。后台程序扫描这些记录，向队列发送消息，并标记已发送。这种做法通常称为事务性发件箱（transactional outbox）模式。

若后台程序在发送成功、更新标记之前退出，下次会重发。待发送记录让恢复程序能够找回尚未发送的任务；稳定编号与重复识别让消息重发后仍能关联原任务。两者需要配合使用。

外部动作要按相应服务的规则处理。邮件可能已发送，调用方却没收到响应；若邮件服务支持按操作标识查询，就可以核对后更新本地记录。这种跨组件的状态核对与修复称为<Term id="reconciliation">对账</Term>（reconciliation）。无法确认的结果需要保留供后续处理。

## 文件提交与日志追踪

报告文件放在对象存储，完成状态放在数据库时，两者也分别提交。可以让每次尝试写入各自的对象键，例如 `reports/17/attempt-2.pdf`，然后用条件更新提交完成状态和对象键。记录失败会留下未引用文件，待相应尝试结束后再清理。先发布记录再上传，则可能让用户取得打不开的报告。

排查任务时，用任务编号关联提交、发送、计算和保存记录。日志应说明每一步的输入标识与结果；跨机器的时间戳可能有偏差，消息收发和状态版本还能帮助还原先后关系。

## 练习

API 已保存任务与待发送记录，消息发送成功后却在更新标记之前退出。写出恢复后的动作，并解释工作进程为何仍需识别重复任务。

报告文件已上传，数据库完成记录尚未提交时，工作进程退出。下一次应根据什么判断任务是否完成？哪些文件可能成为未引用内容？
