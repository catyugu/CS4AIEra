前面的正常过程是：API 保存任务并送入队列，工作进程计算并保存结果，再向队列确认。进程可能在任意两步之间退出。恢复程序需要根据留下的记录，决定继续哪一步。

## 分别追踪组件的进度

部分失败是某些组件或它们之间的通信失败，其他组件仍继续运行。例如 API 已把任务 17 保存到数据库，随后发送消息时超时。数据库记录已经存在，消息是否接收仍未知。超时的含义见 <CrossRef id="networks-and-web.latency-timeouts-and-retries" />。

| 中断位置 | 已知事实 | 需要恢复的工作 |
| --- | --- | --- |
| 保存任务后，尚未发送 | 数据库有任务，队列没有 | 继续发送 |
| 消息已接收，确认未返回 | 数据库有任务，发送方不确定队列状态 | 查询或重发，并识别重复 |
| 计算结果已提交，消费确认未发送 | 数据库有结果，队列可能重投 | 复用原结果，再确认 |

每个组件只完成自己的动作。数据库里的记录不会因为消息发送超时自动撤销，已经写入的报告也不会因为工作进程退出自动消失。

## 重试关联到同一任务

任务 17 的各次尝试都使用同一个编号。工作进程收到任务时，先读保存的状态：已取消就结束处理，已完成就复用结果，待处理则按条件转为处理中并计算。处理中任务的接管需要确认原执行者已经退出，再安排重新执行。允许重新投递的队列可能多次送来同一消息，这属于<Term id="delivery-semantics">投递语义</Term>，例如 [Amazon SQS 标准队列](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues-at-least-once-delivery.html)允许重复投递。

只检查一次“是否完成”还不能协调同时到来的两个处理者。保存结果时，可以用任务编号的唯一约束识别重复，并把结果与完成记录放在同一事务中。它们共同提交，重复处理者按冲突结果重新读取原结果。

| 数据库事务 | 重投后怎样处理 |
| --- | --- |
| 尚未提交 | 没有完成记录，可以重新计算 |
| 已提交，尚未确认队列消息 | 找到原结果，复用并确认 |

这样，即使计算重复执行，数据库仍可只保存一份对应任务的业务结果。唯一约束与事务分别见 <CrossRef id="persistence.relations-keys-and-constraints" /> 和 <CrossRef id="persistence.transactions-and-recovery" />。

## 保存待办进度

为了找回保存后尚未发送的任务，API 可以在保存任务的同一个事务中记录“待发送”。后台程序扫描这些记录，发送成功后再标记。

若后台程序在发送成功、更新标记之前退出，下次会重发。因此，待发送记录解决遗漏，稳定编号与重复识别解决重发的影响。两者配合，恢复才能继续推进。

外部动作要按相应服务的规则处理。邮件可能已发送，调用方却没收到响应；若邮件服务支持按操作标识查询，就可以核对后更新本地记录。将双方记录核对并修正差异，称为<Term id="reconciliation">对账</Term>。无法确认的结果需要保留供后续处理。

## 文件、记录与日志

报告文件放在对象存储，完成状态放在数据库时，两者也分别提交。可以先上传新文件，再提交引用它的记录；记录失败会留下未引用文件，供后续清理。先发布记录再上传，则可能让用户取得打不开的报告。

排查任务时，用任务编号关联提交、发送、计算和保存记录。日志应说明每一步的输入标识与结果；跨机器的时间戳可能有偏差，消息收发和状态版本还能帮助还原先后关系。

## 练习

API 已保存任务与待发送记录，消息发送成功后却在更新标记之前退出。写出恢复后的动作，并解释工作进程为何仍需识别重复任务。

报告文件已上传，数据库完成记录尚未提交时，工作进程退出。下一次应根据什么判断任务是否完成？哪些文件可能成为未引用内容？
