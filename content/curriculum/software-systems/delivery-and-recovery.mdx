工作进程已经完成任务，却在向队列确认之前退出。调度方无法确认它做到了哪一步，只能再次安排处理。恢复工作因此既要防止任务遗漏，也要识别已经完成的工作。

## 重试时沿用同一个任务编号

假设任务 17 要在数据库中保存一份统计结果。它可能被执行一次，也可能因为进程退出而重新执行。每次尝试都使用编号 17，处理方才能知道它们是在做同一件事。

开始处理时，先按编号查找完成记录。若结果已存在，就返回原结果；尚未完成，才继续计算。这样，重新收到任务不必重新生成一份业务结果。

消息队列可能重复投递，这种行为属于<Term id="delivery-semantics">投递语义</Term>。例如 [Amazon SQS 标准队列](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues-at-least-once-delivery.html)允许重复投递，使用它的程序需要识别重复工作。消息到达几次和最终保存几份结果，可以是不同的数量。

## 结果与完成记录一起保存

如果先记录“已完成”，再保存统计结果，进程可能在两步之间退出。下一次处理看到已完成就跳过，实际结果却还没写入。反过来，先保存结果、再单独记完成，也可能因中途退出而重复修改。

当两项记录都在同一个数据库时，可以把结果与完成记录放入同一个事务，用任务编号的唯一约束识别重复提交。事务提交后，两项记录一起存在；事务未提交，则都不作为完成结果。事务与唯一约束分别见 <CrossRef id="persistence.transactions-and-recovery" /> 和 <CrossRef id="persistence.relations-keys-and-constraints" />。

| 进程退出的位置 | 下一次处理时的动作 |
| --- | --- |
| 保存结果的事务尚未提交 | 没有完成记录，可以重新处理 |
| 事务已提交，尚未确认队列消息 | 找到原结果，复用它，再确认消息 |

这使结果已经保存、消息尚未确认的任务也有了恢复办法。

## 从保存的记录中继续工作

API 也可能在保存任务之后、把它送入队列之前退出。可以在保存任务时一并记下“待发送”，由后台程序找到这些记录并继续发送。恢复的依据就保存在数据库里，不依赖原来的 API 进程还记得什么。

外部操作还需要向对方核实。例如邮件服务可能已经发出通知，调用方却没收到响应。若服务支持按操作标识查询，就能据此更新本地状态；无法确认时，保留未知结果供后续处理。将本地记录与对方结果核对、修正差异，称为<Term id="reconciliation">对账</Term>。

这些恢复过程都依赖保存下来的任务编号、进度和结果。进程退出之后，接替它的程序才能找到未完成的工作，并识别已经完成的部分。

## 练习

API 保存了任务 17 及“待发送”记录，发送成功后却在更新发送状态前退出。恢复程序只知道它仍待发送。写出恢复动作，并说明工作进程为什么还要识别重复任务。

另一份报告先上传文件，再把文件键与完成状态写入数据库。工作进程在上传完成、数据库事务提交之前退出。下一次处理时应如何判断是否完成？哪些文件可能需要清理？与“数据库已提交、队列尚未确认”的情形比较。
