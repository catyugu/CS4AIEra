用户提交一份报告生成任务后，计算可能持续几十秒。网页需要先获得任务编号，随后查询进度；如果用户在计算开始前改变主意，还可以取消任务。服务端必须记住任务当前处于哪个阶段，才能回答这些后续请求。

## 任务标识与交互协议

客户端创建报告时，服务分配任务编号 17。随后浏览器可以多次查询该任务，也可以请求取消。下面是一组用于说明协议的 JSON 查询请求与响应：

```json
{"request_id": 5, "action": "get_task", "task_id": 17}
```

```json
{"request_id": 5, "task_id": 17, "status": "running"}
```

`request_id` 用来关联本次请求与响应，`task_id` 标识任务。后续查询使用同一个 `task_id`，但每次请求都有自己的 `request_id`。这两个字段在这里属于示例应用自行约定的消息格式。

<Term id="protocol">协议</Term>规定参与方怎样交换和解释消息，包括字段含义、允许的交互顺序与失败行为。HTTP 约定请求响应的通用结构，应用还要约定任务 17 的业务规则。

## 任务生命周期与状态机

<Term id="state-machine">状态机</Term>用状态、事件和转移规则表达过程。状态保存后续操作所需的信息；事件触发动作，并可能使状态改变。

先约定一套可实现的业务规则：任务创建后进入“待处理”，工作进程开始执行时变为“处理中”；只有待处理任务可以取消。处理中任务最终进入“已完成”或“已失败”。

| 当前状态 | 事件 | 动作 | 新状态 |
| --- | --- | --- | --- |
| 尚未创建 | 提交 | 分配编号，保存输入引用 | 待处理 |
| 待处理 | 开始执行 | 记录开始 | 处理中 |
| 待处理 | 取消 | 拒绝后续执行 | 已取消 |
| 处理中 | 计算成功 | 保存结果 | 已完成 |
| 处理中 | 计算失败 | 保存原因 | 已失败 |
| 处理中 | 查询 | 返回当前状态 | 处理中 |
| 已完成 | 查询 | 返回保存的结果 | 已完成 |
| 已取消 | 查询 | 返回取消状态 | 已取消 |
| 已取消 | 请求开始 | 拒绝 | 已取消 |

读取状态时通常保持原状态。创建、开始、取消和完成则可能改变状态。只保存 `exists = True` 无法区分这些阶段，也就无法决定请求是否有效。

例如，任务 17 的一次正常执行可以记为：

```text
提交任务 17 → 待处理
查询任务 17 → 返回「待处理」，状态不变
工作进程开始 → 处理中
查询任务 17 → 返回「处理中」，状态不变
计算完成   → 已完成
查询任务 17 → 返回结果，状态仍为「已完成」
```

另一种执行是提交后立即取消：`待处理 → 已取消`。此后即使工作进程收到旧的启动通知，也应拒绝执行。客户端重复查询时，服务持续返回“已取消”。

## 状态转移的条件更新

如果用户点击“取消”的同时，工作进程准备开始任务，两个请求可能都读到“待处理”。服务需要让状态更新具有条件：只有数据库中的状态仍为“待处理”，才能更新为“已取消”或“处理中”。这两个更新由数据库原子地判断条件并执行时，最终只有一个能成功，相关 SQL 用法见 <CrossRef id="persistence.data-changes" />。

| 首先成功的更新 | 任务状态 | 另一方的处理 |
| --- | --- | --- |
| 取消成功 | 已取消 | 工作进程放弃启动 |
| 开始成功 | 处理中 | 服务拒绝取消，返回当前状态 |

页面可以根据响应更新按钮、等待提示和结果，但任务是否允许取消由服务端保存的状态决定。工作进程与 Web 服务分离后，这套规则仍可使用。

## 练习

依次执行“提交任务 17、取消任务 17、工作进程请求开始、查询任务 17”。写出每步的状态、返回结果，并说明工作进程是否会运行。

如果产品改为支持处理中取消，尝试补充一条状态转移规则。取消请求返回成功后，计算是否立即停止？已经产生的部分结果如何处理？根据你的选择，说明服务端应保存什么状态，页面应显示什么。
