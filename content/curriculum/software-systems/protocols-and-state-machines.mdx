用户在网页上请求生成报告，计算可能需要几十秒。服务先建立任务记录，返回编号 17。用户凭编号查询进度；如果计算还没开始，也可以请求取消。

## 用任务编号接续多次请求

浏览器提交报告参数，服务接受 `POST /reports` 请求，创建任务并返回：

```json
{"task_id": 17, "status": "queued"}
```

此后，浏览器用 `GET /reports/17` 查询状态。工作进程开始计算后，同一个查询会得到：

```json
{"task_id": 17, "status": "running"}
```

`task_id` 始终指向那份报告任务。创建请求早已结束，任务仍由服务端保存和处理，浏览器可以随时发起新的查询。

这些请求还需要约定操作结果。例如 `POST /reports/17/cancel` 请求取消任务，成功时返回“已取消”；任务已经开始时，服务返回当前状态，告知用户取消未成功。参与方遵循的请求格式、字段含义和处理规则，合起来构成<Term id="protocol">协议</Term>。

## 报告任务的状态如何变化

任务刚创建时处于“待处理”。工作进程领取它，开始计算后变为“处理中”；计算结束时，记录结果或失败原因。用户只可以取消尚未开始的任务。

```text
创建 → 待处理 ──开始执行──→ 处理中 ──计算成功──→ 已完成
            │                    │
            │ 取消               │ 计算失败
            ▼                    ▼
          已取消                已失败
```

这张图规定了允许发生的状态变化。例如，“已取消”的任务不能再进入“处理中”；已经开始执行的任务按当前规则也不能直接转成“已取消”。用有限的状态和明确的转移规则描述这样的过程，称为<Term id="state-machine">状态机</Term>。

沿着一次正常生成报告的过程，可以看到请求与任务状态的关系：

| 发生的操作 | 服务端保存的状态 | 浏览器查询到的内容 |
| --- | --- | --- |
| 创建任务 17 | 待处理 | 任务编号 17 |
| 第一次查询 | 待处理 | 等待执行 |
| 工作进程开始计算 | 处理中 | 计算进行中 |
| 第二次查询 | 处理中 | 计算进行中 |
| 工作进程保存报告 | 已完成 | 报告结果 |
| 第三次查询 | 已完成 | 同一份报告结果 |

查询只是读取任务记录。只有开始、完成、失败和取消等操作会改变状态。

另一种情况是，用户在工作进程领取任务前发起取消，任务从“待处理”进入“已取消”。之后查询始终得到“已取消”；工作进程即使收到了任务编号，也应根据保存的状态放弃执行。

## 取消和开始执行同时发生时

假设任务 17 还处于“待处理”。用户点击取消的同时，工作进程准备开始计算。两边如果先各自读取状态、判断可以操作，再直接写回，就可能出现这样的顺序：用户和工作进程都读到“待处理”，用户写入“已取消”，工作进程随后写入“处理中”。页面已经报告取消成功，后台却开始执行了。

可以让数据库在修改时检查原状态。取消和开始执行分别尝试下面两种转换：

- 取消：`queued → cancelled`。
- 开始执行：`queued → running`。

两者执行的 SQL 具有相同的条件：**只有任务仍处于 `queued`，才修改它。** 下面用 SQLite 重放取消先成功的顺序：

```python run id="software-systems.protocols-and-state-machines.claim-or-cancel"
import sqlite3

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE tasks (id INTEGER PRIMARY KEY, status TEXT)")
db.execute("INSERT INTO tasks VALUES (17, 'queued')")

def change_status(new_status):
    changed = db.execute(
        "UPDATE tasks SET status = ? WHERE id = 17 AND status = 'queued'",
        (new_status,),
    ).rowcount
    print(new_status, "更新行数:", changed)

change_status("cancelled")
change_status("running")
print("最终状态:", db.execute("SELECT status FROM tasks WHERE id = 17").fetchone()[0])
db.close()
```

第一次更新影响一行，状态变成 `cancelled`；第二次更新影响零行，工作进程因此放弃执行。把两次 `change_status` 的调用顺序交换，工作进程就会先取得执行权，取消请求则失败，任务保持 `running`。

SQL 的 `UPDATE` 在同一次操作中检查 `WHERE` 条件并修改记录。先成功的一方改变了原状态，另一方的条件随即失效。服务根据受影响行数判断操作是否成功：取消失败时返回当前任务状态；开始执行失败时，工作进程跳过该任务。条件更新的原理见 <CrossRef id="persistence.data-changes" />。
