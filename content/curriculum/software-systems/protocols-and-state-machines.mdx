用户提交销售表格后，服务端建立任务 17。页面凭这个编号查询进度。用户过会儿再打开网站，也可以从自己的任务列表找到同一条记录。

## 交互协议与任务标识

| 操作 | 接口 | 服务器的动作 |
| --- | --- | --- |
| 提交报告 | `POST /reports` | 保存任务，返回编号和查询地址 |
| 查询任务 17 | `GET /reports/17` | 读取状态，完成后给出报告下载地址 |
| 取消任务 17 | `POST /reports/17/cancel` | 仍在等待时取消，否则返回当前状态 |

这些接口的请求格式、字段含义和处理规则，组成客户端与服务端的交互 <Term id="protocol">协议</Term>。例如，提交响应可以使用 `202 Accepted`，表示请求已接纳，处理尚待完成。应用在响应中返回任务编号和查询地址，供客户端发起后续查询。见 [RFC 9110 的 202 Accepted 定义](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3)。

## 状态与转移

数据库保存任务当前状态。在每次正常处理尝试中，后台程序把等待任务改为处理中，随后写入报告链接或失败原因。用户可以取消还在等待的任务。

| 当前状态 | 动作 | 更新后的状态 |
| --- | --- | --- |
| 等待执行 `queued` | 后台程序开始处理 | 处理中 `running` |
| 等待执行 `queued` | 用户取消 | 已取消 `cancelled` |
| 处理中 `running` | 保存结果 | 已完成 `completed` |
| 处理中 `running` | 记录业务失败 | 已失败 `failed` |

这组状态及允许的转移构成一个<Term id="state-machine">状态机</Term>。协议规定客户端可以请求哪些操作，状态机规定每项操作在当前状态下是否允许发生。查询只读取记录；取消成功后，迟到的领取操作看到的是已取消状态，应当跳过该任务。

## 并发转移与条件更新

假设用户刚提交任务 17 就点击取消，后台程序同时来领取。两边可能同时读到“等待执行”。如果两边各自读完再直接写，后台程序会覆盖用户刚写入的取消结果。把检查放进同一条 `UPDATE`，就可以让数据库只接受其中一个操作。下面用 SQLite 建立一条模拟记录，按顺序重放两个操作。输出中的行数代表本次操作改动了几条记录。

```python run id="software-systems.protocols-and-state-machines.claim-or-cancel"
import sqlite3

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE tasks (id INTEGER PRIMARY KEY, status TEXT)")
db.execute("INSERT INTO tasks VALUES (17, 'queued')")
db.commit()

def change_status(new_status):
    changed = db.execute(
        "UPDATE tasks SET status = ? WHERE id = 17 AND status = 'queued'",
        (new_status,),
    ).rowcount
    db.commit()
    print(new_status, "更新行数:", changed)

change_status("cancelled")
change_status("running")
print("最终状态:", db.execute("SELECT status FROM tasks WHERE id = 17").fetchone()[0])
db.close()
```

取消先改动一行；开始处理时，记录已离开 `queued`，改动零行。交换两个调用，开始处理先成功。事务成功提交后，API 和后台程序都可以根据更新行数判断这次操作是否生效。条件更新见 <CrossRef id="persistence.data-changes" />。

## 练习

产品希望允许用户为正在计算的报告提出取消请求。计算可能已经开始写文件。为「已请求取消」增加一个状态，写出用户提出请求、工作进程确认停止、报告先一步完成这三种操作允许的转移，并说明页面何时可以显示「已取消」。
