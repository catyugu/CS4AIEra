报告生成后，用户可以查询结果；报告还没完成时，用户可以取消。服务需要记住任务处于哪个阶段，才能处理下一次请求。

## 一个任务，多次请求

客户端创建报告，服务返回编号 17；之后查询和取消都使用这个编号。例如下面两份构造的 JSON 消息分别表示查询请求与响应：

```json
{"request_id": 5, "action": "get_task", "task_id": 17}
```

```json
{"request_id": 5, "task_id": 17, "status": "running"}
```

`request_id` 关联本次请求与响应，`task_id` 标识持续存在的任务。一个任务可以涉及创建、查询、取消等多次请求。

<Term id="protocol">协议</Term>规定参与方怎样交换和解释消息，包括字段含义、允许的交互顺序与失败行为。HTTP 约定请求响应的通用结构，应用还要约定任务 17 的业务规则。

## 用状态机描述生命周期

<Term id="state-machine">状态机</Term>用状态、事件和转移规则表达过程。状态保存后续操作所需的信息；事件触发动作，并可能使状态改变。

下面先固定一套简单规则：取消只允许发生在任务尚未开始时。任务进入处理中之后，会完成或失败。

| 当前状态 | 事件 | 动作 | 新状态 |
| --- | --- | --- | --- |
| 尚未创建 | 提交 | 分配编号，保存输入引用 | 待处理 |
| 待处理 | 开始执行 | 记录开始 | 处理中 |
| 待处理 | 取消 | 拒绝后续执行 | 已取消 |
| 处理中 | 计算成功 | 保存结果 | 已完成 |
| 处理中 | 计算失败 | 保存原因 | 已失败 |
| 已完成 | 查询 | 返回原结果 | 已完成 |
| 已取消 | 请求开始 | 拒绝 | 已取消 |

查询不一定改变状态。完成和取消则会影响以后允许的动作。只保存 `exists = True` 无法区分这些阶段，因此不足以执行表中的规则。

## 让处理遵守状态规则

应用可以用数据库字段保存任务状态。开始计算时，要求原状态仍为待处理，再改为处理中；取消同样要求仍为待处理。通过条件更新，就能让竞争的请求中只有一个成功，方法见 <CrossRef id="persistence.data-changes" />。

客户端根据状态显示等待、进度或结果。页面上的按钮帮助用户选择；服务端按同一套状态规则处理实际收到的请求。下一课把计算移到工作进程，状态表仍可沿用。

## 练习

依次提交、取消、请求开始、查询任务。逐步写出当前状态和处理结果。

如果产品改为允许处理中取消，需要先决定计算是否立即停止、已经产生的结果怎样处理。选择一套明确规则，补充状态与转移，再说明页面应显示什么。
