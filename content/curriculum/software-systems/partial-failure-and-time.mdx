API 能响应查询，报告工作进程却取不到输入文件；数据库已经保存任务，对象服务暂时不可达。应用仍有一些部分正常运行，任务却无法沿整条路径完成。

## 先声明哪些故障可能发生

部分失败是多个组件中仅一部分失败，或组件之间的通信失败。分析需要给出失败模型：进程可能退出；消息可能延迟、丢失或重复；存储可能暂时不可读；已经完成的持久修改不会因另一组件失败而自动撤销。

这个模型允许 API 正常、数据库正常、消息服务暂时不可达。数据库中的接纳记录与消息服务中的任务消息，就不能通过一个“系统正常/异常”布尔值概括。

对第三方服务，还要按操作区分失败：请求可能被明确拒绝、被限流、被接纳但没有及时返回，或返回的结果不符合约定。相同的异常文本若覆盖这些情况，应用就缺少作出恢复决定的信息。

## 无响应需要保留不确定性

超时怎样结束等待而不证明操作未完成，见 <CrossRef id="networks-and-web.latency-timeouts-and-retries" />。将这个规则放进应用结构后，每条有副作用的边界都需要检查。

| 步骤 | 数据库 | API 与消息服务 |
| --- | --- | --- |
| 1 | 已保存任务 17 | API 发布任务 17 |
| 2 | 任务 17 仍为待处理 | 消息服务可能已经接收，但确认未到 API |
| 3 | 没有新的结果记录 | API 等待超时 |

此时可以确定数据库里有任务，也可以确定 API 没得到确认。任务消息是否已接收，需要另外确认；超时不能将数据库记录直接改成“消息一定未发送”。

如果 API 因超时删除记录，而消息已经进入队列，工作进程随后会收到一项找不到原记录的任务。选择保留“发布结果未知”，用相同操作标识继续查询或安全补发，可以让后续处理围绕实际状态进行；补发是否安全还取决于消费端如何处理重复。

## 时间戳不能代替因果关系

假设 API 的时钟比工作进程快两分钟。API 记录提交时间 10:05，工作进程收到任务后记录开始时间 10:03。按字符串排序，会把开始放在提交之前；消息实际从 API 发到工作进程，先发送再接收的因果关系没有改变。

墙上时间表达日期与时刻，可能因校时发生跳变，跨机器也可能有偏差。单调时间适合在同一运行环境中测量经过时长；Python `time.monotonic()` 的参考起点未定义，只有读数差用于测量时间，见 [Python time：monotonic](https://docs.python.org/3/library/time.html#time.monotonic)。单调时间也不自动给两台机器提供同一个全局起点。

事件 A 产生的消息被事件 B 接收，可以推出 A 先于 B。互不通信的两件事，仅凭不准确的时间戳通常无法确定先后。操作标识、同一任务的版本号与消息因果关系，能补充定位所需信息；时间戳仍有查找用途，但应保留它的误差条件。

## 等待预算与业务期限不同

“客户端最多等五秒”规定客户端等待；“任务必须在当天完成”规定业务期限。前者到期，不表示后者已取消。

如果把一个跨机器的绝对截止时刻传给工作进程，就需要说明时钟偏差怎样影响判断；如果每层重新给完整的五秒，则会累加超过原有总预算。期限要明确由谁执行、从哪里计算，以及到期后已经完成的修改如何处理。

同样，几秒没收到另一个实例的心跳，只能说明它可能退出或通信很慢。若此时另一个实例直接接管写入，旧实例也可能仍在运行。接管方案需要另行保证旧执行者不能继续作出冲突修改，不能把“怀疑失败”直接当成“已经停止”。
