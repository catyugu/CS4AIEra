API 能响应查询，报告工作进程却取不到输入文件；数据库已经保存任务，对象服务暂时不可达。应用仍有一些部分正常运行，任务却无法沿整条路径完成。

## 一个组件失败，其他组件可能继续运行

部分失败是多个组件中仅一部分失败，或组件之间的通信失败。为了推断后果，需要先说清考虑哪些故障，这些假设称为失败模型。例如进程可能退出；消息可能延迟、丢失或重复；存储可能暂时不可读；已经完成的持久修改不会因另一组件失败而自动撤销。

这个模型允许 API 正常、数据库正常、消息服务暂时不可达。此时数据库中可能已有接纳记录，消息服务却没有对应任务。诊断和恢复需要分别记录这两个组件的状态。

对第三方服务，还要按操作区分失败：请求可能被明确拒绝、被限流、被接纳但没有及时返回，或返回的结果不符合约定。相同的异常文本若覆盖这些情况，应用就缺少作出恢复决定的信息。

## 分别记录数据库和消息服务的进度

API 保存任务后，还要向消息服务发布。网络课已经解释了响应丢失导致的未知结果，见 <CrossRef id="networks-and-web.latency-timeouts-and-retries" />。这里增加的是两个组件的进度：数据库里的记录可以已经确定，消息发布仍然未知。

| 步骤 | 数据库 | API 与消息服务 |
| --- | --- | --- |
| 1 | 已保存任务 17 | API 发布任务 17 |
| 2 | 任务 17 仍为待处理 | 消息服务可能已经接收，但确认未到 API |
| 3 | 没有新的结果记录 | API 等待超时 |

此时可以确定数据库里有任务，也可以确定 API 没得到确认。任务消息是否已接收，需要另外确认；超时不能将数据库记录直接改成“消息一定未发送”。

如果 API 因超时删除记录，而消息已经进入队列，工作进程随后会收到一项找不到原记录的任务。保留“发布结果未知”，就能把任务留给后续恢复流程。怎样找回待发布工作、处理重复消息，见 <CrossRef id="software-systems.delivery-and-recovery" />。

## 时间戳不能代替因果关系

假设 API 的时钟比工作进程快两分钟。API 记录提交时间 10:05，工作进程收到任务后记录开始时间 10:03。按字符串排序，会把开始放在提交之前；消息实际从 API 发到工作进程，先发送再接收的因果关系没有改变。

墙上时间表达日期与时刻，可能因校时发生跳变，跨机器也可能有偏差。单调时间适合在同一运行环境中测量经过时长；Python `time.monotonic()` 的参考起点未定义，只有读数差用于测量时间，见 [Python time：monotonic](https://docs.python.org/3/library/time.html#time.monotonic)。单调时间也不自动给两台机器提供同一个全局起点。

事件 A 产生的消息被事件 B 接收，可以推出 A 先于 B。互不通信的两件事，仅凭不准确的时间戳通常无法确定先后。操作标识、同一任务的版本号与消息因果关系，能补充定位所需信息；时间戳仍有查找用途，但应保留它的误差条件。

## 等待预算与业务期限不同

“客户端最多等五秒”规定客户端等待；“任务必须在当天完成”规定业务期限。前者到期，不表示后者已取消。

网络等待沿用 <CrossRef id="networks-and-web.latency-timeouts-and-retries" /> 的总截止期限。后台业务期限则要另外规定由谁检查、到期是否取消任务、已经完成的结果如何处理。把跨机器的绝对时刻传给工作进程时，还要考虑时钟偏差。

## 接管任务时，旧进程可能还在运行

工作进程定期向调度方报告自己仍在运行，这种消息称为心跳。几秒没收到心跳，可能是进程退出，也可能是通信很慢。若调度方直接把任务交给另一个进程，旧进程恢复通信后也可能继续提交结果。

可以让存储端识别当前获准提交的执行者：接管使新的执行权限生效，旧执行者随后提交时被拒绝。这个检查必须在接受写入的位置执行；只在调度方标记“旧进程已失效”，挡不住旧进程直接写入。

数据库仍显示任务“处理中”，工作进程两分钟没有报告进度。现在把任务交给另一进程，旧进程若只是暂时无法通信，会发生什么？接管前需要限制谁的写入，才能避免两个进程各发布一份结果？

<details>
<summary>参考推理</summary>

旧进程可能继续生成报告，新进程也开始处理同一个任务，两者都可能尝试发布结果。心跳缺失只能触发调查或接管流程，无法让旧进程停止。接管时应更新提交权限，并让存储端拒绝旧执行者的写入；外部发布如果绕过该检查，也要有自己的去重或权限安排。
