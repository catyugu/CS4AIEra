API 能响应查询，报告工作进程却取不到输入文件；数据库已经保存任务，对象服务暂时不可达。应用仍有一些部分正常运行，任务却无法沿整条路径完成。

## 一个组件失败，其他组件可能继续运行

部分失败是多个组件中仅一部分失败，或组件之间的通信失败。为了推断后果，需要先说清考虑哪些故障，这些假设称为失败模型。例如进程可能退出；消息可能延迟、丢失或重复；存储可能暂时不可读；已经完成的持久修改不会因另一组件失败而自动撤销。

这个模型允许 API 正常、数据库正常、消息服务暂时不可达。此时数据库中可能已有接纳记录，消息服务却没有对应任务。诊断和恢复需要分别记录这两个组件的状态。

## 分别记录数据库和消息服务的进度

API 保存任务后，还要向消息服务发布。网络课已经解释了响应丢失导致的未知结果，见 <CrossRef id="networks-and-web.latency-timeouts-and-retries" />。这里增加的是两个组件的进度：数据库里的记录可以已经确定，消息发布仍然未知。

| 步骤 | 数据库 | API 与消息服务 |
| --- | --- | --- |
| 1 | 已保存任务 17 | API 发布任务 17 |
| 2 | 任务 17 仍为待处理 | 消息服务可能已经接收，但确认未到 API |
| 3 | 没有新的结果记录 | API 等待超时 |

此时可以确定数据库里有任务，也可以确定 API 没得到确认。任务消息是否已接收，需要另外确认；超时不能将数据库记录直接改成“消息一定未发送”。

如果 API 因超时删除记录，而消息已经进入队列，工作进程随后会收到一项找不到原记录的任务。保留“发布结果未知”，就能把任务留给后续恢复流程。怎样找回待发布工作、处理重复消息，见 <CrossRef id="software-systems.delivery-and-recovery" />。

## 用任务记录和日志还原经过

排查同一任务时，先用任务编号找到数据库记录、消息发送和工作进程日志。它们共同说明最后完成了哪一步。

跨机器时间戳可能有偏差。例如 API 记录提交时间 10:05，工作进程的慢时钟记录接收时间 10:03。发送先于接收的关系没有改变，因此不能只按时间文本推断顺序。任务编号、状态版本与消息收发关系提供了额外依据。

超时用于判断等待期限已到。测量本机经过时长适合使用单调时钟，避免校时改变计算的时长，见 [Python time.monotonic](https://docs.python.org/3/library/time.html#time.monotonic)。等待结束后，任务实际到达哪一步，仍要查询已经保存的状态。
