源文件里能找到函数名字，不代表运行程序时就能调用它。这个名字需要对应一个实现；实现要转换成当前机器能执行的指令，调用方和实现还要采用一致的参数与返回值规则。

## 每个文件先得到自己的目标文件

下面两个文件分别使用和定义 `twice`：

```c
/* main.c */
int twice(int x);

int main(void) {
    return twice(21);
}
```

```c
/* twice.c */
int twice(int x) {
    return x + x;
}
```

`int twice(int x);` 是函数声明，告诉编译器参数和返回值均为整数；带函数体的写法是定义。`/* ... */` 是注释。`main` 是这个可执行程序的入口函数，返回值交给运行环境。

预处理先处理 `#include` 这样的指令。宏也发生在这个阶段，例如 `#define LIMIT 16` 会把后续代码中的相应标记替换为 `16`，无需等到程序运行。然后编译器依据语法与类型规则转换代码，汇编阶段将指令编码进目标文件。

目标文件（object file）通常包含机器指令、数据、符号以及待修正的引用位置。符号把名字与定义联系起来。编译 `main.c` 时，编译器知道怎样调用 `twice`，却还没有它的实现；目标文件可以保留这个未解析引用。

链接器把多个目标文件和库组合起来，匹配引用与定义，并修正需要的位置。缺少 `twice` 的定义会在这里失败。阶段划分与 GCC 的“只生成目标文件”模式见 [GCC Overall Options](https://gcc.gnu.org/onlinedocs/gcc/Overall-Options.html)。

```text
main.c  → main.o  ┐
                 ├→ executable
twice.c → twice.o┘
```

“语法正确”“每个文件都编译成功”“整个程序成功链接”是三种不同证据。跨文件声明不一致还可能逃过普通链接检查，函数名能找到，并不证明双方采用相同的参数类型。

## 装载与动态库

可执行文件交给操作系统装载时，代码与数据进入进程的地址空间。静态链接把所需库代码并入产物；动态链接则保留对<Term id="dynamic-library">动态库</Term>的依赖，由动态装载器找到库并完成必要的符号解析。

Linux 动态装载器的搜索规则受可执行文件信息、运行环境和系统配置影响，见 [Linux ld.so 手册](https://man7.org/linux/man-pages/man8/ld.so.8.html)。所以本机有某个库、部署机器没有它，可以导致装载失败，甚至还没进入 `main`。

即使库文件存在，也要检查机器架构和<Term id="abi">应用二进制接口</Term>（ABI）：参数放在哪、整数和指针有多大、结构体怎样排列、返回值怎样传递。源代码层面的相同名字不能替代这些约定。

## CPU 执行的是指令与当前状态

CPU 依据程序计数器找到待执行指令。寄存器（register）保存当前运算使用的少量状态；读取内存的操作通常称为 load，写入内存称为 store。加法可以先把值读进寄存器、在寄存器中计算，再写回内存。具体指令集合和参数寄存器随架构及 ABI 改变。

普通函数调用需要保存“返回后继续到哪里”以及尚未完成的调用状态。许多实现使用调用栈，为各次调用保留栈帧（stack frame），其中可以包含返回位置、保存的寄存器和局部数据。局部量也可能放在寄存器或被优化消除，不能据源代码声明数推出真实栈大小。

以 `main` 调用 `twice(21)` 的未内联执行为例：

| 时刻 | 当前执行 | 必须保留的信息 |
| --- | --- | --- |
| 调用前 | main | 参数 21，调用后继续的位置 |
| 调用中 | twice | 参数 x 为 21，返回到 main 的位置 |
| 返回时 | main | 接收返回值 42，继续执行返回语句 |

递归多次进入同一个函数时，各次调用需要各自尚未完成的状态。因而栈需求取决于同时未返回的调用深度。编译器可以内联函数，使某次源代码调用没有实际调用指令；分析栈和耗时需要确认实际产物。

## Python 到本地扩展仍在同一个调用链里

普通 CPython 的实现执行 Python 程序；一些库将工作交给编译好的本地扩展。例如 NumPy 的许多数值运算由预编译实现处理数组，见 [NumPy 对运算实现的说明](https://numpy.org/doc/stable/user/whatisnumpy.html)。Python 调用只发生一次，内部循环可以在编译好的实现中完成，而不逐项执行 Python 循环体。

调用本地库本身没有创建新进程，也没有自动发起系统调用。它仍可能访问同一进程的内存；本地扩展越界等缺陷可以破坏整个进程。这里有两件独立的事：谁解释或执行这段代码，以及执行时位于哪个资源和隔离边界。

## 练习

一个构建日志说明 `main.c` 已生成目标文件，随后报告 `twice` 的引用未找到。另一个部署日志说明动态库未找到，程序没有进入入口函数。分别判断应检查源文件语法、链接输入，还是部署依赖；仅重新运行同一个源代码单元格能验证哪些结论？

比较逐项 Python 循环和一次调用数组运算：两者需要处理同样数量的元素。若后者更快，能否据此推断渐近复杂度变小？若库调用还要复制输入数组，应该把哪部分成本纳入比较？
