Python 中，两个名字可以指向同一份列表，修改列表以后，两个名字都能看到变化。运行中的程序需要一种办法找到这份共享数据。在机器这一层，内存提供按地址编号的字节位置；一个整数可能占多个连续字节，它的地址标出起始位置。

C 的指针让这个“找到对象”的过程直接可见。下面只读函数体内的语句，追踪地址与对象怎样分别变化；这里的 C 片段供阅读，浏览器单元格不执行它们。

## 两个指针可以找到同一个对象

在 C 中，`int` 表示整数类型，`int *` 表示指向整数对象的指针类型。`&x` 取得 `x` 的地址，`*p` 访问 `p` 指向的对象。分号结束一条语句：

```c
int x = 7;
int y = 20;
int *p = &x;
int *q = p;
*q = 9;
p = &y;
*p = 21;
```

| 执行到 | x | y | p 指向 | q 指向 |
| --- | --- | --- | --- | --- |
| `int *q = p` | 7 | 20 | x | x |
| `*q = 9` | 9 | 20 | x | x |
| `p = &y` | 9 | 20 | y | x |
| `*p = 21` | 9 | 21 | y | x |

`q = p` 复制地址，两个指针找到同一个整数。给 `p` 换一个地址后，`q` 仍指向 `x`。这与 Python 的<Term id="alias">别名</Term>现象相通：共享对象与改变某个名字的指向是两件事。Python 的名字绑定没有提供 C 这样的直接指针运算。

## 地址不会告诉你数组有多长

`int values[3] = {10, 20, 30};` 声明一个含有三个整数的数组，元素连续存放。合法下标是 0、1、2，`values[1]` 读取第二个整数。C 的数组访问不会自动执行 Python 列表那样的下标检查。

```text
values → [10] [20] [30]
index      0    1    2
```

`values[3]` 试图访问数组之外。那里即使恰好有可读的内存，也没有这个数组的第四项。接口只传一个指针时，调用方通常还需要单独知道可访问的元素数量。

## 对象结束后，旧地址不能继续使用

函数里的普通局部对象只在所属代码块执行期间存在：

```c
int *make_value(void) {
    int value = 42;
    return &value;
}
```

函数名前的 `int *` 表示返回整数指针，`void` 表示没有参数，花括号围住函数体。`make_value` 返回后，局部对象 `value` 的生命周期已经结束。返回它的地址不能让它继续存在；随后碰巧读到 42，也不能使这次访问合法。

C 还可以动态申请内存，让对象不随这次函数调用结束而消失。`malloc` 申请空间，`free` 释放空间；这时必须约定由谁负责释放。把指针返回给调用方，可以让调用方继续使用对象，也可以把适时释放的责任交给它。若一直不释放，不再需要的对象仍占着空间；若过早释放，其他使用者手中的指针就失效了。

释放后，指向它的所有旧指针都不能再用来访问该对象。复制指针不会复制对象，也不会延长生命周期。

数组越界和访问已经失效的对象属于<Term id="undefined-behavior">未定义行为</Term>：C 不规定这类程序的结果，不能要求它一定报错或立即崩溃。对象生命周期与访问规则见 [WG14 C 工作草案 N3096](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n3096.pdf)。

因此，一个返回数组的接口通常要一起交代元素类型、元素数量和释放责任。调用方用地址找到起点，用长度限定访问范围，并在约定的生命周期内使用它。Python 把许多这样的管理工作交给运行时；调用本地库时，接口仍可能要求使用者遵守这些约定。

一个接口返回动态申请的数组，同时给出元素数，约定由调用方释放。A 把指针复制给 B 后释放数组，B 随后读取第一项。数组长度正确能使这次读取合法的吗？若改为 A 不释放，B 使用结束后也不释放，又留下什么问题？
