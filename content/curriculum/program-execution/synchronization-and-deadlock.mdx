两个任务都要把共享计数器从 0 增加 1。按顺序执行，最后应该得到 2；但如果两次操作的读取和写回交错，结果可能是 1。

## 两次递增怎样丢失一次更新

假设递增由“读出旧值、加一、写回”三个步骤组成，可能出现以下顺序：

| 步骤 | 任务 A | 任务 B | 共享计数 |
| --- | --- | --- | --- |
| 1 | 读到 0 | | 0 |
| 2 | | 读到 0 | 0 |
| 3 | 写回 1 | | 1 |
| 4 | | 写回 1 | 1 |

A 和 B 都根据旧值 0 计算新值，第二次写回覆盖了第一次更新。这种结果取决于执行交错的情况，称为<Term id="race-condition">竞态条件</Term>。单核处理器轮流执行两项工作，也可能出现这张表中的顺序。

下面用上一课的 `asyncio` 任务重现它。每个任务先读取 `count`，再等待另一个任务也完成读取，然后才写回。`Event` 的 `set()` 发出通知，`wait()` 等待通知：

```python run id="program-execution.synchronization-and-deadlock.lost-update"
import asyncio

count = 0

async def add_one(mine, other):
    global count
    old = count
    mine.set()
    await other.wait()
    count = old + 1

async def main():
    a_read = asyncio.Event()
    b_read = asyncio.Event()
    await asyncio.gather(
        add_one(a_read, b_read),
        add_one(b_read, a_read),
    )

await main()
print(count)
```

两个任务都读到 0，最后输出 1。`global count` 表示函数的赋值修改外部的 `count`。这里使用通知让两次读取必定先于写回；实际程序在访问数据库、等待网络或进行其他异步操作时，也可能发生类似交错。

## 把检查和修改放在同一临界区

互斥锁（mutex）同一时刻只允许一个执行者持有。访问共享状态的代码如果需要作为一个整体完成，就可以放进由锁保护的临界区。

`asyncio.Lock` 保护同一事件循环中的协作任务。`async with lock` 取得锁后进入代码块，离开时释放。下面仍让任务在读取后暂停一次，观察锁怎样防止两个任务同时使用旧值：

```python run id="program-execution.synchronization-and-deadlock.protected-update"
import asyncio

count = 0
lock = asyncio.Lock()

async def add_one():
    global count
    async with lock:
        old = count
        await asyncio.sleep(0)
        count = old + 1

await asyncio.gather(add_one(), add_one())
print(count)
```

输出为 2。A 在持锁时读取 0，写回 1 后释放锁；B 随后读到 1，再写回 2。分别锁住“读取”和“写回”仍可能得到旧值 0，因此需要把整个递增操作放在同一临界区。

同样，如果库存只有一件，“检查库存大于零”和“扣减一件”也需要共同受保护，才能维持库存不得为负、同一件货物不会卖给两人的<Term id="invariant">不变量</Term>。锁的保护范围由这些操作之间的依赖决定。

本例的交错发生在 `await` 处。对于仅在单个事件循环中运行、没有其他线程访问的共享变量，不含 `await` 的直接计算可以连续执行到下一次让出控制。操作系统线程有不同的调度方式；`asyncio.Lock` 也不用于同步多个操作系统线程。见 [Python asyncio 同步原语](https://docs.python.org/3/library/asyncio-sync.html)。

## 两把锁怎样形成死锁

假设任务 A 和 B 都要取得两把锁 L、R，且每把锁一次只能由一个任务持有。若它们按不同顺序获取锁，就可能停在下面的状态：

| 任务 | 已取得 | 正在等待 |
| --- | --- | --- |
| A | L | R |
| B | R | L |

A 等待 B 释放 R，B 等待 A 释放 L。两者都无法继续到释放锁的代码，这种循环等待称为<Term id="deadlock">死锁</Term>。

一种避免方法是给锁规定统一顺序：所有任务先取得 L，再取得 R。这样当 A 持有 L 时，B 会先等 L，无法提前占有 R。对于更多锁，也可以规定统一的获取顺序，避免形成锁与锁之间的循环等待。所有需要同时持有多把锁的路径都要遵循这个顺序。
