两段程序各读取一百万个整数，读取顺序不同，耗时仍可能相差很大。一次读取需要多长时间，还取决于数据已经在哪里，以及刚搬来的数据是否很快又被用到。

## 容量与访问速度不同的存储

```text
CPU registers
      ↕
CPU caches
      ↕
main memory
      ↕
persistent storage
```

寄存器保存 CPU 当前运算使用的少量数据；处理器缓存保存一部分近期访问的数据；主存提供更大空间；文件等持久数据存放在存储设备上，需要时再读入内存。各层的容量和访问速度不同，具体数值随硬件改变。

CPU 缓存里已经有需要的数据，称为命中；没有则要从更远的一层取得，称为未命中。缓存通常一次搬来一块连续字节，所以读取一个元素时，附近的数据也可能已经到达。

## 让搬来的数据多用几次

连续数组按顺序读取时，接着要用的元素常与当前元素一起搬入缓存。若每次跳到很远的位置，刚搬来的附近数据可能没有用上，就又要取得另一块数据。

```text
layout: [a b c d] [e f g h] [i j k l]
scan:    a b c d   e f g h   i j k l
jump:    a         e         i
```

很快访问附近数据，称为空间局部性；很快再次访问同一份数据，称为时间<Term id="locality">局部性</Term>。反复需要的数据太多，缓存装不下，早先的数据可能在再次使用前被替换。

这能解释访问顺序为何影响性能，却不能直接算出耗时。硬件会提前读取数据，多个读取也可能重叠，其他工作还可能争用缓存。

## 下标相邻，不一定表示对象相邻

C 数组的整数连续存放。CPython 列表保存对象引用，元素对象不保证挨在一起，见 [Python C API 的列表对象](https://docs.python.org/3/c-api/list.html)。因此 Python 中依次读取 `items[0]`、`items[1]`，不能直接当作读取两个连续存放的整数。

连续的定型数组能提供不同的布局；NumPy 也支持并非连续的数组视图，见 [NumPy ndarray 的内存布局](https://numpy.org/doc/stable/reference/arrays.ndarray.html#internal-memory-layout-of-an-ndarray)。检查性能时，要看实际表示，而非只看接口都写成 `a[i]`。

同一算法第二次扫描可能复用第一次留下的缓存，也可能因数据太大而无法复用。若实际任务只扫描一次，只测第二次就不能代表它。先确认算法处理多少数据，再核对布局、访问顺序和测量起点，才能解释这次速度差异。
