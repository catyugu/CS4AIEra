两段程序各读取一百万个整数，读取次数都随元素数线性增长，但运行耗时仍可能相差很大。原因之一是 CPU 取得数据的方式：顺序访问连续地址，通常比频繁跳到远处更容易利用缓存。

这里先固定一种表示：整数连续存放在数组里。一段程序按顺序读，另一段反复跳到远处。读取次数相同，但它们利用已经搬来的数据的方式不同。

## 存储层次与缓存

```text
CPU registers
      ↕
CPU caches
      ↕
main memory
      ↕
persistent storage
```

寄存器保存 CPU 当前运算使用的少量数据；处理器缓存保存一部分近期访问的数据；主存提供更大空间；文件等持久数据存放在存储设备上，需要时再读入内存。各层的容量和访问速度不同，具体数值随硬件改变。

CPU 缓存里已经有需要的数据，称为命中；没有则要从更远的一层取得，称为未命中。缓存通常一次搬来一块连续字节，所以读取一个元素时，附近的数据也可能已经到达。

## 空间局部性与时间局部性

连续数组按顺序读取时，接着要用的元素常与当前元素一起搬入缓存。若每次跳到很远的位置，刚搬来的附近数据可能没有用上，就又要取得另一块数据。

```text
layout: [a b c d] [e f g h] [i j k l]
scan:    a b c d   e f g h   i j k l
jump:    a         e         i
```

很快访问附近数据，称为空间局部性；很快再次访问同一份数据，称为时间<Term id="locality">局部性</Term>。反复需要的数据太多，缓存装不下，早先的数据可能在再次使用前被替换。

图中每块四项：扫描完第一块可以用上 a、b、c、d，而跳着读 a、e、i 时，每取得一块只使用其中一项。这个简化布局展示了两种访问方式的数据利用率；实际 CPU 缓存块的大小由硬件决定。

改善局部性可以减少取数的开销，两段处理 n 个元素的代码仍然可以都是线性工作量。具体加速倍数需要测量：硬件可能提前读取数据，多个读取也可能重叠，其他工作还可能争用缓存。

## 局部性与性能测量

要判断顺序访问能否加速，先找到实际连续存放的数据，再看相邻读取是否复用了同一缓存块。接口写成 `a[i]` 本身没有交代底层布局；本课的数组示意有明确的连续存放前提。

同一算法第二次扫描可能复用第一次留下的缓存，也可能因数据太大而无法复用。若实际任务只扫描一次，测量也应包含首次取数的成本。比较两次运行时，应使用相同数据布局，并说明计时前是否已经访问过数据。

## 练习

设缓存一次取得四个连续元素，暂时只能保留一块。数组有 12 项，分成第 0—3、4—7、8—11 三块。缓存开始为空。

分别追踪两种读取顺序：`0, 1, 2, 3, 4, 5, 6, 7` 和 `0, 4, 1, 5, 2, 6, 3, 7`。每一步需要哪一块，原来的块是否还能复用？两种顺序读取次数相同，各需取得几块数据？

这个简化模型解释了一种成本来源。要判断真实机器上的加速倍数，还应使用目标数据与访问顺序测量。
