两段程序各读取一百万个整数，都是一次扫描，工作量随元素数线性增长。选择算法时，这个估算很有用；要解释实际耗时，还需要看每次读取怎样取得数据。

这里先固定一种表示：整数连续存放在数组里。一段程序按顺序读，另一段反复跳到远处。读取次数相同，但它们利用已经搬来的数据的方式不同。

## 容量与访问速度不同的存储

```text
CPU registers
      ↕
CPU caches
      ↕
main memory
      ↕
persistent storage
```

寄存器保存 CPU 当前运算使用的少量数据；处理器缓存保存一部分近期访问的数据；主存提供更大空间；文件等持久数据存放在存储设备上，需要时再读入内存。各层的容量和访问速度不同，具体数值随硬件改变。

CPU 缓存里已经有需要的数据，称为命中；没有则要从更远的一层取得，称为未命中。缓存通常一次搬来一块连续字节，所以读取一个元素时，附近的数据也可能已经到达。

## 让搬来的数据多用几次

连续数组按顺序读取时，接着要用的元素常与当前元素一起搬入缓存。若每次跳到很远的位置，刚搬来的附近数据可能没有用上，就又要取得另一块数据。

| 访问方式 | 同样读取 12 项的次序 |
| --- | --- |
| 顺序读取 | a、b、c、d、e、f、g、h、i、j、k、l |
| 交错读取 | a、e、i、b、f、j、c、g、k、d、h、l |

假定每块包含四项：第一块 a–d，第二块 e–h，第三块 i–l。为突出替换的影响，再假定缓存只容纳一块，并且开始时为空。

很快访问附近数据，称为空间局部性；很快再次访问同一份数据，称为时间<Term id="locality">局部性</Term>。反复需要的数据太多，缓存装不下，早先的数据可能在再次使用前被替换。

在这个简化模型里，顺序读取每取得一块就能用完四项，共取得三块。交错读取每次都转向另一块，刚才的块已经被替换，共取得十二次。两者都读了十二项，区别在于每次取来的数据被使用了多少。真实缓存能容纳许多块；若三块都能留住，这组交错读取也只需取得三块，不能仅凭“下标跳动”就断定大量未命中。

因此，局部性改善的是取数的方式。若两段代码都处理 n 个元素，它们仍然可以都是线性工作量。要给出具体加速倍数，还需要测量：硬件可能提前读取数据，多个读取也可能重叠，其他工作还可能争用缓存。

## 审查速度提升的依据

“改成顺序访问会更快”是一项关于数据布局和访问模式的解释。审查它时，先找到实际连续存放的数据，再看相邻读取是否复用了同一块。接口写成 `a[i]` 本身没有交代底层布局；本课的数组示意有明确的连续存放前提。

同一算法第二次扫描可能复用第一次留下的缓存，也可能因数据太大而无法复用。若实际任务只扫描一次，测量也应包含首次取数的成本。算法工作量、数据布局和测量起点共同决定这份证据适用于什么任务；具体的性能测量见 <CrossRef id="debugging-and-observability.performance-evidence" />。

## 练习

一份优化报告说：“两种实现都读取 n 项，都是 O(n)，因此耗时相同。”数组连续存放，第一种顺序读取，第二种按打乱的下标读取。报告漏掉了哪个机制？仅据这个机制，能否断言第二种一定慢两倍？

另一份报告连续扫描同一小数组一百次，只展示最后一次耗时。实际任务每次启动后只读取一次新数组。应如何调整测量，才能支持对实际任务的判断？
