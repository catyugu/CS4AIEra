两段程序各读取一百万个整数，读取顺序不同，耗时仍可能相差很大。算法分析中的“一次读取”是计数单位；机器实际付出的时间还取决于数据已经在哪里，以及访问是否让刚搬来的数据被充分使用。

## 一次读取可能在哪层完成

CPU 寄存器容量小；处理器缓存保存部分最近访问的数据；主存提供更大空间；持久存储容纳程序暂时没有装入主存的数据。通常容量与访问代价不同，缓存也可以分多级。具体容量、延迟和共享关系需要查目标硬件，不能把一张示意图当成所有机器的参数。

```text
registers
    ↕
CPU caches
    ↕
main memory
    ↕
persistent storage
```

从缓存中找到所需数据称为命中。没有找到，需要向更远的一层请求，称为未命中。CPU 缓存常按连续的一块字节搬运，称为缓存行（cache line）；读取一个元素可能连同附近元素一起带入。搬入之后能否继续使用附近数据，成为时间成本的一部分。

## 顺序访问怎样复用已经搬来的数据

固定一个简化成本模型：元素连续存放，每项 8 字节，缓存行 64 字节；数组起点恰好与缓存行起点对齐，最初没有这些数据。每行装 8 个元素。

| 访问方式 | 一开始访问的下标 | 对缓存行的使用 |
| --- | --- | --- |
| 顺序读取 | 0、1、2、3、4、5、6、7 | 这一组都在第一行 |
| 跨行读取 | 0、8、16、24、32、40、48、56 | 每项落在不同的行 |

顺序读 $n$ 项至少覆盖 $\lceil n/8\rceil$ 行。在忽略预取、容量驱逐与其他访问的模型下，一行搬来后可以服务其中连续的 8 次读取。若每行只需要一项，则同样数量的有效元素会需要更多块传输。

如果随后又读取同一块，并且它尚未被驱逐，也能复用原有缓存。这两种规律分别称为空间与时间<Term id="locality">局部性</Term>。它们解释了为什么工作集大小与访问顺序会影响性能。工作集指一段执行实际反复需要的数据；缓存装不下工作集时，旧块可能在再次使用前被替换。

缓存行数不是实际耗时：硬件可能提前搬入后面的行，多个请求可能重叠，其他线程也可能竞争缓存。这个模型能解释传输需求，不能独立给出毫秒数。

## 表示选择也改变了访问路径

C 数组的整数可以直接连续存放。Python 列表通常保存对象引用，读取某项后还要通过引用访问对象；对象本身不保证与邻项连续。对于 CPython，这个表示见 [Python C API 的列表对象与 PyList_GetItem](https://docs.python.org/3/c-api/list.html)。因此即使 Python 写出相邻下标，也不能直接套用“每行 8 个整数”的 C 数组模型。

连续的定型数组规定每项相同的元素类型与布局。NumPy 可以提供这种表示，也可以用步长描述非连续视图，见 [NumPy ndarray 的数据与步长模型](https://numpy.org/doc/stable/reference/arrays.ndarray.html#internal-memory-layout-of-an-ndarray)。只看接口上都写 `a[i]`，不足以判断内存是否连续。

缓存还会增加内存占用，但程序不必为每次读取显式管理 CPU 缓存。在设计判断中，更有用的问题是：访问多少不同块、会不会很快复用、有没有不必要的复制。若总体工作量从平方降到线性，首先发生的是算法层面的变化；若两种线性扫描只有布局不同，需要的是机器访问层面的证据。

## 练习

一个连续矩阵有 1024 行，每行 1024 个 8 字节元素，按行连续存放。方案甲逐行读取，方案乙先读完第一列，再读第二列。沿用 64 字节缓存行的模型，算出同一行相邻元素与同一列相邻元素的地址距离。若缓存不足以在一整列读取期间保留所有访问过的行，两种顺序分别能怎样复用数据？

有人只测了第二次扫描，报告“数据访问不需要搬运成本”。判断第一次与第二次扫描的初始缓存状态是否相同。要让这个测量支持目标工作负载，还需给出哪些环境与输入信息？
