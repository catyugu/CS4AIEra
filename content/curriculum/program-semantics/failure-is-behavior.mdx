一批任务按提交顺序处理，每项带一个耗时，程序把各项耗时相加得到这一批的总工作量。前三项是 `resize-covers` 12、`send-digest` 3、`build-index`，第三项的耗时字段写成了 `"fast"`。Agent 交来的版本把这一次失败记作 0，继续处理 `archive-logs`，最后报告总工作量 20，日志里没有失败记录。要判断这次处理是否成立，先看清一次失败在程序里发生了什么。

## 异常沿调用链离开当前执行

一段代码遇到它无法继续的条件时，抛出一个异常对象：对象带一个类型（失败的种类）和一个消息（这一次的具体值）。`raise` 接受一个异常类（解释器实例化它）或一个异常实例，把它交给当前这次调用。抛出之后，当前这段执行被放弃：`raise` 之后的语句不再执行，解释器沿调用链退到调用方，逐帧检查那一帧的 `try` 有没有与异常类型匹配的 `except` 子句，子类的异常也匹配父类的子句；退出的每一帧先运行它自己的 `finally`。没有一层匹配时，程序停止，解释器打印回溯。

下面这段程序里，`parse_seconds` 在 `int("fast")` 处抛出 `ValueError`；`process` 与 `run_batch` 都没有 `except`，异常一路退到最外层被接住。

```python run id="program-semantics.failure-is-behavior.path"
def parse_seconds(text):
    return int(text)

done = []

def process(name, text):
    seconds = parse_seconds(text)
    done.append((name, seconds))
    print("processed", name, seconds)

def run_batch(tasks):
    for name, text in tasks:
        process(name, text)

tasks = [("resize-covers", "12"), ("send-digest", "3"), ("build-index", "fast"), ("archive-logs", "5")]
try:
    run_batch(tasks)
except ValueError as failure:
    print("stopped:", type(failure).__name__, "-", failure)
print("results kept:", done)
```

`processed` 只打印两次：`build-index` 在 `int` 处失败，`process` 里它后面的语句没有执行，`run_batch` 的循环停在它这里，`archive-logs` 从未被处理。异常对象携带的类型与消息在捕获处读出：`ValueError` 指出值不合法，消息指到具体那一个值 `'fast'`。失败从抛出点开始放弃剩下的路径：抛出点之后的语句不再执行，此前已经产生的结果仍然保留。

## 在哪一层处理

同一个失败可以在多个位置被接住，接住它的位置决定调用方随后看到的是失败本身还是一个值。下面同一批任务、同一段解析逻辑写成三个版本：`run_lenient` 在每一项就地接住 `ValueError`，用一个默认值 0 顶替；`run_strict` 不接住，让失败退到调用方；`run_tagged` 接住后补上任务名，再用 `raise` 继续向上抛。

```python run id="program-semantics.failure-is-behavior.positions"
def parse_seconds(text):
    return int(text)

def run_lenient(tasks):
    total = 0
    for name, text in tasks:
        try:
            seconds = parse_seconds(text)
        except ValueError:
            seconds = 0
        total += seconds
        print("counted", name, seconds)
    return total

def run_strict(tasks):
    total = 0
    for name, text in tasks:
        total += parse_seconds(text)
    return total

def run_tagged(tasks):
    total = 0
    for name, text in tasks:
        try:
            total += parse_seconds(text)
        except ValueError as failure:
            raise ValueError(name + ": " + str(failure))
    return total

tasks = [("resize-covers", "12"), ("send-digest", "3"), ("build-index", "fast"), ("archive-logs", "5")]
print("lenient total:", run_lenient(tasks))
try:
    print("strict total:", run_strict(tasks))
except ValueError as failure:
    print("strict stopped:", type(failure).__name__, "-", failure)
try:
    print("tagged total:", run_tagged(tasks))
except ValueError as failure:
    print("tagged stopped:", type(failure).__name__, "-", failure)
```

三个版本对前两项的处理相同（`counted` 打印出 12 与 3），差别落在 `build-index`：`run_lenient` 把它记作 0、继续到 `archive-logs`，返回总工作量 20；`run_strict` 停在 `build-index`，调用方接住并读出 `ValueError`；`run_tagged` 也在 `build-index` 停下，但它先接住失败，再 `raise` 一个带任务名的新异常，调用方读到的消息里因此有 `build-index`。`run_lenient` 的返回值看不出 `build-index` 出过错：0 与「这一项真的耗时 0」没有区别，调用方拿到的是一份看起来完整的报告。

要决定捕获放在哪里，问的是这一层能不能据此产生正确的结果。`run_lenient` 不知道 `build-index` 的耗时，却照样交出一个数，它没有处理这次失败，只是把它擦掉。`run_tagged` 给出的是中间做法：这一层不能算出 `build-index` 的耗时，但它知道失败的是哪一项，于是接住后补上这条信息、再用 `raise` 把失败继续向上抛。能决定整批继续还是停下的是调用方，也就是调用 `run_batch` 的一方。可以就地恢复的情形是这一层掌握产生正确结果所需的信息，例如换一条路径取回同一个值；拿不到时，把失败继续向上抛。

## 捕获范围决定哪些失败被看见

捕获子句按类型匹配，写宽一点会把不同种类的失败一起接住。失败至少分两类。一类由这次输入或环境带来，这段代码把它当作一种需要处理的结果：文件不存在、输入不合法、请求超时。另一类说明程序本身有缺陷：访问了不存在的名字、某个内部约束被破坏。前一类属于<Term id="specification">规约</Term>覆盖的情况，哪一种输入对应哪一种结果由规约写明；后一类是<Term id="precondition">前置条件</Term>被违反或实现本身有误，重试和默认值都不会让它消失。

下面两个函数体相同，只在 `except` 的宽度上不同。`seconds_from` 要求参数是字符串：`"abc"` 是这次输入带来的失败，`None` 违反了这个要求。

```python run id="program-semantics.failure-is-behavior.scope"
def seconds_from(text):
    return int(text.strip())

def broad(text):
    try:
        return "handled: " + str(seconds_from(text))
    except Exception as failure:
        return "handled: " + str(failure)

def narrow(text):
    try:
        return "handled: " + str(seconds_from(text))
    except ValueError as failure:
        return "handled: " + str(failure)

print("broad on bad input:", broad("abc"))
print("broad on defect:", broad(None))
print("narrow on bad input:", narrow("abc"))
print("narrow on defect:", narrow(None))
```

`broad` 两次都返回 `handled: ...`，把 `None` 触发的 `AttributeError` 也写成一条处理结果，缺陷被贴上「已处理」的标签；`narrow` 只接 `ValueError`，`"abc"` 被处理，`None` 触发的 `AttributeError` 没有被接住，从这一行退出并向上抛。捕获写成能接住的最窄类型，多出来的类别留在外面，缺陷因此停在它第一次出现的位置，不会变成一条「已处理」的结果。

## 清理在失败路径上也执行

释放资源、关闭句柄、记录结束这类动作在成功与失败两条路径上都要做。写在 `try` 之后的语句属于被放弃的路径，异常展开时不会执行；`finally` 把这些动作放到一个无论正常结束、`return` 还是异常展开都会经过的位置。下面两个版本的收尾都写在函数末尾，`run_plain` 的收尾在 `try` 之外，`run_guarded` 的收尾在 `finally` 里。

```python run id="program-semantics.failure-is-behavior.finally"
log = []

def run_guarded(name, text):
    log.append("start " + name)
    try:
        return int(text)
    finally:
        log.append("end " + name)

def run_plain(name, text):
    log.append("start " + name)
    value = int(text)
    log.append("end " + name)
    return value

print("guarded ok:", run_guarded("resize-covers", "12"))
print("plain ok:", run_plain("send-digest", "3"))
try:
    run_plain("build-index", "fast")
except ValueError as failure:
    print("plain failed:", type(failure).__name__, "-", failure)
try:
    run_guarded("archive-logs", "fast")
except ValueError as failure:
    print("guarded failed:", type(failure).__name__, "-", failure)
print("log:", log)
```

`log` 里 `build-index` 只有 `start build-index`、没有 `end`：失败在 `int` 处展开，`run_plain` 里它后面的语句被跳过。`archive-logs` 有 `start archive-logs` 也有 `end archive-logs`：`run_guarded` 的 `finally` 在异常继续向上传之前运行，`end` 照常补上。异常本身仍然到达调用方——`plain failed` 与 `guarded failed` 打印的是同一个 `ValueError`。

成对的获取与释放有专门的语言形式：`with` 语句在进入时获取、退出时释放，正常结束与失败退出都经过同一个释放点，把释放放进 `finally` 就是它的展开。

```python
with open("report.csv") as handle:
    rows = handle.read().splitlines()
```

## build-index 那一次捕获

回到开头那批任务。`build-index` 的 `"fast"` 是这份输入带来的失败，`run_lenient` 把 `ValueError` 接成一个 0。它并不知道 `build-index` 的耗时，却把这一项记成 0，报告里也没有哪一栏标出这一项没算出来；总工作量 20 少算了 `build-index`。知道失败的是哪一项、能决定整批继续还是停下的是调用方：它接住 `ValueError` 之后可以点名 `build-index`、保留已经算出的两项，也可以整批作废。`run_lenient` 两者都做不到，它交出的「完整报告」比一次明确的失败更难发现。

判定这次捕获是否成立，看它能不能产生正确的结果：能产生就留在这一层，不能就让失败向上抛。`run_strict` 在 `build-index` 处停下并抛出 `ValueError: invalid literal for int() with base 10: 'fast'`，调用方据此知道是哪一项、哪一个值出的问题。

## 练习

下面是一个 Agent 写成的调度函数，每一项最多重试三次，三次都失败后用一个默认值补齐。指出 `except Exception` 接住了哪几类失败、其中哪些不是重试能恢复的，并说明 `if seconds is None: seconds = 0` 掩盖了什么。

```python run id="program-semantics.failure-is-behavior.exercise-retry-and-default"
attempts = []


def fetch_seconds(task):
    attempts.append(task[0])
    return int(task[1])


def schedule(tasks):
    report = []
    for task in tasks:
        seconds = None
        tries = 0
        while tries < 3 and seconds is None:
            try:
                seconds = fetch_seconds(task)
            except Exception:
                tries += 1
        if seconds is None:
            seconds = 0
        report.append((task[0], seconds))
    return report


print(schedule([("build-index", "fast")]))
print(attempts)
print(schedule([("build-index",)]))
print(attempts)
```
