一个程序调用图片转换工具，把输入文件转换成输出文件。工具放在独立进程里，调用方拿到的是退出状态与输出字节。如果等待超过两秒，该如何报告：转换失败，还是没有在两秒内确认完成？

## 一次普通调用增加了哪些环节

进程内函数可以接收对象引用，正常返回值，也可以让异常沿同一调用链传播。独立进程有自己的运行状态；调用方需要通过参数、标准输入输出或其他通信机制传递数据，不能把一个普通 Python 列表引用直接当成另一个进程里的列表使用。

调用方把输入文件路径传给工具；工具进程读取文件、生成输出，并用退出状态报告结果。标准输出用于返回数据，标准错误常用于诊断。双方需要约定每种输出的格式。

边界增加了新的失败位置：进程可能未能启动；工具可能拒绝输入；执行中可能退出；调用方可能未能读到完整结果。工具内部的 Python `ValueError` 不会自动跨进程成为调用方的异常对象，工具需要约定如何用退出状态或消息表示它。

独立进程可以使用不同语言与依赖，也能隔离许多进程内部故障，使其不直接破坏调用方的内存状态。两个进程若都修改同一个文件，还需要协调对这份共同状态的访问。

## 读取一个真实调用

下面是普通桌面或服务器 Python 中启动工具的代码，作为静态材料阅读。浏览器单元格的 Python 运行时不提供这种操作系统进程启动能力。

```python
import subprocess

completed = subprocess.run(
    ["converter", "input.png", "output.webp"],
    capture_output=True,
    timeout=2,
    check=True,
)
```

列表中的字符串分别是程序名与参数；`capture_output=True` 收集标准输出与标准错误；`check=True` 将非零退出状态报告为 `CalledProcessError`；`timeout=2` 限定等待时间。这些是 [Python subprocess.run](https://docs.python.org/3/library/subprocess.html#subprocess.run) 的具体约定。

能启动并收到零退出状态，表示工具按退出状态约定报告成功。输出文件是否完整、输出格式是否正确，还取决于工具自身的契约。工具把警告打印在标准错误中，也不必然表示操作失败；调用方应按契约读取退出状态，并检查业务结果；标准错误中的文字可作为诊断线索。

## 超时后，输出文件可能已经改变

超时表示约定的等待期限到了，调用方没有在期限内得到所需结果。它本身不能证明工具未执行操作。

转换工具可能尚未写出文件，也可能已完成写入、还没退出。停止等待之后，应按工具约定检查输出是否完整，并确认是否需要终止进程。终止进程也不会撤销已经写入的内容。

本例的 `subprocess.run` 在超时后会终止直接启动的子进程并等待其结束，再抛出 `TimeoutExpired`，见 [Python subprocess.run](https://docs.python.org/3/library/subprocess.html#subprocess.run)。使用其他 API 时，应查阅它如何处理超时和清理。

## 谁负责等待之后的状态

超时契约需要交代：等待什么结果、期限从哪里计算、超时后操作是否继续、谁终止进程并读取剩余输出，以及此前产生的副作用如何处理。

“已拒绝且无修改”“已完成”“结果未知”需要不同的后续动作。对未完成的操作可以选择继续查询，对已拒绝的输入可以修正请求；对结果未知的有副作用操作，直接再做一次可能产生重复效果。结果仍未知时，包装层应把这份不确定性传给调用方，使其先核对输出或查询状态，再决定是否重试。

把本地工具包装成 `convert(...)` 函数时，包装层需要把这些结果与处理责任传达给调用方。

## 练习

转换接口收到输入路径，启动工具，再读取输出。分别为下面三种情况选择下一步处理：程序文件不存在；工具返回非零退出状态并报告输入格式错误；工具已超时且输出文件存在。

如果工具返回的是一份很大的 JSON 文本，调用方应按什么顺序处理退出状态、字节解码和 JSON 解析？其中哪一种失败适合让用户修改输入，哪一种需要维护者检查部署？
