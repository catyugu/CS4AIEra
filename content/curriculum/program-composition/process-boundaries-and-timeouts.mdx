一个程序调用图片转换工具，把输入文件转换成输出文件。工具放在独立进程里，调用方拿到的是退出状态与输出字节。如果等待超过两秒，该如何报告：转换失败，还是没有在两秒内确认完成？

## 一次普通调用增加了哪些环节

进程内函数可以接收对象引用，正常返回值，也可以让异常沿同一调用链传播。独立进程有自己的运行状态；调用方需要通过参数、标准输入输出或其他通信机制传递数据，不能把一个普通 Python 列表引用直接当成另一个进程里的列表使用。

典型的转换链是：

```text
caller ── arguments / input bytes ──> converter process
caller <── output bytes / exit status ── converter process
```

边界增加了新的失败位置：进程可能未能启动；工具可能拒绝输入；执行中可能退出；调用方可能未能读到完整结果。工具内部的 Python `ValueError` 不会自动跨进程成为调用方的异常对象，工具需要约定如何用退出状态或消息表示它。

这也是独立进程的价值之一：可以使用不同语言与依赖，并使许多进程内部故障不直接破坏调用方的内存状态。两个进程若都修改同一个文件，仍然有共同状态；进程分开并不消除这项关系。

## 读取一个真实调用

下面是普通桌面或服务器 Python 中启动工具的代码，作为静态材料阅读。浏览器单元格的 Python 运行时不提供这种操作系统进程启动能力。

```python
import subprocess

completed = subprocess.run(
    ["converter", "input.png", "output.webp"],
    capture_output=True,
    timeout=2,
    check=True,
)
```

列表中的字符串分别是程序名与参数。标准输出和标准错误是进程向外写字节的两个通道，工具通常用前者输出结果，用后者输出诊断。`capture_output=True` 收集这两个通道；`check=True` 将非零退出状态报告为 `CalledProcessError`；`timeout=2` 限定等待时间。这些是 [Python subprocess.run](https://docs.python.org/3/library/subprocess.html#subprocess.run) 的具体约定。

能启动并收到零退出状态，表示工具按退出状态约定报告成功。输出文件是否完整、输出格式是否正确，还取决于工具自身的契约。工具把警告打印在标准错误中，也不必然表示操作失败；退出状态、标准错误与业务结果是不同观察面。

## 超时后，输出文件可能已经改变

超时表示约定的等待期限到了，调用方没有在期限内得到所需结果。它本身不能证明工具未执行操作。

考虑两个都可能发生的过程：

| 时间顺序 | 过程 A | 过程 B |
| --- | --- | --- |
| 开始 | 工具读取输入 | 工具读取输入 |
| 等待期间 | 工具尚未产生输出文件 | 工具已经完成输出，仍在做结束处理 |
| 到达期限 | 调用方等待超时 | 调用方等待超时 |

调用方观察到相同的超时，文件状态却不同。因此超时报告应当保留“不知道操作是否完成”的可能性。即使随后终止工具，已完成的文件写入也不会自动撤销。

对本地进程，等待超时后的动作也要读 API。Python 的 `subprocess.run` 在超时后会终止直接启动的子进程并等待其结束，然后抛出 `TimeoutExpired`；`Popen.communicate(timeout=...)` 超时后抛异常，但不会自动终止子进程，见 [Python subprocess：communicate](https://docs.python.org/3/library/subprocess.html#subprocess.Popen.communicate)。两个 API 都写了 `timeout`，取消与清理责任却不同。进程创建本身在不少平台上不能被这个超时中断，因此也不能将参数解释为整次调用精确不超过两秒。

## 输出路径存在，还不能证明转换完成

转换工具直接写入 `output.webp` 时，可能先创建文件，再逐段写入。若写到一半被终止，调用方看到的文件路径仍然存在，却不是完整图片。如果这条路径原来保存着可用图片，新的半份输出还可能覆盖旧结果。检查“文件是否存在”，区分不了这些状态。

可以把工作文件与已确认结果分开：每次转换先写到自己的临时路径；调用方依据成功状态和输出格式检查，确认结果完整，且不会再被本次尝试修改，再把它交给使用者或替换正式路径。如果工具另行启动了写入进程，只观察直接子进程结束还不足以确认这一点。没有通过检查的临时文件不作为成功结果发布。这样安排的价值，是使用者不会把一份仍在写入或已中断的文件误当成完成结果。

这仍需要约定谁删除失败的临时文件，以及何时允许替换已有结果。临时路径不能在旧工具还可能写入时交给下一次尝试复用；同一任务多次尝试需要区分各自输出。路径替换对其他读取者是否原子、断电以后是否持久，还取决于文件系统接口，见 <CrossRef id="persistence.files-and-durability" />。一个临时文件名没有自动提供这些保证。

## 谁负责等待之后的状态

一个可使用的超时契约需要交代：等待什么结果、期限从哪里计算、超时后操作是否继续、谁终止进程并读取剩余输出，以及此前产生的副作用如何处理。

“已拒绝且无修改”“已完成”“结果未知”需要不同的后续动作。对未完成的操作可以选择继续查询，对已拒绝的输入可以修正请求；对结果未知的有副作用操作，直接再做一次可能产生重复效果。若没有新的结果证据，就应报告未知，而不是把它翻译成一个确定的业务失败。

把本地工具包装成 `convert(...)` 函数可以简化使用，但包装层仍要保留这些区别。函数形状无法消除跨进程交互的故障与等待规则。

## 练习

两个方案都在图片转换超过两秒时报告超时。方案 A 使用 `subprocess.run(timeout=2)`，超时后只要发现 `output.webp` 就向用户显示图片。方案 B 使用 `Popen.communicate(timeout=2)`，捕获异常后删除输出文件并立即允许再次转换。需求是“超时后不留下仍在执行的直接子进程；不展示未完成的图片；下一次尝试不与旧尝试共同写同一输出”。分别追踪进程、文件和使用者会看到的结果，审查各方案需要补哪些动作或证据。

另一个工具的操作是“向已有报告末尾追加一段结果”。在未知是否已经追加的情况下，包装层将超时统一翻译成“追加失败，可立即重试”。用两条可能的执行轨迹判断这句话是否有足够依据。
