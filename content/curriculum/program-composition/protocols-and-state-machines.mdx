编辑器可以把代码补全交给另一个进程：编辑器传送正在编辑的代码，服务进程返回候选项。启动后，双方先交换支持的功能，再开始补全请求。补全消息的每个字段都合法，也可能因为初始化尚未完成而不能发送。接口需要规定消息形状，还需要规定交互次序。

## 一次请求怎样对应一次结果

<Term id="protocol">协议（protocol）</Term>规定参与方交换什么消息、怎样解释它们，以及哪些交互顺序有效。JSON-RPC 2.0 是一种调用协议：请求指定方法、参数与标识，响应携带同一个标识，便于调用方把结果对应到请求，见 [JSON-RPC 2.0：请求与响应对象](https://www.jsonrpc.org/specification#request_object)。

下面是一对完整的 JSON 消息。假定双方已经约定 `subtract` 计算第一个参数减去第二个参数。第一份由调用方发送，第二份由被调用方发送：

```json
{"jsonrpc": "2.0", "method": "subtract", "params": [42, 23], "id": 7}
```

```json
{"jsonrpc": "2.0", "result": 19, "id": 7}
```

若同时有多个请求在处理，调用方不能仅凭“先发出的请求”判断某个结果归谁；`id` 提供显式对应关系。成功响应有 `result`，失败响应有 `error`，两者互斥。例如另一个标识为 8 的请求调用了不存在的方法，可以得到以下响应：

```json
{"jsonrpc": "2.0", "error": {"code": -32601, "message": "Method not found"}, "id": 8}
```

JSON-RPC 还定义通知：没有 `id` 的请求。接收方不对通知返回响应，调用方也就不能通过这个协议收到相应错误结果，见 [JSON-RPC 2.0：通知](https://www.jsonrpc.org/specification#notification)。通知适用于调用方不等待返回值的交互；没有响应不能据此推断处理成功。

## 合法字段之外还有合法次序

语言服务器协议（Language Server Protocol，LSP）让编辑器与语言服务交换代码分析请求，使用 JSON-RPC 表达消息。LSP 3.17 规定：`initialize` 是客户端发出的第一个请求，初始化结果返回前，客户端不能继续发其他请求或通知；得到结果后，还要发送一次 `initialized` 通知，见 [LSP 3.17：初始化请求](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#initialize)和[初始化完成通知](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#initialized)。

状态机（<Term id="state-machine">state machine</Term>）用一组状态和转移规则表达这种限制。状态保存决定后续动作是否合法的信息；事件是收到消息、完成操作等发生的事情；转移规则根据当前状态与事件，规定动作和新状态。

从客户端视角，可以把正常启动与关闭过程抽取成以下状态表。这里关注客户端何时能发消息；协议中服务端在初始化期间发送少量指定消息的规则，仍由协议规定。

| 当前状态 | 事件或动作 | 新状态 | 客户端后续约束 |
| --- | --- | --- | --- |
| 已启动，未初始化 | 发送 `initialize` 请求 | 等待初始化结果 | 等待结果，不发送其他请求或通知 |
| 等待初始化结果 | 收到成功结果 | 待发送完成通知 | 先发送 `initialized` |
| 待发送完成通知 | 发送 `initialized` 通知 | 可工作 | 按已协商能力发送工作消息 |
| 可工作 | 发送 `shutdown` 请求 | 等待关闭结果 | 不再发送工作消息 |
| 等待关闭结果 | 收到关闭响应 | 待退出 | 发送 `exit` 通知 |
| 待退出 | 发送 `exit` 通知 | 结束交互 | 不再依赖该会话 |

`shutdown` 要求服务端停止工作但暂不退出，使关闭响应仍能送达；客户端应等响应后再发 `exit`，见 [LSP 3.17：关闭请求](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#shutdown)。这个次序来自确认的需要：若收到关闭请求立刻终止进程，客户端可能无法判断正常关闭是否完成。

同一条补全请求在“可工作”状态有效，在“等待初始化结果”状态就违反客户端规则。模式校验检查消息内容，状态机检查消息与历史之间的关系。

## 状态要足以决定后续行为

只保存一个 `started = True`，无法区分正在初始化与可以工作：两个阶段进程都已启动，但允许的动作不同。状态划分需要保存会影响后续规则的差别。

可以用不变量审查实现：客户端发送工作请求时，初始化结果已经收到，`initialized` 已经发送，而且 `shutdown` 尚未发送。初始状态没有发送工作请求，因此成立；初始化阶段的转移只在完成必要消息后进入可工作状态；关闭请求一发出就退出可工作状态。若发送代码只允许在可工作状态运行，这条性质便在所有按规则转移的交互中保持。

进程崩溃会使正常生命周期中断。新进程需要建立新的会话状态，不能仅因为旧进程曾初始化过，就把它记成可以工作。状态存在于哪次交互中，也是协议实现的一部分。

| 次序 | 客户端观察或动作 |
