需求：「用户在商品页上设定价格上限、只看现货、指定类目，页面返回满足全部这些条件的商品，按相关度从高到低排列；用户点开其中任意一件，页面显示它的详情。」这句话没有说商品有多少件，也没有说这套条件一天会被问多少次、每件商品会被点开多少次。两位设计者读到同一句话，得到两份不同的方案：一位把它当成偶尔问一次的一次性筛选，每次都从头把商品列表看一遍；另一位担心目录会持续增长、条件会被反复问，于是把重点放在会反复发生的那件事上。两份方案都符合这段要求，处理的是两个不同的问题。

一段要求要能当成计算问题来讨论，得把几件事补齐：输入是什么、输出是什么、哪些条件必须成立、数据大概有多少、这些数据在使用期内会增长到多大，以及哪些操作会被反复执行、各执行多少次。漏掉其中一项，后面的选择就建立在一个未确认的假设上。

## 把要求写成输入、输出与条件

从这段话里读出的计算问题：

| | 内容 |
| --- | --- |
| 输入 | 一批商品，每件带标识、标题、价格、是否现货、类目与相关度；一次查询，带价格上限、现货要求与目标类目 |
| 输出 | 命中的商品，按相关度从高到低排列 |
| 必须满足的条件 | 每件命中商品满足全部三个筛选条件；同一件商品不重复出现；排序覆盖全部命中项 |

要求里有两种读法没被定下来，各对应一个要补的条件。相关度相同的两件商品谁在前——排序规则没有给出同分的处理。结果是全部命中项还是只取靠前的若干项——输出没有给出截断的位置。这两种情况在算完之前看起来像细节；只要目录里有相关度相同的商品，或者命中项比页面一次敢显示的多，它们就决定输出的具体内容。

## 哪些操作会被反复执行

要求里能数出两类操作。一类是筛选：把每件商品依次对照价格、现货、类目三个条件，留下命中的。另一类是按标识定位：打开一件商品时，用它的标识在列表里找到它。

两类操作的代价随它们各自发生多少次累积。筛选发生一次，就把每件商品看一遍。按标识从头查找，找列表里靠后的商品要先看过它前面的每一件——把每件商品各打开一次，定位的查看次数就是各件所在位置之和。同一批商品，筛选做一次和定位做很多次，得到的工作量完全不同。把这两类操作在同一批商品上各数一遍，再把商品换成更大的一批，查看次数分别变成多少？

```python run id="data-and-computation.from-problem-to-computation.work-counts"
base = [
    ("p-201", "Desk lamp",     32.0, True,  "lighting",   0.71),
    ("p-202", "Floor lamp",    88.0, True,  "lighting",   0.65),
    ("p-203", "Desk lamp pro", 55.0, True,  "lighting",   0.80),
    ("p-204", "Notebook",       6.0, True,  "stationery", 0.42),
    ("p-205", "Clip lamp",     24.0, False, "lighting",   0.58),
    ("p-206", "Wall clock",    41.0, True,  "decor",      0.66),
]
more = [
    ("p-301", "Reading lamp",  45.0, True,  "lighting",   0.52),
    ("p-302", "Lantern",       18.0, True,  "lighting",   0.61),
    ("p-303", "Bookend",        8.0, True,  "decor",      0.35),
    ("p-304", "Lamp shade",    12.0, True,  "lighting",   0.44),
    ("p-305", "Smart plug",    29.0, True,  "decor",      0.48),
    ("p-306", "Power strip",   21.0, False, "decor",      0.39),
]
budget = 60.0
wanted = "lighting"

for label, catalogue in (("catalogue", base), ("catalogue with 6 more", base + more)):
    open_ids = []
    for row in catalogue:
        open_ids.append(row[0])

    examined = 0
    matched = 0
    for row in catalogue:
        examined += 1
        if row[2] <= budget and row[3] and row[4] == wanted:
            matched += 1

    looked_at = 0
    for want in open_ids:
        for row in catalogue:
            looked_at += 1
            if row[0] == want:
                break

    print(label, "products", len(catalogue), "filter examines", examined, "matches", matched)
    print(label, "locate each product once examines", looked_at)
```

筛选的查看次数等于商品件数：一次筛选会把每件商品看一遍。按标识定位的查看次数等于各件位置之和；找靠前的商品看得少，找靠后的商品要先看过它前面所有件。商品增多时两类计数都变大，定位的计数增长得更快，因为位置本身也在随件数变大。这段要求没有写筛选与定位各发生多少次，也没有写目录会停在哪个量级，所以这两个计数里哪一个会主导，还没有定。

## 数据规模与它在使用期内会增长到多大

决定方案的是使用期末的件数。商品目录在使用期内只会增长——新商品上架，旧商品很少撤下——使用期末的件数大于今天的件数，查询发生的总次数也随使用时长累积。这两个数只要求量级和方向，不要求精确值：目录停在今天的量级，还是会增长几个数量级；条件是被问一次，还是每次页面加载都被问；详情是偶尔点开，还是每件商品每天都被打开。从当前件数和增长速度外推使用期末的件数，再把每一类操作在那段时间里会发生多少次估出来，就得到判断方案要用的两个数。方向不同，值得优先照顾的操作也不同。

目录很小、条件偶尔被问，两类操作的总量都小，按最简单的写法就够用。目录增长、定位被反复触发，按标识从头查找就从可忽略变成主导量。要求只给出「要有这个页面」，上面这些要么从运营事实里读出来，要么向需求方问出来；不补齐它们，方案就在替需求方选一个他还没作出的决定。

## 哪些信息必须保留

一件商品身上通常带着很多字段，要求只用得到其中一部分。在这段要求里，标识、标题、价格、现货、类目与相关度都被读到：三个条件读价格、现货、类目，输出读标识、标题与相关度。商品的库存数量、内部备注这类信息，没有一条输出或条件读它，删掉它们不改变命中结果、排序或详情页的内容，也就不属于这个计算问题。要求一旦补上「相关度相同时按上架先后来排」，上架序号就从「可以不保留」变成「必须保留」——只有那一条排序规则读它，读不到，顺序就定不出来。

判据：一项信息是否必须保留，看有没有一条输出或条件读它；筛选条件、排序规则、去重判等、页面显示的字段都算读。没有一处读它的信息，删去不改变任何结果。信息「被要求」和「被读」是两回事：要求里提到一个字段，却没有一条输出或条件用它，它就不进入这个计算问题；换一条用到它的要求，它就要被保留。

## 练习

一份方案这样写：

> 搜索页每次请求都从头遍历商品列表，逐件比对价格、现货与类目，把命中的商品按相关度排好返回；打开详情时，再从头遍历一遍找到该商品。商品不多，这样最简单。

这段话对要求做了哪些没被确认的假设？逐条指出，并说明要求要补上什么，才能判断这个方案是否成立。下面这一格把方案里的两类操作各数了一遍。

```python run id="data-and-computation.from-problem-to-computation.exercise-scan-count"
catalogue = []
for index in range(50):
    catalogue.append((index, "in stock" if index % 5 else "out of stock"))

requests = 20
scans = 0
for request in range(requests):
    for item in catalogue:
        scans += 1

for opened in range(requests):
    for item in catalogue:
        scans += 1
        if item[0] == opened:
            break

print("products", len(catalogue), "requests", requests, "scans", scans)
```
