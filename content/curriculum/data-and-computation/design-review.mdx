一个结果库服务上线前，Agent 交回一份方案：

> 仿真运行的结果用一个以 `run_id` 为键的字典保存；建库时按 `run_id` 写入，每条运行的一条完整记录——参数组、指标、状态、写入时间——是它的值。用户提交筛选条件（指标达到门槛、只看状态为 `converged`、目标参数组）时，程序取出字典里的全部记录逐条比对，把命中的运行按指标排好返回。点开某条运行时，用它的 `run_id` 直接从字典取出详情。方案末尾附了一句：按键查找已经是常数时间，结果库已经按 `run_id` 去重，按 `run_id` 取这一项优化过了。
>
> 数据规模按建库时的一次快照定：库保持现在的量级，之后只做查询。

结果库的运营方给出这份服务的<Term id="workload">工作负载</Term>：

| 项目 | 数值 |
| --- | --- |
| run 记录数 | 现在 50000 条，每月增长约 5% |
| 参数筛选请求 | 每天约 20000 次 |
| 按 run_id 打开详情 | 每天约 2000 次 |
| 追加运行、更新状态 | 每天约 200 次 |
| 参数组取值个数 | 20 |
| 读（筛选与详情）与写的比例 | 约 110 : 1 |

方案里那两句声明——按键查找已经优化、库保持现在的量级——都要对到这份负载上逐条核对。

## 方案对上的是哪一类操作

以 `run_id` 为键的映射，把「按 `run_id` 取一条」和「按 `run_id` 写一条」变成对单条记录的定位。这份负载用到它的操作有两类：按 `run_id` 打开详情，每天约 2000 次；按 `run_id` 追加运行、更新状态，每天约 200 次。两类都走映射。方案说的去重也由它承担：同一个 `run_id` 再次写入时覆盖同一条记录（见 <CrossRef id="data-and-computation.representation-and-workload" />）。

负载里次数最多的操作是筛选，每天约 20000 次。一次筛选要取出指标、状态、参数组三项都满足的一组记录，它不按 `run_id` 定位单条。映射的键是 `run_id`，值里虽然存着指标与参数组，映射本身不按这些字段组织；从映射里取出满足三项条件的全部记录，只能把每一条值都过一遍。方案优化的「定位」是按 `run_id` 找到那一条的方式，筛选这条路没有被任何一个结构支持，仍然逐条走过整份库。

选定表示之前要看的是：负载里反复发生的是哪几类操作，候选表示让哪一类变便宜。方案把 2000 次的那一类变便宜了，20000 次的那一类留在原地。

## 把频率乘以成本形状

哪一项主导，用一条计数规则把三类操作折到同一单位上：一次按键取一条记一次记录查看，一次按键写一条记一次记录查看，一次筛选把整份库逐条看一遍、记记录数次。把每类操作的频率乘以各自的单次查看量，再求和。

计数规则把一次按键定位记作一次查看。以 `run_id` 为键时，常见实现（哈希表）给出的一次定位，平均行为接近一次查看：速度取决于键的分布与具体实现，定位本身也不是可以忽略的成本。

```python run id="data-and-computation.design-review.daily-cost"
records = 50000
filters_per_day = 20000
details_per_day = 2000
writes_per_day = 200

filter_term = filters_per_day * records
detail_term = details_per_day * 1
write_term = writes_per_day * 1
total = filter_term + detail_term + write_term

print("filter", filter_term)
print("detail", detail_term)
print("write", write_term)
print("total", total)
print("filter share percent", round(100.0 * filter_term / total, 4))

grown = records
for month in range(12):
    grown = grown * 105 // 100
print("size after 12 months", grown)
print("filter term after growth", filters_per_day * grown)
```

筛选一天要查看 1000000000 条次记录，详情合计 2000 条次，写入合计 200 条次，三项合计 1000002200 条次，筛选占 99.9998%。被方案点名优化过的按键定位，合计是全部工作里万分之一都不到的一项。

库按每月 5% 增长，12 个月后是 89788 条，筛选项随之涨到 1795760000 条次，其余两项不变。这份负载里会随规模放大的是筛选项，它是一天的筛选次数乘上库的记录数；筛选次数是给定的常数，随规模上涨的只有记录数这一个因子。

## 哪些候选当场淘汰

需要动手的只有筛选。给筛选列几个候选，按「一次筛选要碰多少条记录」排开；这个数不低于整份遍历的候选，不必再算频率。

| 候选做法 | 一次筛选碰到的记录数 | 一天合计（20000 次筛选） |
| --- | --- | --- |
| 方案现用：取出映射的全部值逐条比对 | 整份库，$n$ | $20000n$，当前 1000000000 条次 |
| 每次筛选之前把库按参数组重排一遍，再取一段 | 至少整份库，重排还要额外的比较与搬移 | 比方案更高：每次筛选都重做一遍整表工作 |
| 每条记录对照全部参数组各打一个标记，筛选时按标记取 | $n$ 乘以参数组数 | 再乘上 20 个参数组，约为方案的 20 倍 |
| 主数据之外维护一份按参数组组织的记录，筛选只碰目标参数组 | 约为 $n$ 除以参数组数 | 首个把单次量降到整表之下的形状 |

主数据之外另有一份结构的做法，机制与两侧代价已有完整说明（见 <CrossRef id="data-and-computation.preprocessing-and-indexes" />）；这里是同一种东西换了分组字段。

除最后一行以外的候选，光看它们一次筛选碰的记录数，被每天 20000 次的频率一乘就比现方案更差，当场排除。能被保留的只有最后一行：把一次筛选要碰的集合从整份库缩到目标参数组那一段。

最后一行那个「$n$ 除以参数组数」是假设各参数组的记录数在取值上大致均匀才成立的估计；真实数据常常高度偏斜，某个参数组的记录数可能远高于或远低于这个平均值，偏斜时按这个估计得出的单次量就会偏离实际。保留这一行，便宜由写入承担：库每追加一条或改一次状态，分组记录要跟着改一条。它值不值得建，要看筛选的选择性——一次筛选命中的记录占多大比例——以及维护成本、内存占用与延迟目标，读写比例只是其中一项。

## 方案依赖哪几条前提

方案的可用性依赖四条<Term id="precondition">前置条件</Term>。每一条都要在工作负载里找到依据；找不到依据时，要说清哪一类操作会先出问题。

第一条是数据规模与增长方向。方案自己写「库保持现在的量级」，负载写的是 50000 条、每月增长约 5%。这两句对不上：筛选项按记录数增长，12 个月后涨到接近 1.8 倍，而它本来就是主导项。

第二条是唯一性。按 `run_id` 建映射，前提是 `run_id` 能唯一确定一条记录。同一条运行被重跑、或几次写入共用一个 `run_id` 时，映射只留最后写入的那一条，先写的那些从表示里消失；筛选按它计数就会少算。把一份带重复 `run_id` 的记录分别按行与按映射的值筛一遍：

```python run id="data-and-computation.design-review.dict-drops-record"
rows = [
    ("r-201", "gain2", 0.98, True, "2024-05-02"),
    ("r-202", "gain2", 0.55, True, "2024-05-02"),
    ("r-201", "gain4", 0.42, False, "2024-05-03"),
    ("r-203", "gain2", 0.77, True, "2024-05-02"),
]
threshold = 0.50
wanted = "gain2"

by_row = []
for row in rows:
    if row[2] >= threshold and row[3] and row[1] == wanted:
        by_row.append(row[0] + "/" + row[4])

by_id = {}
for row in rows:
    by_id[row[0]] = row

by_dict = []
for key in sorted(by_id):
    row = by_id[key]
    if row[2] >= threshold and row[3] and row[1] == wanted:
        by_dict.append(key + "/" + row[4])

print("source rows", len(rows))
print("records held by dict", len(by_id))
print("matched by row scan", by_row)
print("matched by dict values", by_dict)
```

源数据四行，映射只持有三个 `run_id`：`r-201` 的 gain2 记录被后写的 gain4 记录覆盖，按行筛出三条、按映射的值筛出两条。唯一性不成立时，方案丢记录是静默的：筛选给出的结果偏少，没有任何一处报错。要留住全部记录，键得能唯一确定一条运行（`run_id` 加写入时间），或者先把同一 `run_id` 的多条记录合并成一条再建映射。

第三条是有序性，它只对用边界定位的那个候选项成立。把「按指标取一段」交给排好序的序列、用取中点砍半的方式定位，前提是序列在每次写入之后仍然有序。负载里每天约 200 次追加与改状态，而方案只在建库时排序一次；写入不改动次序，定位就落不到正确的边界上。要让这条前提成立，写入一侧要跟着维护次序，这是它单独的一份代价。

第四条是查询与写入的比例。按参数组分组的那份记录只在读远多于写时划算：负载现在是 110 : 1，把维护一条记录的代价摊到每次筛选上很轻。写入集中放大时——一次整批改状态、一次全量重建——维护项按被改的条数增长，筛选次数不变，比例一走低，这份记录就可能比它省下的更多。读写比例只是其中一项：筛选的选择性决定分组记录能把要碰的集合缩小多少，维护这份记录要多少额外写入、它占多少内存、延迟目标有多紧，同样决定它划不划算；选择性低时省下的查看有限，维护成本或内存占用高时，比例再高也未必划算。

## 方案逐项对回负载

方案选中的表示与算法，逐项对回负载：

- 按 `run_id` 取详情、按 `run_id` 追加与改状态、按 `run_id` 去重都走以 `run_id` 为键的映射，合计每天约 2200 次。
- 每天约 20000 次的筛选没有对应的结构，它逐条走过整份库，一天 1000000000 条次，占全部工作的 99.9998%。
- 方案声称优化过的按键定位，对应的是那 2200 次里的定位。
- 「库保持现在的量级」与「每月 5% 增长」对不上，主导项继续随记录数放大。
- 唯一性不成立时，映射静默丢记录，筛选结果偏少。

审查这份方案要给的判断：把操作频率与成本形状一并看，当场排除的是那些一次筛选要碰不低于整份库的候选；保留的是把一次筛选要碰的集合缩到目标参数组的做法；这个做法把代价从读移到写，能不能成立要看筛选的选择性、维护成本、内存与延迟目标，读写比例只是其中一项。方案的薄弱处在主导项、增长方向与唯一性三处，不在它优化过的那条按 `run_id` 定位的方式上。

## 练习

同一个结果库上，Agent 提了两个「加速筛选」的候选，都想替掉现在的整表遍历：

> 甲：每次筛选之前，先把库按参数组重排一遍，再沿着参数组取一段——先排好再取总是更快。
>
> 乙：给每条记录对照全部参数组各打一个标记，筛选时按标记取——检查得越全，筛得越快。

工作负载：库 50000 条记录，20 个参数组，每天 20000 次筛选。

两个候选在一次筛选里碰到的记录数，以及一天里的合计数，与整表遍历比；重排那个候选只数了一遍全表读取，重排还要比较与搬移，这个数只是下界。

```python run id="data-and-computation.design-review.exercise-candidates"
records = 50000
groups = 20
filters_per_day = 20000


def scan_whole(n):
    touched = 0
    for record in range(n):
        touched += 1
    return touched


def resort_then_take(n):
    touched = 0
    for record in range(n):
        touched += 1
    return touched


def mark_every_group(n, g):
    touched = 0
    for record in range(n):
        for group in range(g):
            touched += 1
    return touched


whole = scan_whole(records)
resort = resort_then_take(records)
mark = mark_every_group(records, groups)

print("whole scan one filter", whole, "one day", whole * filters_per_day)
print("resort one filter", resort, "one day", resort * filters_per_day)
print("mark one filter", mark, "one day", mark * filters_per_day)
```
