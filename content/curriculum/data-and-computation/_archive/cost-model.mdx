从列表里判断一个值在不在，最小的写法是逐元素比较：

```python run id="alg.cost.linear-search"
def contains(values, target):
    """Return whether target occurs in values."""
    for value in values:
        if value == target:
            return True
    return False


def counted(values):
    """Yield the same values, recording how many the caller pulls."""
    counted.pulled = 0
    for value in values:
        counted.pulled += 1
        yield value


for target, label in ((0, "first element"), (99, "last element"), (100, "absent")):
    found = contains(counted(range(100)), target)
    print(f"n=100  {label:13s} found={str(found):5s} comparisons={counted.pulled}")
```

`counted` 只把输入换成会记录「被取走多少个元素」的生成器，是观察用的插桩，不是 `contains` 接口的一部分。循环体每轮恰好做一次 `value == target`，被取走的元素个数就是比较次数：目标在第 $k$ 个位置命中就只比较 $k$ 次，不在列表里则要检查完整个列表，比较 $n$ 次。同一段代码、同一个规模，「它要比较多少次」还没有唯一答案——输入只要可能把目标放在首位，成本就能取到 $1$。

要把成本写成关于 $n$ 的函数，先分清两个层次。程序在**某一个具体输入** $x$ 上的成本记作

$$C(x),$$

它不必只由 $n$ 决定——同一个 $n$ 下的不同输入，成本可以差出很多。从具体输入走到关于 $n$ 的函数，还需要一条把同规模输入汇总起来的规则；最常用的是取其中最坏的一个。设 $X_n$ 是长度为 $n$ 的全部合法输入，最坏情形成本是

$$W(n) = \max_{x \in X_n} C(x).$$

线性查找在「只数元素比较」这条成本模型下有 $W(n) = n$：任何长度为 $n$ 的输入都最多比较 $n$ 次，而目标不在列表里这一族输入恰好达到 $n$。

到这里也定下了两件事：$n$ 是<Term id="input-size">输入规模</Term>，「只数元素比较、每次记 1」是一套 <Term id="cost-model">成本模型</Term>。换一个成本模型或换一个规模度量，同一个算法会得到另一条成本函数。

一句成本论断至少得写清四件事：

1. 研究的是哪一个实现——换一种表示，同一个操作的成本可能换一个量级，链式结构上的头部插入就不必搬移；
2. 采用什么成本模型——哪些操作进入计数、每种操作单价多少；
3. 以哪个量作为输入规模——元素个数、字节数还是位数；
4. 同一规模的多个输入怎样汇总成一个成本——最坏、最好、期望，还是明确指定的某一输入族。

补齐这四样，论断才可能在两种实现之间比较，也才可能在别人换掉其中一条约定时被推翻；把「增长方式相同」写成精确记号的那一步在 <CrossRef id="algorithms.asymptotic-analysis" /> 里完成。

## 成本模型

成本模型规定哪些操作进入计数、每种操作单价多少。结论永远相对于某个成本模型：「元素比较记 1，下标访问记 1，对象分配记 1」是一套，「只计比较与交换」是另一套；换模型会换结论，所以模型必须与结论一起出现。

最常用的一套是 <Term id="unit-cost-model">单位成本模型</Term>：每次基本操作记一个固定单位，访问内存里任意位置的代价相同。这是一套假设，不描述测量结果——真实硬件的访问代价取决于数据是否在缓存里、工作集有多大。抹掉这些差异换来结论可脱离机器比较，代价是它预测不出同阶实现之间的实际快慢；要把访问模式当成研究对象，就得换一套更丰富的成本模型，或在原生环境里做受控测量（<Term id="locality">局部性</Term>）。

单位成本模型里的「一次」必须与操作数的规模匹配。字符串长度没有固定上界时，比较两个字符串不能计作常数：在逐字符比较的模型里，成本取决于要检查多少个字符。具体运行时可能采用额外优化，那属于实现层，写结论时要么换模型，要么把假设写出来。

Python 层面的「一次操作」也常常不是常数时间：`list.insert(0, value)` 要移动后面所有元素，`value in some_list` 要扫描，字符串相加会构造新对象。写模型时要把这些高层操作折算成基本操作，或明确记为一次，并说明它的真实成本随什么增长。

## 输入规模

成本论断的自变量是输入规模，用哪个量度量属于结论的一部分。元素个数 $n$ 最常见，但并非总是正确：整数算法按位数算，字符串匹配同时依赖文本长度与模式长度。同一段代码换一种度量，增长阶可以完全不同——试除法分解一个 $k$ 位整数的成本随 $k$ 指数增长，写成按数值的平方根就把指数级藏了起来。

## 计数与计时

计数只依赖算法与成本模型，因此可复现、可推理；计时还依赖实现、机器、编译方式与当前负载。操作计数是模型中的量，运行时间是某个实现、某台机器、某个输入上的测量结果。同一段逻辑写成显式循环还是调用内建，计数可以相同，墙钟时间却可能差出一个常数因子——这个因子由实现决定，不改变增长量级。渐近分析研究前者，计时不能代替复杂度论证：一次基准测试只证明这个配置下的行为，把结论推广到别的机器或更大的输入需要另外的论证。
