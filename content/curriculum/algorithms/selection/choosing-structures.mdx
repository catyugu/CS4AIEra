给一组整数键，要求支持插入、按键查找、以及在键的区间 $[low, high)$ 内取出一段。有序数组和哈希表都能存下这组键，两者的单次操作成本来自不同的机制，在给定的操作频率下谁更便宜没有统一答案。把「选哪种表示」拆成两步按顺序做：先按功能需求排除丢掉所需信息的结构，再用<Term id="workload">工作负载</Term>比较剩下候选的成本。不满足功能需求的结构在任何频率下都不合格，筛选在前，比较在后。

## 第一步：用功能需求筛选

这一层的清单来自要做的操作本身，与规模无关：

| 维度 | 要问的问题 |
| --- | --- |
| 顺序 | 遍历顺序要不要稳定、要不要按键有序 |
| 唯一性 | 同一元素可不可以重复出现 |
| 位置 | 要不要按下标访问，插删之后旧下标要不要仍然指向同一元素 |
| 句柄 | 容器给出的、指向其内部位置或节点的句柄，在增删其他元素后要不要仍指向同一逻辑元素 |
| 范围 | 要不要按键的区间取一段 |
| 极值 | 要不要反复取出最小或最大的元素 |

这一步只问一件事：**这个表示有没有丢掉问题定义需要的信息**。重复元素被去重、旧下标在搬移后指向别的元素、节点引用在结构重建后失效——这些信息或绑定被丢掉之后无法再从表示里恢复，属于不满足功能需求，与规模无关。分界是：**能从表示已经保存的信息里算出来的适配属于成本问题；问题定义要求的信息已经被表示丢掉的属于功能需求问题。** 给结构额外维护一份元数据是选择了一个新的复合表示，不算把丢掉的信息找回来。

「顺序」在这里分成两种。**按键排序**：键值本身还在集合里，`sorted(s)` 就能排出来，属于成本问题。**原始顺序**（插入顺序、历史顺序）：`set` 没有保存它，再花时间也恢复不了，要保留只能从一开始额外维护一份序列，那时选的是「`set` + 序列」这个复合表示。范围查询与取极值都只是扫描——扫一遍筛出区间、扫一遍取极值，信息都在，属于成本问题；`dict` 可以利用它保存的插入顺序先把键列出来再索引。反复取最小或最大的对数界落在 <CrossRef id="algorithms.heaps" />。只有把候选限死在「结构自带的迭代器与访问原语、不许任何适配步骤」时，这些操作才直接淘汰结构；本课不设这条限制，下面工作负载单元格里 `dict` 的范围查询正是「扫描 + 输出」这种适配。

| 需求 | 被排除的常见结构 | 原因 |
| --- | --- | --- |
| 同一元素允许重复出现 | `set`、`dict` 的键 | 去重把重复信息丢掉了，恢复不出来 |
| 增删其他元素后，容器句柄仍指向同一逻辑元素 | 动态数组 | 搬移把位置句柄与那个元素的绑定丢掉了 |

`set` 与 `dict` 的键各自去重，需要保留重复元素时它们直接不合格。动态数组在中间插入或删除时会搬移后续元素，**容器给出的位置句柄**——下标、指向内部存储槽位的指针、按位置走动的迭代器——就不再指向原来那个元素；链表给出的是节点句柄，只要该节点没被删除就继续指向它。句柄与对象引用要分开：调用方对**元素对象本身**的外部引用属于调用方的引用，`items[10]` 拿到的对象在列表搬移之后依然是同一个对象，失效的是那个「第 10 个槽位」的位置含义。功能不匹配没有成本上的补救：哈希表在一次查找上省下的比较，补不回一个它没有保存的原始顺序，功能上的缺失用更贵的算法也换不回来。

筛选之后答案不必是单个结构。混合表示是合法的答案——哈希表加一份按键有序的缓存、堆加字典做延迟删除，都比强行二选一更常见；选择的对象是「表示组合」。

## 第二步：用工作负载比较成本

剩下的候选在同一条基准上比：把每个操作的单次成本乘以它在工作负载里的次数，求和。写清工作负载在先，填成本在后。一个工作负载要交代四件事：操作集合与各自的频率、输入规模与增长方式、访问模式（顺序读或随机读、有无局部性、是否成批）、以及对最坏情形的容忍度（摊还界够不够，还是单次延迟要有界）。加权里的权重来自实际发生的操作；把「将来可能要用」的操作计进去，比较的就是另一种工作负载。

统一规定计数单位：一次键比较、一次元素搬移、一次散列探测、一次结果元素的产出各记一个抽象步。这四类基本操作能相加，正因为它们被显式赋予同一个单位。两个候选必须在同一份操作清单上计分，对其中一个计入它擅长的操作、对另一个省略同类操作，比较的就不是同一件事。

设结构里持有 $n$ 个键，两个候选持有同一组键，记二分查找定位需要的比较次数 $p = \lceil \log_2 n \rceil$。逐项写出单次操作的成本：

| 操作 | 有序数组 | 哈希表 |
| --- | --- | --- |
| 插入 | 二分定位 $p$ 次比较，再加平均 $n/2$ 次搬移 | 一次散列探测 |
| 按键查找 | $p$ 次比较 | 一次散列探测 |
| 区间查询 | 两次二分定位 $2p$ 次比较，再加输出 $k$ 个元素 | 扫描全部 $n$ 个键各做一次区间测试，再加输出 $k$ 个元素 |

动态数组在末尾追加的插入是摊还常数成本，在中间插入每次都要搬移 $\Theta(n)$ 个元素；上表的插入记的是中间插入这一次的代价，对延迟敏感的场景按单次最坏成本比较（见 <CrossRef id="algorithms.amortized" />）。

```python run id="alg.choose.workload"
n = 200                       # keys held; both candidates store the same set
k = 20                        # elements a range query returns
p = (n - 1).bit_length()      # comparisons to binary-search n keys

# the workload: these three operation counts are the model's only inputs
workload = {"insert": 200, "lookup": 800, "range": 40}

# steps per operation: one comparison, one move or one emitted element
per_op = {
    "sorted array": (p + n // 2, p, 2 * p + k),
    "hash table": (1, 1, n + k),
}
totals = {}
for name, (insert, lookup, range_) in per_op.items():
    totals[name] = (workload["insert"] * insert + workload["lookup"] * lookup
                    + workload["range"] * range_)
    print(f"{name:<13}{totals[name]:>8}")
print("cheaper:", min(totals, key=totals.get))

(ai, al, ar), (bi, bl, br) = per_op.values()
switch = (workload["insert"] * (ai - bi) + workload["lookup"] * (al - bl)) / (br - ar)
print(f"range queries tying the totals: {switch:.0f}")
```

固定 $n = 200$、$k = 20$，此时 $p = 8$。代入一组操作次数，哈希表的总成本约为有序数组的三分之一。随着区间查询次数增加，哈希表每次都要扫描全表，累计成本增长更快；超过临界值后更省的一方变成有序数组。单元格最后一行给出这个临界次数，在当前插入与查找次数下，区间查询达到该值附近时两边总成本相等，继续提高由有序数组胜出。临界位置把工作负载当成变量解出来——离开频率谈「哪个结构更好」没有答案。

渐进阶只描述成本随 $n$ 增长的那一层，上面的表达式里没有常数、内存与局部性。这三项只在改变当前比较的结论时才需要进入模型：$O(1)$ 与 $O(\log n)$ 的差别可能被单次操作的常数因子抵消，$O(n)$ 的线性扫描在 $n$ 很小的实际规模上常常最快；访问模式决定一次顺序扫描与同样次数的随机探测哪一个先受到内存带宽限制（见 <CrossRef id="algorithms.complexity-in-practice" />）。按功能需求筛选不涉及这三项，因为一项功能需求是否被满足与规模、常数无关。
