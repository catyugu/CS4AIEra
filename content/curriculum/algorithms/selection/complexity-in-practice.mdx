<CrossRef id="algorithms.choosing-structures" /> 用工作负载比较成本，比较的却是模型里的单位成本。这一节处理成本模型与机器之间的差额：许多实现级的时间分析以**单位成本的 RAM 模型**作默认基线，把每次基本操作当作 1、把内存当作均匀且无限快的一层；有些结论另外声明比较模型、哈希概率模型等附加假设。而真实的机器里单位操作代价不同、内存分层次、内存有限。

渐进记号描述函数的增长率；成本模型决定我们在数什么。这三条约定属于成本模型，不属于 $O$ 与 $\Theta$ 记号本身：换一个模型，$\Theta(n)$ 次缓存失配、$\Theta(n/B)$ 次 I/O、$\Theta(n)$ 空间、位复杂度、外存复杂度都是完全合法的渐进结论；改变成本模型既可能只改变常数，也可能改变得到的渐进式。差额通常不改变关于输入规模的阶——常数因子就是这样——但换到比特复杂度或外存模型的记账方式，渐进表达式本身也可能变；而在阶不变的地方，差额经常改变同一渐进阶内部的选择，大部分工程决策正发生在这里。

## 单位成本模型把什么当作 1

一份成本模型要落地就得给出三个约定，单位成本的 RAM 模型把它们的取值固定成最省事的那种：

| 约定 | 模型假设 | 实际 |
| --- | --- | --- |
| 单位操作 | 每次基本操作代价相同 | 比较、加法、分配、方法调用的代价差几倍到几十倍 |
| 内存 | 访问任意位置代价相同 | 寄存器、各级缓存、主存之间差一到三个数量级 |
| 内存容量 | 无限，忽略占用 | 容量有限，占用决定能处理多大规模 |

三个约定各自对应一类现实成本：**常数因子**来自第一条，**局部性**来自第二条，**内存占用**来自第三条。它们没有被前面选定的那个单位成本时间函数计入，也不会因为 $O$ 相同就自动相等；换一个成本函数（缓存失配次数、I/O 次数、比特数），完全可以继续用 $O$ 与 $\Theta$ 描述它们。

## 常数因子从哪来

同一渐进阶的两个实现，差异来自可以点数的地方：

- 每个元素要做多少次基本操作（比较次数、拷贝次数、方法调用次数）；
- 单位操作本身的代价（整数比较远便宜于一次字典查找或一次分配）；
- 每次操作的固定开销（函数调用、边界检查、对象创建）；
- 内存布局与访问顺序（下一条）。

这些量分两类，回答的问题不同。**操作次数可以数**：比较几次、拷贝几次、调用几次，插一段计数就能得到，而且可复现。**单位操作的价钱数不出来**：一次整数比较、一次字典查找、一次分配各值多少，只能来自成本模型或实测，不是计数能得到的。点数说明差额从哪里来，实测给出差额有多大；两者都要，且要分开陈述。点数与计时各有所长：点数可复现、可解释来源，但需要自己定义单位操作；计时包含真实效果，但依赖环境——受控条件下它当然可以复现，只是带噪声，也不像抽象计数那样跨机器、跨解释器可移植，所以给出数字时要连同环境与统计一起报。常数不能脱离规模谈：同一实现「快 3 倍」只对特定规模、特定工作负载成立；把限定条件写进结论。

## 局部性：同一渐进阶下的数量级差别

遍历 $n$ 个元素在两种表示里都是 $\Theta(n)$，但访问模式不同。连续数组按下标前进，相邻元素落在同一条缓存行里；链式结构顺着指针跳到下一个节点，而节点的位置由分配顺序决定，与遍历顺序无关。把内存分成固定大小的行、用一个直接映射的小缓存来数：

```python run id="alg.practice.locality"
import random
import sys

LINE = 8      # cells per cache line
LINES = 64    # lines the modelled cache holds


def count_misses(addresses):
    """Direct-mapped cache: an access misses when its line is not the one the
    slot currently holds."""
    resident = {}
    misses = 0
    for address in addresses:
        line = address // LINE
        slot = line % LINES
        if resident.get(slot) != line:
            resident[slot] = line
            misses += 1
    return misses


n = 8192
rng = random.Random(20260605)
jumps = list(range(n))
rng.shuffle(jumps)

print(f"{n} accesses | line = {LINE} cells | cache = {LINES} lines")
print(f"  forward scan:  {count_misses(list(range(n))):>5} misses")
print(f"  random jumps:  {count_misses(jumps):>5} misses")
print()
import array
import struct

values = list(range(1000))
packed = struct.pack("<1000i", *values)   # the same 1000 integers, 4 bytes each
print("the same 1000 integers in three representations (sizes are for this build):")
print("  representation footprint of these 1000 values, under this accounting:")
print(f"  list:                {sys.getsizeof(values) + sum(sys.getsizeof(v) for v in values):>6} bytes"
      "  (the list object + the 1000 separate int objects it points at)")
print(f"  array('l'):          {sys.getsizeof(array.array('l', values)):>6} bytes")
print(f"  struct '1000i':      {sys.getsizeof(packed):>6} bytes"
      "  (the bytes object, 4000 of payload plus its header)")
```

顺序扫描的失配次数约为 $n / L$，随机跳转接近 $n$：两者都是 $\Theta(n)$，差额却由行的长度决定。它说明的是同一组抽象地址下，顺序访问比随机访问用到了更多<Term id="locality">空间局部性</Term>；指针追逐型的结构（链表、树、哈希表的链地址）**更容易付出这类局部性代价**，但真实机器上还有分配布局、硬件预取与依赖加载在起作用，具体倍数得由这个模型之外的证据给出。这也是「数组比链表快」这句话的真实内容：不是渐进阶的差别，是访问模式与成本模型假设的差别。模拟不是硬件：上面的缓存模型只有一套参数，真实机器有多级缓存、预取与乱序执行；模型能说明机制，不能预测具体机器的倍数。微基准要固定条件：解释器版本、机器、输入分布、是否预热；换一个环境结论可能翻转，所以报告数字时必须连条件一起报告。

## 模型过粗的两个例子

**期望常数时间依赖散列函数的行为与负载因子**。哈希表的期望 $O(1)$ 成本来自两条前提：散列把键均匀分散到桶里，并且负载因子受到控制。前者是关于哈希落点或探测序列的概率模型，后者是结构状态与扩容策略维持的条件；二者都是该期望界的前提，但都不是渐进记号本身的含义，也不属于单位成本模型的那三条约定。换一个把全部键映到同一个桶的散列函数，同一份代码就退化了：第 $k$ 次插入要探测 $\Theta(k)$ 个位置，连续插入 $n$ 个键的总探测数是 $\Theta(n^2)$：

```python run id="alg.practice.probing"
import random

def probes(keys, buckets, hash_of):
    """Linear probing: count the probes used by every insertion."""
    table = [None] * buckets
    total = 0
    for key in keys:
        index = hash_of(key) % buckets
        while table[index] is not None:
            total += 1
            index = (index + 1) % buckets
        table[index] = key
        total += 1
    return total


count, buckets = 200, 400
spread = list(range(count))
rng = random.Random(20260606)
placement = {key: rng.randrange(buckets) for key in spread}   # uniform initial buckets
print(f"linear probing, {count} insertions into {buckets} buckets"
      f" (load factor {count / buckets:.2f})")
print(f"  uniform hashing:              {probes(spread, buckets, lambda key: placement[key]):>6} probes")
print(f"  every key hashes to bucket 0: {probes(spread, buckets, lambda key: 0):>6} probes"
      f"  = {count * (count + 1) // 2}")
```

在同样的最终负载因子 $0.5$ 下，均匀散列的这一组插入一共只用 $279$ 次探测（这组样本中平均约 $1.4$ 次/插入），退化构造是 $20100$ 次——差别不在代码，在哈希概率模型与负载因子这两个分析前提。

这条退化不是「实现不好」，而是分析前提被破坏：分析给出的界带前提，前提不成立时界也不成立。输入由对手控制时，这从「慢」升级为「可被构造的攻击面」。

**摊还界控制一段操作序列的总成本，不给单次操作单独的最坏上界**。动态数组的追加是摊还 $O(1)$，其中有些追加会触发扩容并搬移全部元素（<CrossRef id="algorithms.amortized" />）。对吞吐量而言摊还界就是答案；对单次延迟有上限要求的场景，它不构成承诺，要按单次最坏成本重新比较。摊还界与平均情形分析不是一回事：它不假定输入的分布，也不对随机变量取期望。

## 渐进分析仍然不可替代

反过来也不成立：不能因为常数重要就跳过渐进分析。它给出三类别的工具给不出的判断：

- **趋势**：$\Theta(n \log n)$ 与 $\Theta(n^2)$ 在小规模上可以互相超越，规模一大次序就固定下来；
- **不可行**：小规模输入上用指数级方案当然可行，但规模一大，指数增长很快压倒常数优化，所以换更快的机器不改变可扩展性结论；
- **约束**：内存占用给出可处理规模的上限，与实现速度无关。

所以顺序是固定：先做渐进分析排除掉错误的量级，再在剩下的同阶候选项之间比较常数、局部性与内存，并且把比较的条件写清楚。结论是分两层判断：量级用渐进记号，同阶内部用常数、局部性与内存。
