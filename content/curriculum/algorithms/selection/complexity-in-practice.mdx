一次单位成本的 RAM 分析把每次基本操作当作 1，把一次内存访问计为固定的单位成本、忽略缓存层次，并假定地址空间足够；有些结论另外声明比较模型、哈希概率模型等附加假设。真实的机器里单位操作代价不同、内存分层次、内存有限。因此同一渐近阶内的一对实现可能差出数量级，这个差别在渐近记号里看不见。

成本模型决定一次计数里什么记为 1，渐近记号只描述计数值随规模增长的速率。上面三条约定属于成本模型，不属于 $O$ 与 $\Theta$ 记号：换一个成本函数，$\Theta(n)$ 次缓存失配、$\Theta(n/B)$ 次 I/O、位复杂度、外存复杂度都是合法的渐近结论。换模型可能只改变常数因子，也可能改变渐近式本身，比特复杂度与外存复杂度数的是不同的量。阶不变时，差额决定同一渐近阶内部的选择，多数工程决策发生在这里。

## 单位成本模型把什么当作 1

一份成本模型要能应用就得给出三个约定，单位成本的 RAM 模型把它们的取值固定成最省事的那种：

| 约定 | 模型假设 | 实际 |
| --- | --- | --- |
| 单位操作 | 每次基本操作代价相同 | 比较、加法、分配、方法调用的代价差异显著，且依赖微架构与运行时 |
| 内存 | 访问任意位置代价相同 | 寄存器、各级缓存、主存之间的代价差异显著，且依赖微架构与运行时 |
| 内存容量 | 无限，忽略占用 | 容量有限，占用决定能处理多大规模 |

三个约定各自对应一类现实成本：**常数因子**来自第一条，**局部性**来自第二条，**内存占用**来自第三条。这三类成本不在单位成本模型的时间函数里，相同的 $O$ 不保证它们相等；换一个成本函数（缓存失配次数、I/O 次数、比特数），仍然可以用 $O$ 与 $\Theta$ 描述它们。

## 常数因子从哪来

同一渐近阶的两个实现，差异来自可以点数的地方：

- 每个元素要做多少次基本操作（比较次数、拷贝次数、方法调用次数）；
- 单位操作本身的代价（整数比较远便宜于一次字典查找或一次分配）；
- 每次操作的固定开销（函数调用、边界检查、对象创建）；
- 内存布局与访问顺序（下一条）。

这些量分两类。**操作次数可以数**：比较几次、拷贝几次、调用几次，插一段计数就能得到。**单位操作的代价数不出来**：一次整数比较、一次字典查找、一次分配各计多少成本，取决于微架构与运行时，只能取自成本模型或实测。常数不能脱离规模：同一实现「快 3 倍」只对特定规模、特定工作负载成立，限定条件要写进结论。

## 局部性：同一渐近阶下的数量级差别

遍历 $n$ 个元素在两种表示里都是 $\Theta(n)$，但访问模式不同。连续数组按下标前进，相邻元素落在同一条缓存行里；链式结构顺着指针跳到下一个节点，而节点的位置由分配顺序决定，与遍历顺序无关。把内存分成固定大小的行、用一个直接映射的小缓存来数：

```python run id="alg.practice.cache-misses"
import random

LINE = 8     # cells per cache line
LINES = 64   # lines the modelled cache holds


def count_misses(addresses):
    resident, misses = {}, 0
    for address in addresses:
        line = address // LINE
        slot = line % LINES
        if resident.get(slot) != line:
            resident[slot] = line
            misses += 1
    return misses


n = 8192
rng = random.Random(20260605)
jumps = list(range(n))
rng.shuffle(jumps)
print(f"forward misses: {count_misses(list(range(n)))}")
print(f"random misses: {count_misses(jumps)}")
```

顺序扫描的失配次数约为 $n / L$，随机跳转接近 $n$：两者都是 $\Theta(n)$，差额由行的长度决定。同一组抽象地址下，顺序访问用到了更多<Term id="locality">空间局部性</Term>；指针追逐型的结构（链表、树、哈希表的链地址）付出的局部性代价更高。这也是「数组比链表快」这句话的真实内容：两者的渐近阶相同，差别出在访问模式与成本模型假设上。上面的缓存模型只有一套参数，真实机器还有多级缓存、预取、乱序执行与分配布局在起作用，模型说明机制，具体倍数由这个模型之外的证据给出。

## 内存

第三个约定是内存无限。同一份逻辑数据换一种表示，占用的内存可以差出数倍，来源是对象的表示方式：`list` 存的是指向对象的指针，每个整数是一个独立对象、自带对象头；`array` 与 `bytes` 把定宽整数直接存放在对象内部，没有每元素的对象头与指针。

```python run id="alg.practice.footprint"
import array
import struct
import sys

values = list(range(1000))
packed = struct.pack("<1000i", *values)

print(f"list:           {sys.getsizeof(values) + sum(sys.getsizeof(v) for v in values)} bytes")
print(f"array('l'):     {sys.getsizeof(array.array('l', values))} bytes")
print(f"struct '1000i': {sys.getsizeof(packed)} bytes")
```

上面的单元格按「表示这批值所需的直接对象大小」计数：对 `list` 计容器本身加它引用的每个 `int` 对象的直接大小，对 `array` 与 `bytes` 一次 `sys.getsizeof` 已包含元素存储。三个数字都只统计直接占用，不含共享对象、分配器开销与元数据，随指针与对象头的宽度变化。内存占用决定两件事：能处理的最大规模，以及缓存与分页的压力，它把第一条与第二条的代价又带回来一部分。`sys.getsizeof` 的统计口径见 [sys.getsizeof](https://docs.python.org/3/library/sys.html#sys.getsizeof)，`array` 的定宽元素见 [array](https://docs.python.org/3/library/array.html)，对象头与值分开存放、`list` 只持有指针这一布局见 CPython 的 [object.h](https://github.com/python/cpython/blob/main/Include/object.h)。

## 期望成本的前提被破坏时

**期望常数时间依赖散列函数的行为与负载因子**。哈希表的期望 $O(1)$ 成本来自两条前提：散列把键均匀分散到桶里，负载因子受到控制。前者是散列落点或探测序列的概率模型，后者由结构状态与扩容策略维持；两者都是这条期望界的前提，不进入 $O$ 与 $\Theta$ 记号的含义。换一个把全部键映到同一个桶的散列函数，同一份代码就退化了：第 $k$ 次插入要探测 $\Theta(k)$ 个位置，连续插入 $n$ 个键的总探测数是 $\Theta(n^2)$：

```python run id="alg.practice.probing"
import random

def probes(keys, buckets, hash_of):
    """Linear probing: count the probes used by every insertion."""
    table = [None] * buckets
    total = 0
    for key in keys:
        index = hash_of(key) % buckets
        while table[index] is not None:
            total += 1
            index = (index + 1) % buckets
        table[index] = key
        total += 1
    return total


count, buckets = 200, 400
spread = list(range(count))
rng = random.Random(20260606)
placement = {key: rng.randrange(buckets) for key in spread}   # uniform initial buckets
print(f"linear probing, {count} insertions into {buckets} buckets"
      f" (load factor {count / buckets:.2f})")
print(f"  uniform hashing:              {probes(spread, buckets, lambda key: placement[key]):>6} probes")
print(f"  every key hashes to bucket 0: {probes(spread, buckets, lambda key: 0):>6} probes"
      f"  = {count * (count + 1) // 2}")
```

在同样的负载因子下，均匀散列的插入每次平均只探测与负载因子有关的常数次，退化的构造要 $\Theta(n^2)$ 次：$n$ 次插入每次都从空槽位一路探测到下一个空位，合计 $n(n+1)/2$ 次探测。两项的具体次数由单元格给出，差异来自哈希概率模型与负载因子这两个分析前提，同一份代码在两种前提下的成本不同。

这条退化来自分析前提被破坏：分析给出的界带前提，前提不成立时界也不成立。输入由对手控制时，这从「慢」升级为「可被构造的攻击面」。

## 摊还成本与尾延迟

摊还界控制一段操作序列的总成本，单独一次操作的最坏成本不受它约束。动态数组的追加是摊还 $O(1)$，其中有些追加会触发扩容并搬移全部元素（<CrossRef id="algorithms.amortized" />）。对吞吐量而言摊还界就是答案：它把一段操作的总成本摊到每次操作上，给的是一个平均值。对单次延迟有上限要求的场景，平均值不够——约束服务的是那少数几次最坏操作，工程上按分位数（尾延迟）而不是平均值衡量，同一个摊还 $O(1)$ 的结构在按尾延迟衡量的负载下与一个每次成本恒定的实现是两种东西。要按单次最坏成本重新比较；摊还界不假定输入分布，也不对随机变量取期望。

## 计数与计时

同一渐近阶内差额的大小由实测给出。计数与计时回答不同的问题：计数（比较次数、拷贝次数、探测次数）可复现，跨机器、跨解释器稳定，指出差额来自哪里；计时把运行时的真实代价包含进来，给出特定配置下差额有多大。

计时与它测量的环境绑定。同一个算法逻辑在不同语言实现、不同机器、不同输入分布下测出的倍数不同，预热前后、CPU 频率与后台负载都影响结果；预热把解释器与缓存推到稳定状态，测量才落在程序本身。

一次基准测试证明该配置下的行为，不证明渐近律。它给出所测规模区间内的成本，外推到未测过的规模没有依据；要说一个实现比另一个快，需要同一配置下的对照测量，或一个把单位操作成本写清楚的成本模型。内存占用的直接字节数同样只对测量它的构建成立，指针与对象头的宽度一变，数字就变。

## 渐近分析仍然不可替代

常数重要不削弱渐近分析。它给出三类其他工具给不出的判断：

- **趋势**：$\Theta(n \log n)$ 与 $\Theta(n^2)$ 在小规模上可以互相超越，规模一大次序就固定下来；
- **不可行**：小规模输入上用指数级方案当然可行，但规模一大，指数增长很快压倒常数优化，所以换更快的机器不改变可扩展性结论；
- **约束**：内存占用给出可处理规模的上限，与实现速度无关。

所以顺序固定：先用渐近分析排除错误的量级，再在剩下的同阶候选项之间比较常数、局部性与内存，把比较的条件写清楚。同阶内部的比较把这些量变成成本模型里的单位成本系数，再与工作负载频率合起来解出临界点（见 <CrossRef id="algorithms.choosing-structures" />）。
