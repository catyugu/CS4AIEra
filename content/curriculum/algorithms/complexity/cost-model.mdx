从列表里判断一个值在不在，最小的写法是逐元素比较：

```python run id="alg.cost.linear-search"
def contains(values, target):
    """Return whether target is in values, and the element comparisons used."""
    comparisons = 0
    for value in values:
        comparisons += 1
        if value == target:
            return True, comparisons
    return False, comparisons


values = list(range(100))
for target, label in ((0, "first element"), (99, "last element")):
    found, comparisons = contains(values, target)
    print(f"n=100  {label:14s} found={str(found):5s} comparisons={comparisons}")

for size in (100, 200, 400):
    found, comparisons = contains(list(range(size)), size)
    print(f"n={size:<4d} absent         found={str(found):5s} comparisons={comparisons}")
```

长度固定为 100 时，两种命中位置给出不同的比较次数：命中的是第一个元素 1 次，命中的是最后一个元素 100 次。目标不在列表里时，长度 100、200、400 分别对应 100、200、400 次。同一段代码、同一个规模，成本在 1 到 100 之间都能取到，「它要比较多少次」还没有唯一答案。要把它写成关于 $n$ 的函数，先得把研究对象缩小：这里规定只看目标不在列表里的输入，并且只数元素比较。未命中时必须检查完整个列表，比较次数正好是 $n$。

到这里同时定下了三件事：$n$ 是<Term id="input-size">输入规模</Term>；「只数元素比较、每次记 1」是一套 <Term id="cost-model">成本模型</Term>；在这两个约定下得到的函数 $C(n) = n$ 是成本函数。换一个成本模型或换一个规模度量，同一个算法会得到另一条成本函数。

一句成本论断至少得写清三件事：

1. 研究的是哪一个实现——换一种表示，同一个操作的成本可能换一个量级，链式结构上的头部插入就不必搬移；
2. 采用什么成本模型——哪些操作进入计数、每种操作单价多少；
3. 以哪个量作为输入规模——元素个数、字节数还是位数。

补齐这三样，论断才可能在两种实现之间比较，也才可能在别人换掉其中一条约定时被推翻；把「增长方式相同」写成精确记号的那一步在 <CrossRef id="algorithms.asymptotic-analysis" /> 里完成。

## 成本模型

成本模型规定哪些操作进入计数、每种操作单价多少。结论永远相对于某个成本模型：「元素比较记 1，下标访问记 1，对象分配记 1」是一套，「只计比较与交换」是另一套；换模型会换结论，所以模型必须与结论一起出现。

最常用的一套是 <Term id="unit-cost-model">单位成本模型</Term>：每次基本操作记一个固定单位，访问内存里任意位置的代价相同。这是一套假设，不描述测量结果——真实硬件的访问代价取决于数据是否在缓存里、工作集有多大。抹掉这些差异换来结论可脱离机器比较，代价是它预测不出同阶实现之间的实际快慢；要把访问模式当成研究对象，就得换一套更丰富的成本模型，或在原生环境里做受控测量（<Term id="locality">局部性</Term>）。

单位成本模型里的「一次」必须与操作数的规模匹配。字符串长度没有固定上界时，比较两个字符串不能计作常数：在逐字符比较的模型里，成本取决于要检查多少个字符。具体运行时可能采用额外优化，那属于实现层，写结论时要么换模型，要么把假设写出来。

Python 层面的「一次操作」也常常不是常数时间：`list.insert(0, value)` 要移动后面所有元素，`value in some_list` 要扫描，字符串相加会构造新对象。写模型时要把这些高层操作折算成基本操作，或明确记为一次，并说明它的真实成本随什么增长。

## 输入规模

成本论断的自变量是输入规模，用哪个量度量属于结论的一部分。元素个数 $n$ 最常见，但并非总是正确：整数算法按位数算，字符串匹配同时依赖文本长度与模式长度。同一段代码换一种度量，增长阶可以完全不同——试除法分解一个 $k$ 位整数的成本随 $k$ 指数增长，写成按数值的平方根就把指数级藏了起来。

## 计数与计时各自能回答什么

计数只依赖算法与成本模型，因此可复现、可推理；计时还依赖实现、机器、编译方式与当前负载。操作计数是模型中的量，运行时间是某个实现、某台机器、某个输入上的测量结果。同一段逻辑写成显式循环还是调用内建，计数可以相同，墙钟时间却可能差出一个常数因子——这个因子由实现决定，不改变增长量级。渐近分析研究前者，计时不能代替复杂度论证：一次基准测试只证明这个配置下的行为，把结论推广到别的机器或更大的输入需要另外的论证。

## 时间与空间是两个维度

成本不只有时间。研究额外存储时，同样先规定计什么单位——槽位、字节或对象数量——再把它写成输入规模的函数。时间与空间是两个独立指标，不能合成一个「总复杂度」；用空间换时间的选择要分别给出两边的量级与各自依赖的规模。
