元素个数 $n$ 从 100 变成 200，比较次数怎么变？一段顺序查找会从 100 次变成 200 次，把这个成本写成关于 $n$ 的函数就是 `comparisons(n) = n`；换一段程序，函数可以长成别的形状。要回答「这段程序多快」，先得决定数什么。取一次下标、比对一次元素、搬移一个元素，被记成一次还是几次，直接决定算出来的函数长什么样；同一段代码按元素个数、字节数或位数度量，得到的函数也可以完全不同。

一句成本论断至少得写清三件事：

1. 研究的是哪一个实现——换一种表示，同一个操作的成本可能换一个量级，链式结构上的头部插入就不必搬移；
2. 采用什么成本模型——哪些操作进入计数、每种操作单价多少；
3. 以哪个量作为输入规模——元素个数、字节数还是位数。

补齐这三样，论断才可能在两种实现之间比较，也才可能在别人换掉其中一条约定时被推翻；把「增长方式相同」写成精确记号的那一步在 <CrossRef id="algorithms.asymptotic-analysis" /> 里完成。

## 成本模型

为计算选定「哪些操作进入计数、每种操作单价多少」，这套约定就是 <Term id="cost-model">成本模型</Term>。结论永远相对于某个成本模型：「元素比较记 1，下标访问记 1，对象分配记 1」是一套，「只计比较与交换」是另一套；换模型会换结论，所以模型必须与结论一起出现。

最常用的一套是 <Term id="unit-cost-model">单位成本模型</Term>：每次基本操作记一个固定单位，访问内存里任意位置的代价相同。这是一套假设，不描述测量结果——真实硬件的访问代价取决于数据是否在缓存里、工作集有多大。抹掉这些差异换来结论可脱离机器比较，代价是它预测不出同阶实现之间的实际快慢；要把访问模式当成研究对象，就得换一套更丰富的成本模型，或在原生环境里做受控测量（<Term id="locality">局部性</Term>）。

排序上常用另一套 <Term id="comparison-model">比较模型</Term>，它限制算法获取次序信息的方式：只能通过比较两个键判断相对次序，每次键比较计一次，数据移动与交换另行计数；比较排序的比较次数有一个随 $n \log n$ 增长的下界，这条下界只在比较模型里成立。

单位成本模型里的「一次」必须与操作数的规模匹配。字符串长度没有固定上界时，比较两个字符串不能计作常数：在逐字符比较的模型里，成本取决于要检查多少个字符。具体运行时可能采用额外优化，那属于实现层，写结论时要么换模型，要么把假设写出来。

Python 层面的「一次操作」也常常不是常数时间：`list.insert(0, value)` 要移动后面所有元素，`value in some_list` 要扫描，字符串相加会构造新对象。写模型时要把这些高层操作折算成基本操作，或明确记为一次，并说明它的真实成本随什么增长。

## 输入规模

成本论断的自变量是 <Term id="input-size">输入规模</Term>，用哪个量度量属于结论的一部分。元素个数 $n$ 最常见，但并非总是正确：图算法通常同时用顶点数 $V$ 与边数 $E$，整数算法按位数算，字符串匹配同时依赖文本长度与模式长度。同一段代码换一种度量，增长阶可以完全不同——试除法分解一个 $k$ 位整数的成本随 $k$ 指数增长，写成按数值的平方根就把指数级藏了起来。

```python run id="alg.cost.linear-search"
def linear_search(values, target):
    """Return the index of target, counting element comparisons."""
    comparisons = 0
    for index, value in enumerate(values):
        comparisons += 1
        if value == target:
            return index, comparisons
    return -1, comparisons


for size in (100, 200, 400):
    values = list(range(size))
    index, comparisons = linear_search(values, size - 1)
    print(f"n={size:4d}  comparisons={comparisons:4d}  comparisons/n={comparisons / size:.2f}")

index, comparisons = linear_search(list(range(1000)), 2000)
print("miss:", index, comparisons, "comparisons (the whole input)")
```

命中位置不同，成本就不同：命中靠前时很少比较，命中末尾或未命中时要扫完整个输入。这一组计数本身还没有定义任何分布，所以它只支持「同一份代码在不同输入上成本不同」这个观察。

## 计数与计时各自能回答什么

计数只依赖算法与成本模型，因此可复现、可推理；计时还依赖实现、机器、编译方式与当前负载。

```python run id="alg.cost.constants"
import time

size = 400_000
values = list(range(size))

start = time.perf_counter()
total_loop = 0
for value in values:
    total_loop += value
loop_seconds = time.perf_counter() - start

start = time.perf_counter()
total_builtin = sum(values)
builtin_seconds = time.perf_counter() - start

print("same result:", total_loop == total_builtin)
print(f"python loop: {loop_seconds:.4f}s   builtin sum: {builtin_seconds:.4f}s   ratio: {loop_seconds / builtin_seconds:.1f}x")
```

绝对数字每次不同，比例也会波动。能稳定得到的结论只有一条：常数因子由实现决定。要比较两个实现，必须固定机器、输入与实现，并把测量条件写出来；一次基准测试只证明这个配置下的行为，把结论推广到别的机器或更大的输入需要另外的论证。

## 时间与空间是两个维度

空间成本用同一套纪律陈述：先固定模型，再给出规模。以图的存储为例，模型计槽位数，规模是 $V$ 与 $E$。

```python run id="alg.cost.space"
def matrix_slots(vertices):
    """Slots held by an adjacency matrix of an undirected graph."""
    return vertices * vertices


def list_slots(vertices, edges):
    """Vertex entries plus two endpoint entries per edge."""
    return vertices + 2 * edges


print(f"{'V':>5} {'E':>7} {'matrix':>8} {'list':>7} {'ratio':>7}")
for vertices in (64, 128, 256):
    edges = 2 * vertices
    matrix = matrix_slots(vertices)
    listing = list_slots(vertices, edges)
    print(f"{vertices:>5} {edges:>7} {matrix:>8} {listing:>7} {matrix / listing:>7.1f}")
```

顶点数翻倍时矩阵的槽位数变成四倍，邻接表按 $V + 2E$ 增长：每个顶点一个入口，每条边的两个端点各一个条目。这里计的是抽象槽位，不是 Python 对象的真实字节数。邻接表的槽位数是 $V + 2E$：$E$ 与 $V$ 同量级时两项都不可忽略，$E$ 远大于 $V$ 时边条目主导，$E$ 远小于 $V$ 时顶点入口主导。矩阵则始终是 $V^2$ 个槽位：只有 $E$ 已经达到 $V^2$ 的量级时，它的空间才与边数处于同一增长量级；当 $E$ 的增长明显慢于 $V^2$ 时，它为大量不存在的边保留了槽位。单元格里的例子取 $E = 2V$，两项同量级，说明的是第一种情形。表示决定空间成本。时间与空间也不能合成一个数，用空间换时间的选择要分别给出两边的量级与各自依赖的规模。
