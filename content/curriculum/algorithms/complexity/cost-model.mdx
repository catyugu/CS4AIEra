「这个操作的成本不随规模增长」不是一句可检验的话。它至少缺四样东西：研究的是哪个实现在哪个成本模型下、一次操作指什么、规模用哪个量度量，以及成本怎样量化——对同规模的输入取最大、对声明的分布取期望，还是对一串操作分摊。补齐这四样，论断才可能在两种实现之间比较，也才可能在别人换掉其中一条约定时被推翻。这一课建立这套约定，记号本身在 <CrossRef id="algorithms.asymptotic-analysis" /> 里定义。

## 成本模型

为计算定义一组操作与每种操作的单价，就是**成本模型**。结论永远相对于某个成本模型：「元素比较记 1，下标访问记 1，对象分配记 1」是一套，「只计比较与交换」是另一套。换模型会换结论，所以模型必须与结论一起出现。

成本模型只包含「哪些操作、各自多少单价」以及必要的机器假设。一条复杂度论断要固定的东西比这更多，至少四件：研究哪个算法或实现、采用什么成本模型、以什么量度作为输入规模、以及怎样把同规模下的执行成本量化或聚合。规模度量与量化方式都是独立的选择，把它们一起叫作「成本模型」会让后面出现「换了最坏情形就换了成本模型」这类错误。

最常用的一套假设是**单元成本模型**（unit cost，RAM-style）：每次基本操作花固定时间，访问内存里任意位置同样便宜。它是一个假设。真实硬件的访问成本取决于数据是否在缓存中、工作集有多大；把这些差异抹掉，换来的是结论可以脱离机器比较。RAM 模型故意忽略内存层次，因此即使工作集超过缓存，模型下的计数结论依然成立；受影响的是它的预测能力——模型可能预测不出实际时间，也解释不了两个同阶实现为什么差出数倍。要把局部性当成研究对象，就得换一个更丰富的成本模型，或者做受控测量。

**基于比较的排序模型**是另一套常用假设，它限制的是算法获取次序信息的方式：算法只能通过比较两个键来判断它们的相对次序。研究比较复杂度时，把每次键比较计为一次并关注比较次数，数据移动与交换可以另行计数；后面的排序子章节里 $\Omega(n \log n)$ 的下界限制的就是这套模型中的比较次数。

Python 层面的「一次操作」常常不是常数时间：`list.insert(0, value)` 要移动后面所有元素，`value in some_list` 要扫描，字符串相加会构造新对象。写成本模型时要把这些高层操作折算成基本操作，或者明确按一次计价并说明它的真实成本随什么增长。

**单元成本必须与操作数的规模匹配。** 字符串长度没有固定上界时，「比较两个字符串」不能无条件定价为一次常数操作：在逐字符比较的模型里，成本取决于要检查多少个字符，最坏情况与字符串长度有关。具体运行时可能采用额外的优化，那属于实现层，写结论时要么换模型，要么把假设写出来。

## 输入规模

规模用哪个量度量，属于结论的一部分。元素个数 $n$ 是最常见的选择，但并非总是正确：图算法通常同时用顶点数 $V$ 与边数 $E$；整数算法按位数算（按数值大小会得出错误的增长率）；字符串匹配同时依赖文本长度与模式长度。

按错误的量度量会得出看似成立的错误结论：试除法分解一个 $k$ 位整数的成本随 $k$ 指数增长，把它写成按数值的平方根就把指数级藏了起来。这一课描述结论时只说成本随哪个量怎样增长；把这些话写成记号是下一课的事，而在那之前，先确认规模是哪个量。

```python run id="alg.cost.linear-search"
def linear_search(values, target):
    """Return the index of target, counting element comparisons."""
    comparisons = 0
    for index, value in enumerate(values):
        comparisons += 1
        if value == target:
            return index, comparisons
    return -1, comparisons


for size in (100, 200, 400):
    values = list(range(size))
    index, comparisons = linear_search(values, size - 1)
    print(f"n={size:4d}  comparisons={comparisons:4d}  comparisons/n={comparisons / size:.2f}")

index, comparisons = linear_search(list(range(1000)), 2000)
print("miss:", index, comparisons, "comparisons (the whole input)")
```

命中位置不同，成本就不同：命中靠前时很少比较，命中末尾或未命中时要扫完整个输入。最坏情形可以对同规模输入取最大值；平均情形必须先声明「是否命中、命中位置」这些输入如何分布，之后才能谈期望。这一组计数本身还没有定义任何分布，所以它只支持「同一份代码在不同输入上成本不同」这个观察。

## 计数与计时各自能回答什么

计数只依赖算法与成本模型，因此可复现、可推理；计时还依赖实现、机器、编译方式与当前负载。

```python run id="alg.cost.constants"
import time

size = 400_000
values = list(range(size))

start = time.perf_counter()
total_loop = 0
for value in values:
    total_loop += value
loop_seconds = time.perf_counter() - start

start = time.perf_counter()
total_builtin = sum(values)
builtin_seconds = time.perf_counter() - start

print("same result:", total_loop == total_builtin)
print(f"python loop: {loop_seconds:.4f}s   builtin sum: {builtin_seconds:.4f}s   ratio: {loop_seconds / builtin_seconds:.1f}x")
```

绝对数字每次不同，比例也会波动。能稳定得到的结论只有一条：常数因子由实现决定，而渐进记号刻意把它丢掉。要比较两个实现，必须固定机器、输入与实现，并把测量条件写出来；一次基准测试只证明这个配置下的行为，不支持渐进结论。

## 时间与空间是两个维度

空间成本用同一套纪律陈述：模型、规模、情形。以图的存储为例，模型计槽位数，规模是 $V$ 与 $E$。

```python run id="alg.cost.space"
def matrix_slots(vertices):
    """Slots held by an adjacency matrix of an undirected graph."""
    return vertices * vertices


def list_slots(vertices, edges):
    """Vertex entries plus two endpoint entries per edge."""
    return vertices + 2 * edges


print(f"{'V':>5} {'E':>7} {'matrix':>8} {'list':>7} {'ratio':>7}")
for vertices in (64, 128, 256):
    edges = 2 * vertices
    matrix = matrix_slots(vertices)
    listing = list_slots(vertices, edges)
    print(f"{vertices:>5} {edges:>7} {matrix:>8} {listing:>7} {matrix / listing:>7.1f}")
```

顶点数翻倍时矩阵的槽位数变成四倍，邻接表按 $V + 2E$ 增长：每个顶点一个入口，每条边的两个端点各一个条目。这里计的是抽象槽位，不是 Python 对象的真实字节数。邻接表的槽位数是 $V + 2E$：$E$ 与 $V$ 同阶时两项都不可忽略，$E$ 远大于 $V$ 时边条目主导，$E$ 远小于 $V$ 时顶点入口主导。矩阵则始终是 $V^2$ 个槽位：只有 $E$ 已经达到 $V^2$ 的量级时，它的空间才与边规模处于同一渐进量级；当 $E$ 的增长严格低于 $V^2$（即 $E = o(V^2)$）时，它为大量不存在的边保留了槽位。单元格里的例子取 $E = 2V$，两项同阶，说明的是第一种情形。表示决定空间成本。时间与空间也不能合成一个数，用空间换时间的选择要分别给出两边的量级与各自依赖的规模。

## 几种常见的成本量化方式

| 表述 | 量化对象 | 是否需要概率分布 |
| --- | --- | --- |
| 最坏情形 | 固定规模 $n$ 的所有合法输入中取最大成本 | 否 |
| 平均情形 | 固定规模 $n$ 的输入按声明的分布取期望 | 是 |
| 摊还分析 | 对任意合法操作序列控制总成本，再分配到各次操作 | 否 |

最坏与平均回答「同一规模下的不同执行怎样聚合成一个函数」，摊还分析回答「一串操作的总成本怎样分摊到各次操作」。两者不是严格互斥的分类，这里并列只是为了区分三种常见的成本论断；它们也可以组合，例如随机化数据结构的期望摊还成本，就是对随机位取期望之后的摊还成本。

摊还的定义不是事后求平均。对长度为 $m$ 的任意合法操作序列，如果能证明总实际成本至多为 $F(m)$，那么分摊到每次操作上的摊还成本至多为 $F(m)/m$；这条论证不对操作序列施加任何概率分布。不同操作的摊还收费可以不同：给每次操作指定一个收费，证明任何合法序列上的总实际成本不超过相应收费之和，具体方法留给 <CrossRef id="algorithms.amortized" />。摊还与平均混用，会让一个在对抗性输入下退化的结构看起来安全。

采用按比例扩容策略的动态数组（典型的 Python list 实现就是如此）里，单次扩容可能复制当前全部元素，但一串连续追加的总复制工作量只随追加次数线性增长：这是几何扩容的性质，证明在 <CrossRef id="algorithms.amortized" />，那里是摊还分析的唯一归属地；这里只应用结论。语言层的 append 契约并不规定扩容策略，按比例扩容是具体实现的选择。

## 小结

- 结论相对于显式的成本模型与显式的规模度量，两者都要与结论一起给出；成本模型只含操作与单价，规模度量与量化方式都是另外的选择。
- 单元成本模型与基于比较的模型都是假设；高层语言操作的单价要单独说明。
- 最坏情形只依赖规模，平均情形依赖声明的分布，摊还分析对任意操作序列控制总成本并分摊，不做随机性假设。
- 计数实验可以显示增长趋势并检查模型是否可信，严格的渐进结论仍需分析证明；计时的用途是在固定条件下比较实现。
- 时间与空间是两个维度，各自有成本模型、规模度量与量化方式。
