手上有序列 `[7, 2, 5, 3, 8, 1, 6, 4]`。把它排成升序可以用一条规则做到：取来一个区间，按中点切成左右两半，把两半各自排好，再把两个有序半区合并成一个有序序列。合并时同时读两个半区的首元素，取走更小的那个；某个半区读空后，把另一个半区剩下的元素整体接上。

这条规则对更短的半区同样适用，一直用到区间只剩一个元素——单个元素已经有序。切开、把两半分别排好、把两个有序半区合并，整段过程反复执行这三个动作。

## 归并排序

切分只做一个决定：取中点，把区间分成规模各约一半的两部分。递归把两个半区都排成升序，`merge` 再合并它们——同时推进两个下标，取走当前更小的元素，某一段走完后接上另一段的剩余部分。下面的单元格记录每一次 `merge` 的输入与输出。

```python run id="alg.techniques.merge-sort"
def merge(left, right, trace):
    merged, i, j = [], 0, 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            merged.append(left[i]); i += 1
        else:
            merged.append(right[j]); j += 1
    merged.extend(left[i:]); merged.extend(right[j:])
    trace.append((tuple(left), tuple(right), tuple(merged)))
    return merged


def sort(values, trace):
    if len(values) <= 1:
        return values
    middle = len(values) // 2
    left = sort(values[:middle], trace)
    right = sort(values[middle:], trace)
    return merge(left, right, trace)


data = [7, 2, 5, 3, 8, 1, 6, 4]
trace = []
ordered = sort(data, trace)
for left, right, merged in trace:
    print(f"combine {left} + {right} -> {merged}")
print(f"sorted {ordered}")
print(f"combine steps: {len(trace)}  (n - 1 = {len(data) - 1})")
```

八个数产生七次合并（$n - 1$ 次）。输出按发生顺序排列：先把长度为 1 的区间两两合成，再往上一层合成更长的区间，最后一步把两个半区拼成整个序列。递归在长度为 1 的区间上停止，合并从最下一层开始往上拼。

## 分治

切开、递归求解、合并这三个动作对归并排序之外的许多问题同样成立，这一类做法叫**分治**。把待解问题记作 $P$，它的抽象规约写清两端：

| 规约 | 内容 |
| --- | --- |
| `solve(P)` 的前置条件 | $P$ 是这一类问题的一个实例，且规模在可解范围内 |
| `solve(P)` 的后置条件 | 返回 $P$ 的一个解，且该解满足这类问题的定义 |

分治版本只用三个动作描述：

| 动作 | 说明 |
| --- | --- |
| `divide(P)` | 产生有限个更小的同类子实例 $P_1, \dots, P_k$ |
| `conquer` | 递归求解这些子实例 |
| `combine(P, solution_1, \dots, solution_k)` | 用原实例的必要信息与子问题的解，构造 $P$ 的解 |

归并排序把这几个符号落回具体的操作：`divide` 按中点把区间切成两半，$k = 2$，两个子实例仍是「排好一个区间」这一类型的问题；`conquer` 对两个半区递归调用同一个 `solve`；`combine` 做一次归并。二分查找是少了第二个子问题的退化情形（<CrossRef id="algorithms.binary-search" />）：$k = 1$，`combine` 把唯一的子解直接交回。

## 递归设计的正确性

正确性由对规模的归纳给出：假设每个更小的子实例都返回满足定义的正确解，`combine` 把这些子解与原实例的必要信息合成为 $P$ 的解；基本情形是规模落到可解范围、直接返回的那一步。调用树上每个结点的解都正确，根结点的解就是整个问题的解（与 <CrossRef id="algorithms.correctness" /> 的归纳同形）。

归纳假设必须覆盖每一个实际子调用：归并排序的两个半区都要满足各自的规约，只假设一个成立会漏掉另一个分支。终止的硬条件是递归路径上的某个终止度量严格下降，通常就是问题规模；规模是非负整数，每次递归取到更小的实例，递归深度有限，算法终止。

`divide` 与 `combine` 可以读原实例的数据，本层工作量是这一次调用执行的全部非递归工作，很多分治算法的 $\Theta(n)$ 级工作恰恰发生在拆分与合并阶段。子问题是同一份状态沿不同递归路径反复出现时，工作量上升，方案仍然成立；把重复状态折叠起来就是记忆化与动态规划（<CrossRef id="algorithms.dynamic-programming" />）。

## 拆分比例决定深度

两个子问题的规模按固定比例缩小（各 $n/2$、三段各 $n/3$）时，调用树的深度是 $\Theta(\log n)$；每次只把规模减一时，深度是 $\Theta(n)$。把每一层的成本与层数写下来是一条 <Term id="recurrence">递推式</Term>，它的解从调用树上读，这一步交给 <CrossRef id="algorithms.recurrences-and-call-trees" />。

同一个「递归排好两半、再合并」的骨架，只改拆分比例，深度就分开：

```python run id="alg.techniques.split-ratio"
def merge(left, right):
    out, i, j = [], 0, 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]: out.append(left[i]); i += 1
        else: out.append(right[j]); j += 1
    return out + left[i:] + right[j:]

def half(values, depth=0):
    if len(values) <= 1:
        return values, depth + 1
    middle = len(values) // 2
    left, ldeep = half(values[:middle], depth + 1)
    right, rdeep = half(values[middle:], depth + 1)
    return merge(left, right), max(ldeep, rdeep)

def one_off(values, depth=0):
    if len(values) <= 1:
        return values, depth + 1
    rest, deep = one_off(values[1:], depth + 1)
    head, position = values[0], 0
    while position < len(rest) and rest[position] < head:
        position += 1
    return rest[:position] + [head] + rest[position:], deep

for size in (8, 64, 512):
    values = list(range(size, 0, -1))
    hsorted, hdepth = half(values)
    osorted, odepth = one_off(values)
    print(f"n={size:>4} half-split depth {hdepth:>4} one-off depth {odepth:>5} both sorted {hsorted == sorted(values) == osorted}")
```

折半的深度随规模取对数（$n = 512$ 时深度 10），每次只切出一个元素的深度与规模同阶（同一行 512），两种写法都排对。规模只减一时每层只让问题小一点，层数与 $n$ 同阶，总工作量也随之从 $n \log n$ 退化成 $n^2$——普通快速排序在极端不平衡划分下递归深度退化是同一个机制。

终止与深度是两件事：只要每次递归的规模严格下降，深度就有限、算法一定终止；只有当每次把规模缩到至多固定比例 $\rho n$（$\rho < 1$）时，深度才是 $\Theta(\log n)$。普通快速排序的划分不保证比例，对较小的一侧递归、较大的一侧改成迭代可以把栈控制在 $O(\log n)$，那是对实现的要求。递归栈空间随深度增长，<CrossRef id="algorithms.recurrences-and-call-trees" /> 从调用树上读出这一项。

## 什么时候不能分治

失效点都在设计上：

- **子问题不再是同一类型**。拆分得到的实例必须能交给同一个 `solve`。若切出来的子问题换了问题、缺少原问题的一部分约束，递归调用没有可用的规约，方案在这里断掉。
- **合并的成本超过拆分省下的**。把问题拆小，只有在子问题各自变便宜、并且合并代价被这层省下的工作覆盖时才有意义。若 `combine` 要重新扫描原实例的绝大部分，每层付 $\Theta(n)$、共 $\Theta(\log n)$ 层，总成本相对不拆的版本没有改善。
- **分治不总是更快**。增长阶相同的两份实现，常数因子与调用开销可以决定胜负。把一个线性扫描求最小值改写成递归对半的版本：传索引范围时结论仍是 $\Theta(n)$，只多付递归调用的常数；每层都切片的写法每层复制一遍 $\Theta(n)$、共 $\Theta(\log n)$ 层，成本变成 $\Theta(n \log n)$——同一个想法，两种实现，两个答案。要说明这类差别，机制计数（调用次数、元素移动次数）比计时可靠。
