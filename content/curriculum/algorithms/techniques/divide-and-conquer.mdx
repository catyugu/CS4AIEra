排序一个序列可以这样安排：把它切成两半，分别排好，再把两个有序半区合成一个有序序列。每一步把规模 $n$ 的问题换成两个同类型的、规模 $n/2$ 的问题，再用这些子问题的答案拼出原答案。二分查找是少了第二个子问题的退化情形（<CrossRef id="algorithms.binary-search" />）：每次只保留一个仍可能包含目标的半区。

归并排序从头到尾是同一个例子：拆分在哪里发生、子问题带着什么契约被解掉、合并用什么信息把两个子解拼成一个解。

## 拆分、求解、合并

待解问题记为 $P$，它的抽象契约写清两端：

| 契约 | 内容 |
| --- | --- |
| `solve(P)` 的前置条件 | $P$ 是这一类问题的一个实例，且规模在可解范围内 |
| `solve(P)` 的后置条件 | 返回 $P$ 的一个解，且该解满足这类问题的定义 |

分治版本只用三个动作描述：

| 动作 | 说明 |
| --- | --- |
| `divide(P)` | 产生有限个更小的同类子实例 $P_1, \dots, P_k$ |
| `conquer` | 递归求解这些子实例 |
| `combine(P, solution_1, \dots, solution_k)` | 用原实例的必要信息与子问题的解，构造 $P$ 的解 |

归并排序把这三个动作落到具体操作上。`divide` 按下标中点把区间切成两半，两个子实例仍是「排好一个区间」这一类型的问题，规模各约一半；`conquer` 对两个半区递归调用同一个 `solve`；`combine` 做一次归并——反复取两个半区当前更小的首元素，一个半区取空后接上另一个的剩余部分，得到整个区间的有序序列。二分查找是 $k = 1$ 的取法，`combine` 把唯一的子解直接交回；归并排序是 $k = 2$、`combine` 真正做事的取法。快速选择只留一个子实例（<CrossRef id="algorithms.selection-and-top-k" />），快速排序留两个（<CrossRef id="algorithms.comparison-sorting" />）。

区间用下标表示，`divide` 只算出两个下标范围，不复制元素。

```python run id="alg.techniques.merge-sort"
def merge(left, right, trace):
    merged, i, j = [], 0, 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            merged.append(left[i]); i += 1
        else:
            merged.append(right[j]); j += 1
    merged.extend(left[i:]); merged.extend(right[j:])
    trace.append((tuple(left), tuple(right), tuple(merged)))
    return merged


def sort(values, trace):
    if len(values) <= 1:
        return values
    middle = len(values) // 2
    left = sort(values[:middle], trace)
    right = sort(values[middle:], trace)
    return merge(left, right, trace)


data = [7, 2, 5, 3, 8, 1, 6, 4]
trace = []
ordered = sort(data, trace)
for left, right, merged in trace:
    print(f"combine {left} + {right} -> {merged}")
print(f"sorted {ordered}")
print(f"combine steps: {len(trace)}  (n - 1 = {len(data) - 1})")
```

八个数产生七次 `combine`（$n - 1$ 次）。输出按发生顺序排列：先把长度为 1 的区间两两合成，再往上一层合成更长的区间，最后一步把两个半区拼成整个序列。叶子是长度为 1 的区间，`combine` 从最下一层开始往上拼。

## 递归设计的正确性骨架

正确性由对规模的归纳给出：假设每个更小的子实例都返回满足定义的正确解，`combine` 把这些子解与原实例的必要信息合成为 $P$ 的解；基本情形是规模落到可解范围、直接返回的那一步。于是调用树上每个结点的解都正确，根结点的解就是整个问题的解（与 <CrossRef id="algorithms.correctness" /> 的归纳同形）。

归纳假设必须覆盖每一个实际子调用：归并排序的两个半区都要满足各自的契约，只假设一个成立会漏掉另一个分支。唯一的硬条件是**递归路径上的某个良基度量严格下降**——通常就是问题规模。规模是非负整数，每次递归都取到更小的实例，所以递归深度有限，算法终止。

有两句话常被当成分治的定义条件，它们都不是：

**「子问题必须互不重叠」**：这里说的是同一个子问题状态沿不同的递归路径出现，输入数据是否相交是另一回事。即使有重复状态，也不必然导致指数级工作，具体爆炸到什么程度由递推式决定：朴素斐波那契是高度重复导致指数工作的例子，不是一个一般定理。

**「combine 只能用子问题的解」**：`divide` 与 `combine` 完全可以读原实例的数据。很多分治算法的 $\Theta(n)$ 级工作恰恰发生在拆分与合并阶段；本层工作量是这一次调用执行的全部非递归工作，从来不专指「合并子解」。

重复状态是**效率特征**，它决定工作量，不影响方案是否成立，也是动态规划的一条入口：把调用树里反复出现的同一个状态折叠起来，树就变成一张状态 DAG，记忆化与动态规划利用的正是这种复用机会（<CrossRef id="algorithms.dynamic-programming" />）。

## 拆分比例对成本的影响

两个子问题的规模要么按固定比例缩小（各 $n/2$、三段各 $n/3$），要么不。这个区别决定调用树的深度：按固定比例缩小时深度是 $\Theta(\log n)$，只把规模减一时深度是 $\Theta(n)$。把每一层的成本与层数写下来就是一条 <Term id="recurrence">递推式</Term>，它的解要从调用树上读。这一步交给 <CrossRef id="algorithms.recurrences-and-call-trees" />，这里只把结论用到拆分比例上：规模按固定比例缩小时深度是对数，对数底由缩小比例决定；规模只减一的递归把层数从对数推成 $n$。

同一个「递归求解、再合并」的骨架，只改拆分比例，深度就分开：

```python run id="alg.techniques.split-ratio"
def merge(left, right):
    out, i, j = [], 0, 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]: out.append(left[i]); i += 1
        else: out.append(right[j]); j += 1
    return out + left[i:] + right[j:]

def half(values, depth=0):
    if len(values) <= 1:
        return values, depth + 1
    middle = len(values) // 2
    left, ldeep = half(values[:middle], depth + 1)
    right, rdeep = half(values[middle:], depth + 1)
    return merge(left, right), max(ldeep, rdeep)

def one_off(values, depth=0):
    if len(values) <= 1:
        return values, depth + 1
    rest, deep = one_off(values[1:], depth + 1)
    head, position = values[0], 0
    while position < len(rest) and rest[position] < head:
        position += 1
    return rest[:position] + [head] + rest[position:], deep

for size in (8, 64, 512):
    values = list(range(size, 0, -1))
    hsorted, hdepth = half(values)
    osorted, odepth = one_off(values)
    print(f"n={size:>4} half-split depth {hdepth:>4} one-off depth {odepth:>5} both sorted {hsorted == sorted(values) == osorted}")
```

折半的深度随规模取对数（$n = 512$ 时深度 10），每次只切出一个元素的深度与规模同阶（同一行 512），两种写法都排对。规模只减一时每层只让问题小一点，层数与 $n$ 同阶，总工作量也随之从 $n \log n$ 退化成 $n^2$——这是普通快速排序在极端不平衡划分下递归深度退化的同一机制。

终止与深度是两件事：只要每次递归的规模严格下降，深度就有限、算法一定终止；只有当每次把规模缩到至多固定比例 $\rho n$（$\rho < 1$）时，深度才是 $\Theta(\log n)$。普通快速排序的划分不保证比例，对较小的一侧递归、较大的一侧改成迭代可以把栈控制在 $O(\log n)$，但那是对实现的要求，不是分治自带的性质。递归栈空间随深度增长，<CrossRef id="algorithms.recurrences-and-call-trees" /> 从调用树上读出这一项。

## 第二个例子：Karatsuba

归并排序的 `divide` 产生两个规模减半的子问题，合并要线性时间。Karatsuba 乘法走的是另一条路：它**减少子问题的个数**。把两个数各拆成高低两半（$x = x_1 B + x_0$，$y = y_1 B + y_0$），朴素做法要算四个半长乘积，Karatsuba 用三次乘法凑出同一个结果：

$$
\begin{aligned}
z_0 &= x_0 y_0, \\
z_2 &= x_1 y_1, \\
z_1 &= (x_0 + x_1)(y_0 + y_1) - z_0 - z_2, \\
x y &= z_2 B^2 + z_1 B + z_0.
\end{aligned}
$$

其中 $z_1$ 恰好等于 $x_0 y_1 + x_1 y_0$。子问题个数从四降到三，本层工作是线性的，成本的增长阶随之从 $n^2$ 降到 $n^{\log_2 3} \approx n^{1.585}$。

```python run id="alg.techniques.karatsuba"
def karatsuba(x, y, counter):
    """Karatsuba on integers; counter[0] records scalar multiplications."""
    if x < 10 or y < 10:
        counter[0] += 1
        return x * y
    half = max(len(str(x)), len(str(y))) // 2
    base = 10 ** half
    x1, x0 = divmod(x, base)
    y1, y0 = divmod(y, base)
    z0 = karatsuba(x0, y0, counter)
    z2 = karatsuba(x1, y1, counter)
    z1 = karatsuba(x0 + x1, y0 + y1, counter) - z2 - z0
    return z2 * base * base + z1 * base + z0


digits = 32
x = int("7" * digits)
y = int("3" * digits)
counter = [0]
product = karatsuba(x, y, counter)
print(f"{digits}-digit product correct: {product == x * y}")
print(f"scalar multiplications performed: {counter[0]}")
print(f"model of three half-size calls per level: 3^5 = {3 ** 5}, naive 4^5 = {4 ** 5}")
```

真实实现的三次递归并不总是恰好一半规模：$(x_0 + x_1)$ 会多出一位，实测乘法次数 381 高于 $3^k$ 的整齐模型 243，远低于朴素做法的 1024。指数 $\log_2 3$ 来自对调用树的分析，这组数字只说明实现与整齐模型之间没有一一对应。

## 什么时候不能分治

失效点都在设计上：

- **子问题不再是同一类型**。拆分得到的实例必须能交给同一个 `solve`。若切出来的子问题换了问题、缺少原问题的一部分约束，递归调用没有可用的契约，方案在这里断掉。
- **合并的成本超过拆分省下的**。把问题拆小，只有在子问题各自变便宜、并且合并代价被这层省下的工作覆盖时才有意义。若 `combine` 必须重新扫描原实例的绝大部分，每层付 $\Theta(n)$、共 $\Theta(\log n)$ 层，总成本相对不拆的版本没有改善。
- **分治不总是更快**。增长阶相同的两份实现，常数因子与调用开销可以决定胜负。把一个线性扫描求最小值改写成递归对半的版本：传索引范围时结论仍是 $\Theta(n)$，只多付递归调用的常数；每层都切片的写法每层复制一遍 $\Theta(n)$、共 $\Theta(\log n)$ 层，成本变成 $\Theta(n \log n)$——同一个想法，两种实现，两个答案。要说明这类差别，机制计数（调用次数、元素移动次数）比计时可靠。
