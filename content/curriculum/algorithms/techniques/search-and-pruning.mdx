有些问题要求状态记住整段历史：已经用过哪些物品、走过哪些点、填过哪些格。把状态显式写出来、同一个状态只求一次，能省下多少取决于状态空间有多大：状态由两个端点决定时（区间型状态）是 $\Theta(n^2)$；按容量建表的背包状态数是 $\Theta(nW)$——它对容量 $W$ 是多项式，对二进制编码后的输入长度只是伪多项式。状态空间大到填不完时，改沿隐式搜索树**选择性枚举部分解，再用剪枝砍掉不可能包含答案的子树**。分治是把问题拆开、贪心是提前作出选择、动态规划是把重复状态合并；搜索骨架不依赖前三种机制，只要求走的过程能证明自己没漏掉答案，实际算法可以把它们组合起来用。

## 什么时候状态无法合并

回忆 <CrossRef id="algorithms.dynamic-programming" /> 判断状态是否足够的办法：给定状态，剩余子问题的答案唯一吗？带时间窗的路径成本不满足这一条，因为「已经晚了多久」不属于当前顶点；把这段历史塞进状态，状态数就爆炸。搜索承认这一点：状态保持完整，代价是状态数不再可控。

动手搜索之前，先试一次压缩状态：如果两个部分解在压缩后落到同一个状态、并且该状态决定的后继答案相同，那份历史就不必保留，重复的部分可以合并。合并之后的状态空间仍可能是指数级或伪多项式级别、大到无法直接填满，这时搜索依然合适。搜索与重复状态消除、记忆化、支配消去并不互斥，可以叠在同一套枚举骨架上。

## 搜索树与完全性

把问题写成搜索树：

| 名称 | 含义 |
| --- | --- |
| 节点 | 一个部分解（partial assignment） |
| 根 | 空的部分解 |
| 分支 | 从部分解出发的一次可扩展选择 |
| 叶子 | 无法再扩展的部分解：要么是一个解，要么被约束挡住 |

首先要证明搜索是**完全**的：每个解都对应搜索树中的某个节点，否则枚举漏解。保证这条性质的是分支的定义——分支必须穷尽「当前节点所有可能的下一个选择」，包括「这个位置什么都不放」这样的选择；剪枝只在已经生成节点的前提下删除节点，改变不了枚举的集合。

搜索树和状态图是同一个问题的两种表示。搜索树可以看作把状态图按到达路径展开：同一个状态若由多条路径到达，在状态图里仍是一个顶点，在搜索树里却会出现为多个节点——这正是搜索重复展开的来源。能安全合并这些节点时，可以把记忆化叠上去，或者换成按拓扑序填表的动态规划。

## 可行性剪枝为什么正确

剪枝是判定「这个节点的整棵子树里不含任何可行解」，然后整棵跳过。需要证明的是关于**整棵子树**的命题：这一节点的子树里不存在任何可行的完成。

常见的充分条件是约束「违反之后无法修复」——n 皇后里「两个皇后同列或同对角线」一旦出现就无法撤销，满足这一条；而「前缀和不超过 100」这类可以靠后续选择拉回来的约束不满足它，按它剪枝会漏解。条条约束都不可修复只是常用情形，不是可行性剪枝的定义。一次尚可修复的违约不足以剪掉子树：若当前约束可以修复，要么换一条真正不可修复的约束来剪，要么把可修复的量并进状态。

检查约束本身要花时间：只有当这次判断的成本比它省下的搜索成本值得时，可行性剪枝才带来收益。

另一类剪枝判定的是子树不可能优于当前最优解，它需要另一套论证——一个覆盖整棵子树的界 <CrossRef id="algorithms.branch-and-bound" />。

## 回溯模板与撤销

本课约定用深度优先的枚举加上可行性剪枝来演示回溯，模板只有三步，顺序固定：

1. **选择**：把当前节点的第 $k$ 个可扩展选择写进部分解。
2. **递归**：进入子节点，继续枚举。
3. **撤销**：退出子节点前把部分解恢复成进入前的样子。

撤销这一步在**原地修改共享状态**的写法里是模板的一部分，不是优化：`choose` 若就地改了供兄弟分支共享的结构，返回前必须恢复，否则后续分支带着上一个分支的选择继续走，枚举的集合会变，结果静默出错。把状态复制一份传给子调用、或让状态不可变，就不存在显式撤销；n 皇后的实现原地修改 `columns`，因此每一步都要 `pop` 回来。

下面这份枚举把约束检查放在一个开关 `prune` 上：打开时每放置一个皇后就立刻检查列与对角线，关闭时一路放到第 $n$ 行、只在叶子处验证整个排列。两种情况给出同一个解数，访问的节点数却相差几个数量级。

```python run id="alg.search.queens"
def queens(n, prune=True):
    """Fill rows top to bottom; prune=False defers the constraint to the leaves."""
    columns, nodes, solutions = [], 0, 0

    def safe():
        return all(columns[i] != columns[j] and abs(columns[i] - columns[j]) != i - j
                   for i in range(len(columns)) for j in range(i))

    def place(row):
        nonlocal nodes, solutions
        nodes += 1
        if row == n:
            if safe():
                solutions += 1
            return
        for column in range(n):
            columns.append(column)
            if not prune or safe():
                place(row + 1)
            columns.pop()

    place(0)
    return solutions, nodes


print(f"{'n':>2} {'solutions':>9} {'unpruned':>9} {'nodes pruned':>12} {'nodes unpruned':>15}")
for n in (4, 5, 6, 7):
    solutions, pruned = queens(n)
    plain, unpruned = queens(n, prune=False)
    print(f"{n:>2} {solutions:>9} {plain:>9} {pruned:>12} {unpruned:>15}")
```

同样的枚举，只在叶子上检查约束，访问的节点数就涨到整棵完全树的规模：$n = 6$ 时是 $153$ 对 $55987$，$n = 7$ 时是 $552$ 对 $960800$——未剪枝的那一列正是 $\sum_{k=0}^{n} n^k$，剪枝省下的就是这些中间节点。两个版本给出的解数逐行相同（$n = 7$ 时两列都是 $40$）——**经证明安全的剪枝只改变需要访问的节点，不改变目标答案**。

## 终止、成本与空间

**终止**需要两件事：搜索树的深度有界（每一步都消耗掉一个待定的选择，深度不超过选择的总数），以及每个节点的分支数有限。剪枝只会让树更小，不影响终止。

**成本**严格说是各访问节点处理成本之和；若每个访问节点的处理成本都有统一上界 $C(n)$，才写成 $O(N \cdot C(n))$（$C$ 不随节点变化，但可以随规模增长）。结论属于最坏情形：可行性剪枝后的节点数没有通用公式，它取决于实例与分支顺序；若树深至多 $d$、每个节点至多 $b$ 个子节点，最坏情况访问 $O(b^d)$ 个节点，形成完整 $b$ 叉树（$b > 1$）时是 $\Theta(b^d)$——这正是搜索不能替代多项式算法的原因。

**空间**：深度优先搜索同时保留的是当前路径上的 $O(d)$ 个活动栈帧，总辅助空间取决于这些栈帧各自保存多少状态。每层的状态是 $O(1)$、或者原地修改加撤销时，辅助空间就是 $\Theta(d)$；n 皇后原地维护 `columns`，每个栈帧只多保存一列。许多搜索实现因此可以避免保存整张状态表。换成广度优先或最优优先则需要保存前沿，空间由最大前沿宽度决定，最坏情况下可以是指数级。
