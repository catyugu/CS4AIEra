在 $n \times n$ 的棋盘上放 $n$ 个皇后，任意两个不能在同一列或同一条对角线上。逐行决定列号：第 0 行先选一列，再选第 1 行，直到第 $n-1$ 行。每个中间结果是一份**部分解**，写成已选列号组成的元组，`(2,0)` 表示第 0 行选第 2 列、第 1 行选第 0 列。前两行的选择展开成一棵树：

```text
()
├── (0)
│   ├── (0,0)  ✗
│   ├── (0,1)  ✗
│   ├── (0,2)
│   └── (0,3)
├── (1)
│   ├── (1,0)  ✗
│   ├── (1,1)  ✗
│   ├── (1,2)  ✗
│   └── (1,3)
├── (2)
│   ├── (2,0)
│   ├── (2,1)  ✗
│   ├── (2,2)  ✗
│   └── (2,3)  ✗
└── (3)
    ├── (3,0)
    ├── (3,1)
    ├── (3,2)  ✗
    └── (3,3)  ✗
```

标 ✗ 的节点已经把两个皇后放在同一列或同一条对角线上。第 2 行以下只会再往棋盘上加皇后，改不掉前两行的位置，所以这些节点的整棵子树里没有一种合法摆法；在生成这样的节点时直接放弃它，连同它下面所有尚未展开的分支。要是不做这次判断、一直放到第 $n$ 行末尾才验证，完整摆法有 $n^n$ 种，$n = 8$ 时是 $8^8 = 16777216$ 种。

节点是一份部分解，边是一次选列，这棵把同一个问题的所有部分解按构造顺序铺开的树叫**搜索树**。自上而下构造解、在某个节点走不通时退回上一层换下一个选择，是**回溯**；判定一个节点的子树里没有解、不再展开它，是**剪枝**。砍掉的是一整棵子树，它不会在别处被重新走一遍，所以剪之前要确定子树里确实没有解。

## 搜索树与完全性

把逐行决定列号的过程一般化：

| 名称 | 含义 |
| --- | --- |
| 节点 | 一个部分解（partial assignment） |
| 根 | 空的部分解 |
| 分支 | 从部分解出发的一次可扩展选择 |
| 叶子 | 无法再扩展的部分解：要么是一个解，要么被约束挡住 |

枚举是**完全**的，当每个解都对应搜索树中的某个节点，否则会漏解。保证这条性质的是分支的定义——分支穷尽「当前节点所有可能的下一个选择」，包括「这个位置什么都不放」这样的选择；剪枝只在已经生成节点的前提下删除节点，改变不了枚举的集合。

搜索树和状态图是同一个问题的两种表示：同一个状态若由多条路径到达，在状态图里是一个顶点，在搜索树里则是多个节点，搜索因此会重复展开同一个状态。把状态压缩后，如果同一个压缩状态决定的后继答案相同（判断状态是否足够的办法见 <CrossRef id="algorithms.dynamic-programming" />），跨路径重复的部分可以合并，于是能在同一套枚举骨架上叠上记忆化，或改成按拓扑序填表的动态规划；合并后的状态空间仍可能大到填不满，此时搜索仍然合适。

## 可行性剪枝为什么正确

剪枝判定的是「这个节点的整棵子树里不含任何可行解」，然后整棵跳过。需要证明的是关于**整棵子树**的命题：这个节点的子树里不存在任何可行的完成。

一个常用的充分条件是约束「违反之后无法修复」——n 皇后里「两个皇后同列或同对角线」一旦出现就无法撤销，满足这一条。而「前缀和不超过 100」这类可以靠后续选择拉回来的约束不满足它，按它剪枝会漏解。约束条条都不可修复是常用情形，可行性剪枝的定义只要求上面那条覆盖整棵子树的命题。一次尚可修复的违约不足以剪掉子树：若当前约束可以修复，要么换一条无法修复的约束来剪，要么把可修复的量并进状态。

检查约束本身要花时间：只有当这次判断的成本比它省下的搜索成本值得时，可行性剪枝才带来收益。

另一类剪枝判定的是子树不可能优于当前最优解，它需要另一套论证——一个覆盖整棵子树的界 <CrossRef id="algorithms.branch-and-bound" />。

## 回溯模板与撤销

深度优先的枚举加上可行性剪枝构成回溯模板，只有三步，顺序固定：

1. **选择**：把当前节点的第 $k$ 个可扩展选择写进部分解。
2. **递归**：进入子节点，继续枚举。
3. **撤销**：退出子节点前把部分解恢复成进入前的样子。

撤销是模板的一部分：`choose` 若就地改了供兄弟分支共享的结构，返回前必须恢复，否则后续分支带着上一个分支的选择继续走，枚举的集合会变，结果静默出错。把状态复制一份传给子调用、或让状态不可变，就不存在显式撤销；n 皇后的实现原地修改 `columns`，因此每一步都要 `pop` 回来。

下面的枚举把约束检查放在一个开关 `prune` 上：打开时每放置一个皇后就立刻检查列与对角线，关闭时一路放到第 $n$ 行、只在叶子处验证整个排列。两种情况给出同一个解数，访问的节点数却相差几个数量级。

```python run id="alg.search.queens"
def queens(n, prune=True):
    """Fill rows top to bottom; prune=False defers the constraint to the leaves."""
    columns, nodes, solutions = [], 0, 0

    def safe():
        return all(columns[i] != columns[j] and abs(columns[i] - columns[j]) != i - j
                   for i in range(len(columns)) for j in range(i))

    def place(row):
        nonlocal nodes, solutions
        nodes += 1
        if row == n:
            if safe():
                solutions += 1
            return
        for column in range(n):
            columns.append(column)
            if not prune or safe():
                place(row + 1)
            columns.pop()

    place(0)
    return solutions, nodes


print(f"{'n':>2} {'solutions':>9} {'unpruned':>9} {'nodes pruned':>12} {'nodes unpruned':>15}")
for n in (4, 5, 6, 7):
    solutions, pruned = queens(n)
    plain, unpruned = queens(n, prune=False)
    print(f"{n:>2} {solutions:>9} {plain:>9} {pruned:>12} {unpruned:>15}")
```

同样的枚举，只在叶子上检查约束，访问的节点数就涨到整棵完全树的规模：$n = 6$ 时是 $153$ 对 $55987$，$n = 7$ 时是 $552$ 对 $960800$——未剪枝的那一列正是 $\sum_{k=0}^{n} n^k$，剪枝省下的就是这些中间节点。两个版本给出的解数逐行相同（$n = 7$ 时两列都是 $40$）——**经证明安全的剪枝只改变需要访问的节点，不改变目标答案**。

## 终止、成本与空间

**终止**需要两件事：搜索树的深度有界（每一步都消耗掉一个待定的选择，深度不超过选择的总数），以及每个节点的分支数有限。剪枝只会让树更小，不影响终止。

**成本**严格说是各访问节点处理成本之和；若每个访问节点的处理成本都有统一上界 $C(n)$，才写成 $O(N \cdot C(n))$（$C$ 不随节点变化，但可以随规模增长）。结论属于最坏情形：可行性剪枝后的节点数没有通用公式，它取决于实例与分支顺序；若树深至多 $d$、每个节点至多 $b$ 个子节点，最坏情况访问 $O(b^d)$ 个节点，形成完整 $b$ 叉树（$b > 1$）时是 $\Theta(b^d)$——搜索因此不能替代多项式算法。

**空间**：深度优先搜索同时保留的是当前路径上的 $O(d)$ 个活动栈帧，总辅助空间取决于这些栈帧各自保存多少状态。每层的状态是 $O(1)$、或者原地修改加撤销时，辅助空间就是 $\Theta(d)$；n 皇后原地维护 `columns`，每个栈帧只多保存一列。许多搜索实现因此可以避免保存整张状态表。换成广度优先或最优优先则需要保存前沿，空间由最大前沿宽度决定，最坏情况下可以是指数级。
