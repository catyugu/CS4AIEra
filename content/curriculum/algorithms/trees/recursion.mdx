`total([1, 2, 3])` 要算一串数的和。函数每次取出首元素，把余下的列表交给同一次函数调用，等它返回后再相加：

$$
\text{total}([1, 2, 3]) = 1 + \text{total}([2, 3]) = 1 + (2 + \text{total}([3])) = 1 + (2 + (3 + \text{total}([])))
$$

空列表没有首元素可拿，`total([])` 直接返回 $0$，不再调用自己；剩下的加法从最里层往外逐层算回：$3 + 0 = 3$，$2 + 3 = 5$，$1 + 5 = 6$。同一段代码收缩了三次，每次交给下一次调用的列表都比上一次少一个元素。

```python
def total(values):
    if not values:                          # base case
        return 0
    return values[0] + total(values[1:])     # every call is on a shorter list
```

## 基本情况与递归情形

展开里出现两种状态。空列表这一种不再调用 `total`，直接给出结果——这是**基本情况（base case）**。非空列表这一种把首元素留在当前调用、把 `values[1:]` 交给下一次 `total`——这是**递归情形（recursive case）**，它含一次递归调用。基本情况常常就是最小输入，但定义本身只要求「不再递归」，不要求它是某个尺寸的最小值。

递归情形要求递归调用作用在更小的状态上。每次调用列表少一个元素，长度在每一次递归调用处严格下降，最终落在最小值 $0$，也就是基本情况。度量严格下降是定义的一部分：递归情形的调用若落在同样的状态上，定义没有前进，后面的论证都无处落脚。

度量不必是输入的直观尺寸。图遍历里图本身不变小，度量取「尚未访问」的集合大小；每写一行递归调用，都要能说出它让选定的度量小了多少。

**实现边界**：`values[1:]` 在 Python 里复制出一份新列表，切片本身有成本；每次调用列表更短这一点不受影响。

## 归纳与递归同形

照着定义写出函数之后，有两个问题要用同一份定义回答：这个函数返回的确实是它应当返回的结果吗（部分正确性），递归调用又会不会一路走下去、始终走不到基本情况（终止）。两者用同一个良基度量论证，这个度量就写在递归情形里，每次递归调用让它严格下降。递归函数的正确性用良基归纳论证，步骤与定义一一对应。先证**部分正确**，再独立证明终止（见 <CrossRef id="algorithms.correctness" />）：

1. **基本情况**：每个基本情况上的返回值满足后置条件。
2. **递归情形**：归纳假设是「对所有满足前置条件、且良基秩严格更小的递归状态 $y$，调用一旦返回，其返回值就满足相应的后置条件」；再证明每个递归子调用都满足前置条件，由它的后置条件推出当前调用一旦返回就满足后置条件。

归纳假设只说「若子调用返回」，因此它没有偷偷假设终止——终止必须单独证明。对纯函数，它可以简化成「若子调用返回，则其返回值满足后置条件」。

归纳假设是一个参数化命题，把它实例化到每个实际子调用上，就得到那次递归调用的后置条件；论证因此不必展开计算过程。以取最大值为例：

```python
def largest(values):
    if len(values) == 1:
        return values[0]
    rest = largest(values[1:])
    return values[0] if values[0] > rest else rest
```

前置条件：`values` 是非空有限序列，元素属于同一个全序域。后置条件：返回值是输入中的元素，且输入中不存在比它更大的元素。基本情况里唯一的元素即答案；递归情形里，进入分支时有 `len(values) > 1`，所以 `values[1:]` 仍非空，递归调用满足前置条件；按归纳假设 `rest` 是 `values[1:]` 中不小于任何元素的值，返回值取 `values[0]` 与 `rest` 中较大者，它既不小于 `values[0]`，也不小于 `values[1:]` 中的任何元素，后置条件成立。递归调用满足前置条件这一步必须写出来——只有前置条件成立，才能使用它的后置条件。

命题实例化到子问题上，前提是后置条件说的量与该次调用的参数对得上。一个从下标 `index` 开始求和的辅助函数，后置条件是「返回值等于 `values[index:]` 的和」；若把一个带初值 `running` 的累加版本也写成这条后置条件，归纳假设覆盖的命题与它实际返回的量（`running` 加上后缀和）就不是同一个，论证再整齐也不成立。

归纳假设要覆盖每一个实际递归子调用。一次调用可能沿多于一条更小的路径下去：斐波那契的递归情形用到规模 $n-1$ 与 $n-2$ 两个调用，只假设 $n-1$ 这一个点成立就覆盖不到另一个分支。逻辑上必须做到的是覆盖所有实际子调用；「对所有良基秩更小的状态成立」是达成它的统一模板，也让归纳与终止共用同一个度量。

与 <CrossRef id="algorithms.correctness" /> 的循环论证对照：循环的三步是初始化、保持、退出，性质要在每个迭代边界成立；递归只有两步，其中「保持」被换成了归纳假设。共同的纪律是覆盖所有路径——遗漏一轮迭代与遗漏一个递归分支，同样让论证失效。

## 终止由度量给出

基本情况存在并不保证终止。对每个满足前置条件的调用，终止接口由三件事组成：

1. 本次调用中**除递归子调用之外**的工作会终止；
2. 每个递归子调用仍满足前置条件；
3. 每个递归子调用的良基秩严格下降。

由良基归纳即可推出所有满足前置条件的调用都在有限步内结束。度量取值落在没有无穷下降链的集合上（非负整数、序列长度、有限集合的大小都属于这类）；「严格递减 + 有下界」不够，$1, 1/2, 1/4, \dots$ 严格递减且有下界却可以无限进行。

某条递归边上选定的度量没有严格下降，只说明这个度量不足以完成终止证明，需要换一个更合适的（组合度量、字典序度量都常见）——它本身推不出程序不终止。例如状态按 $(n, 0) \to (n, 1) \to (n-1, 0)$ 变化时，只看 $n$ 第一步没有下降，也确实不能当作终止证明；但对状态对的字典序换上排名函数 $\mu(n, p) = (n, 1 - p)$ 之后，$\mu(n, 0) = (n, 1) > \mu(n, 1) = (n, 0) > \mu(n-1, 0) = (n-1, 1)$，每一步都严格下降，终止照样可证。

运行时不会让递归无限延伸：深度超过上限时抛 `RecursionError`（当前限制由 [sys.getrecursionlimit](https://docs.python.org/3/library/sys.html#sys.getrecursionlimit) 读取、由 [sys.setrecursionlimit](https://docs.python.org/3/library/sys.html#sys.setrecursionlimit) 调整；它属于解释器的运行时配置，Python 算法语义里没有这个常数；可支持的上限还受平台影响，见 <CrossRef id="python.runtime-vs-language" />）。它是防止栈被耗尽的安全网，与算法的终止性属于两个层次：抽象执行模型里问的是调用链是否有穷，运行时问的是一条有限的调用链是否还落在当前运行时的深度限制内。因此终止证明完整的递归（例如每步长度严格下降的线性递归）在输入足够大时同样可能触发 `RecursionError`；反过来说，`RecursionError` 不能区分「逻辑上无限递归」与「逻辑上有限但太深」。终止仍要由度量论证。

```python run id="alg.recursion.termination"
def hops(remaining, stride):
    """Precondition: remaining and stride are integers, and stride > 0.

    Postcondition: hops of length stride needed to reach 0 or below.
    """
    hops.calls += 1
    if remaining <= 0:
        return 0
    return 1 + hops(remaining - stride, stride)


def count_hops(remaining, stride):
    hops.calls = 0
    try:
        result = hops(remaining, stride)
    except RecursionError as error:
        return f"{type(error).__name__}: {error}", hops.calls
    return result, hops.calls


for stride in (1, 3):
    result, calls = count_hops(9, stride)
    print(f"remaining=9 stride={stride}: result={result} calls={calls}")
result, calls = count_hops(9, 0)
print(f"remaining=9 stride=0: result={result} calls={calls}")
```

三次调用只有 `stride` 一个参数不同，基本情况与递归情形都没有变。`stride` 为 1 或 3 时度量每次调用严格减小，基本情况在有限步内到达；`stride = 0` 是故意撤掉终止条件的实验：状态原封不动地再次调用自身，抽象模型里的调用链是无限的，在当前运行时里这条无限链先被深度限制截断。它不满足上面那条总正确规约，展示的是「写了基本情况并不自动意味着所有参数选择都能到达它」。打印出的 `calls` 数值取决于运行环境与调用上下文（进入 `hops` 之前解释器已有活动的调用帧），该实验观察的是最终触发 `RecursionError` 这一点。
