在一张表里按键查找，最直接的做法是把查询键与每个已存键比较一遍，比较次数随条目数增长。哈希改变了这个起点：先用键算出一个位置，只在它的候选区域里确认目标。这个位置怎样算出、它把搜索范围缩到多小、为什么缩到某个位置之后一次查找的成本仍然可能失控？

哈希函数把键映射成一个整数，再按容量折到槽位下标：

$$\text{hash}(key) \rightarrow \text{整数}, \qquad \text{bucket} = \text{hash}(key) \bmod \text{capacity}.$$

桶数组有 `capacity` 个槽位。落到同一槽位的键由冲突策略容纳：<Term id="separate-chaining">链地址法</Term>在每个槽位挂一个容器，把落进来的条目都放进去；<Term id="open-addressing">开放寻址法</Term>把条目直接放进槽位，冲突时按 <Term id="probing">探测</Term> 序列依次检查后续槽位。

这份表示维持两条不变量：

1. 任意两个已存条目的键都不相等：每个相等类至多有一个条目；
2. 键 `k` 只可能出现在它自己的候选区域里——`(hash(k) mod capacity)` 那个槽位、挂在它上面的冲突容器，或者从它出发的探测序列。

哈希把搜索范围从整张表缩到一个槽位附近，缩小的代价是可能的键远多于槽位数：两个不同的键算到同一个槽位是必然的，这种情形是 <Term id="hash-collision">哈希冲突</Term>。冲突来自把很大的键空间装进有限的槽位，与哈希函数的分散程度无关。它不破坏正确性，把成本加到定位之后的候选比较上：查找要在候选之间用相等契约确认目标，候选有几个、探测要走多远，决定一次查找比较多少次。

**成本模型**：一次键比较记 1，一次槽位访问记 1。查找成本 = 定位一个槽位 + 在冲突容器或探测序列中与键比较的次数。

```python run id="alg.hash.bucket-index"
def bucket_of(key, capacity):
    """A toy polynomial hash; real functions mix the bits much more thoroughly."""
    total = 0
    for character in key:
        total = total * 31 + ord(character)
    return total % capacity


capacity = 8
keys = ["alpha", "beta", "gamma", "delta", "epsilon", "zeta", "eta", "theta", "iota", "kappa"]
buckets = {}
for key in keys:
    buckets.setdefault(bucket_of(key, capacity), []).append(key)

for index in sorted(buckets):
    chain = buckets[index]
    marker = "  <- collision" if len(chain) > 1 else ""
    print(f"bucket {index}: {chain}{marker}")
print("keys:", len(keys), "| capacity:", capacity, "| buckets used:", len(buckets))
```

这十个键放进 8 个槽位，冲突必然出现：槽位下标只有 `capacity` 种取值，键数超过它时必有两个键共享一个槽位。落点由键与 `capacity` 共同决定，用到的槽位数不超过 `capacity`；具体哪些槽位落了几条键由哈希函数决定。

## 负载因子与探测长度

槽位越满，键越容易挤到一起，探测要走得更远。已存条目数与槽位数之比是 <Term id="load-factor">负载因子</Term> $\alpha = n/m$，它衡量表有多满，也是链长与探测长度的自变量：$\alpha$ 越大，落到同一候选区域的键越多，一次查找在链上或探测序列里扫过的槽位越多。链式表示里这一步对应链长，开放寻址法里对应探测序列的长度。

把 $\alpha$ 压在常数以内是获得常数期望成本的必要结构条件之一，但它不排除所有键落进同一个桶，单凭这一条推不出常数查找；常数期望成本还要加一条关于哈希落点的分布或随机模型。$\alpha$ 到期望探测长度的精确关系由 <CrossRef id="algorithms.average-and-randomized" /> 推导。

## 扩容与摊还

把 $\alpha$ 维持在阈值以内，条目增长到阈值后就要扩容。扩容分配更大的槽位数组，并让每个条目按新容量重新落位，因为槽位下标依赖容量。链地址法在 $\alpha > 1$ 时仍然正确，扩容是为控制链长或探测长度而选的表示策略。

若容量按几何因子增长，前 $n$ 次插入引起的搬移总量是 $\Theta(n)$，分摊到每次插入是常数；这条论证的是一串操作的总成本（<Term id="amortized-analysis">摊还成本</Term>，见 <CrossRef id="algorithms.amortized" />）。某一次触发扩容时，单是搬移仍然需要 $\Theta(n)$ 工作。

```python run id="alg.hash.resizing"
def bucket_of(key, capacity):
    total = 0
    for character in key:
        total = total * 31 + ord(character)
    return total % capacity


def insert_all(keys, max_load=1.0, initial=8):
    """A chained table that doubles its bucket array past max_load."""
    capacity = initial
    table = [[] for _ in range(capacity)]
    size = moved = 0
    for key in keys:
        if size >= capacity * max_load:
            old_items = [item for chain in table for item in chain]
            capacity *= 2
            table = [[] for _ in range(capacity)]
            moved += len(old_items)
            for item in old_items:
                table[bucket_of(item, capacity)].append(item)
        table[bucket_of(key, capacity)].append(key)
        size += 1
    return moved


for count in (1000, 2000, 4000):
    moved = insert_all([f"key-{index:05d}" for index in range(count)])
    print(f"n={count:5d}  entries moved={moved:6d}  moved/n={moved / count:.2f}")
```

$n$ 从 1000 翻到 4000，搬移总数随之增长，`moved/n` 基本不变：搬移的摊还附加成本是常数。这条结论只覆盖扩容引起的搬移，与哈希把键分散得多好无关。

## 冲突退化的两种来源

把 $\alpha$ 压在常数以内，前提是键大致均匀地落到各候选区域。两种机制会打破这条前提。

第一种是哈希分配不均匀：哈希函数把大量键算到同一个槽位时，链或探测序列线性增长，一次查找退化为 $\Theta(n)$ 次比较。常量哈希是最直接的例子，所有键都落进同一个槽位。哈希表把「按键顺序扫描」换成「按哈希位置扫描」，扫描仍然存在，范围由哈希分配决定。

第二种是对抗性输入：哈希函数本身分布良好，但攻击者能预先算出键的落点时，他可以挑出一批全部落到同一槽位的键。为挡住这种构造，Python 的字符串哈希默认混入不可预测的进程级随机值，同一进程内稳定，不同解释器启动之间默认不可预测（[object.__hash__](https://docs.python.org/3/reference/datamodel.html#object.__hash__)）。随机化降低的是预构造冲突输入的可行性，它不把哈希表变成具有最坏常数时间保证的数据结构。

## Python 字典是具体实现

```python run id="alg.hash.python-dict"
import sys

mapping = {}
observations = []
previous = sys.getsizeof(mapping)
for index in range(1000):
    mapping[f"key-{index:05d}"] = index
    current = sys.getsizeof(mapping)
    if current != previous:
        observations.append((len(mapping), current))
        previous = current

print("growth in bytes (entries, bytes):", observations[:4])
print("1 == 1.0 and hashes alike:", 1 == 1.0, hash(1) == hash(1.0))
print("dict keeps one entry for both keys:", {1: "int", 1.0: "float"})
print("first keys in insertion order:", list(mapping)[:3])
```

**体积分档跳变**说明字典的内部存储不随每次插入逐字节增长；`sys.getsizeof` 的观测不足以推出增长因子或重建算法，这里只展示可观察到的分档分配。

**`1` 与 `1.0` 是同一个键**：判等用的是键的相等契约，哈希负责把候选缩小到同一个位置。数值哈希用同一条素数取模规则（[sys.hash_info](https://docs.python.org/3/library/sys.html#sys.hash_info) 给出该模数）。

**迭代顺序属于语言保证**：字典保插入序，从 3.7 起是语言规范保证的行为（[stdtypes](https://docs.python.org/3/library/stdtypes.html#dict)），集合不保证迭代顺序；插入序与成本性质无关，需要按键序迭代要用有序映射（见 <CrossRef id="algorithms.maps-and-sets" />）。
