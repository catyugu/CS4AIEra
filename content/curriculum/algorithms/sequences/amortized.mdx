对一个按需增长的只追加数组连续追加 $m$ 个元素。它的表示与成本固定：元素个数到达已分配容量时容量精确翻倍；未满载的追加写入一个槽位，成本 1；满载的那次追加先把已有的 $c$ 个元素复制进新块，再写入新元素，成本 $c + 1$。判断这个实现能不能用，要看 $m$ 次追加的**总成本**有多高，以及能否把它分摊成每次追加的一个常数。

单次追加的最坏成本可以高达当时的元素个数，昂贵的复制却只发生在容量翻倍的那一次。把它算清楚需要一种对**整串操作**给出总成本界的论证：设 $\sigma = (op_1, \dots, op_m)$ 是一个合法操作序列，$T(\sigma) = \sum_{i=1}^{m} c_i$ 是它的真实总成本，其中 $c_i$ 是第 $i$ 次操作的真实工作量。<Term id="amortized-analysis">摊还分析</Term>给出一条**对所有合法序列统一成立**的总成本界——为每次操作规定一个摊还代价 $\hat c_i$，使任意合法序列都满足 $T(\sigma) \le \sum_{i=1}^{m} \hat c_i$；若还能取 $\hat c_i \le C$，就得到 $T(\sigma) \le C \cdot m$，即每次操作 $O(1)$ 的摊还上界。

## 聚合分析：对整串追加计数

逐次界定一次追加的成本很难，整串追加的总成本却可以直接数出来。复制只发生在容量从 $2^{j-1}$ 扩到 $2^j$ 的那一次追加上，搬运的元素数依次是 $1, 2, 4, \dots$，前 $j$ 次复制加起来不到 $2^j$，因此 $m$ 次追加里复制搬运的元素总数小于 $m$；再加上每次追加写入一个新元素、共 $m$ 次写入，得到

$$
T(m) \;<\; 2m .
$$

除以操作次数，$T(m) / m < 2$：每一次追加摊到不到两次基本操作。这条论证只用对整串操作的计数，没有为任何一次操作单独规定摊还代价，也不要求序列停在某个特定长度上。

把 16 次追加逐次跑出来，容量、实际成本与累计复制量就是要核对的量。

```python run id="alg.amortized.aggregate"
class GrowingArray:
    """A dynamic array that doubles its capacity and reports each append's cost."""

    def __init__(self):
        self.capacity = 0
        self.size = 0
        self.copies = 0

    def append(self):
        if self.size == self.capacity:
            real_cost = 1 + self.size          # write the element, copy the existing ones
            self.copies += self.size
            self.capacity = max(1, self.capacity * 2)
        else:
            real_cost = 1
        self.size += 1
        return self.capacity, real_cost, self.copies


array = GrowingArray()
rows = [array.append() for _ in range(16)]

print(f"{'n':>3} {'capacity':>8} {'real':>5} {'copies':>6}")
for step, (capacity, real, copies) in enumerate(rows, start=1):
    print(f"{step:>3} {capacity:>8} {real:>5} {copies:>6}")

real_costs = [real for _, real, _ in rows]
total_real = sum(real_costs)
writes = len(rows)
print("real costs:", real_costs)
print("sum of real costs:", total_real, "| average T/m:", round(total_real / writes, 2))
print("worst single operation:", max(real_costs))
print("copies + writes:", array.copies, "+", writes, "=", array.copies + writes)
```

16 次追加的实际成本是 $1, 2, 3, 1, 5, 1, 1, 1, 9, 1, 1, 1, 1, 1, 1, 1$，总和 31；其中复制搬运共 15 个元素，写入 16 个，合计 31，小于 $2 \times 16 = 32$。单次最大的一次是 9，出现在把容量从 8 扩到 16 的那次追加上。

$31 / 16 = 1.94$ 是这个具体序列上的**实际平均成本**；聚合计数给出的是一致的摊还界 2，对每个合法序列都成立，与序列具体长什么样无关。整串成本随追加次数线性增长，单次成本却在 1 与 9 之间摆动：偶尔一次 $O(n)$ 的复制，不会让连续 $m$ 次追加变成非线性的总成本。

这条界依赖实现里的扩容策略：复制总量被压到 $m$ 以下，靠的是容量按几何级数增长。固定增量扩容下复制总量随追加次数平方增长，整串成本变成 $\Theta(n^2)$，两种策略的取舍见 <CrossRef id="algorithms.arrays-and-lists" />。

## 摊还上界与单次最坏成本

摊还上界衡量整串操作，单次成本衡量一次调用，两者回答的是不同问题。

```python run id="alg.amortized.latency-gap"
class GrowingArray:
    def __init__(self):
        self.capacity = 0
        self.size = 0

    def append(self):
        if self.size == self.capacity:
            real_cost = 1 + self.size
            self.capacity = max(1, self.capacity * 2)
        else:
            real_cost = 1
        self.size += 1
        return real_cost


count = 64
array = GrowingArray()
append_costs = [array.append() for _ in range(count)]

total = sum(append_costs)
print(
    f"appends={count} actual average T/m={total / count:.2f} "
    f"worst single={max(append_costs)} ratio={max(append_costs) / (total / count):.1f}x"
)
print("same sequence, two questions: throughput and tail latency")
```

这 64 次追加的实际平均成本是 1.98，单次最大的一次是 33，是平均值的 16.6 倍。批量导入、按批处理的流水线关心总吞吐，摊还结论足够；在线路径关心尾延迟，必须看单次最坏成本。把摊还结论当作延迟保证写进接口文档，就是把一个正确的数学结论用在了它不覆盖的场合。序列很短时，渐近记号隐藏的常数与初始化成本可能主导实际时间，仅凭一个 $O(1)$ 的摊还记号不足以判断性能。

## 摊还界的确切含义

把上面的论证收紧成一条定义。摊还界是一条对**所有**合法操作序列成立的界：若存在摊还代价 $\hat c_i$，使任意长度 $m$ 的合法序列 $\sigma$ 都满足

$$
T(\sigma) = \sum_{i=1}^{m} c_i \;\le\; \sum_{i=1}^{m} \hat c_i ,
$$

这组摊还代价就是该序列的摊还界；当 $\hat c_i \le C$ 时得到常数摊还成本 $T(\sigma) \le C \cdot m$。序列可以任意长，也可以在任意位置结束，而前缀本身也是一个合法序列，所以界必须覆盖每一个前缀。

聚合计数不为任何单次操作规定摊还代价。需要逐次代价时，可以给每次操作预先记一笔固定代价（记账法），或把累计差额写成状态函数（势能法）；它们是同一上界的另一种写法，构造出的逐次摊还代价可以比聚合界更松，但只要在任意合法序列上的和都不低于真实总成本就同样有效——上面这串追加既可以由聚合计数得到每次不到 2 的界，也可以给每次操作记 3。

摊还上界**不主张**某一次操作的**真实**成本不超过它自己那次的摊还代价，也不主张未被用掉的摊还代价一定会被用到：$T(\sigma)$ 可以严格小于摊还代价之和，这不影响上界成立。

摊还证明不对序列施加分布。**期望摊还成本**是另一维：它对输入的随机性（或算法的随机位）取期望之后再摊还，因而需要写出所采用的分布，平均情形处理那一维（见 <CrossRef id="algorithms.cost-model" />），概率与期望留给 <CrossRef id="algorithms.average-and-randomized" />。两者可以组合，组合出的结论要把这两个维度分开陈述。
