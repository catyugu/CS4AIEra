一个数组有一百万个元素，读取 `items[900000]` 要先走过前面那 899999 个吗？连续布局把这个问题的答案放进了地址算术：槽位宽度固定时，元素 $i$ 的地址就是基址加上 $i$ 个槽位宽度，这个算术与序列里有多少元素无关，取值因此只做一次地址计算，不产生任何遍历。同一块内存为维持连续付出另一种代价：在中间插入或删除，必须把空出的或要合上的位置之后的元素依次挪动，位置越靠前，需要挪动的槽位越多。

把位置换算成地址得到取值的常数成本，把插入或删除位置之后仍然占着槽位的元素个数数出来得到搬动成本。这两种成本放到具体的分配方式上会进一步分化：同样是连续槽位，固定大小的块和会自己长大的块，为插入、删除和追加付出的代价各不相同。本课程运行时里的 `list` 是会自己长大的那一类：追加一个元素平时只写一个槽位，块满了却要把整块搬进更大的存储。

## 随机访问与顺序查找

下标访问不遍历，查找必须遍历：面对同样多的元素，成本随元素个数增长的是查找，下标访问不随元素个数变化。这一差别来自表示。

```python run id="alg.arrays.access-vs-search"
def search_steps(values, target):
    """Count element comparisons until the target is found."""
    comparisons = 0
    for value in values:
        comparisons += 1
        if value == target:
            return comparisons
    return comparisons


values = list(range(1000))
print("index access needs no comparisons:", values[500])
for target in (values[0], values[500], values[-1]):
    print(f"search for {target:4d}: {search_steps(values, target):4d} comparisons")

values.append(2000)
print("a miss scans the whole input:", search_steps(values, -1), "comparisons for n =", len(values))
```

比较次数的上界在未命中或命中末尾时达到：两种情况都要扫完整个输入。这是 $\Theta(n)$ 的比较次数，与元素是否有序无关——有序性可以支持更快的查找，那是另一类表示与算法要解决的问题。

## 插入与删除要移动元素

如果移动量确实由「插入位置之后还有多少槽位」决定，那么把规模翻倍，头插的移动数会怎样变化，尾部插入呢？下面的单元格把这两种移动量数出来。

```python run id="alg.arrays.insert-shift"
def insert_with_moves(values, index, value):
    """Insert while counting element moves."""
    moves = 0
    values.append(None)
    for position in range(len(values) - 1, index, -1):
        values[position] = values[position - 1]
        moves += 1
    values[index] = value
    return moves


for size in (100, 200):
    values = list(range(size))
    front = insert_with_moves(values, 0, -1)
    values = list(range(size))
    tail = insert_with_moves(values, len(values) - 1, -1)
    print(f"n={size:4d}  front insert moves {front:4d}  tail insert moves {tail}")

removals = 500
values = list(range(1000))
moved = 0
for _ in range(removals):
    values.pop(0)
    moved += len(values)
print(f"deleting the front {removals} times moves about {moved} elements (n = 1000)")
```

头部插入移动全部元素，尾部附近插入几乎不移动：规模从 100 翻到 200，头插的移动数也跟着翻倍。连续删除头部元素的总移动量随删除次数与输入规模同时增长：初始长度为 $n$、删除 $m$ 次（$1 \le m \le n$）时总移动量是 $\sum_{j=0}^{m-1}(n - j - 1) = m(n - 1) - m(m - 1)/2$，即 $\Theta(n m)$；$n = 1000$、删除 500 次时实测移动 374750 个元素。这种用法代价高昂：这正是「用 `list` 当队列」代价高昂的原因，队列需要另一种表示（见 <CrossRef id="algorithms.stacks-and-queues" />）。

## 连续数组与动态数组

**连续数组**：元素存放在一块连续内存里，元素 $i$ 的位置由基址与元素大小算出。在固定宽度槽位、单位成本地址访问的模型下，下标访问是一次地址计算，与 $n$ 无关。代价是插入与删除必须移动元素以维持连续性：在单位成本槽位移动的模型下，`insert(i)` 移动 $n - i$ 个已有元素，总成本是 $\Theta(n - i + 1)$；`delete(i)` 移动 $n - i - 1$ 个后继元素，合法删除总有 $n - i \ge 1$，因此总成本是 $\Theta(n - i)$。头部是 $\Theta(n)$，靠近尾部可以是 $\Theta(1)$，对位置取最坏情形才是 $\Theta(n)$；CPython 的复杂度表把 `insert` 简写成 $O(n - k)$，本课不沿用它在端点上的这种简写。

**动态数组**：在连续数组之上维护两个量——`capacity`（已分配槽位）与 `size`（实际元素数）；把两者混用会得出错误的复制量。它的表示不变量是 $0 \le \texttt{size} \le \texttt{capacity}$，前 `size` 个槽位表示抽象序列 $S$，其余槽位不属于抽象序列、其内容不参与抽象状态；`insert`、`delete` 与扩容都必须保持这条不变量。`size == capacity` 时扩容：分配更大的块，把已有元素复制过去。

## 容量跳变与单次成本尖峰

追加一个元素平时只写一个槽位，那么昂贵的复制发生在什么时候？如果容量每次只加一个槽位，追加就要频繁地整块搬家。一个具体的观测对象是容器体积随追加的变化：容量是在每次追加后重新分配，还是成批地跳变。

```python run id="alg.arrays.capacity-growth"
import sys


def capacity_events(count):
    """Record (appends so far, container bytes) whenever the list's stored size changes."""
    values = []
    events = []
    previous = sys.getsizeof(values)
    for index in range(count):
        values.append(index)
        current = sys.getsizeof(values)
        if current != previous:
            events.append((index + 1, current))
            previous = current
    return events


events = capacity_events(64)
print("growth steps (appends, container bytes):", events[:5])
print("growth events over 64 appends:", len(events))
```

列表对象在追加过程中反复改变体积，而且每次都跳过若干槽位：64 次追加里容器体积只变了 8 次（第 1、5、9、17、25、33、41、53 次），一次追加后容器直接得到容纳后续若干元素的空间。按比例的 over-allocation 是 CPython（本课程使用的 Pyodide 运行时同源）的实现事实，具体字节数与增长比例随解释器版本与指针宽度变化；以上观测所能确认的是容量按批跳动这一行为。

把容量翻倍的那一次追加要把已有元素全部搬走，其余追加只写一个槽位。用一个自己设定的翻倍策略把每次追加的工作量记下来：

```python run id="alg.arrays.amortized-cost"
def append_costs(count, growth_factor=2):
    """Work for each append under a grow-by-a-factor policy: write one slot, or write and copy."""
    capacity = 1
    size = 0
    costs = []
    for _ in range(count):
        if size == capacity:
            capacity *= growth_factor
            costs.append(1 + size)
        else:
            costs.append(1)
        size += 1
    return costs


costs = append_costs(64)
print("work for the first 16 appends:", costs[:16])
print("typical append work:", min(costs), "| largest single append:", max(costs), "at append", costs.index(max(costs)) + 1)
```

这段代码用的是自己设定的翻倍策略，给出的是成本模型，与上面 `list` 的实际字节变化分开。追加平时只写一个槽位，偶尔一次要把整块搬走：64 次追加里，单次最大的一次写在第 33 次追加上，那一次要搬走 32 个已有元素；其余追加大多只写一个槽位，常态工作量是 1。为什么这样仍然可以称为便宜？这需要一条把整串操作放在一起计数的论证：<Term id="amortized-analysis">摊还分析</Term> 给出的就是这条论证（见 <CrossRef id="algorithms.amortized" />）。

## CPython 的 `list` 是具体的动态数组

CPython 中的 `list` 是可变长的对象引用数组：容器存储指向对象的引用，不存储对象本身。`sys.getsizeof` 统计的是直接归属于列表容器的内存，不递归计入它引用的对象——因此容器字节数与 payload 对象本身的大小无关，但确实取决于已分配容量以及运行时的分配与增长历史。每个槽位保存一个对象引用，被引用对象与指针数组分离，多个槽位也可以引用同一个对象。切片返回一个新的 `list`，它建立新的引用数组并复制其中的引用，在单位成本引用复制的模型下，长度 $k$ 的切片成本是 $\Theta(k)$。本课程的浏览器运行时 Pyodide 是 CPython 到 WebAssembly 的移植，本节研究的就是这一具体实现；其他实现的 `list` 不保证同样的表示。

```python run id="alg.arrays.list-holds-references"
import sys

shared = [0] * 1000
distinct = list(range(1000))
print("container size with repeated payload:", sys.getsizeof(shared))
print("container size with 1000 distinct payloads:", sys.getsizeof(distinct))
print("the repeated element is one object:", shared[0] is shared[1])

small = [0]
huge = [10 ** 100]
print("container size ignores payload size:", sys.getsizeof(small) == sys.getsizeof(huge))
print("payload sizes differ:", sys.getsizeof(small[0]), "vs", sys.getsizeof(huge[0]))
```

容器本身是连续排列的引用，被引用的对象与指针数组分离。这有两个后果：下标访问仍然 $O(1)$（引用数组可以按位置计算）；而在关注内存访问的原生成本模型里，引用数组多了一层间接寻址，payload 对象也没有随指针数组紧凑排列，因此通常具有更弱的 <Term id="locality">空间局部性</Term>。这本身推不出「Python 层某个遍历循环必然更快或更慢」——实际时间还包含迭代器实现、装箱与拆箱等成本；紧凑的值数组、引用数组与复制出来的子序列三者的常数与内存行为也各不相同。把「连续数组」与「CPython 的 `list`」当成同一个东西，会得到错误的局部性结论。

需要紧凑布局时用 `array` 模块或 `bytes`/`bytearray` 这类按值存储的类型，它们存的是定长值序列，不是对象引用；本课程的浏览器运行时没有硬件性能计数器，因此无法把 wall-clock 差异归因到缓存行为，局部性收益需要在原生环境里做受控测量才能确认。

## 序列的抽象接口

连续数组与动态数组在物理布局上做了不同的取舍，对外提供的是同一组接口：按下标读取、按下标写入、在某个位置插入、删除某个位置、按顺序遍历、查找某个值。把这组接口与具体表示分开写下来，得到的就是抽象 sequence——一个 <Term id="abstract-data-type">抽象数据类型</Term>：操作与行为由下表给出，内部怎么存不属于它。抽象状态是有限序列 $S = (s_0, \dots, s_{n-1})$，元素来自一个定义了相等关系的域。

| 操作 | 行为 |
| --- | --- |
| `get(i)` | 返回 $s_i$ |
| `set(i, value)` | 把 $s_i$ 替换为 `value`，其余位置不变 |
| `insert(i, value)` | 把序列变为 $S$ 的前 $i$ 个元素、`value`、$S$ 的剩余元素按序拼接（逻辑位置改变，与物理存储无关） |
| `delete(i)` | 把序列变为 $S$ 的前 $i$ 个元素与 $S$ 从 $i + 1$ 起的剩余元素按序拼接 |
| `iterate` | 按位置顺序访问每个元素一次 |
| `search(value)` | 返回最小的满足 $s_i = \texttt{value}$ 的 $i$，不存在时返回约定的未找到结果 |

表格中的 `get`、`set`、`delete` 以 $0 \le i \lt n$ 为 <Term id="precondition">前置条件</Term>，`insert` 以 $0 \le i \le n$ 为前置条件；不满足前置条件的调用不在本抽象 sequence 契约的范围内，本契约不规定其结果：具体类型可以另行规定这些输入的语义，例如 Python `list` 支持负索引，`insert` 对超出范围的位置也有自己的截断规则。相等关系属于契约层（它决定什么叫命中），而「一次相等判定的成本」属于成本模型：在 Python 里 `==` 可能执行用户代码，因此准确的结论是「最多 $n$ 次相等比较」，对一般对象的真实时间不下结论。

同一个抽象接口可以有多种表示：连续数组、动态数组、链式结构、维护子树大小等秩信息的平衡树。它们的操作成本不同，因此「序列的查找是 $O(n)$」这种句子没有意义。接口的功能本身并不决定复杂度：`get` 是常数还是线性，取决于四件事——哪种表示、什么成本模型、按什么规模度量、成本怎样量化（见 <CrossRef id="algorithms.cost-model" />）；同一个物理表示也不唯一决定算法或成本模型。
