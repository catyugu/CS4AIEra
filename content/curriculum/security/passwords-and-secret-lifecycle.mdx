注册时，服务器要保存以后能验证口令的信息；登录时，再检查用户输入是否匹配。如果将原口令直接存进数据库，一次泄露就会暴露所有口令。可以改为保存专门计算的验证记录，让登录无需恢复原文。

## 验证口令不需要恢复原文

服务器需要判断输入口令是否与注册口令匹配，通常没有必要恢复原文。<Term id="password-hash">口令散列</Term>使用专用算法、每份口令独立的盐和成本参数生成验证值；登录时用相同参数处理候选口令，再验证匹配。

盐（salt）是随验证记录保存的独立随机值，通常无需保密。它让相同口令的记录也具有不同结果，并减少跨用户复用预计算结果的机会。攻击者拿到盐与验证值后，仍可逐个尝试候选口令；独立的盐使它通常需要针对每份记录重新计算。

专用口令散列增加每次猜测的计算或内存成本。通用快速散列适合快速处理数据，直接用一次 SHA-256 保存口令会让攻击者快速测试大量候选。算法选择与成本配置应采用维护中的库和当前规范要求，见 [OWASP：口令存储](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)；这些库会实现所选算法的盐生成、成本参数和验证流程，应用应按其接口保存与检查验证记录。

登录时，库从保存的记录取得算法参数，用候选口令计算并验证。攻击者拿到数据库后也能反复猜测，所以专用散列通过计算和内存成本减慢每次尝试；服务端还需限制在线尝试次数。具体要求见 [NIST 口令验证器](https://pages.nist.gov/800-63-4/sp800-63b.html)。

## 散列、加密与认证回答不同问题

数据结构使用的<Term id="hash-value">哈希值</Term>不自动具备密码学性质。密码学散列把输入映射为摘要，但公开摘要本身不认证来源：对手若能替换文件，也能为替换后的文件重新计算摘要。只有通过可信渠道取得的预期摘要，才支持检查收到的文件与它是否相符。

| 机制 | 输入和关键材料 | 主要用途 |
| --- | --- | --- |
| 密码学散列 | 数据 | 在可信摘要已知时检查数据是否匹配 |
| 加密 | 数据与密钥 | 让没有密钥的观察者难以取得原文 |
| 消息认证码 | 数据与共享秘密密钥 | 检查内容未被改动，并确认产生者持有相同秘密密钥 |
| 数字签名 | 数据与私钥；验证用公钥 | 检查内容未被改动，并确认签名与对应私钥相符 |

加密还需要考虑完整性，实际系统通常选用同时保护保密性和完整性的成熟方案。签名不让内容保密，也不证明签名者的业务陈述真实。TLS 怎样建立通信端点的认证与保护见 <CrossRef id="networks-and-web.addressing-and-listening" />。

## 让服务端取得所需凭据

数据库口令、服务访问令牌、签名私钥都属于<Term id="secret">秘密</Term>：保密要求来自它们赋予的能力。前端脚本及其资源会交给用户，压缩、混淆或改名不改变可取得的事实。把数据库口令写进前端，就把它代表的数据库能力交给每个取得产物的人。

服务端使用秘密也要限制范围。只读查询服务使用的凭据，不应同时允许删除数据库。环境变量是一种把配置交给进程的方式，进程、调试输出和错误报告仍可能读到它；因此还要限制能读取进程环境和诊断材料的身份，并避免把秘密写入输出。

| 阶段 | 需要决定的事实 |
| --- | --- |
| 创建 | 谁生成，随机性和用途是否合适 |
| 分发 | 哪些身份和进程能取得，是否进入构建产物 |
| 使用 | 允许访问哪些资源，是否会写进日志 |
| 轮换 | 新旧凭据如何切换，哪些客户端需要更新 |
| 撤销 | 旧凭据何时不再被接受，失败怎样发现 |

轮换时，要先让客户端切换到新凭据，再按计划停止接受旧凭据。泄露之后还需要终止旧能力，并检查泄露期间发生了什么。秘密管理的生命周期见 [OWASP：秘密管理](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html#27-secret-lifecycle)。

## 练习

团队把公开下载文件及其 SHA-256 摘要放在同一个可被替换的服务器目录，声称“攻击者无法修改文件，因为摘要会不匹配”。审查这项保证依赖什么可信信息，以及哪种替换仍能通过检查。

排查连接故障时，服务把完整数据库连接字符串写进日志。列出可能取得这项能力的人与程序。设计一次凭据替换：哪些服务先更新，旧凭据何时撤销，日志访问和已有副本怎样处理？
