服务器已经确认请求来自用户 A，但请求目标是用户 B 的文档。确认是谁发起请求，仍没有回答这个人能否读取这份资源。

## 身份与动作分别检查

**认证**（authentication）建立请求者身份的证据，例如验证口令或身份凭据。**授权**（authorization）根据身份、目标资源、动作及相关规则决定是否允许操作。

同一个用户可以读取某份文档，却不能编辑。多人组织中的“管理员”“编辑者”是角色，它们概括一组权限，但权限还要有适用范围。例如一项服务同时供两家公司使用，每家公司都有自己的编辑者；只检查用户的角色是 `editor`，却不检查文档所属公司，会让一家公司的编辑者修改另一家公司的文档。

一次权限判断至少要把三个对象接起来：已经认证的身份、请求选择的目标、要执行的动作。下面固定一项规则：只有同组织的编辑者可以修改文档。`identity` 假定来自服务端已验证的会话，文档的归属来自服务端记录；请求只提供目标编号。

```python run id="security.identity-authorization-and-sessions.organization"
identity = {"user": "Ada", "organization": "north", "role": "editor"}
documents = {
    7: {"organization": "north", "body": "north notes"},
    8: {"organization": "south", "body": "south notes"},
}

def can_edit(identity, document):
    return (identity["role"] == "editor"
            and identity["organization"] == document["organization"])

for document_id in [7, 8]:
    document = documents[document_id]
    print(document_id, can_edit(identity, document))
```

两次请求使用同一个合法身份、同一个角色，目标文档不同，判断就不同。删掉组织比较后，`editor` 会被解释成对所有组织都有效。若组织字段改为取自请求中自报的值，对手又能让比较成立；因此不仅要检查条件，还要追踪条件中的每份数据由谁建立。这段代码展示权限规则，不实现会话验证；真实接口必须先取得可信身份，再在执行修改前检查规则。

权限检查应覆盖每个请求，并在没有明确允许规则时拒绝；页面、下载地址和批量接口必须保持相同边界，见 [OWASP：授权检查](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#validate-the-permissions-on-every-request)。资源编号可以来自客户端，资源的真实归属和权限则需要可信数据。

## 会话让后续请求关联到身份

用户登录之后，不会在每次读取文档时重新输入口令。**会话**（session）把后续请求与已建立的身份关联起来。一个常见安排是服务器保存会话记录，浏览器保存不可预测的会话标识，并在请求中附带它。服务器用标识查找身份、过期时间和撤销状态。

| 事件 | 浏览器状态 | 服务器状态 |
| --- | --- | --- |
| 认证成功 | 收到新的会话标识 | 建立身份与标识的关联 |
| 请求文档 | 携带标识 | 验证会话，再检查文档权限 |
| 会话到期 | 可能仍保存旧标识 | 拒绝过期会话 |
| 用户退出 | 删除本地标识 | 撤销服务器会话 |

会话标识通常是持有者凭据：取得标识的人可能以相同身份使用它。因此标识需要安全随机生成、限制生命周期，并在登录或权限提升时按设计更新，防止把攻击者已知的旧标识升级成登录会话。会话管理规则见 [OWASP：会话管理](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)。

如果退出只删除浏览器 cookie，已经复制走的标识仍可能有效。撤销需要服务器可执行的规则。

另一种会话安排是把身份和有效期写进令牌，再通过数字签名防止内容被修改。服务器可以验证令牌而不查找会话记录，但仍需要决定：令牌尚未到期时，怎样撤销它代表的权限。

## cookie 属性限制不同的攻击路径

cookie 是浏览器按适用规则附带到请求的状态信息。`Secure` 限制通过安全通道发送，`HttpOnly` 限制页面脚本通过 cookie API 读取，`SameSite` 约束某些跨站请求是否携带它。会话 cookie 可以设置：

```http
Set-Cookie: session=example-opaque-id; Path=/; Secure; HttpOnly; SameSite=Lax
```

这是格式示例，`example-opaque-id` 不是可以使用的安全凭据。`HttpOnly` 能降低脚本直接读取标识的风险，但若同源脚本被对手控制，它仍可能发起自动携带 cookie 的请求。因此这些属性各自限制一条路径，不能代替资源授权。

## 有效签名仍需要解释被签的内容

数字签名的性质见 <CrossRef id="security.passwords-and-secret-lifecycle" />。即使令牌的签名有效，服务器也要检查谁签发它、它是给哪个服务使用的、是否到期，以及当前操作需要的权限。为预览服务签发的令牌，不应仅因签名有效就被数据库管理接口接受；同一个身份在权限撤销后，也可能需要立即失去某项能力。

认证与授权之间还可能发生变化：检查编辑权限后，管理员撤销权限，修改才提交。系统需要定义按哪个时刻的权限判断，以及检查和使用之间怎样避免不允许的变化。这里的要求来自业务，不是“已登录”三个字能够决定的。

## 练习

用户 A 在 10:00 获得会话，10:02 被移出组织。一个下载接口每次都读取当前成员记录，另一个接口只验证会话未过期，并使用 10:00 保存的组织身份。产品要求移出组织后不能再读取该组织文档。列出两条读取路径在 10:03 各自依据的事实。应当怎样设计测试，才能区分“会话有效”和“当前仍有权限”？

文档下载地址只包含难以猜测的长编号，访问时不检查身份。它可以符合“拿到链接的人都能读取”的共享规则吗？它可以同时符合“只有已授权成员能读取”的规则吗？分别说明所需的信任假设。
