小林编辑笔记后点击「保存」。服务端从会话认出小林，从权限表确认他可以修改笔记 7。服务还要判断这次修改是否经由允许的页面发起。浏览器会按规则附带 cookie，而另一个网站也可能让浏览器向笔记服务提交请求。

## 请求到了服务器会怎样

<Term id="csrf">跨站请求伪造</Term>（CSRF）利用浏览器自动携带凭据的行为，借已登录用户的浏览器发起用户无意执行的操作。考虑一个用 cookie 登录、支持表单修改的旧接口。若外站发起的提交携带了有效 cookie，而服务只核对会话和编辑权限，数据库就可能接受这次修改。

浏览器的同源策略和 CORS 影响一个<Term id="origin">源</Term>上的脚本能否读取另一源的响应。对于普通表单等浏览器可以直接发送的请求，即使外站脚本无法读取响应，服务器也可能已执行写入。检查一次修改是否生效，要看服务端返回的结果和数据库状态。浏览器如何处理跨源响应见 <CrossRef id="networks-and-web.browser-and-frontend" />。

## 增加服务端的请求检查

一种常见做法是由服务端生成不可预测的 CSRF 令牌，将它关联到小林的会话，并交给笔记页。笔记页在保存时把令牌显式提交，例如放在表单字段中。服务端比对通过后才允许执行修改。会话 cookie 提供用户身份，令牌提供第二项证据，外站通常无法读取笔记页中的令牌。应选用框架内置防护，让网页表单和 API 的相关写操作都遵守同一套规则。

服务端也可按部署约定核对请求的 `Origin`。会话 cookie 的 `SameSite` 属性在浏览器端限制某些跨站请求携带凭据，两处共同减少请求被接受的机会。**同站**与**同源**是两套判断，同一个站点下的不同子域可以属于不同源。实际采用的规则取决于应用的登录方式和受支持的入口。参见 [OWASP CSRF 防护指南](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)和 [MDN 对 SameSite 的说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie#samesitesamesite-value)。

把保存、删除和创建分享链接设为写操作，读取链接继续使用 `GET`。验收时固定一个有效会话，分别检查带有效令牌的修改和缺少令牌的修改，并用数据库中的正文确认只有获准的修改生效。
