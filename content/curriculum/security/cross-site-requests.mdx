用户登录了文档服务，随后又打开一个其他网站。那个网站构造了一次指向文档服务的修改请求。若浏览器在请求中附带登录 cookie，服务端可能看到合法会话，却无法仅凭会话判断这次操作是否来自文档服务允许的页面流程。

## CSRF 的攻击过程

<Term id="csrf">跨站请求伪造</Term>（CSRF）利用浏览器自动携带凭据的行为，让受害者的浏览器对目标服务提交攻击者选择的操作。资产是用户账户下的修改能力，对手控制的是另一个网页。

假设文档服务用 cookie 识别会话，浏览器的当前 cookie 配置允许它随这次跨站表单提交发送。修改接口接受普通表单编码，而且没有令牌或来源检查。攻击页面可以写出这样的 HTML：

```html
<form action="https://notes.example/settings/email" method="post">
  <input type="hidden" name="email" value="other@example.test">
  <button type="submit">查看文档</button>
</form>
```

这段 HTML 供阅读，地址和邮件均为示例；它展示浏览器提交表单时会发送哪些信息。表单规定提交目标与方法，隐藏字段提供对手选择的内容。用户点击按钮时，浏览器提交表单；能否附带 cookie 由 cookie 和浏览器规则决定。

| 步骤 | 发起动作的参与者 | 服务器可能看到的内容 |
| --- | --- | --- |
| 打开攻击页面 | 用户 | 尚无修改请求 |
| 提交表单 | 攻击页面的结构与用户点击 | 目标地址、对手选择的邮件 |
| 附带适用 cookie | 浏览器 | 有效登录会话 |
| 处理请求 | 文档服务 | 已认证用户与修改内容 |

服务器在最后一步验证到了有效会话，还需要检查这份修改请求是否来自允许的发起流程。

## 跨源读取限制与请求副作用

浏览器的<Term id="origin">源</Term>与 CORS 规则见 <CrossRef id="networks-and-web.browser-and-frontend" />。CORS 主要约束跨源脚本能否读取响应；普通 HTML 表单仍可以向其他站点提交请求。即使攻击页面读不到响应，服务器也可能已经修改邮箱。跨源与跨站的判定不同：相同站点的两个子域名也可以属于不同源。

修改状态的接口应使用 `POST` 等适合的方法，并验证请求来源或 CSRF 令牌。上面的攻击表单使用的就是 `POST`。`GET` 用于读取，把修改放在 `GET` 中还可能让普通链接访问触发状态变化。

## CSRF 令牌与请求来源检查

服务可以向合法页面提供一个不可预测、与当前会话关联的 CSRF 令牌。合法页面在修改请求里显式提交令牌，服务器据此验证请求。攻击页面即使能让浏览器自动携带会话 cookie，通常也无法读取合法页面上的令牌；只检查一项会自动发送的 cookie 是否存在，无法证明请求来自合法页面。令牌不应只依赖一个会自动随请求发送的 cookie，也不应进入 URL 或日志。

服务器还可以检查请求的 `Origin` 等来源信息，拒绝来自未允许页面的修改。采用框架提供的完整防护机制，可以统一处理各个入口，见 [OWASP：CSRF 防护](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)。

`SameSite` 限制某些跨站请求携带 cookie，可以作为额外保护。其具体适用条件与登录、跳转流程有关，应按框架与浏览器规则配置，见 [MDN：SameSite](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie#samesitesamesite-value)。服务器应对所有相关修改入口采用一致的令牌或来源检查。

若合法页面存在 XSS，攻击者可能直接使用页面的请求能力。因此，CSRF 防护也依赖 <CrossRef id="security.parsing-injection-and-output" /> 中的输出处理。

## 练习：跨站表单与令牌验证

一个修改接口同时接受表单和 JSON，团队只对 JSON 请求验证 CSRF 令牌，并声称“攻击页面无法通过 CORS 读取响应”。按上述攻击路径审查剩余的入口与可观察效果。
