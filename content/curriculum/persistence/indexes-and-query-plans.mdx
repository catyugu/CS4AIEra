表里有十万本书，页面每次只要 history 分类中价格最低的十本。返回十行不意味着只读取十行：若没有合适的访问路径，引擎仍可能检查整张表，再排序候选。

## 索引保存另一种次序

没有索引时，引擎可以逐行检查分类，留下 history 的记录，再按价格找出最低的十本。十万行都可能需要检查，即使最后只返回十行。索引额外保存一组有序的键及其对应记录，让引擎能从需要的位置开始读。

例如复合索引 `(category, price)` 先比较分类；分类相同，再比较价格。一小段索引可能按下面的次序保存：

| 分类 | 价格 | 对应记录编号 |
| --- | --- | --- |
| computing | 12 | 8 |
| computing | 35 | 2 |
| history | 10 | 5 |
| history | 18 | 1 |
| history | 18 | 9 |
| history | 40 | 4 |
| science | 8 | 6 |

查 history 时，可以定位到它的第一项，沿这个连续范围依价格读取；满足十项就停止，或在范围结束时停止。相同价格之间没有在查询里规定先后，所以“最低十本”可能在价格并列处有多种合法结果。若还需要稳定的编号次序，查询和所需访问路径也要表达这个要求。

若只查 `price < 20`，符合条件的键分别出现在 computing、history、science 的不同段中。价格在每个分类内有序，却没有在整个索引中统一排序。因此前一种查询的“定位一段，然后依次读取”不能直接照搬。

## 从哪里开始读，又如何找到那里

有序的键很多时，数据库还需要快速定位起点。磁盘上的树通常按页组织，一页保存许多键及下一层的位置。页是数据库组织读写的一块数据。假设根页标出不同分类所在的分支，读取根页后就能排除其他分支；再读选中的下层页，继续缩小范围，最终到达保存索引项的位置。这类多分支有序结构称为 B 树。

树负责定位，随后按键次序读取负责取得所需范围。返回的列若已在索引中，引擎可以直接取得它们；若需要书的详细介绍等其他列，还要按索引里的记录位置访问表。查询是否能省去这些访问，会影响索引的实际收益。

夹具 <LabRef id="catalog-indexes" /> 在 SQLite 内准备 2000 行记录，其中十分之一属于 history 分类。每次运行从没有额外索引的原始表开始，输出查询计划而不测耗时。

```sql run id="persistence.indexes.plan" fixture="catalog-indexes"
EXPLAIN QUERY PLAN
SELECT id, price FROM entries
WHERE category = 'history' ORDER BY price LIMIT 10;
CREATE INDEX by_category_price ON entries(category, price);
EXPLAIN QUERY PLAN
SELECT id, price FROM entries
WHERE category = 'history' ORDER BY price LIMIT 10;
```

`CREATE INDEX` 建立索引，`LIMIT 10` 限制返回行数，`EXPLAIN QUERY PLAN` 显示选定的访问方法。比较两份计划时，沿实际查询读它们：

- `SCAN entries`：扫描表，再检查每行的分类；`SCAN` 也可以用于扫描某个索引，需要看后面的对象。
- `USE TEMP B-TREE FOR ORDER BY`：当前访问次序不能直接满足排序，引擎还要组织排序结果。它并不表示一定把整个临时结构写到磁盘。
- `SEARCH ... (category=?)`：用分类条件定位索引范围。这里计划中的 `?` 说明搜索条件，并不是要求再给单元格填写参数。
- `COVERING INDEX`：这个查询需要的列可以从索引取得，无须为这些列再读取表记录。

有了分类和价格索引后，定位 history 并沿价格次序读取，还能省去额外排序。计划说明选择了哪些操作，没有报告精确访问了多少页，也没有证明某个耗时倍数。[SQLite 查询计划文档](https://www.sqlite.org/eqp.html)说明这些字段，并提醒显示格式可能随版本变化。

## 为什么优化器有时不选索引

语句描述结果，引擎的优化器选择访问路径。它会估计候选数量，也就是 <Term id="cardinality">基数</Term>。若某分类只占少量记录，索引可能减少访问；若几乎所有记录都符合条件，索引查找后再读表可能比顺序扫描更贵。行宽、页是否已在缓存、输出列是否在索引中也影响成本。

统计信息帮助估计数据分布；SQLite 用 `ANALYZE` 收集相关信息。[SQLite 查询规划文档](https://www.sqlite.org/queryplanner.html#multiple_indices)解释选择索引时如何使用统计信息。这次计划只显示当前引擎对这份数据选了什么路径；数据规模或分布改变后，应重新检查。

## 索引还参与写入

加入一本书时，要把它写进表，也要把相关键插入每个索引。修改价格时，价格索引需要更新；删除书时，其索引项也要移除。更多索引增加持久空间、缓存占用和写入工作，并可能增加锁竞争。

因此“所有列都建索引”没有统一收益。应当依据查询频率、候选比例与修改频率比较代价。表示选择的一般成本模型见 <CrossRef id="data-algorithms-and-scale.representation-preprocessing-and-indexes" />。

## 练习

把实验的筛选条件换成 `price < 10`，保留复合索引。先判断哪些记录可能连续，再看计划。SQLite 可能采用扫描或其他优化；解释应依据实际路径，不把“存在索引”直接写成“只访问十行”。

现在系统每秒更新价格 2000 次，每小时只有一次按分类的报表。比较保留这个复合索引与仅为报表临时准备有序数据两种方案，还要统计哪些查询、更新次数和准备成本？
