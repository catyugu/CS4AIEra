目录首页要取出 history 分类中最便宜的十本书。没有合适的索引时，数据库可能要扫描表，再为匹配结果排序。

## B 树与复合索引

B 树按键组织多层节点，查找时逐层定位键范围。索引 `(category, price)` 先按分类排、再按价格排。history 占一段连续范围，可以从范围起点直接按价格读取。只按价格筛选时，匹配项可能分散在不同分类段。

用扩展目录 <LabRef id="catalog-indexes" /> 查看 SQLite 的查询计划。这份数据有 2000 行，十分之一属于 history 分类。两次 `EXPLAIN QUERY PLAN` 查看同一条查询，第二次是在建立索引之后。同价书目按编号排列，`LIMIT 10` 只取前十行。

```sql run id="persistence.indexes.plan" fixture="catalog-indexes"
EXPLAIN QUERY PLAN
SELECT id, price FROM entries
WHERE category = 'history' ORDER BY price, id LIMIT 10;

CREATE INDEX by_category_price ON entries(category, price);

EXPLAIN QUERY PLAN
SELECT id, price FROM entries
WHERE category = 'history' ORDER BY price, id LIMIT 10;
```

| SQLite 计划中的描述 | 在这条查询中的含义 |
| --- | --- |
| `SCAN entries` | 扫描表，逐行找出 history 记录 |
| `USE TEMP B-TREE FOR ORDER BY` | 用临时结构完成排序 |
| `SEARCH entries ... (category=?)` | 利用索引定位 history 范围 |

这里 `id` 是 SQLite 整数主键，索引项也保存该编号，可以按编号排列同价结果。这条查询的列都能从索引取得时，称为覆盖索引。查询计划给出访问方法，响应时间需要在实际负载下测量。[SQLite 查询规划](https://www.sqlite.org/queryplanner.html) · [SQLite 查询计划](https://www.sqlite.org/eqp.html)

## 索引的收益与成本

优化器估计候选行的数量，即<Term id="cardinality">基数</Term>，再比较扫描、查索引、回表与排序的成本。若几乎所有记录都匹配，且需要从表读取额外列，直接扫描可能更便宜。增加索引还会占用空间，并给插入、删除和改价增加维护工作。见 <CrossRef id="data-algorithms-and-scale.representation-preprocessing-and-indexes" />。

## 练习

改为跨分类查找价格低于 10 的书，再按价格和编号列出头十条。先判断这些记录在原有复合索引中如何分布，再修改两条查询，读出引擎选择的访问与排序步骤。
