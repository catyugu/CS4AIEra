库存只有一件，两个请求都先读库存，再各自提交减一后的结果。每条语句都成功，库存最后是零，却可能创建了两笔订单。需要检查的是读取与修改之间允许发生什么。

## 并发读写与丢失更新

| 步骤 | 请求 A | 请求 B | 库存 |
| --- | --- | --- | --- |
| 1 | 读到 1 | | 1 |
| 2 | | 读到 1 | 1 |
| 3 | 把库存写成 0，创建订单 | | 0 |
| 4 | | 把库存写成 0，创建订单 | 0 |

两个请求根据同一旧状态决定结果，后一次写回覆盖了前一次修改。这是丢失更新。此时 `stock >= 0` 仍成立，但两笔订单购买了同一件库存，已经超卖。检查库存最终是否非负，会漏掉这段重复购买的过程。

若数据库对冲突写入提供必要的协调，可以用一条条件更新把检查和减库存结合起来，再根据受影响行数决定是否创建订单。订单创建与库存修改还需在同一事务中。

## 版本检查与条件更新

另一个方案为记录保存版本号。读取数量和版本，修改时要求版本仍等于读取值，成功后增加版本。数据库需要在同一次条件更新中检查版本并写入新值，使两个请求无法都凭版本 0 修改成功。

将每条记录增加一个 `version` 字段。两个请求先读到数量 1、版本 0：

| 操作 | 条件 | 数据库中的结果 |
| --- | --- | --- |
| A 更新 | 版本仍为 0 | 数量改为 0，版本改为 1 |
| B 更新 | 版本仍为 0 | 条件不成立，零行修改 |

版本检查与写入必须在同一条更新中完成。下面用 SQLite 重放表中的顺序。两个旧值代表两次请求各自读到的数据；单元格按固定顺序执行，便于观察条件，而不依赖线程调度。

```python run id="persistence.isolation.version"
import sqlite3

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE stock (id INTEGER PRIMARY KEY, quantity INTEGER, version INTEGER)")
db.execute("INSERT INTO stock VALUES (1, 1, 0)")
old_a = db.execute("SELECT quantity, version FROM stock WHERE id = 1").fetchone()
old_b = db.execute("SELECT quantity, version FROM stock WHERE id = 1").fetchone()

for label, old in [("A", old_a), ("B", old_b)]:
    changed = db.execute(
        "UPDATE stock SET quantity = ?, version = version + 1 WHERE id = 1 AND version = ?",
        (old[0] - 1, old[1]),
    ).rowcount
    print(label, changed)
print(db.execute("SELECT quantity, version FROM stock").fetchall())
db.close()
```

`fetchone()` 读取一行，结果元组包含数量与版本；`rowcount` 是修改影响的行数。SQL 中的问号是值参数占位符，后面的元组依次提供新数量和原版本，见 [Python sqlite3 参数绑定](https://docs.python.org/3/library/sqlite3.html#sqlite3-placeholders)。

A 使版本增加，B 再按旧版本修改便影响零行。应用需要重新读取和判断，不能继续按原值创建订单。实际购买还应把成功的库存修改与订单插入放在同一事务中。


## 事务隔离与冲突

<Term id="isolation-level">隔离级别</Term>规定并发事务允许观察和改变哪些状态。事务能把多条修改一起提交，隔离机制则决定这些修改如何与其他事务交错。

数据库可以通过锁、版本和冲突检测组织访问。例如<Term id="mvcc">多版本并发控制</Term>让读取使用某个版本的数据，减少读写之间的等待。业务中的“检查并修改”仍需放进合适的保护范围：本例以同一次条件更新检查版本并写入，只有成功的请求才继续创建订单。

具体冲突行为取决于引擎与隔离级别，见 [SQLite 隔离](https://www.sqlite.org/isolation.html)和 [PostgreSQL 事务隔离](https://www.postgresql.org/docs/current/transaction-iso.html)。应用遇到要求重做事务的冲突时，需要重新读取并判断，而非继续使用已经过时的旧值。
