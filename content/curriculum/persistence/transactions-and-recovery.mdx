购买一本书需要减库存并创建订单。如果库存已经减少，订单创建却失败，数据就只完成了一半业务操作。把两条语句写在同一函数中，不能自动使它们共同成功。

## 哪些修改一起生效

事务（transaction）把若干数据库操作组合为一次提交单位。在购买的例子里，需要保留“减库存且有订单”或“库存未减且无订单”，避免只留下一半。修改共同生效或共同撤销，称为原子性。

事务还有其他需要分别检查的保证：持久性要求成功提交的修改在约定故障下可恢复；隔离性处理并发事务之间能观察什么；一致性要求事务前后满足业务规则。后者仍依赖约束与正确的操作逻辑，不能由“用了事务”自动推出。

`BEGIN` 开始事务，`COMMIT` 提交，`ROLLBACK` 撤销尚未提交的修改。以下实验主动撤销一次购买，可把最后的 `ROLLBACK` 改为 `COMMIT` 比较结果。

```sql run id="persistence.transactions.rollback" fixture="catalog"
BEGIN;
UPDATE books SET stock = stock - 1 WHERE id = 1;
INSERT INTO orders (id, reference, book_id, quantity)
VALUES (13, 'r13', 1, 1);
SELECT id, stock FROM books WHERE id = 1;
ROLLBACK;
SELECT id, stock FROM books WHERE id = 1;
SELECT id, reference FROM orders ORDER BY id;
```

事务中间的查询能看到本事务已经做出的修改，撤销后查询看到原状态。这个实验使用内存数据库，验证的是事务语义，不能验证磁盘的断电恢复。

示例开始时书 1 的库存足够。若改用带 `stock >= 1` 的条件更新，库存不足时可能只影响零行而不抛异常；此时仍执行订单插入，也能提交一笔没有扣库存的订单。事务只能让写下的修改共同提交，应用还必须检查扣减成功后才创建订单。

## 失败之后由谁撤销

SQLite 在默认冲突处理规则下，许多约束错误只撤销失败的那条语句，保留事务内先前语句的修改。不能假定一条语句出错就已回滚整个事务。[SQLite ON CONFLICT 文档](https://www.sqlite.org/lang_conflict.html)区分了这些行为。

程序应在购买失败时决定是否撤销。下面使用 Python 的真实 SQLite API，`execute` 执行一条语句，`commit` 和 `rollback` 分别提交和撤销；`fetchall` 读取全部结果行。

```python run id="persistence.transactions.failure"
import sqlite3

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE stock (id INTEGER PRIMARY KEY, quantity INTEGER)")
db.execute("CREATE TABLE orders (reference TEXT UNIQUE)")
db.execute("INSERT INTO stock VALUES (1, 3)")
db.execute("INSERT INTO orders VALUES ('r1')")
db.commit()
try:
    db.execute("UPDATE stock SET quantity = quantity - 1 WHERE id = 1")
    db.execute("INSERT INTO orders VALUES ('r1')")
    db.commit()
except sqlite3.IntegrityError as failure:
    print(failure)
    db.rollback()
print(db.execute("SELECT quantity FROM stock").fetchall())
db.close()
```

提交调用本身也可能失败，调用方要依据连接和错误状态处理。数据库无法替应用撤销已经寄出的邮件或已经完成的外部支付；这些动作不在本地数据库事务内。

## 数据页与日志

存储设备不能保证任意多个页瞬间一起写完。数据库通过日志记录足以恢复的信息，并规定写入顺序。采用 <Term id="write-ahead-log">预写日志</Term> 的机制，先让恢复所需日志持久保存，再允许相应数据页写回；提交信息决定恢复时哪些事务应被保留。读者不需要背日志格式，但要能解释写到一半为何仍可恢复。

| 断电时刻 | 恢复所需判断 |
| --- | --- |
| 修改仅在易失内存中 | 尚未提交的修改不能当作已完成 |
| 部分日志已持久化，提交尚未完成 | 依据日志规则识别未完成事务 |
| 提交已持久化，部分数据页尚未写回 | 用日志恢复已提交修改 |

SQLite 的回滚日志与 WAL 是两种不同方案；上表说明恢复需要的区分，不复制某一种格式。具体的 WAL 提交与检查点行为见 [SQLite WAL 文档](https://www.sqlite.org/wal.html#how_wal_works)。持久性仍依赖同步配置、文件系统和硬件兑现契约，备份用于应对设备丢失或错误修改。

## 练习

在失败实验中把 `db.rollback()` 换成 `db.commit()`。先判断调用方捕获异常后留下什么状态，再运行。根据结果审查“异常已经捕获，所以购买已完整撤销”这句话。

一笔购买先提交订单，再调用邮件服务。邮件超时后，代码试图回滚刚才的事务。画出这两个动作的提交边界，说明数据库恢复机制能够证明哪些事实。
