购买一本书需要扣减库存并创建订单。这两项修改共同组成一次购买：购买成功时，两项都应保存；购买失败时，两项都应撤销。

## 事务与原子性

事务（transaction）把一组数据库操作组织为一次提交单位。`BEGIN` 开始事务，`COMMIT` 提交，`ROLLBACK` 撤销尚未提交的修改。

下面先扣库存并创建订单，再主动撤销。可将 `ROLLBACK` 改为 `COMMIT`，比较事务结束后留下的记录：

```sql run id="persistence.transactions.rollback" fixture="catalog"
BEGIN;
UPDATE books SET stock = stock - 1 WHERE id = 1;
INSERT INTO orders (id, reference, book_id, quantity)
VALUES (13, 'r13', 1, 1);
SELECT id, stock FROM books WHERE id = 1;
ROLLBACK;
SELECT id, stock FROM books WHERE id = 1;
SELECT id, reference FROM orders ORDER BY id;
```

事务内可以看到自己的修改；撤销后，库存回到原值，订单没有加入。将多个修改共同生效或共同撤销的性质称为原子性。

事务把实际执行的修改组合起来，业务判断仍由应用完成。例如条件扣库存影响零行时，应用应停止购买；若继续插入订单再提交，数据库会保存这组实际修改。

## 事务回滚

假设库存已扣减，随后订单编号重复，插入失败。应用需要撤销本次购买的事务。SQLite 的许多约束错误只撤销失败语句，先前修改仍留在事务中，见 [SQLite 冲突处理](https://www.sqlite.org/lang_conflict.html)。

下面用 Python 的 SQLite API 明确安排提交和撤销。`execute` 执行语句，`commit` 提交，`rollback` 撤销：

```python run id="persistence.transactions.failure"
import sqlite3

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE stock (id INTEGER PRIMARY KEY, quantity INTEGER)")
db.execute("CREATE TABLE orders (reference TEXT UNIQUE)")
db.execute("INSERT INTO stock VALUES (1, 3)")
db.execute("INSERT INTO orders VALUES ('r1')")
db.commit()
try:
    db.execute("UPDATE stock SET quantity = quantity - 1 WHERE id = 1")
    db.execute("INSERT INTO orders VALUES ('r1')")
    db.commit()
except sqlite3.IntegrityError as failure:
    print(type(failure).__name__)
    db.rollback()
print(db.execute("SELECT quantity FROM stock").fetchall())
db.close()
```

订单插入触发 `IntegrityError`，异常处理执行 `rollback()`，因此最终库存仍为 3。把错误报告给调用方之前，应用先把本次购买留下的数据库状态处理完整。

## ACID 与崩溃恢复

事务通常用 ACID 概括四种性质：原子性组织共同提交；一致性由约束与正确的业务逻辑维护；隔离性约束并发事务的相互影响；持久性使成功提交的数据在约定故障下可恢复。下一阶段会分析并发更新。

数据库实际写入多个数据块，可能在中途崩溃。日志记录恢复所需信息，使重新启动的数据库能够恢复已提交修改、处理未完成事务。<Term id="write-ahead-log">预写日志</Term>机制要求相应数据块写回之前先保存恢复所需日志。SQLite 的具体机制见 [原子提交](https://www.sqlite.org/atomiccommit.html)。这里的内存数据库实验只展示事务语义，断电恢复还依赖磁盘、同步配置与硬件。

数据库事务的范围是本次数据库操作。邮件发送等外部动作由其他系统完成；它们与数据库怎样协调，将在应用故障恢复中讨论。
