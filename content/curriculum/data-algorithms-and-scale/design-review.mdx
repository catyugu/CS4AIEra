一个仿真结果库上线前，Agent 提交了这样的方案：

> 用以 `run_id` 为键的字典保存每次运行。打开详情时按键读取。按参数组、成功状态和指标门槛筛选时，遍历全部值，再把命中的记录按指标排序。字典查找很快，所以查询性能已经优化好了。数据规模按建库时的快照考虑。

需求却是保留全部运行结果，库还会继续增长。运营方给出的<Term id="workload">工作负载</Term>如下：

| 项目 | 规模或频率 |
| --- | --- |
| 当前记录数 | 50000 条，每月增长约 5% |
| 按条件筛选 | 每天约 20000 次 |
| 按 run_id 打开详情 | 每天约 2000 次 |
| 追加记录、更新状态 | 每天约 200 次 |
| 参数组 | 20 个，数量分布尚未统计 |

审查要回答的是：方案是否保留所需数据，哪类操作消耗最多，以及增长和写入是否会破坏它的假设。

## 字典加速了哪种查询

按 `run_id` 取详情，确实可以利用字典的键。筛选按参数组、状态和指标进行，这些字段存在值里，字典并没有按它们组织记录，因此仍要逐条检查。

假设每次筛选必须检查全部 $n$ 条记录，当前每天检查的记录条次是 $20000n$。可以直接计算这个量，无须用一个只做计数的循环模拟扫描：

| 时点 | 记录数约为 | 每天筛选检查的记录条次约为 |
| --- | ---: | ---: |
| 当前 | 50000 | 10 亿 |
| 一年后，按每月 5% 增长 | $50000\times 1.05^{12}\approx 89800$ | 18 亿 |

当前每天十亿条次检查，只是工作量估计，不能直接断言耗时或不可行。还要结合每条检查的成本和时间预算。按每月 5% 增长，一年后记录数约为现在的 1.8 倍；如果查询次数不变，扫描工作也相应增长。

这还没有计算命中结果的排序。一次命中 $r$ 条记录，比较排序通常需要 $O(r\log r)$ 的工作，返回结果本身也有成本。详情查找、写入与记录扫描不是相同的基本操作，不能仅按调用数量算出各自占总耗时的百分比。

## 减少每次筛选的范围

可以比较三种候选：

| 方案 | 每次查询的工作 | 其他代价 |
| --- | --- | --- |
| 扫描全部记录 | 检查 $n$ 条，再排序命中项 | 无额外分组结构 |
| 每次查询先按参数组排序 | 对全库排序，再定位组内记录 | 每次都重做排序，很可能比直接扫描更贵 |
| 维护按参数组组织的索引 | 只检查目标组的 $k$ 条，再排序命中项 | 额外空间、构建和更新成本 |

按组索引的做法见 <CrossRef id="data-algorithms-and-scale.representation-preprocessing-and-indexes" />。这里实际比较全库扫描与组内扫描，排序需求暂保持相同：

```python run id="data-algorithms-and-scale.design-review.group-query"
runs = [
    {"run_id": "r1", "group": "A", "success": True, "score": 0.8},
    {"run_id": "r2", "group": "B", "success": True, "score": 0.9},
    {"run_id": "r3", "group": "A", "success": False, "score": 0.7},
    {"run_id": "r4", "group": "A", "success": True, "score": 0.5},
]
by_group = {}
for run in runs:
    group = run["group"]
    if group not in by_group:
        by_group[group] = []
    by_group[group].append(run)


def scan_all(records, wanted, threshold):
    matched = []
    for record in records:
        if record["group"] == wanted and record["success"] and record["score"] >= threshold:
            matched.append(record["run_id"])
    return matched


def scan_group(group_records, threshold):
    matched = []
    for record in group_records:
        if record["success"] and record["score"] >= threshold:
            matched.append(record["run_id"])
    return matched


wanted = "A"
group_records = by_group.get(wanted, [])
print("whole scan:", scan_all(runs, wanted, 0.5))
print("group scan:", scan_group(group_records, 0.5))
print("records checked:", len(runs), len(group_records))
```

`scan_all` 检查参数组、成功状态与指标。`scan_group` 的输入已经由索引选定参数组，只检查后两项；索引有效是这个函数的输入要求。两次筛选输出一致，第二次只查看 A 组。这并不保证每次都省很多：若目标组包含绝大多数记录，$k$ 接近 $n$。只有各组近似均匀时，才可以估计 $k \approx n/20$。

索引需要维护。追加记录要加入相应分组；改参数组要从旧组移到新组。这里只按组建立索引，组内记录的成功状态与指标仍在查询时检查。若进一步按状态或指标组织，还要承担相应更新成本。

## 核对方案假设

**规模。** “只考虑初始快照”与持续增长不符。查询量、分组分布也可能改变，应按目标期间的规模估算，实测是否满足延迟预算。

**唯一性。** 要保留全部运行，`run_id` 必须唯一标识一次运行。若重跑共用标识，字典会覆盖旧记录。可以为每次运行分配唯一标识，或使用标识与版本组成的唯一键；静默覆盖不能替代需求确认。

**更新。** 索引必须与主记录保持一致。即使例子里保存了同一条记录的引用，修改参数组也不会自动把它移到另一个列表。若维护已排序的索引，追加和指标变化还必须维护有序性。

**收益。** 每天两万次查询值得研究预处理，但读写比例不能独自证明方案划算。还要看各组实际大小、额外内存、更新成本与时间预算。若测量发现排序占主要时间，单独减少扫描可能还不够。

这份方案应先确认唯一性与增长假设，再针对高频筛选评估索引。按键取详情很快，只解释了其中一种操作。

## 练习

下面建库代码是否满足“全部运行结果都要保留”？先预测记录数和 A 组查询结果，再运行。分别考虑“重跑必须保留”和“只留最新结果”两种需求，说明该如何处理重复标识。`by_id.values()` 遍历字典保存的值，也就是这里的记录。

```python run id="data-algorithms-and-scale.design-review.dict-drops-record"
rows = [
    {"run_id": "r1", "group": "A", "score": 0.8},
    {"run_id": "r2", "group": "A", "score": 0.7},
    {"run_id": "r1", "group": "B", "score": 0.4},
]
by_id = {}
for row in rows:
    by_id[row["run_id"]] = row
print("source count:", len(rows), "stored count:", len(by_id))
matched = []
for row in by_id.values():
    if row["group"] == "A":
        matched.append(row["run_id"])
print("group A:", matched)
```
