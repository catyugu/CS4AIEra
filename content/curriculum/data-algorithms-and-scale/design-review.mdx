一个书目查询功能准备上线。初版方案如下：

> 用以 `id` 为键的字典保存书目。打开详情时按键读取。按分类、可借状态和评分门槛筛选时，遍历全部值，再把命中的记录按评分排序。字典查找很快，应该能满足查询需求。

书目会继续增加，借出和归还也会改变可借状态。目前对使用情况的估计如下：

| 项目 | 规模或频率 |
| --- | --- |
| 当前书目数 | 50000 条，每月增长约 5% |
| 按条件筛选 | 每天约 20000 次 |
| 按编号打开详情 | 每天约 2000 次 |
| 追加书目、更新记录 | 每天约 200 次 |
| 分类 | 20 个，各类书目数量尚未统计 |

## 字典加速了哪种查询

按 `id` 取详情，确实可以利用字典的键。筛选需要分类、可借状态和评分，这些字段存在值里，字典没有按它们组织记录，因此仍要逐条检查。

假设每次筛选检查全部 $n$ 条记录，当前每天检查的记录条次是 $20000n$：

| 时点 | 记录数约为 | 每天筛选检查的记录条次约为 |
| --- | ---: | ---: |
| 当前 | 50000 | 10 亿 |
| 一年后，按每月 5% 增长 | $50000\times 1.05^{12}\approx 89800$ | 18 亿 |

“十亿条次”指所有查询合计的检查次数，同一条记录会被反复检查。它不能直接换算成运行时间，还要知道每条检查的成本和允许等待多久。

这还没有计入排序。一次命中 $r$ 条记录，比较排序的成本上界为 $O(r\log r)$，返回结果本身也有成本。按键查找和逐条筛选不是相同的基本操作，不能只根据调用次数算出它们各占多少运行时间。

## 比较准备、查询与更新

可以考虑三种方案：

| 方案 | 每次筛选的工作 | 准备与更新的代价 |
| --- | --- | --- |
| 扫描全部记录 | 检查 $n$ 条，再排序命中项 | 无额外分类结构 |
| 保存按分类排序的列表 | 二分找到分类范围，检查其中的 $k$ 条，再排序命中项 | 初次排序；追加或改分类时要维护有序性 |
| 维护“分类 → 记录列表”索引 | 按分类取得 $k$ 条，检查后排序命中项 | 初次分组、额外空间；追加或改分类时要维护分组 |

这里的排序列表按分类排列，不能同时保证每次筛选的结果按评分排列。两种整理方法都减少了扫描范围，但都还有查询和更新成本。

下面实际比较全库扫描与分类索引。两次使用同一个查询函数，区别只在交给它检查的记录范围。

新增的排列要求由 `sorted(matched, key=ranking_key)` 完成：它返回排好序的新列表，不修改 `matched`。`key` 指定一个函数，为每本书生成比较用的值；这里把函数交给排序工具，不在这个位置自己调用它。`ranking_key` 返回元组 `(-评分, 编号)`，元组先比较第一项，再比较第二项。评分前加负号，升序排列便得到评分从高到低、同分编号从小到大的结果。规则见 [Python 排序指南：键函数](https://docs.python.org/3/howto/sorting.html#key-functions)。

```python run id="data-algorithms-and-scale.design-review.group-query"
books = [
    {"id": "b1", "category": "science", "available": True, "rating": 4.0},
    {"id": "b2", "category": "science", "available": False, "rating": 4.9},
    {"id": "b3", "category": "history", "available": True, "rating": 4.7},
    {"id": "b4", "category": "science", "available": True, "rating": 4.5},
    {"id": "b5", "category": "science", "available": True, "rating": 3.0},
    {"id": "b6", "category": "science", "available": False, "rating": 4.8},
]
by_category = {}
for book in books:
    category = book["category"]
    if category not in by_category:
        by_category[category] = []
    by_category[category].append(book)


def ranking_key(book):
    return (-book["rating"], book["id"])


def query(records, category, threshold):
    matched = []
    for book in records:
        if book["category"] == category and book["available"] and book["rating"] >= threshold:
            matched.append(book)
    return sorted(matched, key=ranking_key)


category_books = by_category.get("science", [])
print("whole scan:", query(books, "science", 4.0))
print("category scan:", query(category_books, "science", 4.0))
print("records checked:", len(books), len(category_books))
```

两次输出都先是 `b4`、再是 `b1`。分类索引让第二次检查五条科学类书目，全库扫描检查六条；查历史类时则只需检查一条。类别数量没有说明每类包含多少记录。若目标分类包含绝大多数书目，$k$ 接近 $n$，就省不了多少。只有各类数量近似均匀时，才可以估计 $k\approx n/20$。

## 更新以后，哪些假设还要成立

借出一本书时，只修改它的 `available`，按分类索引仍有效，因为分类没变，查询也会重新检查可借状态。把一本书改到另一类，就要从旧分类列表移除，再加入新分类列表。共享记录对象不会自动维护这种分组关系。

每个编号还必须唯一标识需求中的一本书。如果同一书目编号下要保存多册副本，单个字典值就要能表达这些副本；若每册分别编号，也要明确编号代表什么。先确定数据含义，再决定同名键该覆盖、合并还是拒绝。

## 练习

为了进一步减少扫描，有人提出分类分组只保存当前可借的书，借出、归还时只修改原记录。下面的方案在两次状态更新后，查询是否仍符合要求？共享记录对象解决了哪些更新，又有哪些信息需要另外维护？

```python run id="data-algorithms-and-scale.design-review.exercise-availability-index"
books = [
    {"id": "b1", "category": "science", "available": True},
    {"id": "b2", "category": "science", "available": False},
]
available_by_category = {"science": []}
for book in books:
    if book["available"]:
        available_by_category[book["category"]].append(book)

books[0]["available"] = False
books[1]["available"] = True
matched_ids = []
for book in available_by_category["science"]:
    if book["available"]:
        matched_ids.append(book["id"])
print("available science books:", matched_ids)
```

再审查两个需求变化：

- 分类很少变，可借状态每天变化很多次。与保存全部分类记录相比，只保存可借记录的方案增加了哪些维护工作？你会根据什么选择？
- 查询只返回评分最高的十本。是否仍然必须排列全部命中记录？尝试用已学过的结构描述一种保留候选的方案，并说明同分时怎样处理。找到十本就立即停止扫描是否足够？
