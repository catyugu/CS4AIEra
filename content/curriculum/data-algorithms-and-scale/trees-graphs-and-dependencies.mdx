在普通目录层次里，每个子文件夹只有一个直接上级。准备发布一份网页时，生成页面却可能要同时等待下载内容和读取配置。前一种关系可以用树表示，后一种需要更一般的图。

## 树表达层次

有根的树有一个根节点，根没有上级；其余每个节点恰好有一个上级，从根沿父子关系可以到达全部节点。

```text
project
├── source
│   └── main.py
└── tests
```

节点是结构中的一个元素，连接父子节点的是边。这棵树里，`main.py` 的上级是 `source`，`source` 的上级是 `project`。沿上级追溯，不会绕回自己，而会停在根。

```python run id="data-algorithms-and-scale.trees-graphs-and-dependencies.layers"
parent = {"project": None, "source": "project",
          "main.py": "source", "tests": "project"}
node = "main.py"
depth = 0
while parent[node] is not None:
    node = parent[node]
    depth += 1
print("root:", node, "depth:", depth)
```

深度是从根到该节点经过的边数。根的深度为 0，`main.py` 为 2。找上级直到根，需要的步数随深度增长：相同数量的节点，排成很长的单链和较浅的分支结构，查找步数可以很不一样。

`parent[node] is not None` 检查这个节点是否还有上级。程序假定 `parent` 真正表示一棵树，且所有上级都在字典里。只规定“每个节点至多一个上级”还不足以保证这一点：两个节点互为上级就会形成环，追溯就无法停在根。

## 图表达更一般的关系

图由节点与边组成。下面用有向<Term id="simple-graph">简单图</Term>表示依赖关系，其中边 `build → test` 表示必须先完成 `build`，才能开始 `test`：

```text
fetch → build → test
config ───┘
```

这里 `fetch` 表示下载内容，`config` 表示读取配置，`build` 表示生成页面，`test` 表示检查结果。`build` 同时等待 `fetch` 和 `config`，这种多个前置的关系不能用一个上级表达。箭头从前置指向后续任务，方向不能反过来读。

从一个节点沿有向边连续前进，能到达另一个节点，就称后者从前者可达。依赖图中，修改 `fetch` 的结果可能影响 `build`，再影响 `test`。下面把每个节点直接指向的后续节点保存成列表，用队列逐项检查：

```python run id="data-algorithms-and-scale.trees-graphs-and-dependencies.reachable"
from collections import deque

after = {"fetch": ["build"], "config": ["build"],
         "build": ["test"], "test": []}
pending = deque(["fetch"])
seen = {"fetch"}
while pending:
    node = pending.popleft()
    for next_node in after[node]:
        if next_node not in seen:
            seen.add(next_node)
            pending.append(next_node)
print("reachable, including start:", sorted(seen))
```

`after[node]` 保存这个节点直接指向的后续节点。先从 `fetch` 发现 `build`，再从 `build` 发现 `test`；`config` 不在这条方向的路径上。`seen.add(next_node)` 把新发现的节点加入集合，`sorted(seen)` 将集合元素排好序后返回列表，让输出次序固定。

| 刚取出的节点 | 检查后队列中的节点 | 已发现的节点 |
| --- | --- | --- |
| 尚未取出 | fetch | fetch |
| fetch | build | fetch、build |
| build | test | fetch、build、test |
| test | 空 | fetch、build、test |

队列保存已发现但还没检查后续边的节点，`seen` 保存所有已发现节点。二者用途不同；最终的排序输出只方便核对，不表示发现次序。

这种使用先进先出队列、逐层发现可达节点的过程称为<Term id="breadth-first-traversal">广度优先遍历</Term>（BFS）。`seen` 避免同一个节点重复加入队列。输出包括起点本身。即使有限图里有环，每个节点也最多入队一次，遍历仍会结束。这里找的是“从起点能到哪里”，没有安排任务执行；`build` 是否已经等到全部前置完成，要另外判断。

## 依赖环与执行顺序

要安排执行，必须把每个任务放在全部前置之后。这种顺序称为<Term id="topological-order">拓扑序</Term>。上图可以按 `fetch, config, build, test` 执行，也可以交换前两个任务，顺序不一定唯一。

如果再加入 `test → build`，`build` 等 `test`，`test` 又等 `build`，形成<Term id="cycle">环</Term>。在“全部前置完成后才能开始”的规则下，谁都不能先完成，因而不存在满足全部依赖的顺序。

可以维护每个任务尚未完成的前置数量，将数量为 0 的任务放入队列。每取出一个任务，就把它的后续任务的未完成前置数量减 1；某个后续任务变成 0 时，加入队列。这是 Kahn 拓扑排序的思路。

对上面的图，过程如下：

| 时刻 | 可执行任务 | 等待中的任务 |
| --- | --- | --- |
| 开始 | fetch、config | build 等两个前置，test 等 build |
| fetch 完成 | config | build 还等 config |
| config 完成 | build | test 还等 build |
| build 完成 | test | 无 |
| test 完成 | 无 | 无 |

如果加入 `test → build`，完成前两个任务后，`build` 还等 `test`，`test` 还等 `build`，队列为空，但任务没有完成。在所有前置都有效、节点都已列出的假设下，这表示存在依赖环。

未完成任务不一定全在环上：以 `test` 为前置的 `publish` 也会被阻塞，却不在 `build → test → build` 这个环中。
