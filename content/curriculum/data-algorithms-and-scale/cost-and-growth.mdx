一个列表有 100 项时，逐项求和只做 100 次加法；检查每两个位置上的值是否相等，要比较 4950 次。代码都不长，列表变成 10000 项以后，差距却会大幅增加。要判断方案能处理多大规模，需要数清程序实际重复了哪些工作。

## 先选一种可以数的工作

<Term id="input-size">输入规模</Term>记作 $n$，这里指列表的元素个数。求和时数加法，检查元素对时数值比较。比较两种实现的计数时，还要确认它们数的是同一种操作；一次比较和一次文件读取不能直接当成相同用时。

暂时假定读取一个列表位置、比较两个小整数、做一次小整数加法，各自的成本不随 $n$ 改变。这是一个简化的成本模型：第一个位置和最后一个位置同样容易读取，小整数不会因列表变长而更难相加。超长字符串和很大的整数则还要考虑自身长度。

下面的函数真实地计算结果，同时记录完成计算所需的加法或比较次数。计数不测耗时；可以改动 `values`，观察规模、结果与次数分别怎样变化。

```python run id="data-algorithms-and-scale.cost-and-growth.sum-and-pairs"
def total(values):
    answer = 0
    additions = 0
    for value in values:
        answer += value
        additions += 1
    return answer, additions


def equal_pairs(values):
    pairs = []
    comparisons = 0
    for i in range(len(values)):
        for j in range(i + 1, len(values)):
            comparisons += 1
            if values[i] == values[j]:
                pairs.append((i, j))
    return pairs, comparisons


values = [2, 5, 2, 8]
print("sum, additions:", total(values))
print("equal pairs, comparisons:", equal_pairs(values))
```

`range(n)` 依次给出 0 到 $n-1$ 的整数；`range(i + 1, n)` 给出 $i+1$ 到 $n-1$ 的整数。`(i, j)` 用元组保存一对下标。`return answer, additions` 返回由两个值组成的元组，分别是计算结果和计数。

求和遍历四项，做四次加法。查找相等元素对时，第一个位置和后面三个位置比较，第二个和后面两个比较，第三个再和最后一个比较：共 3+2+1=6 次。有没有找到相等的值，不改变这些比较次数。把列表改成四个互不相同的数，输出结果会变成空列表，比较工作仍然存在。

## 从一次计数得到增长规律

求和的加法次数为 $n$；元素对比较次数为

$$ (n-1)+(n-2)+\dots+1=\frac{n(n-1)}{2} $$

右边的计数可以这样理解：每个位置与其他 $n-1$ 个位置配对，一共计入 $n(n-1)$ 次；但一对位置被正反各计一次，所以除以 2。代码让第二个下标始终大于第一个，恰好保留每对一次。

| 元素数 | 求和的加法次数 | 元素对的比较次数 |
| --- | ---: | ---: |
| 100 | 100 | 4950 |
| 200 | 200 | 19900 |
| 400 | 400 | 79800 |

求和的次数与 $n$ 成正比，称为线性增长。两两比较包含 $n^2$ 项，称为二次增长；元素数翻倍，比较次数逐渐接近原来的四倍。只看当前四项的运行速度，很难察觉这种差别。

读取非空列表的第一项只需一次读取，不管列表多长，这是常数工作。这里关注的是要完成的操作次数，不是函数写了几行。

所需空间也由结果决定。求和只保留一个累加值；若所有元素都相等，`equal_pairs` 的结果列表有 $n(n-1)/2$ 项，结果空间也会二次增长。若需求只问“有没有重复值”，找到一对就能停止，也无须保存全部元素对。先确认要返回什么，才能判断哪份工作真的必要。

## 减半与分层合并的成本

在有序列表里找一个值，可以比较中间元素，再把可能位置缩到一半。原来有 16 个可能位置，缩成 8、4、2、1，只需四次减半；原来有 32 个，则需要五次。

把 $n$ 连续除以 2，直到剩下 1，需要约 $\log_2 n$ 次。这里的对数回答的是“2 的几次方等于 $n$”。元素数翻倍，所需减半次数只多一次，所以二分查找的最坏比较次数是对数增长。具体定位方式见 <CrossRef id="data-algorithms-and-scale.representation-preprocessing-and-indexes" />。

还有一种常见增长是 $n\log_2 n$。例如把八个数不断分成两半，直到每组只有一个数，再逐层把两组已经排好序的数合并：

| 合并阶段 | 合并后的组数与每组长度 | 这一层处理的元素总数 |
| --- | --- | ---: |
| 两个单项合并 | 4 组，每组 2 项 | 8 |
| 每两个 2 项组并成一组 | 2 组，每组 4 项 | 8 |
| 两个 4 项组并成一组 | 1 组，共 8 项 | 8 |

合并两组有序的数时，比较两组尚未取出的第一个数，取较小的那个；一组取完后，直接取另一组的剩余项。每层都处理全部元素；八项需要三层，十六项需要四层。一般地，层数约为 $\log_2 n$，每层工作与 $n$ 成正比，总工作就与 $n\log_2 n$ 成正比，称为线性对数增长。这解释了归并排序的成本来源。

## 用增长阶描述一类成本

精确计数适合推导，但比较大规模方案时，常把固定倍数和较低次项省去。例如 $n(n-1)/2$ 展开是 $n^2/2-n/2$，规模增大后主要由二次项决定。算法资料用渐近记号描述这样的增长关系。

$O(n^2)$ 表示渐近上界：当 $n$ 足够大，工作量不超过某个固定倍数的 $n^2$。$\Theta(n^2)$ 进一步表示渐近紧确界：工作量也不会低于某个正的固定倍数的 $n^2$。这里的“固定”要求倍数不随 $n$ 增加。

例如设操作次数为 $T(n)=3n+2$。当 $n\ge 1$ 时，$3n\le T(n)\le 5n$，因此它在两个固定倍数的 $n$ 之间，记作 $\Theta(n)$。上面的求和也是 $\Theta(n)$，元素对比较是 $\Theta(n^2)$。

上界可以很宽松：线性工作量也属于 $O(n^2)$，因为它没有超过二次增长的上限。因此报告只写“$O(n^2)$”时，不能就推断翻倍会增加四倍工作。这里的近四倍关系来自具体计数公式；$\Theta$ 本身也不保证每次翻倍的准确比值。完整定义见<Term id="asymptotic-notation">渐近记号</Term>。

| 增长阶 | 典型工作 |
| --- | --- |
| $\Theta(1)$ | 读取一个已知位置 |
| $\Theta(\log n)$ | 二分查找的最坏比较次数 |
| $\Theta(n)$ | 逐项求和 |
| $\Theta(n\log n)$ | 逐层合并的工作量 |
| $\Theta(n^2)$ | 检查所有元素对 |
| $\Theta(2^n)$ | 对每个子集各做固定数量的工作 |

最后一行来自每个元素“选或不选”的二选一：每多一个元素，子集数翻倍。候选数的估算与方案取舍见 <CrossRef id="data-algorithms-and-scale.search-pruning-and-branch-and-bound" />。

## 增长阶不能确定实际运行时间

固定倍数会影响小规模结果。假设方案甲要做 $4n$ 份工作，方案乙要做 $n(n-1)/2$ 份工作，计数单位相同。$n=4$ 时分别为 16 和 6，乙更少；$n=100$ 时分别为 400 和 4950，甲更少。只看一个小样例，就可能选错适合大规模的方案。

渐近记号也不能直接回答“能否在一秒内结束”。要先按程序推导工作量，再在目标环境测量实际时间。有限几个规模的测量有助于检查估算，却不能证明所有规模的增长律。操作成本的建模方法可参阅 [MIT 6.006：计算模型与 Python 成本](https://ocw.mit.edu/courses/6-006-introduction-to-algorithms-fall-2011/resources/mit6_006f11_lec02/)。

## 练习

有 $n$ 条记录，每条有 $m$ 个指标。计算每条记录的指标总和，要做多少次加法？分别考虑“只增加记录数”和“记录数、指标数同时翻倍”。为什么只写“这是两层循环，所以是二次增长”不足以描述成本？

两种实现的工作量分别是 $3n+2$ 和 $100n+2$，计数单位相同。它们的增长阶是否相同？在同一规模下，是否做了同样多的工作？还需要什么信息，才能判断它们实际用时的差别？
