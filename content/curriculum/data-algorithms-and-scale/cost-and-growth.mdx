同样是遍历一个列表，计算总和与检查所有元素对，需要的工作量不同。列表变长后，一个程序仍然很快，另一个可能慢得多。判断原因时，先看它到底重复了哪些操作。

## 规模和计数单位

<Term id="input-size">输入规模</Term>记作 $n$，这里指列表的元素个数。暂时把读取一个元素、比较两个小整数、做一次小整数加法都按固定成本计；列表的第一个位置和最后一个位置读取成本相同。

这是一个简化的成本模型。它允许我们比较操作次数怎样增长，不等于每种操作在机器上用时完全相同。超长字符串和很大的整数也不能始终按固定成本处理。

## 逐项计算与两两比较

下面两个函数分别计算总和、找出值相等的元素对。返回的计数帮助我们观察实际执行了多少次加法或比较。

```python run id="data-algorithms-and-scale.cost-and-growth.sum-and-pairs"
def total(values):
    answer = 0
    additions = 0
    for value in values:
        answer += value
        additions += 1
    return answer, additions


def equal_pairs(values):
    pairs = []
    comparisons = 0
    for i in range(len(values)):
        for j in range(i + 1, len(values)):
            comparisons += 1
            if values[i] == values[j]:
                pairs.append((i, j))
    return pairs, comparisons


values = [2, 5, 2, 8]
print("sum and additions:", total(values))
print("equal pairs and comparisons:", equal_pairs(values))
```

`range(n)` 依次给出 0 到 $n-1$ 的整数；`range(i + 1, n)` 给出 $i+1$ 到 $n-1$ 的整数。内层循环只检查当前位置之后的元素，避免把同一对比较两遍。

四个元素求和需要四次加法。检查元素对则比较 3+2+1=6 次，找到下标 `(0, 2)` 上的两个 2。

一般地，求和需要 $n$ 次加法，元素对比较需要

$$ (n-1)+(n-2)+\dots+1=\frac{n(n-1)}{2} $$

次。这是把每个位置与它后面的所有位置配对得到的计数，不取决于有没有找到重复值。

| 元素数 | 求和的加法次数 | 元素对的比较次数 |
| --- | ---: | ---: |
| 100 | 100 | 4950 |
| 200 | 200 | 19900 |
| 400 | 400 | 79800 |

求和的工作量与 $n$ 成正比，称为线性增长。两两比较包含一个二次项，称为二次增长；元素数翻倍，比较次数逐渐接近原来的四倍。

读取一个非空列表的第一项只需一次读取，不管列表有多长，这是常数工作。三种计算都可能只有几行代码，代码长度说明不了执行次数。

还要看额外保存了多少数据。求和只保留一个累加结果；`equal_pairs` 保存所有相等元素对。若所有元素都相等，结果列表就有 $n(n-1)/2$ 项，存储量也会二次增长。若需求只问“有没有重复值”，找到一对就可以结束，没有必要生成全部元素对。计算什么结果，会同时影响时间和空间成本。

## 每次减半为什么是对数增长

在有序列表里找一个值，可以比较中间元素，再把可能位置缩到一半。原来有 16 个可能位置，缩成 8、4、2、1，只需四次减半；原来有 32 个，则需要五次。

把 $n$ 连续除以 2，直到剩下 1，需要约 $\log_2 n$ 次。这里的对数回答的是“2 的几次方等于 $n$”。元素数翻倍，所需减半次数只多一次，所以二分查找的最坏比较次数是对数增长。具体定位方式见 <CrossRef id="data-algorithms-and-scale.representation-preprocessing-and-indexes" />。

如果一种计算有约 $\log_2 n$ 层，每层处理全部 $n$ 个元素，总工作就约为 $n\log_2 n$。例如把序列不断一分为二，再合并有序的两半：每个合并层处理全部元素，层数随 $\log_2 n$ 增长。这解释了常见比较排序的线性对数成本，不要求亲手实现排序。

## 上界与紧确增长阶

算法资料通常用 $O$ 或 $\Theta$ 描述增长。它们不写固定倍数和较低次项，但含义不同。

- $O(n^2)$ 给出渐近上界：足够大时，工作量不超过某个固定倍数的 $n^2$。
- $\Theta(n^2)$ 给出紧确增长阶：足够大时，工作量既不低于某个正的固定倍数的 $n^2$，也不超过另一个固定倍数的 $n^2$。

例如 $T(n)=3n+2$。当 $n\ge 1$ 时，$3n\le T(n)\le 5n$，所以它的工作量被两个固定倍数的 $n$ 夹住，可以写成 $\Theta(n)$。这里 $T(n)$ 表示规模为 $n$ 时的操作次数。完整的符号定义见<Term id="asymptotic-notation">渐近记号</Term>。

上面的求和是 $\Theta(n)$，元素对比较是 $\Theta(n^2)$。线性工作同样可以写成 $O(n^2)$，因为这是一个宽松上界；因此单凭 $O(n^2)$ 不能断言“翻倍约四倍”。该例的翻倍比值来自具体公式。$\Theta$ 也只规定固定倍数的范围，不规定每次翻倍的准确比值。

| 增长阶 | 典型工作 |
| --- | --- |
| $\Theta(1)$ | 读取一个已知位置 |
| $\Theta(\log n)$ | 二分查找的最坏比较次数 |
| $\Theta(n)$ | 逐项求和 |
| $\Theta(n\log n)$ | 逐层合并的工作量 |
| $\Theta(n^2)$ | 检查所有元素对 |
| $\Theta(2^n)$ | 对每个子集各做固定数量的工作 |

最后一行来自每个元素“选或不选”的二选一：每多一个元素，子集数翻倍。候选数的估算与方案取舍见 <CrossRef id="data-algorithms-and-scale.search-pruning-and-branch-and-bound" />。

## 增长阶不能确定实际运行时间

固定倍数会影响小规模结果。假设方案甲要做 $4n$ 份工作，方案乙要做 $n(n-1)/2$ 份工作，计数单位相同。$n=4$ 时分别为 16 和 6，乙更少；$n=100$ 时分别为 400 和 4950，甲更少。只看一个小样例，就可能选错适合大规模的方案。

渐近记号也不能直接回答“能否在一秒内结束”。要先按程序推导工作量，再在目标环境测量实际时间。有限几个规模的测量有助于检查估算，却不能证明所有规模的增长律。操作成本的建模方法可参阅 [MIT 6.006：计算模型与 Python 成本](https://ocw.mit.edu/courses/6-006-introduction-to-algorithms-fall-2011/resources/mit6_006f11_lec02/)。
