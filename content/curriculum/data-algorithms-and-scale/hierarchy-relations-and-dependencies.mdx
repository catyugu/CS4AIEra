目录中的一个文件夹有一个上级；构建任务却可能要等待多个任务完成。树与图能表达这两种不同的关系。

## 树表达层次

有根的树有一个根节点，根没有上级；其余每个节点恰好有一个上级，从根沿父子关系可以到达全部节点。

```text
project
├── source
│   └── main.py
└── tests
```

节点是结构中的一个元素，连接父子节点的是边。这棵树里，`main.py` 的上级是 `source`，`source` 的上级是 `project`。沿上级追溯，不会绕回自己，而会停在根。

```python run id="data-algorithms-and-scale.hierarchy-relations-and-dependencies.layers"
parent = {"project": None, "source": "project",
          "main.py": "source", "tests": "project"}
node = "main.py"
depth = 0
while parent[node] is not None:
    node = parent[node]
    depth += 1
print("root:", node, "depth:", depth)
```

深度是从根到该节点经过的边数。根的深度为 0，`main.py` 为 2。找上级直到根，需要的步数随深度增长：相同数量的节点，排成很长的单链和较浅的分支结构，查找步数可以很不一样。

上述程序假定 `parent` 真正表示一棵树，且所有上级都在字典里。只规定“每个节点至多一个上级”还不足以保证这一点：两个节点互为上级就会形成环。

## 图表达更一般的关系

图由节点与边组成。依赖关系中的有向边 `build → test` 表示必须先完成 `build`，才能开始 `test`：

```text
fetch → build → test
config ───┘
```

`build` 同时等待 `fetch` 和 `config`，这种多个前置的关系不能用一个上级表达。边的方向有含义：完成 `build` 可以让 `test` 更接近就绪，反过来不成立。这里把依赖表示为有向<Term id="simple-graph">简单图</Term>，不包含自环和同端点的重复边。

从一个节点沿有向边连续前进，能到达另一个节点，就称后者从前者可达。依赖图中，修改 `fetch` 的结果可能影响 `build`，再影响 `test`。下面把每个节点直接指向的后续节点保存成列表，用队列逐项检查：

```python run id="data-algorithms-and-scale.hierarchy-relations-and-dependencies.reachable"
from collections import deque

after = {"fetch": ["build"], "config": ["build"],
         "build": ["test"], "test": []}
pending = deque(["fetch"])
seen = {"fetch"}
while pending:
    node = pending.popleft()
    for next_node in after[node]:
        if next_node not in seen:
            seen.add(next_node)
            pending.append(next_node)
print("reachable, including start:", sorted(seen))
```

`seen` 记录已经发现的节点，避免同一个节点重复加入队列。输出包括起点本身。即使图里有环，也不会因重复入队而一直循环；每个节点最多入队一次。

## 依赖环与执行顺序

要安排执行，必须把每个任务放在全部前置之后。这种顺序称为<Term id="topological-order">拓扑序</Term>。上图可以按 `fetch, config, build, test` 执行，也可以交换前两个任务，顺序不一定唯一。

如果再加入 `test → build`，`build` 等 `test`，`test` 又等 `build`，形成<Term id="cycle">环</Term>。在“全部前置完成后才能开始”的规则下，谁都不能先完成，因而不存在满足全部依赖的顺序。

简单的排法是反复挑一个前置都已排好的任务。下面按任务名选择第一个就绪项，因此相同输入给出固定输出。字典里的列表保存**前置**，与上面保存后续的 `after` 方向相反；所有前置都必须是字典中的任务。

```python run id="data-algorithms-and-scale.hierarchy-relations-and-dependencies.order"
requires = {"fetch": [], "config": [],
            "build": ["fetch", "config"], "test": ["build"]}
order = []
left = sorted(requires)
while left:
    ready = None
    for task in left:
        waiting = False
        for prereq in requires[task]:
            if prereq not in order:
                waiting = True
                break
        if not waiting:
            ready = task
            break
    if ready is None:
        break
    order.append(ready)
    left.remove(ready)
print("order:", order)
print("not scheduled:", left)
```

`remove` 从列表中删除指定值。每轮排出一项，或因没有就绪项而退出。若还剩任务却没有任何就绪项，在前置都有效、没有遗漏节点的假设下，就存在依赖环。剩余任务既可能在环中，也可能只是等待环中的任务，不能把它们全都称为环上的节点。

这个实现方便观察“找就绪项”的规则，反复扫描的成本可能很高。大图上可以维护每个节点尚未完成的前置数量，配合队列避免重复扫描。

## 练习

给 `build` 增加前置 `test`，再增加一个以 `test` 为前置的 `publish` 任务。预测排出的顺序和剩余任务，再运行。哪些任务真正位于环中，哪些只是受环阻塞？如果只删除一个依赖，怎样恢复可执行顺序？
