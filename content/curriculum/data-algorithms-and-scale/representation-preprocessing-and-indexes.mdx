同一批书目，按编号打开详情、按分类筛选、追加记录，做的是不同的操作。数据怎样组织，取决于以后要反复执行什么操作，以及愿意为准备和更新付出多少工作。

<Term id="workload">工作负载</Term>描述操作的种类、次数，以及数据的规模与分布。每天查一次与每天查几万次，可能适合不同的结构。

## 三种组织方式保留什么

假定书目编号唯一，按编号查询要返回对应记录。原始列表保存全部记录和原有次序；排序会改变排列；以编号为键的字典增加“编号 → 记录”的定位关系。若编号重复，写入同一个字典键会覆盖已有值，不能直接用它保留多个版本。

| 组织方式 | 准备 | 查询 | 更新 | 保留的信息 |
| --- | --- | --- | --- | --- |
| 原始列表 | 无额外整理 | 通常逐条扫描 | 可直接追加或修改 | 原顺序与全部记录 |
| 按字段排序的列表 | 排序 | 按该字段缩小范围 | 插入或改字段时维护有序性 | 全部记录，按选定字段排列 |
| 额外按键索引 | 建立定位关系 | 按索引键取得对应记录 | 同步维护键与记录的关系 | 原数据，加上额外映射 |

## 有序性怎样减少查询工作

编号 `[8, 2, 11, 5, 1]` 排序后是 `[1, 2, 5, 8, 11]`。找 8 时先比较中间的 5：因为列表已按编号递增排列，5 以及它左边的编号都小于 8，可以一起排除。剩下 8、11，再比较 8，就找到目标。

这叫二分查找。每次用中间值与目标的大小关系缩小候选范围。找不存在的 7 时，先排除 5 及左边，再发现 8 已经大于 7；最后没有任何候选，才能确定不存在。这个排除理由依赖有序性，按评分排序的记录不能用相同办法查编号。

以下函数用两个下标保留候选范围：`left` 指向第一项，`right` 指向最后一项，两端都包括在内。函数返回找到的位置；没有找到时返回 `None`。可以改目标，也可以故意打乱列表，检查排除过程是否仍可信。

```python run id="data-algorithms-and-scale.representation-preprocessing-and-indexes.binary-search"
def find_position(values, target):
    left = 0
    right = len(values) - 1
    while left <= right:
        middle = (left + right) // 2
        print("range:", left, right, "middle value:", values[middle])
        if values[middle] == target:
            return middle
        if values[middle] < target:
            left = middle + 1
        else:
            right = middle - 1
    return None


values = [1, 2, 5, 8, 11]
print("position:", find_position(values, 8))
```

`// 2` 将非负整数除以 2 后取整数部分，用来选中间位置。排除左半边时，将 `left` 移到中间位置之后；排除右半边时，将 `right` 移到中间位置之前。每轮至少排除刚比较的位置，范围最终变空或找到目标，循环不会停在同一范围里。

## 整理一次，查询多少次才值得

有 $n$ 条记录、$q$ 次查询，每次编号比较按固定成本计算，查询期间数据不变。直接扫描的单次最坏成本为 $O(n)$，总上界为 $O(qn)$。先排序再二分，成本上界为 $O(n\log n+q\log n)$：准备工作只做一次，查询工作做 $q$ 次。

仅列出这两个式子，还不能得到一个精确的查询次数门槛；排序与查询的固定倍数、扫描何时提前找到，都有影响。可以先比较明确假设下的最坏预算。例如 1024 条记录，扫描每次至多比较 1024 项；上面的二分代码至多检查 11 个中间位置，每轮先判断相等，不相等时再比较大小，因此按至多 22 次数值比较计。再假定选用的排序实现准备时至多做 10240 次比较。

| 查询次数 | 直接扫描的比较次数预算 | 排序并查询的比较次数预算 |
| --- | ---: | ---: |
| 1 | 1024 | 10240 + 22 |
| 1000 | 1024000 | 10240 + 22000 |

偶尔查一次时，整理的工作可能超过它省下的查询工作。反复查同一批数据，准备成本才有机会被抵消。这张表只比较给定假设下的工作预算；真实查询可能提前命中，排序也需要按实际实现核对，不能据此断言所有查询都耗费这些次数。

记录还会变化：在有序列表中插入新项可能需要移动后面的元素，修改排序字段后也要重新定位。更新频繁时，需要把维护成本一起计入。标准库提供二分定位工具，见 [Python bisect](https://docs.python.org/3/library/bisect.html)。

## 按键索引加速哪种查询

索引保存从查询条件到记录的定位关系。主列表保留记录，额外字典按编号定位：

```python run id="data-algorithms-and-scale.representation-preprocessing-and-indexes.record-sharing"
books = [{"id": "b1", "category": "science", "price": 30}]
by_id = {}
for book in books:
    by_id[book["id"]] = book

by_id["b1"]["price"] = 35
print("price in original list:", books[0]["price"])
print("same record:", books[0] is by_id["b1"])
```

`by_id` 与主列表指向同一条记录，价格修改从两处都可见。但这个索引只能直接回答编号查询：按分类筛选时仍要扫描，或者另建“分类 → 记录列表”的索引。改动编号或分类时，共享对象不会自动改写索引里的键和分组；完整维护案例见 <CrossRef id="data-algorithms-and-scale.design-review" />。

## 哈希怎样缩小按键查找的范围

Python 字典通常用哈希表实现。它先从键计算一个整数，称为<Term id="hash-value">哈希值</Term>，用这个值缩小候选范围，再比较原键确认是哪条记录。

可以用下面的简化分组看这一过程。假定四个编号的哈希值如下；这些数只是教学假设，不是 Python 对这些字符串的实际计算结果，也不表示 CPython 的内存布局。

| 键 | 假定哈希值 | 对应候选组 |
| --- | ---: | --- |
| b1 | 2 | b1、b3 |
| b2 | 1 | b2 |
| b3 | 2 | b1、b3 |
| b4 | 0 | b4 |

查 b3 时，先计算出 2，只在候选组 b1、b3 中比较原键，不必检查 b2、b4。b1 和 b3 的哈希值相同，称为冲突；比较原键仍能区分它们。若另一个不存在的编号也算出 2，检查完这一组都不匹配，就应报告不存在，不能返回任意一条记录。

候选分布较分散、定位结构也随数据量适当扩充时，每次只需检查少量原键。若许多键发生冲突，候选组会很长，仍可能检查大量记录。哈希值能帮助定位，不能作为唯一的业务编号。

在通常的哈希分布、固定成本的键处理假设下，按键查找的平均成本为 $O(1)$，最坏情况可能为 $O(n)$。这是实现与输入条件共同产生的性能性质；“映射能按键取值”本身不保证速度。具体实现说明见 [Python FAQ：字典如何实现](https://docs.python.org/3/faq/design.html#how-are-dictionaries-implemented-in-cpython)。

额外索引占空间，建立时要读取数据，后续更新也要维护。按分类索引可把查询范围从全部 $n$ 条缩到该分类的 $k$ 条；可借状态和评分仍要逐条检查，结果排序仍有成本。若目标分类包含大部分记录，节省就有限。
