在一份不变的记录列表中找一条记录，可以从头逐条比对。但如果同样的查找要做很多次，先整理数据可能更合算。

## 有序列表有助于高效排除候选

在无序列表 `[8, 2, 11, 5, 1]` 中找 5，通常要逐项检查。排序后得到 `[1, 2, 5, 8, 11]`。先看中间的 5，就已经找到目标；如果目标是 8，因为 8 大于中间值 5，可以排除左半边。

反复取中间值、排除一半可能位置，就是二分查找。前提是列表按同一种比较规则排好。排序后仍然逐项扫描，不会自动变成二分查找。

Python 标准库的 [bisect](https://docs.python.org/3/library/bisect.html#bisect.bisect_left)可以找到一个值应当插入的位置：

```python run id="data-algorithms-and-scale.preprocessing-and-indexes.lookup"
from bisect import bisect_left

ids = [8, 2, 11, 5, 1]
ordered = sorted(ids)
for wanted in (8, 7, 12):
    position = bisect_left(ordered, wanted)
    if position < len(ordered) and ordered[position] == wanted:
        print(wanted, "found at:", position)
    else:
        print(wanted, "not found; insertion position:", position)
```

`bisect_left` 给出插入位置，不保证目标已经存在。找 7 时，返回的位置上是 8；找 12 时，返回列表长度，不能再用这个下标读取元素。判断是否找到，需要先检查下标是否有效，再比较该位置的值。这里 `and` 按从左到右的顺序求值：左边为假时就不再求值右边，因此不会访问越界下标。

如果目标重复出现，`bisect_left` 给出第一个相等元素的位置。需要全部匹配项时，还要找到这段重复值的终点。

## 排序成本要由后续查询收回

设有 $n$ 条记录，进行 $q$ 次查询，每次比较标识的成本固定。逐条扫描最坏要比较 $qn$ 次；采用最坏成本为 $O(n\log n)$ 的排序后，每次二分查询的成本为 $O(\log n)$，总成本上界为

$$O(n\log n + q\log n).$$

这里包含了排序，不能只拿一次二分查询与一次扫描比较。只查一次时，排序可能比扫描更费事；反复查询不变的数据，才有机会收回预处理成本。实际交叉点由实现、数据和查询位置决定，需要测量，不能把一个增长阶直接当成运行时间。

## 索引保存从查询条件到记录的查找信息

如果关心的是运行标识，用字典也能建立索引。主列表保留全部记录，额外的字典保存“标识 → 对应记录”。

```python run id="data-algorithms-and-scale.preprocessing-and-indexes.index"
runs = [
    {"run_id": "r1", "group": "A", "score": 0.8},
    {"run_id": "r2", "group": "B", "score": 0.5},
    {"run_id": "r3", "group": "A", "score": 0.7},
]
by_id = {}
by_group = {}
for run in runs:
    by_id[run["run_id"]] = run
    group = run["group"]
    if group not in by_group:
        by_group[group] = []
    by_group[group].append(run)

print("one run:", by_id["r2"])
print("group A:", by_group["A"])
```

`by_id` 回答按标识查详情，`by_group` 回答某个参数组有哪些记录。两份索引加速的操作不同。这里假设标识唯一；同一标识重复写入会覆盖旧值。

索引占用额外空间。这里的字典和列表保存的是原记录的引用，没有复制记录本身。如果修改一条记录的 `score`，索引读到的也是新指标；但如果把它的 `group` 从 A 改成 B，`by_group` 不会自动把它从 A 的列表移到 B。主数据改变，查询结构也要相应更新。

排序也是如此：往有序列表中追加一个值，不保证列表继续有序；插到正确位置则可能要移动后面的元素。预处理能减少查询工作，维护结构会增加写入工作。

## 练习

在索引例子中，把 `r1` 的参数组从 A 改成 B。直接改记录之后，`by_group["A"]` 和 `by_group["B"]` 分别会返回什么？更新哪些容器，才能让查询再次符合数据？
