“把符合条件的结果找出来，按指标排序，还能点开看详情。”

这是一项需求，但还不足以决定怎样实现。“符合条件”具体指什么？指标相同时怎样排序？返回全部结果还是前十条？这些选择会改变程序应当返回的答案。

## 写清输入和输出

以一个仿真结果库为例，每次运行有标识、参数组、是否成功和指标值。假设指标越大越好，用户要查询某个参数组中指标不低于门槛的成功运行。

| | 约定 |
| --- | --- |
| 输入 | 运行记录、目标参数组、指标门槛 |
| 输出 | 全部符合条件的记录，按指标从大到小排列 |
| 筛选规则 | 参数组匹配、运行成功、指标大于或等于门槛，三个条件都要满足 |
| 特殊情况 | 没有命中时返回空列表；指标相同时按运行标识排列 |

这些约定有可观察的后果：指标恰好等于门槛的记录不能漏掉，没有命中时不能返回一条“最接近”的记录。用户如果只想要前十条，也应该明确写出来。

先用几条记录检查自己是否理解了要求。字典里的字段名比 `row[2]` 这样的数字下标更容易辨认：

```python run id="data-algorithms-and-scale.from-problem-to-computation.filter"
runs = [
    {"run_id": "r1", "group": "A", "success": True, "score": 0.8},
    {"run_id": "r2", "group": "A", "success": False, "score": 0.9},
    {"run_id": "r3", "group": "B", "success": True, "score": 0.7},
    {"run_id": "r4", "group": "A", "success": True, "score": 0.5},
]
wanted_group = "A"
threshold = 0.5
matched = []
for run in runs:
    if run["group"] == wanted_group and run["success"] and run["score"] >= threshold:
        matched.append(run)
print(matched)
```

筛选得到 `r1` 和 `r4`。`r2` 的指标虽然更大，运行却失败了；`r3` 的参数组不匹配。这里还没有排序，输出恰好已经有序只是这份输入的巧合。

## 一个需求可能包含几种不同操作

“筛选结果”和“打开详情”是两种操作。筛选需要检查参数组、成功状态和指标；打开详情则已经知道 `run_id`，只需找到那一条记录。按标识查得快，不表示筛选也快。

设计之前，需要估计记录数，以及各类操作发生的次数。例如几十条记录、偶尔查询，与几百万条记录、每秒查询很多次，可能需要不同的组织方式。还要知道结果库是否持续追加、旧记录是否删除，以及一次查询允许等多久。

这些信息暂时不确定时，可以写成明确的方案假设。后续测量或真实用量超过假设，就需要重新评估方案；“数据应该不多”无法给出这个检查点。

## 保留哪些信息

筛选需要参数组、成功状态和指标，详情需要运行标识。如果指标相同时还要按运行时间排序，就必须保留运行时间。

某个字段没有参与这次计算，只说明这次计算不需要读它，不能据此决定从整个结果库删除它。历史查询、审计或其他需求可能仍然需要这个字段。
