## 目的

错误处理的目标不是让程序不报错，而是让失败以可判断的形式出现。本课建立最基本的三种能力：认出错误、在能处理它的地方捕获、并把自己发现的错误用同样的机制报出去。

## 模型

失败发生时 Python 抛出一个**异常对象**：它有一个类型（描述失败的种类）和一条消息（描述这一次的细节）。抛出会放弃当前的正常执行路径，沿调用栈向上找处理者；没有人处理，程序终止并打印回溯。

```text
try:
    可能失败的语句
except 某个异常类型 as 变量:
    处理
else:
    没有异常时运行的收尾
```

三条规则决定这段代码的行为：

- **按类型匹配**，并且子类也匹配父类；`except ValueError` 不会捕获 `TypeError`。
- **第一个匹配的子句胜出**，因此具体的类型写在前面。
- **捕获范围只应覆盖会失败的那几条语句**：范围太大就会连自己的缺陷一起吞掉。

常见的失败与它们的类型：

| 类型 | 出现过的地方 |
| --- | --- |
| `TypeError` | 类型不匹配，例如用 `str` 与 `int` 相加 |
| `ValueError` | 类型正确但内容不合法，例如 `int("abc")` |
| `KeyError` / `IndexError` | 键或位置不存在 |
| `ZeroDivisionError` | 除以零 |
| `AttributeError` | 对象上没有这个属性 |
| `FileNotFoundError` | 文件不存在（见 <CrossRef id="python.modules-basics" />） |

自定义错误用继承 `Exception` 的类表示。类型是调用方用来分支的依据，消息是给人读的细节，两者不能互相替代。

## 认出错误

```python run id="py.err.types"
def show(failure):
    print(f"{type(failure).__name__:20s} {failure}")


for operation in (
    lambda: "text" + 1,
    lambda: int("abc"),
    lambda: {"a": 1}["b"],
    lambda: [1, 2][5],
    lambda: 1 / 0,
):
    try:
        operation()
    except Exception as failure:
        show(failure)
```

类名指明失败的种类，消息指明这一处的细节。排查时先看类名确定方向，再看消息定位到具体值。

## 捕获并继续

```python run id="py.err.try-except"
def read_count(text):
    try:
        value = int(text)
    except ValueError as failure:
        return f"not an integer: {failure}"
    else:
        return value * 2


for text in ("21", "abc", "7"):
    print(f"{text!r} ->", read_count(text))

print("execution continues to this line")
```

`else` 里的代码只在没有异常时运行：把成功路径的计算放在 `else`，就不会把它的异常误当成 `int` 的失败。转换失败被就地处理成返回值，调用方拿到的是一个可判断的结果而不是终止。

## 匹配顺序

```python run id="py.err.match-order"
class MissingConfig(Exception):
    pass


def classify(kind):
    try:
        if kind == "config":
            raise MissingConfig("configuration is missing database.url")
        if kind == "value":
            raise ValueError("port must be an integer")
        if kind == "type":
            raise TypeError("port must be a string")
        return "no failure"
    except MissingConfig as failure:
        return f"specific type first: {failure}"
    except (ValueError, TypeError) as failure:
        return f"grouped types: {type(failure).__name__} - {failure}"


for kind in ("config", "value", "type", "other"):
    print(f"{kind:8s} ->", classify(kind))
```

`except (ValueError, TypeError)` 把相近处理的一组类型写在一起。顺序重要，因为一旦某个子句匹配，后面的就不再尝试——把宽的写前面会让窄的永远收不到。

## 抛出自己的错误

```python run id="py.err.custom"
class InvalidRange(Exception):
    """A port outside the valid range."""


def parse_port(text):
    value = int(text)
    if not 1 <= value <= 65535:
        raise InvalidRange(f"port {value} is outside 1..65535")
    return value


for text in ("8080", "70000", "not-a-number"):
    try:
        print(f"{text!r} ->", parse_port(text))
    except InvalidRange as failure:
        print(f"{text!r} -> handled by type: {failure}")
    except ValueError as failure:
        print(f"{text!r} -> invalid value: {failure}")
```

函数在发现不合法状态时抛错，比返回特殊值更明确：`InvalidRange` 与 `ValueError` 在调用侧是两个不同的分支，调用方据此决定是提示用户改输入还是回退默认端口。错误类型属于接口的一部分，写进文档才有意义。

## 捕获范围要窄

```python run id="py.err.narrow-scope"
def parse_wide(text):
    try:
        return int(text.strip())
    except:  # bare except: it swallows defects in this function too
        return None


def parse_narrow(text):
    try:
        return int(text.strip())
    except ValueError as failure:
        raise ValueError(f"not an integer: {failure}")


print("bare except hides a real bug:", parse_wide(None))

try:
    parse_narrow(None)
except AttributeError as failure:
    print("the narrow version lets the real bug through:", type(failure).__name__)

print("both handle the expected failure:", parse_wide("12"), parse_narrow("12"))
```

两段代码对 `"abc"` 的处理相同，差别在 `None`：`text.strip()` 在这里是编程错误，而裸 `except` 把它伪装成「输入不合法」，返回 `None` 让错误继续往下传播到更远的地方。捕获具体类型，让不属于预期的失败照常抛出。

## 边界与失败情形

- **不要用异常做正常控制流**：能判断的状态直接判断，异常留给真正的失败。
- **捕获之后不要静默丢弃**：至少转换、记录或重新抛出；吞掉异常会让失败在更远处以更奇怪的形式出现。
- **异常的边界是函数边界**：把可能失败的调用限制在最小范围内，而不是把整个函数体包进 `try`。
- **`else` 里不要写可能再次失败的清理逻辑**：清理属于资源管理（见 <CrossRef id="python.context-managers" />）。
- **错误类型要表达语义**：`ValueError` 适合参数内容不合法；业务规则失败应使用自定义类型，否则调用方无法区分。
- **异常的传播、`finally` 的执行路径、异常链与自定义异常的层次设计**由 <CrossRef id="python.exceptions" /> 与后续的接口设计内容处理，本课只覆盖「认出来、就地处理、抛出去」。
- **回溯属于输出的一部分**：未处理的异常会打印类型、消息与调用路径，不要为了「界面干净」把它们全部捕获掉。
