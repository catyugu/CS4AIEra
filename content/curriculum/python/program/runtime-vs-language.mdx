CPython 的文档说小整数是缓存的，于是有人写下 `if a is b:`；换一个实现，同样的两个值就不再是同一个对象，`is` 从 `True` 变成 `False`，而源码一个字没改，类型检查与测试不会报出这一点。关于 Python 的论断分属三个层次。**语言保证**写在语言参考与数据模型中，换一个实现、换一个版本都成立；**标准库契约**是标准库文档为某个特性作出的承诺，随这个特性所在的库移动；**实现行为**只存在于具体实现的源码与发布说明里，一个版本之后就能改掉，依赖它的代码不会得到任何警告。读库文档、写性能结论、评审别人的代码，第一步都是先给手上这句论断定层。

## 按出处定层

一条论断属于哪一层，由它能在哪里找到出处决定：

| 层次 | 出处 | 判据 |
| --- | --- | --- |
| 语言保证 | 语言参考与数据模型 | 条款写进语言规范，换实现、换版本仍成立 |
| 标准库契约 | 标准库文档 | 标准库文档为这个特性作出的承诺，随该库版本移动 |
| 实现行为 | 具体实现的源码与发布说明 | 只在该实现、该构建上成立，发布说明可以改掉它 |

三层可依赖的程度递减：语言保证换一个解释器仍然成立，实现行为换一个构建就可能不成立，而调用它的代码不用改一个字。

### 语言保证

```python run id="py.runtime.guarantees"
mapping = {"b": 1, "a": 2, "c": 3}
print("dict iteration order:", list(mapping))
```

`dict` 保持插入顺序自 3.7 起写进语言规范（见 [映射类型](https://docs.python.org/3/library/stdtypes.html#mapping-types-dict)）：遍历一个字典得到的顺序，在符合规范的实现上都一样。集合与字典在元素变化后的迭代顺序没有这条保证，需要稳定输出的地方显式排序。

### 标准库契约

`sorted` 是稳定排序：键相等的元素保持原有相对顺序。这条承诺写在标准库文档里，语言参考里没有并列元素先后的条款，它成立的范围是标准库自己，换一个改了这条的版本，结论就要重新查。

### 实现行为

```python run id="py.runtime.object-caching"
import sys

small_a = int("256")
small_b = int("256")
print("small ints, same object:", small_a is small_b)

large_a = int("257")
large_b = int("257")
print("larger ints, same object:", large_a is large_b)

joined = "".join(["hel", "lo"])
literal = "hello"
print("equal:", joined == literal, "| same object:", joined is literal)
print("after sys.intern:", sys.intern(joined) is literal)
```

同一段源码，只改数值大小，`is` 的结果就变了：CPython 缓存 −5 到 256 之间的整数对象，由字面量构成的名称式字符串被驻留，运行时拼出来的不会，除非显式调用 `sys.intern`。语言保证身份与 `is` 的对应关系——`is` 为真当且仅当两个名字指向同一个对象；哪两个对象恰好是同一个，是实现的选择。`is` 因此会在缓存边界上给出与 `==` 不同的答案，而这些边界由实现决定。对象的回收时机同样落在这一层：语言不规定 `__del__` 何时运行，CPython 用<Term id="reference-counting">引用计数</Term>在引用归零时立即回收。

可执行单元格运行在一份编译为 WebAssembly 的 <Term id="cpython">CPython</Term> 构建（[Pyodide](https://pyodide.org/)）上，发行版固定在仓库里，单元格的观测结果在该版本内可复现；引用具体行为时记录版本与构建方式。语言语义与 CPython 相同；平台层不完整，没有真实进程、网络与持久文件系统，线程依赖跨源隔离。

## 把假设写进代码

判断一条论断属于哪一层，先查语言参考与数据模型里有没有对应条款，没有则查标准库文档，再没有则查实现文档与发布说明；三处都查不到时，这条行为不属于任何一层保证，按当前观测使用，并把假设写进注释。性能论断同样分层：常数因子、内存布局、优化是否触发都属于实现，一次基准测试给出的是该实现、该版本、该输入下的结果。升级 Python 版本可能改变依赖实现行为的结果，类型检查捕捉不到这类变化；测试没覆盖到这条假设时，它只以行为差异的形式露面。把实现假设写成一条断言，上游改动就会先让测试失败。
