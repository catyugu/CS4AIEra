## 目的

本课解释 `str` 与 `bytes` 的表示，以及编码边界上的故障模式。

字符串有四种互不相等的度量：码点数、字节数、字形簇数与显示宽度。`len()` 给出第一种，而协议头、存储字段、终端与用户界面常常按另外几种施加约束。单位不匹配表现为静默截断、乱码，以及「看起来一样却不相等」的标识符。

## 模型

- `str` 是 Unicode <Term id="code-point">码点</Term>序列。码点是抽象字符的编号，`len(s)` 数的是码点个数。
- `bytes` 是 0 到 255 的整数序列。`b[i]` 得到 `int`，与 `str[i]` 得到单字符字符串不同。
- 编码把码点序列映射为字节序列，解码反向映射：`s.encode(enc)` 与 `b.decode(enc)`。编码名称决定映射关系，同一段字节在不同编码下得到不同文本。
- <Term id="utf-8">UTF-8</Term> 是变长编码：ASCII 占 1 字节，多数常用字符占 2 到 3 字节，其余平面占 4 字节。
- 字形簇是由基字符与组合标记、变体选择符、零宽连接符序列构成的一个用户感知字符，可能对应多个码点。显示宽度还取决于字体与终端。
- <Term id="unicode-normalization">Unicode 规范化</Term>把等价的码点序列映射到统一形式（NFC、NFD、NFKC、NFKD）。不同形式的码点序列不相等，UTF-8 字节也不同。

## 码点、字节与字形

```python run id="py.text.code-points"
import unicodedata

composed = "\u00e9"
decomposed = "e\u0301"

print("code points:", len(composed), len(decomposed))
print("equal:", composed == decomposed)
print("utf-8:", composed.encode("utf-8"), decomposed.encode("utf-8"))
print("NFC:", unicodedata.normalize("NFC", decomposed) == composed)
print("NFD:", unicodedata.normalize("NFD", composed) == decomposed)
print("names:", [unicodedata.name(c) for c in decomposed])

family = "\U0001F468\u200D\U0001F469\u200D\U0001F467"
print("family code points:", len(family), "| bytes:", len(family.encode("utf-8")))
```

`"\u00e9"` 是一个码点，`"e\u0301"` 是两个码点（字母 e 加组合尖音符），两者渲染结果相同、比较为假、UTF-8 字节不同。`unicodedata.name` 给出码点名称，是判断「这个字符究竟是什么」的可靠依据。

家庭表情由三个码点和两个零宽连接符组成：5 个码点、18 个字节，渲染为一个字形簇。三种度量都不同，任何一种都不能代替另一种。

标识符、账号名、文件名的比较必须在同一个规范化形式下进行，否则同一个名字会以两个键的形式存在。

## 编码与解码

```python run id="py.text.encoding"
raw = "na\u00efve".encode("utf-8")
print("bytes:", raw)
print("utf-8:", raw.decode("utf-8"))
print("latin-1:", raw.decode("latin-1"))

try:
    raw.decode("ascii")
except UnicodeDecodeError as exc:
    print("ascii:", type(exc).__name__, "| bytes", exc.start, "to", exc.end, "|", exc.reason)

print("replace:", raw.decode("ascii", errors="replace"))
print("ignore: ", raw.decode("ascii", errors="ignore"))

try:
    "caf\u00e9".encode("ascii")
except UnicodeEncodeError as exc:
    print("encode:", type(exc).__name__, "|", repr(exc.object[exc.start:exc.end]), "at", exc.start)
```

同一段字节用 UTF-8 解码得到 `naïve`，用 latin-1 解码得到 `naÃ¯ve`。latin-1 把每个字节映射到一个码点，任何字节序列都能成功解码，因此解码「成功」不证明编码正确。

`ascii` 遇到大于 127 的字节抛 `UnicodeDecodeError`，异常携带出错区间的起止位置。解码失败报的是字节位置，编码失败报的是字符位置，这是定位问题时的第一条线索。

`errors` 参数决定失败行为：`strict` 抛异常，`replace` 用替换字符代替，`ignore` 丢弃。三者的共同点是原始的字节或字符信息丢失，因此它们适用于展示层，不适用于存储与传输路径。

## 截断与边界

```python run id="py.text.truncation"
text = "\u65e5\u672c\u8a9e"
raw = text.encode("utf-8")
print("code points:", len(text), "| bytes:", len(raw))

try:
    raw[:4].decode("utf-8")
except UnicodeDecodeError as exc:
    print("byte slice fails:", type(exc).__name__, "|", exc.reason)

print("byte slice complete on a boundary:", raw[:3].decode("utf-8"))
print("code point slice:", text[:2])

grapheme = "e\u0301"
print("grapheme:", grapheme, "| first code point:", repr(grapheme[:1]))
```

三个码点编码成九个字节。按字节截断到 4 字节切断了第三个码点的序列，解码失败并报告数据在结尾处不完整；截断到 3 字节恰好落在码点边界上，解码成功。按码点切片在解码侧安全，却仍可能切在字形簇内部：`"e\u0301"[:1]` 只剩基字符，重音被丢掉，渲染出的字符与原意不同。

限制长度时先确定下游以什么为单位：HTTP 头与 TLS 记录按字节，数据库的字符类型按字符数（具体定义随引擎），终端与界面按显示宽度。按码点校验的字段完全可能超出下游的字节上限。

## 比较、排序与大小写

```python run id="py.text.ordering"
print(sorted(["Zoe", "apple", "\u00c1lvaro", "\u65e5\u672c"]))
print("'apple' < 'Zoe':", "apple" < "Zoe")
print("'B' < 'a':", "B" < "a")
print("lower:", "stra\u00dfe".lower(), "| casefold:", "stra\u00dfe".casefold())
print("casefold matches:", "stra\u00dfe".casefold() == "STRASSE".casefold())
print("dotted I folds to:", repr("\u0130".casefold()), len("\u0130".casefold()))
```

`str` 的比较按码点进行：大写字母排在小写字母之前，非 ASCII 字符排在 ASCII 之后。这个顺序与任何语言的排序习惯都不一致，也不是稳定的业务排序依据。需要语言相关排序时要指定排序规则，由 `locale`、数据库排序规则或专门的库提供。

`casefold()` 实现 Unicode 的大小写折叠，覆盖 `lower()` 处理不了的规则：德语 `ß` 折叠为 `ss`，土耳其语点号大写 I 折叠后是两个码点。用于认证或去重时，折叠方式必须与存储侧完全一致，否则同一个账号名可以注册两次。

## 字节不是文本

```python run id="py.text.bytes-are-not-text"
data = b"\x00\xff"
print("bytes:", data, "| length:", len(data))
print("index gives an int:", data[0], data[1], list(data))

try:
    data[0] = 1
except TypeError as exc:
    print("bytes is immutable:", type(exc).__name__)

buffer = bytearray(b"\x00\xff")
buffer[0] = 7
print("bytearray:", buffer)
print("bytes == bytearray:", bytes(buffer) == b"\x07\xff")
```

`bytes` 不可变，可变的对应类型是 `bytearray`。索引取到的是 `int`，因此按字节处理二进制数据时不会意外产生文本。`bytes` 与 `bytearray` 按字节内容比较，与文本比较则需要先解码。

二进制协议、哈希摘要、压缩数据必须全程用 `bytes`。把它们当作 `str` 处理会引入一次隐式编码，而那次编码使用的编码名往往不是协议规定的。

## 边界与失败情形

- **未指定编码**：`bytes.decode()` 与 `open()` 的默认编码由运行环境决定。读写文件、解析协议、调用子进程时显式写出编码名。
- **规范化冲突**：同一名字的两种规范化形式在文件系统与数据库中是两个不同的键。部分文件系统在写入时自动归一化、读取时不还原，跨系统搬运文件会改变字符串。
- **不可见字符**：零宽空格、零宽连接符、双向控制符不占显示宽度。双向覆盖字符能让一行代码的渲染顺序与实际解析顺序不同，审查源码时应把它们显示出来。
- **同形字符**：不同码点的字符可能渲染得几乎一样，用于标识符与域名时会产生钓鱼与冒名问题。
- **BOM**：带字节顺序标记的文件用 `utf-8-sig` 读取可以去掉标记，用 `utf-8` 读取会把它变成文本开头的 `U+FEFF` 码点。
- **正则与 Unicode**：`re` 的 `\w`、`\d` 默认按 Unicode 类别匹配，与字节模式的行为不同，处理二进制数据要用 `bytes` 模式。
- **拼接开销**：`str` 不可变，循环内 `s = s + part` 每次都创建新对象，总复制量为 O(N²)。用 `join` 或列表缓冲，不要依赖实现可能存在的原地优化。
- **缓冲大小估计**：UTF-8 下字节数取决于内容，按码点数分配缓冲会低估。

## 生产后果

- 长度校验的单位决定边界：按码点限制的用户名可以在字节长度上超出下游存储的限制，按字节截断会把多字节序列撕开。
- 排序与去重在跨语言数据上不一致，应用层比较与数据库排序规则可能给出不同顺序，同一批数据在不同层看起来「重复」或「缺失」。
- 大小写折叠用于认证或去重时必须与存储侧一致，否则同一个身份可以存在两份记录。
- 日志与终端输出中的控制字符会改变显示，影响审计与排查。
- 序列化边界是故障集中处：JSON 默认转义非 ASCII，CSV 的编码由写入方决定，客户端编码与数据库编码不一致会产生乱码或写入失败。
- 生成代码常按 `len(s)` 做长度限制，在需要字节数的协议边界上出错；也常把 `bytes` 与 `str` 混用，靠隐式编码恰好通过测试。

## 小结

- `str` 是码点序列，`bytes` 是字节序列，两者之间的转换是显式编码与解码。
- `len(str)` 是码点数；字节数与字形簇数需要单独计算。
- 相同渲染的两种规范化形式比较不等，比较标识符前先归一化。
- 同一段字节用不同编码解码得到不同文本，成功解码不证明编码正确。
- 按字节截断会切断多字节序列，按码点切片可能切在字形簇内部。
- 排序按码点，语言相关排序由外部排序规则提供；大小写折叠必须与存储侧一致。
