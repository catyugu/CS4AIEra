异常是一段控制流：抛出之后，控制权如何沿调用栈离开，哪些代码必然运行，调用方最终看到什么信息。

上一课看到生成器体内的 `StopIteration` 会被转换，这个转换与传播顺序、`finally` 的语义共用同一个机制。

## 模型

异常是一个对象。`raise` 接受异常类（会被实例化）或异常实例，并把它交给当前帧：

1. 当前帧的 `try` 语句在子句中从上到下匹配：`except SomeType` 匹配该实例的类型及其子类；
2. 没有匹配则退出当前帧，进入调用方，重复匹配；每退出一层帧，该层的 `finally` 块与 `with` 的退出逻辑都会运行；
3. 到达栈顶仍无人处理时，异常终止程序，并由解释器打印回溯（traceback）；
4. 处理该异常的 `except` 块执行后，控制权在 `try` 语句之后继续——除非处理块自己又抛出。

一个 `try` 语句的四个部分各自有条件：

| 部分 | 何时运行 |
| --- | --- |
| `except` | 匹配到的异常出现时，按书写顺序取第一个匹配 |
| `else` | `try` 块正常结束且未处理异常时 |
| `finally` | 无论正常结束、返回、抛出还是被处理，都运行 |

`finally` 的必然性让它成为释放点：它跨 `return`、`break`、`continue` 与异常展开都执行。

## 子句顺序与各路径

按书写顺序取第一个匹配、子类也匹配父类，这两条规则由 <CrossRef id="python.errors-basics" /> 建立。在本课的模型里它们只决定一件事：`finally` 在哪个分支之后运行。`else` 只在 `try` 块没有触发异常时运行，把「正常路径」与「异常处理」分开，避免处理块捕获自己抛出的异常。

```python run id="py.exc.matching"
class ConfigError(Exception):
    pass


class MissingKey(ConfigError):
    pass


def load(kind):
    try:
        if kind == "missing":
            raise MissingKey("no such key")
        if kind == "config":
            raise ConfigError("bad config")
        if kind == "value":
            raise ValueError("bad value")
        return "loaded"
    except MissingKey as exc:
        return f"specific handler: {type(exc).__name__}"
    except ConfigError as exc:
        return f"general handler: {type(exc).__name__}"
    except (ValueError, TypeError) as exc:
        return f"tuple handler: {type(exc).__name__}"
    else:
        print("else runs only when nothing was raised")
    finally:
        print("finally always runs for", kind)


print(load("missing"))
print(load("config"))
print(load("value"))
print(load("ok"))
```

执行时每个分支结束后都运行一次 `finally`，正常加载的那次还会经过 `else`。这段输出的顺序就是模型里那张表：`else` 只出现在没有异常的那一次，`finally` 出现四次且位置固定在每个分支之后。

## finally 的执行路径

```python run id="py.exc.finally-paths"
def with_return():
    try:
        return "from try"
    finally:
        print("finally runs before the function leaves")


def overridden():
    try:
        raise RuntimeError("original failure")
    finally:
        return "finally wins"


print("return value:", with_return())
print("swallowed:", overridden())

try:
    try:
        raise RuntimeError("propagating")
    finally:
        print("cleanup still runs while unwinding")
except RuntimeError as failure:
    print("the failure still reaches the caller:", type(failure).__name__, "-", failure)
```

`finally` 在函数真正离开之前运行，因此第一个函数先打印再返回值。第二个函数展示了 `finally` 中 `return` 的效果：它结束函数，原来的 `RuntimeError` 被丢弃，调用方看不到任何失败信号。这是把故障静默化的直接机制，清理代码里不应出现 `return`。

## 异常链

```python run id="py.exc.chaining"
class ConfigError(Exception):
    pass


def parse(text):
    try:
        return int(text)
    except ValueError:
        raise ConfigError(f"not a number: {text!r}")


try:
    parse("x")
except ConfigError as exc:
    print("implicit chain:", type(exc).__name__, "| cause:", exc.__cause__)
    print("context kept:", type(exc.__context__).__name__)
    print("the original message is still reachable:", "invalid literal" in str(exc.__context__))


def explicit(text):
    try:
        return int(text)
    except ValueError as exc:
        raise ConfigError(f"not a number: {text!r}") from exc


def suppressed(text):
    try:
        return int(text)
    except ValueError:
        raise ConfigError(f"not a number: {text!r}") from None


try:
    explicit("x")
except ConfigError as exc:
    print("explicit chain:", type(exc.__cause__).__name__, "| suppress_context:", exc.__suppress_context__)

try:
    suppressed("x")
except ConfigError as exc:
    print("suppressed chain:", exc.__cause__, "| suppress_context:", exc.__suppress_context__)
```

在 `except` 块内抛出的新异常自动带上 `__context__`，指向正在处理的异常，因此原始失败不会丢失。`raise ... from exc` 把它登记为 `__cause__`，语义是「这是本次失败的直接原因」；`raise ... from None` 不设原因，只抑制上下文的显示，用于失败细节对调用方无意义、暴露出去只会干扰阅读的边界（例如把内部解析错误统一成公开的输入错误）。两种写法的 `__suppress_context__` 都是真值，区别在于是否存在明确的原因。异常对象持有回溯，回溯引用帧，帧又引用其中的局部变量，因此长期保存异常对象会长期持有这些对象。

## 重新抛出

```python run id="py.exc.reraise"
import traceback


def inner():
    raise ValueError("original")


def bare_reraise():
    try:
        inner()
    except ValueError:
        raise


def instance_reraise():
    try:
        inner()
    except ValueError as exc:
        raise exc


for label, function in [("bare raise", bare_reraise), ("raise instance", instance_reraise)]:
    try:
        function()
    except ValueError as exc:
        frames = traceback.extract_tb(exc.__traceback__)
        print(label, "->", len(frames), "frames |", [frame.name for frame in frames])
```

裸 `raise` 保留原异常对象、回溯与传播位置，只增加调用方的帧；`raise exc` 抛出的是同一个对象，但把当前这一行记为抛出位置，回溯里因此出现两次处理帧：原始抛出点仍在，处理帧多了一次。需要在中间层记录或转换后再抛时，用裸 `raise`；需要包装成新的失败语义时，用 `raise New from exc`。

## 异常的边界

```python run id="py.exc.boundaries"
print("SystemExit is Exception:", issubclass(SystemExit, Exception))
print("KeyboardInterrupt is Exception:", issubclass(KeyboardInterrupt, Exception))


def after_handler():
    try:
        raise ValueError("inner")
    except ValueError as exc:
        print("inside the handler:", type(exc).__name__)
    try:
        print(exc)
    except NameError as failure:
        print(
            "after the handler:",
            type(failure).__name__,
            "| is a NameError:",
            isinstance(failure, NameError),
        )


after_handler()
```

`SystemExit`、`KeyboardInterrupt` 与 `GeneratorExit` 继承 `BaseException` 而不是 `Exception`，因此 `except Exception` 不会接住它们。写 `except BaseException` 或裸 `except:` 会把解释器的正常退出信号也吞掉，让 Ctrl-C 与进程终止失效。`except Exception: pass` 把可诊断的失败变成继续执行的错误状态，只在明确知道如何恢复时才捕获。异常不是廉价的控制流：逐元素依赖它跳过低频分支可以接受，把它当普通分支使用会同时损害性能与可读性。另一个容易忽略的细节是 `except ... as exc` 里的名字：处理块结束时它被删除，之后引用会失败——在模块层是 `NameError`，在函数内表现为它的子类 `UnboundLocalError`。
