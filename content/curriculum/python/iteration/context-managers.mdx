资源在这里是广义的：打开的文件、数据库连接、锁、临时目录、需要成对调用的接口。它们的共同点是释放必须发生，且必须在失败时也发生。`with` 就是这段必经路径的语言形式。

## with 展开成 try/finally

`with` 的语义可以完全展开成 `try/finally`：

```text
manager = expression
enter = type(manager).__enter__
exit = type(manager).__exit__
value = enter(manager)          # 绑定给 as 的名字
try:
    body
except BaseException as error:
    if not exit(manager, type(error), error, error.__traceback__):
        raise
else:
    exit(manager, None, None, None)
```

由此得到四条不变量：

- `__enter__` 的返回值绑定到 `as` 后的名字；它不是管理器本身（除非协议实现这样返回）。
- `__exit__` 在**所有**路径上都调用一次，参数是异常三元组；正常退出时三个参数都是 `None`。
- `__exit__` 返回真值时异常被吞掉，控制流在 `with` 之后继续；返回假值或 `None` 时异常继续向外传播。
- 如果有异常正在展开，`__exit__` 自己抛出的异常会替换它，与 `finally` 中的行为一致。
- `__enter__` 抛异常时 `__exit__` 不会被调用：进入阶段的失败发生在协议建立之前，需要成对时把获取逻辑放进已经建立的管理器内部。

多个管理器写在同一个 `with` 语句里时，进入顺序从左到右，退出顺序从右到左。

## 从 try/finally 到 with

```python run id="py.ctx.manual-vs-with"
events = []


class Session:
    def __init__(self, name):
        self.name = name
        self.open = False

    def __enter__(self):
        self.open = True
        events.append(f"enter {self.name}")
        return self

    def __exit__(self, exc_type, exc, traceback):
        self.open = False
        events.append(f"exit {self.name} (exc_type={exc_type})")
        return False


session = Session("manual")
try:
    events.append("body")
finally:
    events.append("finally release")

with Session("managed") as managed:
    events.append(f"using {managed.name}, open={managed.open}")
    managed_name = managed.name

print("events:", events)
print("after the with block, still open:", session.open, "| released:", not session.open)
print("bound value was the returned object:", managed_name)
```

`with` 与手写的 `try/finally` 表达的是同一条必经路径；区别是释放逻辑写在资源对象自己身上，使用点只需要一行，调用方不可能忘记释放。

## 异常路径

`__exit__` 收到异常三元组，因此它知道正在发生什么，而不是只知道「要清理了」。

```python run id="py.ctx.exit-observes-error"
class Guard:
    def __enter__(self):
        print("enter")
        return self

    def __exit__(self, exc_type, exc, traceback):
        if exc_type is None:
            print("exit: normal path")
        else:
            print("exit: failure path", exc_type.__name__, "-", exc)
        return False


with Guard():
    print("body succeeds")

try:
    with Guard():
        raise ValueError("body failed")
except ValueError as failure:
    print("caller still sees:", type(failure).__name__, "-", failure)
```

正常路径与失败路径都调用 `__exit__`，两者的区别只在参数。返回假值意味着清理完成但异常照常传播，调用方仍然看到原始失败。`with` 本身不决定是否捕获，它把异常交给 `__exit__` 并尊重返回值。

## 抑制异常

```python run id="py.ctx.suppression"
class Suppress:
    def __init__(self):
        self.seen = None

    def __enter__(self):
        return self

    def __exit__(self, exc_type, exc, traceback):
        self.seen = exc_type
        return True


try:
    with Suppress():
        raise KeyError("missing")
    print("body failed but control continued past the with block")
except KeyError:
    print("this line never runs")

with Suppress() as swallowing:
    raise KeyError("missing")

print("suppressed type:", swallowing.seen)
```

返回真值把异常变成控制流的一部分：`with` 之后的语句继续执行，调用方看不到失败。这是有意的能力，代价同样是静默化——写这类上下文管理器必须让意图在名字上可见，并限制在「该失败在此处确实等价于正常结果」的场合。返回值按真值判断，返回非布尔真值同样抑制异常。

## 多个资源的嵌套

```python run id="py.ctx.multiple"
order = []


class Named:
    def __init__(self, name):
        self.name = name

    def __enter__(self):
        order.append(f"+{self.name}")
        return self.name

    def __exit__(self, exc_type, exc, traceback):
        order.append(f"-{self.name}")
        return False


with Named("outer") as outer, Named("inner") as inner:
    order.append(f"body {outer}/{inner}")

print("enter left to right, exit right to left:", order)
```

退出顺序与进入顺序相反，因此内层资源先释放。获取顺序与释放顺序互为逆序，这一点在锁与嵌套事务上直接决定正确性；跨对象的依赖顺序必须由嵌套结构表达，不能靠调用时机凑巧。

## 用生成器写上下文管理器

```python run id="py.ctx.contextmanager"
from contextlib import contextmanager

events = []


@contextmanager
def opened(name):
    events.append(f"open {name}")
    try:
        yield name
    finally:
        events.append(f"close {name}")


@contextmanager
def leaky(name):
    events.append(f"open {name}")
    yield name
    events.append(f"close {name}")


with opened("safe") as handle:
    events.append(f"using {handle}")

try:
    with opened("safe"):
        raise RuntimeError("body failed")
except RuntimeError:
    pass

try:
    with leaky("leaky"):
        raise RuntimeError("body failed")
except RuntimeError:
    pass

print(events)
```

`@contextmanager` 把生成器切成交付点两侧：`yield` 之前是进入逻辑，`yield` 的值绑定给 `as`，之后的代码是退出逻辑；异常从 `yield` 处抛回生成器，因此必须用 `try/finally` 包住 `yield` 才能保证退出逻辑运行。`leaky` 缺少这层结构，body 抛异常时 `close leaky` 从未出现——修复了 `opened` 的那个缺陷，就在 `leaky` 里复现了它。生成器写成的管理器只能使用一次：生成器是迭代器，同一实例第二次进入会抛 `RuntimeError`。

## 释放点与对象生命周期

```python run id="py.ctx.release-point"
class Lock:
    def __init__(self):
        self.held = False

    def __enter__(self):
        self.held = True
        return self

    def __exit__(self, exc_type, exc, traceback):
        self.held = False
        return False


lock = Lock()
with lock:
    print("inside:", lock.held)
print("object still exists:", lock is not None, "| resource released:", not lock.held)
```

对象与资源是两件事：`with` 块结束后对象照旧存在，被释放的是它代表的那份资源。反过来说，对象被回收不保证释放立刻发生，回收时机也不在语言的约定之内（见 <CrossRef id="python.runtime-vs-language" />）。因此获取与释放都必须由 `with` 或 `finally` 表达，而不是「对象没了自然就关了」。`__del__` 的运行时机不在语言约定内，含环的对象还要等垃圾回收，用终结器代替 `with` 只是把释放点推迟到不确定的时刻。
