取消是一条控制流：请求从哪里发出、以什么形式到达、会经过哪些清理代码、在谁那里结束。协作式模型里没有从外部掐断一个任务的操作。取消是一次注入到执行流里的异常，因此它出现的位置、能否被观察到、被吞掉之后调用方看到什么，全部由代码结构决定。

## 取消请求与它的到达时刻

- `task.cancel()` 是**向事件循环发出的请求**：它立即返回，并把该 task 标记为待取消，不对正在运行的协程做任何事。
- 请求在协程**下一次被调度到挂起点**时生效，`CancelledError` 在那个 `await` 处抛出。三条直接后果：
  - 一个在两次挂起点之间完成的协程会跑完并正常返回，取消没有效果；
  - 已经结束的 task 上调用 `cancel()` 返回 `False`，什么也不发生；
  - 还没开始步进的 task 被取消后，函数体一行都不执行。
- `CancelledError` 继承 `BaseException`，不是 `Exception`（见 <CrossRef id="python.exceptions" />）。因此 `except Exception` 不会接住取消，而裸 `except:` 会。
- 取消也是控制流：`try/finally` 会运行，这是执行清理的位置，清理里仍可以使用挂起点。取消不会回滚已经完成的部分，某个挂起点之前产生的状态变化保持不变，收尾逻辑要按这个前提写。资源释放的完整模型由 <CrossRef id="python.context-managers" /> 建立。
- 吞掉 `CancelledError` 而不重新抛出，会让调用方收到「正常结束」：`task.done()` 为真、`task.cancelled()` 为假。调用方因此失去了对任务生命周期的控制。

未被取回的异常与取消由事件循环报告，报告位置是 worker 控制台而不是调用处，具体形式随实现变化。取消通过 `CancelledError` 表现，这是语言参考里异常层次的规定；`cancel` 是标准库 `asyncio` 的接口约定，随标准库版本演进。

`async with` 是 `with` 的异步形式，展开与三条退出路径见 <CrossRef id="python.async-iteration-and-context" />；同步版本的完整模型见 <CrossRef id="python.context-managers" />。取消的两类应用——给一段等待设定期限、给一组任务划定共同生命周期——由 <CrossRef id="python.timeout-and-task-lifecycle" /> 处理。

## 取消在挂起点出现

```python run id="py.async.cancel-at-suspension"
import asyncio


async def worker():
    print("the task starts")
    try:
        await asyncio.sleep(10)
    except asyncio.CancelledError:
        print("the cancellation arrives at the suspension point")
        raise
    print("this line never runs")


async def main():
    task = asyncio.create_task(worker())
    await asyncio.sleep(0)
    print("requesting cancellation")
    task.cancel()
    print("cancel() returned already | finished:", task.done())
    await asyncio.sleep(0)
    print("after the loop delivered it | cancelled:", task.cancelled(), "| finished:", task.done())


await main()
```

`cancel()` 返回时 task 还没有结束，也没有被打断：它把取消记进事件循环的待办里。下一个挂起点——这里是 `worker` 里被挂起的 `await asyncio.sleep(10)`——把 `CancelledError` 抛进协程，`try` 捕获它、`raise` 让它继续传播，task 随后变成已取消状态。10 秒的等待一秒都没有等。

## 没有挂起点就交不出控制权

取消请求到达时，如果协程已经跑完，它就什么也做不了。

```python run id="py.async.cancel-after-completion"
import asyncio


async def busy():
    total = 0
    for value in range(2_000_000):
        total += value
    print("busy() reached the end of its body without a suspension point")
    return total


async def main():
    task = asyncio.create_task(busy())
    await asyncio.sleep(0)
    print("control came back only after busy() had finished:", task.done())
    print("cancel() on a finished task returns:", task.cancel())
    print("the task completed normally | cancelled:", task.cancelled())


await main()
```

`busy` 在一次步进里跑完整段循环，`main` 直到那一刻之后才拿回控制权，因此取消请求到达时 task 已经结束。这不是竞态，而是协作式模型的直接结果：**取消的及时性等于协程到达下一个挂起点的及时性**。

未开始的 task 是另一种情形：请求可以早于第一次步进。

```python run id="py.async.cancel-before-start"
import asyncio


async def worker():
    print("this line never runs")
    await asyncio.sleep(0)


async def main():
    task = asyncio.create_task(worker())
    task.cancel()
    print("right after cancel() | cancelled:", task.cancelled(), "| finished:", task.done())
    await asyncio.sleep(0)
    print("after the loop handled it | cancelled:", task.cancelled())


await main()
```

同一个请求对应两种状态：刚发出时 task 还没被标记，循环处理过之后才是已取消。`worker` 的函数体一次都没有执行——取消在它有第一个挂起点之前就已经生效。

## 清理在 finally 里

取消路径同样经过 `finally`，这是把释放逻辑放对位置的依据。

```python run id="py.async.cancel-cleanup"
import asyncio


async def worker():
    try:
        await asyncio.sleep(10)
    finally:
        print("cleanup runs while the cancellation is in flight")


async def main():
    task = asyncio.create_task(worker())
    await asyncio.sleep(0)
    task.cancel()
    try:
        await task
    except asyncio.CancelledError:
        print("the caller observes the cancellation | cancelled:", task.cancelled())


await main()
```

`finally` 在 `CancelledError` 穿过协程时运行，调用方随后在 `await task` 处收到同一个异常。清理代码本身仍然可以使用挂起点：

```python run id="py.async.finally-may-await"
import asyncio


async def worker():
    try:
        await asyncio.sleep(10)
    finally:
        await asyncio.sleep(0)
        print("a suspension point inside finally still runs")


async def main():
    task = asyncio.create_task(worker())
    await asyncio.sleep(0)
    task.cancel()
    try:
        await task
    except asyncio.CancelledError:
        print("the caller still sees the cancellation")


await main()
```

代价是取消的完成被推迟到清理结束：`await task` 要等 `finally` 跑完才返回。

## 吞掉取消

`CancelledError` 是一个普通异常对象，因此它可以被 `try` 截住、也可以被上下文管理器抑制。截住之后不重新抛出，调用方就再也看不到取消。

```python run id="py.async.swallowing-cancellation"
import asyncio


class Swallower:
    async def __aenter__(self):
        return self

    async def __aexit__(self, exc_type, exc, traceback):
        if exc_type is asyncio.CancelledError:
            print("the manager ate the cancellation")
            return True
        return False


async def worker():
    async with Swallower():
        await asyncio.sleep(10)
    print("control continued past the with block")


async def main():
    task = asyncio.create_task(worker())
    await asyncio.sleep(0)
    task.cancel()
    await task
    print("the caller thinks it finished | cancelled:", task.cancelled(), "| finished:", task.done())


await main()
```

10 秒的等待被取消了，但那个等待被当作「已处理」，于是协程继续执行、正常返回，`cancelled()` 为假。请求取消的一方——无论是超时、上层框架还是关闭流程——都会继续等待一个它以为已经停下的任务。这就是「取消也是控制流」的实际含义：截住它要么完成等价的收尾，要么重新抛出。
