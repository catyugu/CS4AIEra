一个请求最多允许等待 2 秒。超时触发时，`asyncio.timeout` 取消的是进入这个上下文的那个 task：被等待的代码在挂起点收到一次注入的取消异常并照常清理，调用方则看到 `TimeoutError`。给一段等待设定期限、给一组任务划定共同的生命周期，两者的失败模式都来自同一个事实：**谁被取消、谁负责收尾，由结构决定**。

## 超时取消的是当前 task

`asyncio.timeout(delay)` 返回一个异步上下文管理器。到期时它取消进入这个上下文的那个 task，并在上下文内部处理由此产生的 `CancelledError`，把它转换成 `TimeoutError` 抛出：

```python run id="py.async.timeout"
import asyncio


async def slow():
    try:
        await asyncio.sleep(10)
    except asyncio.CancelledError as cancelled:
        print("awaited task caught:", type(cancelled).__name__)
        raise


async def main():
    try:
        async with asyncio.timeout(0.001):
            await slow()
    except TimeoutError as failure:
        print("caller caught:", type(failure).__name__)


await main()
```

被等待的代码在挂起点收到一次普通的取消，因此它的清理路径照常运行；调用方拿到的是 `TimeoutError`。两个异常来源不同：`CancelledError` 进入 task 内部，`TimeoutError` 由上下文管理器在退出时产生（见 [asyncio: Timeouts](https://docs.python.org/3/library/asyncio-task.html#timeouts)）。

`timeout` 只能转换它自己传进去的那个 `CancelledError`。块内的 `except CancelledError` 把它截住并继续执行，上下文退出时就看不到异常，`TimeoutError` 也不会出现——超时被降级成了一次被吞掉的取消，这正是 <CrossRef id="python.cancellation-and-cleanup" /> 描述的破坏。期限内完成的等待不受影响：

```python run id="py.async.timeout-not-expired"
import asyncio


async def main():
    async with asyncio.timeout(10):
        value = await asyncio.sleep(0, result="finished in time")
    print("within the deadline:", value)

    try:
        async with asyncio.timeout(0.001):
            await asyncio.sleep(10)
    except TimeoutError:
        print("past the deadline: TimeoutError")


await main()
```

到期时间由循环的时钟决定，`timeout` 保证的是「不会早于」这个下界，不保证毫秒级的准时（见 <CrossRef id="python.asyncio-scheduling" />）。期限在创建时还不知道时用 `asyncio.timeout(None)` 加 `reschedule()`，之后用 `expired()` 读回是否已经到期。

## 深入：结构化任务生命周期

### 屏蔽取消

`shield` 让内部任务在调用方这次取消中活下来。它挡住的只是取消本身，调用方仍处于被取消之中：

```python run id="py.async.shield"
import asyncio


async def important():
    await asyncio.sleep(0.02)
    return "finished anyway"


async def main():
    task = asyncio.create_task(important())
    try:
        async with asyncio.timeout(0.001):
            await asyncio.shield(task)
    except TimeoutError:
        print("caller timed out | shielded task done:", task.done())
    print("shielded result:", await task)


await main()
```

调用方的等待被取消了，`task` 没有被取消——它继续运行并给出结果。调用方要在超时之后决定那个还在运行的任务怎么办，或者等待它。事件循环对 task 只持弱引用，被屏蔽的任务如果没有别处引用它，可能在结束前被回收，因此必须保留一个引用（见 [asyncio: Shielding from cancellation](https://docs.python.org/3/library/asyncio-task.html#shielding-from-cancellation)）。

### 任务组的取消与失败聚合

`TaskGroup` 为它创建的任务建立共同的生命周期：正常退出时等待全部任务；某个子任务以非 `CancelledError` 异常失败时，取消其他任务，等待它们收尾，再把失败聚合后抛出。单个子任务被取消不自动触发兄弟任务取消。任务组作用域所在的父任务被取消时，组内任务也会被取消并等待结束（见 [asyncio：Task Groups](https://docs.python.org/3.14/library/asyncio-task.html#task-groups)）。

```python run id="py.async.task-group"
import asyncio


async def failing(ready):
    await ready.wait()
    raise ValueError("boom")


async def waiting(ready):
    try:
        ready.set()
        await asyncio.Future()
    finally:
        print("sibling cleanup ran")


async def blocked_child(started):
    started.set()
    await asyncio.Future()


async def scoped(started, children):
    try:
        async with asyncio.TaskGroup() as group:
            children.append(group.create_task(blocked_child(started)))
            await asyncio.Future()
    finally:
        print("scope exit waited for children:", all(task.done() for task in children))


async def main():
    ready = asyncio.Event()
    try:
        async with asyncio.TaskGroup() as group:
            group.create_task(waiting(ready))
            group.create_task(failing(ready))
    except* ValueError as failures:
        print("sibling failed:", type(failures).__name__, [str(error) for error in failures.exceptions])

    started = asyncio.Event()
    children = []
    outer = asyncio.create_task(scoped(started, children))
    await started.wait()
    outer.cancel()
    try:
        await outer
    except asyncio.CancelledError:
        print("parent cancelled: caller saw CancelledError")


await main()
```

`ready` 保证等待任务已经进入受清理保护的路径，失败任务才抛异常。任务组交出的通常是 `ExceptionGroup`（聚合中含不属于 `Exception` 的基类异常时用 `BaseExceptionGroup`），`KeyboardInterrupt` 与 `SystemExit` 取消并等待其他任务后原样重抛、不参与聚合。异常组是保留多个失败的异常树：普通 `except ValueError` 不匹配包含 `ValueError` 的异常组，`except* ValueError` 拆出匹配的子组交给处理块、剩余异常继续传播（见 [语言参考：except*](https://docs.python.org/3.14/reference/compound_stmts.html#except-star)）；同一个 `try` 不能混写 `except` 与 `except*`，即使只有一个失败，TaskGroup 也可能抛出异常组，且不保证失败列表的次序。

### 创建关系与等待关系

`create_task()` 本身不建立结构化的父子关系；取消与收尾的规则取决于这两个任务之间建成了哪一种关系：

| 结构 | 取消与收尾规则 |
| --- | --- |
| `create_task(child())` | 调度独立任务；仅凭创建关系，创建者的取消不会传给它 |
| `parent` 正在 `await child` | 取消 parent 会取消当前等待的 Future 或 Task；取消可沿等待边传播 |
| `TaskGroup` | 显式建立作用域，按组的取消、等待收尾与失败聚合规则管理任务 |

等待边规则由 [asyncio：Task.cancel](https://docs.python.org/3.14/library/asyncio-task.html#task-cancel) 规定；`shield` 可以挡住沿这条边传给内部任务的取消，不接管内部任务的后续生命周期。

等待边能把当前取消传给被等待的任务，却不提供「作用域退出时所有创建的任务都结束」的保证。传播依赖被等待者配合：一个吞掉 `CancelledError` 的 child 不能让调用方据此认定它最终处于 cancelled 状态（<CrossRef id="python.cancellation-and-cleanup" />）。需要这条作用域保证时使用 TaskGroup：组内任务在作用域退出前被取消并等待结束。
