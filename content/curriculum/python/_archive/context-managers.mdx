```python
with open("report.csv") as handle:
    rows = handle.read().splitlines()
```

读取中途抛出异常时，`handle` 仍然要关闭。句柄没有关闭，进程就少一个可用的文件描述符，失败越多泄漏越多；释放也不能等对象被回收，回收的时刻不确定，句柄可能长时间不还。文件、数据库连接、锁、临时目录都属于这一类：获取之后必须释放，且必须在失败时也释放。`with` 是这条必经路径的语言形式。

## 从手写配对到 with

手写这条路径，要把获取与释放配对：

```python run id="py.ctx.manual-vs-with"
events = []


class Session:
    def __init__(self, name):
        self.name = name
        self.open = False

    def __enter__(self):
        self.open = True
        events.append(f"enter {self.name}")
        return self

    def __exit__(self, exc_type, exc, traceback):
        self.open = False
        events.append(f"exit {self.name} (exc_type={exc_type})")
        return False


manual = Session("manual")
manual.open = True
events.append(f"open {manual.name}")
try:
    events.append("body")
finally:
    manual.open = False
    events.append(f"close {manual.name}")

with Session("managed") as managed:
    events.append(f"using {managed.name}, open={managed.open}")
    managed_name = managed.name

print("events:", events)
print("both sessions released:", not manual.open, not managed.open)
print("bound value was the returned object:", managed_name)
```

`with` 与手写的 `try/finally` 表达的是同一条必经路径：进入时获取、退出时释放，正常结束与异常退出都经过同一个释放点。释放逻辑写在资源对象自己身上，使用点只需要一行；一旦进入了 `with` 块，退出协议就一定会运行。

## __exit__ 收到异常

```python run id="py.ctx.exit-observes-error"
class Guard:
    def __enter__(self):
        print("enter")
        return self

    def __exit__(self, exc_type, exc, traceback):
        if exc_type is None:
            print("exit: normal path")
        else:
            print("exit: failure path", exc_type.__name__, "-", exc)
        return False


with Guard():
    print("body succeeds")

try:
    with Guard():
        raise ValueError("body failed")
except ValueError as failure:
    print("caller still sees:", type(failure).__name__, "-", failure)
```

正常路径与失败路径都调用 `__exit__`，两者的区别只在参数。返回假值意味着清理完成但异常照常传播，调用方仍然看到原始失败。`with` 本身不决定是否捕获，它把异常交给 `__exit__` 并尊重返回值。

## 进入与退出协议

`__enter__` 与 `__exit__` 构成完整的协议，`with` 的语义可以完全展开成 `try/finally`：

```python
manager = expression
enter = type(manager).__enter__
exit = type(manager).__exit__
value = enter(manager)          # 绑定给 as 的名字
try:
    body
except BaseException as error:
    if not exit(manager, type(error), error, error.__traceback__):
        raise
else:
    exit(manager, None, None, None)
```

由此得到以下要求：

- `__enter__` 的返回值绑定到 `as` 后的名字，它不是管理器本身，除非协议实现这样返回。
- `__exit__` 在所有路径上都调用一次，参数是异常三元组；正常退出时三个参数都是 `None`。
- `__exit__` 返回真值时异常被吞掉，控制流在 `with` 之后继续；返回假值或 `None` 时异常继续向外传播。
- `__enter__` 抛异常时 `__exit__` 不会被调用：进入阶段的失败发生在协议建立之前，成对的获取与释放要放进已经建立的管理器内部。

## 深入：用生成器写上下文管理器

`@contextmanager` 把一个生成器变成上下文管理器：生成器在 `yield` 处切成两段，`yield` 之前是进入逻辑，`yield` 的值绑定给 `as`，之后的代码是退出逻辑。

```python run id="py.ctx.contextmanager-normal"
from contextlib import contextmanager

@contextmanager
def opened(name):
    print("enter", name)
    try:
        yield name
    finally:
        print("exit", name)

with opened("safe") as handle:
    print("body", handle)
```

body 抛出异常时，异常从 `yield` 处抛回生成器，退出逻辑写进 `try` 的 `finally` 才会在失败路径上运行。

```python run id="py.ctx.contextmanager-error"
from contextlib import contextmanager

@contextmanager
def opened():
    try:
        yield
    finally:
        print("exit ran")

@contextmanager
def absorbing():
    try:
        yield
    except ValueError:
        pass

try:
    with opened():
        raise ValueError("body failed")
except ValueError:
    print("propagated to caller")

with absorbing():
    raise ValueError("body failed")
print("suppressed, caller continued")
```

生成器在 `yield` 处吸收异常、不再抛出时，`with` 调用的 `__exit__` 返回真值，异常被吞掉，控制流继续；未吸收的异常照常向外传播。生成器写成的管理器只能使用一次：`__enter__` 会取走这个管理器保存的参数，同一实例第二次进入时它取不到，抛出 `AttributeError`。

一个 `with` 语句也能同时管理多个对象，进入从左到右，退出从右到左；锁与嵌套事务的正确性依赖这个逆序。
