笔记列表没有显示，可能是脚本未加载、API 返回错误，也可能是取得数据后没有更新界面。先沿完整请求路径观察，才能找到应修改的部分。

## 沿请求定位问题

浏览器开发者工具的网络面板列出页面、脚本、图片和 API 请求；控制台显示脚本错误。

| 观察 | 下一步检查 |
| --- | --- |
| HTML 或脚本没有取得 | 资源路径与服务器响应 |
| 脚本已取得，没有 API 请求 | 控制台错误、事件与调用路径 |
| API 返回 404 或 500 | 方法、路由与服务端日志 |
| 请求到达服务端，脚本读不到响应 | 浏览器报告的 CORS 等限制 |
| JSON 正常返回，界面没有变化 | 解析结果与 DOM 更新 |

给请求一个标识，并在服务端日志中记录它，可以把浏览器中的失败与相应处理过程连起来。日志中的路径、耗时和结果帮助继续缩小范围。

## 时间花在哪里

请求可能经历名称解析、连接建立、发送、排队、处理和返回。往返时间（RTT）表示一次来回的耗时；带宽表示单位时间能传多少数据。

连接已经建立，忽略其他开销，若往返需 80 毫秒，服务端处理需 10 毫秒，三份有依赖的串行请求需约 $3\times(80+10)=270$ 毫秒。独立请求可以重叠等待，有依赖的请求必须等前一份结果。

优化应针对占时较多的环节。减少脚本大小主要减少传输；缩短数据库查询主要减少服务端处理。若请求在等待空闲数据库连接，查询尚未开始，还要检查<Term id="connection-pool">连接池</Term>的等待。

一组请求中，平均耗时会掩盖少数慢请求。第 95 百分位（p95）表示约 95% 的观测不超过该耗时。比较性能时，应使用相同负载，并同时检查失败数量。

## 复用响应与验证缓存

浏览器可以缓存响应，在规则允许时直接复用。服务器可用 `Cache-Control: max-age=60` 指定新鲜期；过期后，客户端可以带上此前取得的 `ETag` 发出验证请求。

| 服务器判断 | 返回结果 | 客户端动作 |
| --- | --- | --- |
| 内容未变 | `304 Not Modified` | 继续使用原正文 |
| 内容已变 | 新的响应正文与标记 | 替换缓存内容 |

验证省去未变化正文的传输，仍需要通信。用户专属数据还要限制共享缓存的使用。具体指令见 [RFC 9111：HTTP 缓存](https://www.rfc-editor.org/rfc/rfc9111.html)。应用内部缓存的更新问题见 <CrossRef id="persistence.caches-and-object-storage" />。

## 超时与重试

超时表示客户端没有在期限内得到结果。下面两种过程都可能表现为超时：

| 服务端经过 | 客户端观察 |
| --- | --- |
| 请求未到达，没有创建笔记 | 等待超时 |
| 笔记已保存，响应丢失 | 等待超时 |

因此，客户端此时可能不知道操作是否完成。读取可以再次请求；有副作用的操作则要考虑重复执行的效果。创建笔记可以使用稳定操作标识，让多次尝试关联到同一次创建。每次换新标识，会失去这种关联。

重试还消耗时间并增加负载。应用应限制次数、安排尝试间隔，并为整个操作设置总时间预算。后台任务怎样保存编号与进度、从中断处恢复，见 <CrossRef id="software-systems.delivery-and-recovery" />。

## 练习

两次有依赖的 API 请求各等待 900 毫秒，服务端各只处理 20 毫秒。应调查哪些等待？若仅把处理缩短到 10 毫秒，总时间会减少多少？

一次操作总共允许四秒。方案最多尝试三次，每次等待两秒，两次重试前分别再等一秒和两秒。计算最长等待，再修改规则，使总等待符合要求。
