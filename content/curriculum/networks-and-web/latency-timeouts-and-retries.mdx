页面打开很慢，可能是脚本太大、请求太多、服务端处理慢，也可能是界面代码收到结果后还在长时间计算。先沿请求路径观察，才能选对修改位置。

## 从浏览器看到发生了什么

浏览器开发者工具的网络面板列出页面、脚本、图片和 API 请求；控制台显示脚本错误。检查笔记列表没有显示的问题，可以按下面的过程缩小范围：

| 观察 | 下一步检查 |
| --- | --- |
| HTML 或脚本没有取得 | 网址、静态资源路径、网络与服务器响应 |
| 脚本已取得，但没有 API 请求 | 控制台错误、事件是否触发、调用路径 |
| API 返回 404 或 500 | 方法与路径、后端路由、服务端日志 |
| 服务端收到请求，脚本却读不到响应 | 浏览器是否报告 CORS 等限制 |
| API 正常返回 JSON，界面未变化 | 解析结果与页面更新逻辑 |

服务端日志可以记录请求标识、路径、处理耗时和结果，用同一个标识关联前端故障与后端处理。日志避免记录口令、会话标识等秘密。

## 时间花在哪一段

一次请求可能经历 DNS 查询、建立连接、TLS 协商、发送、排队、处理和返回。复用连接可以省去部分建立成本；减少内容大小主要影响传输；优化查询主要影响服务端处理。

往返时间（RTT）表示一次来回的耗时，带宽表示单位时间能传多少数据。连接已经建立，忽略其他开销，若往返需 80 毫秒、服务端每次处理需 10 毫秒，三份有依赖的串行请求就需约 `3 × (80 + 10) = 270` 毫秒。独立请求可以重叠等待，有依赖的请求则必须按实际顺序完成。

页面若必须等待多个请求，较慢的一份就可能决定最终等待时间。测量时除了平均值，也应观察慢端：第 95 百分位（p95）表示约 95% 的观测不超过的耗时。统计时要说明数据规模、时间范围和是否计入失败。

后端还可能使用<Term id="connection-pool">连接池</Term>复用数据库连接。请求在等空闲连接时，查询尚未开始；排查慢请求应把这段等待与数据库执行分别记录。

## 缓存复用已有响应

HTTP 缓存可以保存响应，按规则直接复用或向服务器验证。浏览器缓存用于当前用户环境，共享缓存则可能服务多个用户。

| 响应中的指令或字段 | 作用 |
| --- | --- |
| `Cache-Control: max-age=60` | 在规定的新鲜期与其他复用条件下使用已有响应 |
| `ETag: "v7"` | 给内容一个验证标记 |
| `Cache-Control: no-cache` | 可以保存，复用前需要验证 |
| `Cache-Control: no-store` | 禁止按该指令存储 |
| `Cache-Control: private` | 不允许共享缓存保存，私人缓存仍受其他规则约束 |

保存了 ETag 的客户端可以发送 `If-None-Match`。服务器确认内容未变时返回 `304 Not Modified`，客户端继续使用原内容。这省去正文传输，仍有一次通信。规则见 [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html)。

服务器修改资源后，已缓存的响应不会自动变化。静态资源可使用带版本的 URL 区分新旧内容；必须及时更新的数据可以要求复用前验证。因用户而异的内容，要防止共享缓存把一人的响应交给另一人。

## 超时后的操作结果

客户端超时只表明没在期限内得到结果。下面两条过程在客户端看来相同：

| 过程 | 服务端状态 | 客户端 |
| --- | --- | --- |
| 请求未到达 | 没有创建笔记 | 等待超时 |
| 已创建笔记，响应丢失 | 笔记已经保存 | 等待超时 |

创建操作若直接再发一次，可能重复创建。应用可以为同一次操作使用稳定标识，重试时查询或复用已有结果；每次生成新标识就失去了关联作用。幂等性与方法的关系见 <CrossRef id="networks-and-web.http-messages-and-operations" />。

重试还会增加服务器负载。限制次数、在尝试之间等待，并使用总时间预算，才能避免一次点击无限延长。后台任务怎样保存进度并恢复，见 <CrossRef id="software-systems.delivery-and-recovery" />。

## 练习

浏览器记录显示：脚本加载 100 毫秒，第一次 API 等待 900 毫秒，第二次 API 在第一次结束后发出、再等 900 毫秒；两次查询在服务端各用 20 毫秒。应先调查哪些等待与请求依赖？仅将查询加速到 10 毫秒，会改变多少总等待？

另一个页面更新后仍显示旧图片。设计一个排查过程，区分旧文件仍在服务器、浏览器复用了缓存、页面仍引用旧版本 URL 三种情况。

一次操作允许总共等待四秒。方案最多尝试三次，每次等两秒，两次重试前分别再等一秒和两秒。估算最长等待，并修改规则使它满足总预算。
