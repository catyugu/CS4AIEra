小林打开笔记页，编辑区显示“读取失败”。浏览器开发者工具的网络面板列出页面、脚本和 API 请求，控制台显示脚本错误。先确定 `GET /api/notes/7` 到了哪里，再进入相应组件排查。

## 请求路径与诊断

| 观察 | 下一步查什么 |
| --- | --- |
| HTML 或脚本加载失败 | 请求地址、入口返回的状态码和发布文件 |
| 页面加载完成，点击后没有 API 请求 | 控制台错误和事件处理 |
| API 返回 404 | 请求方法和路径，响应来自入口还是应用 |
| API 返回 500 | 后端日志中的处理错误 |
| API 返回 200，正文却是 HTML | 内容类型和 API 路径是否被指向了静态页面 |
| API 返回 200，正文是预期 JSON | 界面是否把数据写入了对应元素 |

入口或后端可以为请求分配一个标识，并把它写入响应首部和日志。维护者用同一个标识查处理状态、查询耗时和错误原因，避免把同时发生的其他请求误认为这一次。

## 请求延迟的组成

一次请求可能包含名称解析、连接、传输、排队和处理。浏览器能观察自己等待了多久；应用日志可以进一步显示是等<Term id="connection-pool">连接池</Term>中的可用连接花了时间，还是查询本身耗时。带宽影响大文件的传输时间；往返时间（RTT）影响请求发出后等待响应的时间。

若连接已建立，一次往返用 80 毫秒，业务处理用 10 毫秒，且其他开销可以忽略，三次有依赖的请求约用 $3\times(80+10)=270$ 毫秒。独立请求可以重叠等待；某次请求如果要用上一响应返回的编号，就要等编号拿到之后再发。

看整体使用体验时，除了平均值，还可以看第 95 百分位（p95）。它描述约 95% 的观测耗时不超过该值。比较改动前后时，同时记录负载、失败数和耗时分布。

## 超时与重试

超时表示调用方在期限内没收到结果。创建笔记时，请求可能尚未到达服务器，也可能已经写入数据库而响应在途中丢失。重新发送 `GET` 可以再次读取；直接重发创建请求，在第二种情况下可能多建一条。

如果接口支持创建重试，客户端可以为每次逻辑创建生成一个稳定的操作标识，后端在同一事务内记录当前用户、操作标识和新建的笔记，并用唯一约束保证同一用户的同一标识只对应一次创建。再次收到该标识时，先核对请求内容是否与首次提交一致。出现超时后，用原标识重发，后端就能返回对应的笔记编号。每次尝试都需要超时，重试的次数和间隔也要服从整个操作的等待预算。涉及后台任务交付的恢复过程见 <CrossRef id="software-systems.delivery-and-recovery" />。

## 练习

自动保存工具最多可等待四秒。现有实现每次等待两秒，失败后等一秒再重试一次。算出它的最长等待时间，调整到四秒以内。若这次操作是新建笔记，第二次请求应当带上什么信息，后端需要保存什么结果？
