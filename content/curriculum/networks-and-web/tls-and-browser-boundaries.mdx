## HTTPS 验证谁在接收数据

普通 TCP 提供有序传输，却不认证对端身份，也不加密应用字节。TLS（Transport Layer Security）在通信双方之间协商密钥，保护后续消息的保密性与完整性；在通常的 HTTPS 配置下，服务器还用证书及私钥证明自己有资格代表目标网站。身份验证使客户端能判断：通信是否确实到达了网址指定的服务，而不是只和某个能接收数据的对端建立连接。

以首次使用证书认证的 TLS 1.3 连接为例，客户端与服务器在握手中交换支持的参数和协商密钥所需的信息；客户端还验证服务器的身份与握手证明。握手完成后，双方用协商出的密钥保护应用数据。

用于签名的一对密钥具有不同用途：私钥由持有者保密，用来产生签名；配对公钥可以公开，用来验证签名。证书把名称和公钥关联起来，客户端根据受信任的签发体系、目标名称和有效性规则验证证书。

服务器还要使用对应私钥对当前握手的记录产生签名，客户端用证书中的公钥验证，见 [RFC 8446：CertificateVerify](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.4.3)。因此只复制一张公开的有效证书，仍缺少产生当前握手签名的私钥。握手与消息保护见 [RFC 8446：TLS 1.3 协议概述](https://www.rfc-editor.org/rfc/rfc8446.html#section-2)。

这些保证成立于 TLS 的两个端点之间。若浏览器先连接到代应用接收请求的反向代理，再由代理转发到应用，浏览器认证的是这个 TLS 端点；代理后面的连接需要另行保护。HTTPS 也没有证明业务结果正确、用户有权执行操作，或服务器保存的数据不会被其他程序读取。

## 同源按三个字段比较

浏览器把通常的 HTTP 与 HTTPS URL 的<Term id="origin">源</Term>定义为协议标识、主机、有效端口组成的三元组。同源策略（same-origin policy）限制一个源上的脚本访问另一个源的资源。这个限制让打开一个页面不会顺便把其他站点的数据交给它的脚本。

以 `https://notes.example/items/7` 为基准：

| 另一个地址 | 是否同源 | 原因 |
| --- | --- | --- |
| `https://notes.example/settings` | 是 | 路径不同不改变源 |
| `https://notes.example:443/settings` | 是 | 显式默认端口与有效端口相同 |
| `http://notes.example/settings` | 否 | 协议标识不同 |
| `https://api.notes.example/items/7` | 否 | 主机不同 |
| `https://notes.example:8443/items/7` | 否 | 有效端口不同 |

页面与 API 使用不同主机名，但部署在同一台机器，并使用一张覆盖两个名字的 TLS 证书。脚本读取 API 响应时，除了证书验证还会遇到什么检查？

两个主机名解析到同一个 IP 地址，仍然可以是不同源；源比较使用 URL 身份。浏览器中跨源写入、嵌入和读取的限制各不相同，见 [MDN：同源策略](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy)。

## CORS 决定响应能否交给脚本

跨源资源共享（CORS）允许服务器通过响应字段声明哪些源的脚本可以读取响应。设页面源是 `https://notes.example`，脚本通过 `fetch` 请求 `https://api.example/items/7`；`fetch` 是浏览器提供的请求接口。

```http
GET /items/7 HTTP/1.1
Host: api.example
Origin: https://notes.example

```

```http
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://notes.example
Content-Type: text/plain
Content-Length: 5

hello
```

在满足 CORS 其他要求时，浏览器依据许可把响应交给发起脚本。缺少许可字段时，某些请求仍已经到达服务器，只是脚本不能读到响应。因此脚本收到 CORS 错误，不证明服务器没有执行请求。

某些方法或请求字段会先触发预检（preflight）：浏览器先发送 `OPTIONS`，询问目标是否允许该源使用拟发送的方法和字段。预检被拒绝时，实际请求不会发送；允许之后才继续发送。详细条件见 [MDN：CORS 与预检](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS#preflighted_requests)。

例如拟发送一个带 `Content-Type: application/json` 的 `PUT` 请求，浏览器可以先询问：

```http
OPTIONS /items/7 HTTP/1.1
Host: api.example
Origin: https://notes.example
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: content-type

```

```http
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://notes.example
Access-Control-Allow-Methods: PUT
Access-Control-Allow-Headers: content-type

```

许可指的是所询问的源、方法和字段。实际 `PUT` 响应仍需满足读取许可规则；不能把一次预检成功当成随后所有响应都会成功。

| 情形 | 请求是否可能已到服务器 | 脚本能否读取响应 |
| --- | --- | --- |
| 不需要预检，但响应无 CORS 许可 | 是 | 否 |
| 需要预检，预检未通过 | 实际请求没有发送 | 否 |
| 请求及响应满足 CORS 规则 | 是 | 是 |

携带凭据的跨源读取还要求显式允许凭据，允许源不能使用通配符 `*`。Cookie 是浏览器附带的状态信息，是否随请求发送另受请求配置和 cookie 规则控制。CORS 的许可只决定浏览器是否把响应交给脚本；服务器仍必须独立检查请求者是否有权限，其他 HTTP 客户端也不受浏览器同源策略约束。
