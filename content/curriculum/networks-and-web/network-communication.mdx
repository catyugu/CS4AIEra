浏览器访问 `https://notes.example:8443/notes/7`，先要找到目标服务，再把请求送过去。这里有两个不同的问题：网络怎样找到接收者，接收者怎样解释所需资源。

## DNS、地址与端口

域名 `notes.example` 是便于使用的名称。<Term id="dns">DNS</Term> 将域名解析为网络地址等信息；<Term id="ip">IP</Term> 地址用于网络寻址，数据经过中间设备转发，到达目标网络端点。

端口帮助操作系统把通信交给相应的服务。程序在某个地址与端口监听，便可以接收发往该处的连接。路径 `/notes/7` 交给应用解释，用来选择笔记资源。

| URL 部分 | 本例 | 作用 |
| --- | --- | --- |
| 方案 | `https` | 指定访问协议 |
| 主机 | `notes.example` | 指定要访问的主机名 |
| 端口 | `8443` | 指定服务端口 |
| 路径 | `/notes/7` | 指定应用中的资源 |
| 查询参数 | 如 `?format=json` | 向应用提供参数 |

网址省略端口时，协议有默认值。`localhost` 指发起访问者自己的环境：服务端程序使用它访问本机服务，用户浏览器使用它则访问用户自己的机器。


## 连接与数据传输

网络把数据拆成分组，经过中间设备转发。多个参与方可以共享链路，这种方式称为<Term id="packet-switching">分组交换</Term>。分组可能延迟、丢失或乱序。

TCP 为应用提供有序、可靠的字节流，用序号、确认和重传处理传输问题。应用按顺序读到字节，再按自己的格式划分消息。UDP 则提供保留单份边界的数据报，由上层安排所需的可靠性。

例如，浏览器可以通过 TCP 连接发送 HTTP 请求。连接被拒绝，说明尚未走到应用处理请求的阶段；收到应用的错误响应，则说明通信已经到达了能解释请求的程序。

## HTTPS 与传输安全

HTTPS 使用 TLS 保护通信内容的保密性和完整性，并通常通过证书验证服务器身份。浏览器检查证书是否适用于当前主机名，以及是否有可信的认证链，见 [MDN：TLS](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Transport_Layer_Security)。

以笔记服务为例，TLS 保护笔记内容经过网络时的传输。服务收到请求后，再按应用规则查找笔记并判断权限。下一课会读取这份请求与响应。

## 从网址到响应

以首次访问一个使用 HTTP/1.1、TCP 和 TLS 的网站为例，可以把前面的机制串成一次通信过程：

```text
URL: https://notes.example:8443/notes/7
  │  提取主机名、端口和路径
  ▼
DNS 解析主机名，取得 IP 地址
  │  向该地址的 8443 端口建立 TCP 连接
  ▼
TLS 握手，验证服务器身份并建立加密通信
  │  发送 HTTP GET /notes/7 请求
  ▼
服务端处理请求，返回 HTTP 响应
```

浏览器用主机名找到服务，用 IP 地址和端口定位通信端点，再通过 HTTP 路径指定要读取的笔记。DNS 的结果和已经建立的连接都可能复用；这里选择首次访问，是为了展示各环节的职责。HTTP 的消息结构见 <CrossRef id="networks-and-web.addressing-and-listening" />。
## 练习

访问开头的网址时，分别遇到“域名无法解析”“连接被拒绝”“收到 404 响应”。每种结果说明请求走到了哪里？应先检查名称解析、监听服务，还是应用路径？

后端部署在远程服务器，前端脚本却请求 `http://localhost:8000/notes`。用户打开页面时，请求会发到哪里？应当修改哪一处地址？
