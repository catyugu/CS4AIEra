浏览器向服务器请求一条记录，服务器返回一段文本。双方交换的是有规定格式的报文；下面按 HTTP/1.1 的形式展示这次请求与响应。

```http
GET /items/7?format=text HTTP/1.1
Host: notes.example
Accept: text/plain

```

这份 HTTP/1.1 示例请求要取得记录 7 的文本内容。客户端发出请求（request），服务器返回响应（response）：

```http
HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Content-Length: 5

hello
```

这些是构造的报文示例，HTTP/1.1 的实际行结束使用回车加换行。HTTP/2 与 HTTP/3 的线格式不同，但仍表达方法、目标、字段与内容这些语义。

## 从报文读出资源与内容

请求行包含方法 `GET`、请求目标和协议版本。`Host` 指定目标主机；同一 IP 地址上可以承载多个主机名。字段（header fields）提供报文的附加语义；空行结束字段部分，之后是内容（body）。响应状态行中的 `200` 是状态码，`OK` 是可读短语，程序应根据状态码而非短语判断。

`Accept` 表示客户端可接受的内容类型；`Content-Type` 声明响应内容的类型及这里使用的字符编码。`Content-Length: 5` 指定内容有五个字节，不是五个任意字符。内容长度也可以通过协议的其他成帧机制确定，解析器必须按具体协议规则找出报文终点，见 [RFC 9112：消息格式](https://www.rfc-editor.org/rfc/rfc9112.html#section-2.1)。

浏览器地址 `https://notes.example/items/7?format=text#details` 还含有 `https` 协议标识和 `details` 片段。片段由客户端用于定位内容，不进入发给服务器的请求目标，见 [RFC 3986：URI 组成与片段](https://www.rfc-editor.org/rfc/rfc3986.html#section-3.5)。查询 `format=text` 怎样解释则由应用约定。

## 请求成功的含义由操作契约决定

方法区分对资源请求的操作。`GET` 请求取得表示；`PUT` 请求创建或替换目标资源的状态；`POST` 请求让目标资源按自己的语义处理内容。不能仅凭一个 URL 就判断请求是否会修改数据。

如果 `/items/7/title` 这个资源的表示就是纯文本标题，替换标题的请求可以携带内容：

```http
PUT /items/7/title HTTP/1.1
Host: notes.example
Content-Type: text/plain; charset=utf-8
Content-Length: 5

hello
```

这里空行之后的五个字节提供新的标题表示。请求方法说明操作，内容类型说明怎样解释这些字节，具体资源契约说明允许哪些标题。字段齐全也不意味着内容一定通过应用校验。

资源的“表示”是用于传送其当前内容的形式，例如这里的纯文本标题，或包含多个字段的 JSON。`GET` 取得这种表示；客户端修改后用 `PUT` 提交替换内容。资源是请求指向的对象，表示是双方交换的内容，两者需要区分。

HTTP 把请求语义上不要求改变服务器状态的方法称为**安全方法**（safe methods）。记录访问日志等附带动作并不因此被禁止。HTTP 把重复相同请求与执行一次具有相同预期服务器效果的方法称为**幂等方法**（idempotent methods）；`GET`、`PUT` 和 `DELETE` 有这一语义，`POST` 没有一般的幂等保证，见 [RFC 9110：方法的共同属性](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2)。

幂等比较的是预期效果，响应不必相同。例如第一次删除已存在的资源后，再次删除可能得到“已不存在”；两次都把资源留在不存在的状态。一个把 `GET /delete-item/7` 实现为删除记录的应用，违背了安全方法的语义，链接预取或缓存就可能触发开发者没有预期的修改。

状态码只表达 HTTP 层的结果种类，业务含义仍需与契约结合。`202 Accepted` 表示请求已接受处理，处理尚未完成；客户端若要知道任务最终结果，需要后续查询或其他通知机制。`404` 表示目标资源没有可提供的当前表示，或服务器不愿说明它存在。`500` 表示服务器遇到妨碍完成请求的意外状况，不能据此推断此前已经完成的修改被撤销。

## 请求之间的状态由应用保存

HTTP 的每份请求携带可独立解释的语义；连接复用只是传输安排。应用仍可以在服务器保存记录，并让多份请求访问它，也可以通过 cookie 等显式信息关联请求。

| 状态的位置 | 刷新页面之后 | 服务器进程重启之后 |
| --- | --- | --- |
| 当前页面脚本中的普通变量 | 重新创建页面时丢失 | 与服务器重启无直接关系 |
| 服务器进程的内存变量 | 若服务器仍运行，可以保留 | 原进程的内存状态丢失 |
| 服务器使用的持久存储 | 页面可重新请求取得 | 是否保留取决于存储与完成写入的保证 |

因此“刷新之后状态没了”首先要问修改存在哪里。浏览器显示过新值，不证明服务器保存过；服务器返回过成功响应，也只有在接口承诺了持久保存时，才能把它作为这项保证的证据。

## 练习

一个 API 通过 `POST /exports` 创建导出任务，返回 `202` 和任务地址；另一个 API 返回 `200` 及已经生成的文件内容。客户端能否在两种响应之后都立即显示“文件已生成”？各自还缺什么证据？

审查两种更新操作：“把记录 7 的标题设为 hello”和“在记录 7 的阅读次数上加一”。在没有其他并发修改时，重复相同请求分别会怎样改变状态？选择方法时，怎样让协议语义和实际操作保持一致？
