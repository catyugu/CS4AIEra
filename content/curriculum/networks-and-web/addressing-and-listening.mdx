连接将字节交给对方，HTTP 则规定浏览器和服务端怎样表达请求与响应。读取一组完整报文，可以把网址、操作、返回数据和处理结果连起来。

## HTTP 请求与响应

下面是一组构造的 HTTP/1.1 报文，供阅读。客户端请求笔记，服务器返回 JSON：

```http
GET /notes/7 HTTP/1.1
Host: notes.example
Accept: application/json

```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"id":7,"title":"reading"}
```

请求中的 `GET` 是方法，`/notes/7` 是目标。响应中的 `200` 是状态码。首部字段说明内容类型等信息，空行之后是正文。实际 HTTP/1.1 还按协议规则界定正文长度；这里省略成帧细节，只观察报文含义。

常见方法包括取得表示的 `GET`、提交内容进行处理的 `POST`、创建或替换目标状态的 `PUT`，以及删除目标的 `DELETE`。例如，创建笔记可以用 `POST /notes`，内容放在 JSON 正文中。

`200` 通常表示成功，`201` 表示已创建，`404` 表示找不到可提供的目标，`500` 表示服务端处理遇到意外错误。`202` 表示已接纳但尚未完成。方法和状态的准确含义见 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)。


## 内容类型与消息正文

返回 JSON 时，`Content-Type: application/json` 告诉接收方按 JSON 解释正文；HTML 页面则使用 `text/html`。客户端应先判断状态和预期格式，再处理内容。例如，查询失败时服务可能返回 HTML 错误页，直接当成 JSON 解析就会出错。

请求也可以包含正文。创建笔记时，`POST /notes` 的正文可以携带标题和内容；服务端解析这些数据，执行创建，再返回新编号。

## HTTP 方法与幂等性

`GET` 用于读取，属于安全方法。`PUT` 和 `DELETE` 具有<Term id="idempotence">幂等性</Term>语义：重复相同请求的预期效果与执行一次相同。把标题设为“reading”，执行两次仍是这个标题；把阅读次数加一，执行两次则增加两次。

幂等性约束操作效果，两次响应可以不同。例如首次删除成功，第二次可以报告目标已经不存在。`POST` 没有一般的幂等保证。方法的定义见 [RFC 9110：方法的共同属性](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2)。

## HTTP 缓存与条件请求

浏览器反复读取同一条笔记时，可以在规则允许的期限内复用先前收到的响应。服务器可用 `Cache-Control: max-age=60` 指定新鲜期；过期后，客户端可以带上此前取得的 `ETag` 发出验证请求。

| 服务器判断 | 返回结果 | 客户端动作 |
| --- | --- | --- |
| 内容未变 | `304 Not Modified` | 继续使用原正文 |
| 内容已变 | 新的响应正文与标记 | 替换缓存内容 |

验证省去未变化正文的传输，仍需要通信。用户专属数据还要限制共享缓存的使用。具体指令见 [RFC 9111：HTTP 缓存](https://www.rfc-editor.org/rfc/rfc9111.html)。应用内部缓存的更新问题见 <CrossRef id="software-systems.caches-and-object-storage" />。

## 练习

一份请求使用 `GET /notes/7`，响应状态为 200、内容类型为 JSON。分别指出哪一部分表示要读哪条记录、哪一部分表示处理结果、哪一部分规定正文格式。

比较“将计数设为 10”和“将计数加 1”。各重复执行两次，最终状态是什么？据此判断它们的操作效果是否幂等。
