## 目的

本课要解决的问题是：当一段代码的正确性无法靠"读起来像是对的"来保证时，我们靠什么来推理它。

答案要先固定三件事：这段程序在任意时刻有哪些**状态**；哪些**转移**会改变状态；哪些性质在转移前后都**必须成立**。第三件事就是 <Term id="invariant">不变量</Term>。它是后续所有内容（循环、数据结构、并发、事务、协议）共用的推理工具，因此必须先在这里建立。

## 状态与转移

把程序看作一个状态机。状态是程序在某一时刻需要记住的全部内容：变量绑定、对象内容、文件位置、连接状态。转移是一条语句或一次调用的效果。

这个模型的价值在于它把"这段代码做什么"换成了一个可以检查的问题：**从任意满足前置条件的状态出发，转移后的状态是否仍满足我声明的性质？**

```text
state  s0 --statement--> s1 --statement--> s2 ...
```

注意状态不是源代码。源代码是状态的转移规则，不是状态本身。混淆二者是"这段代码看起来没问题"这类判断失效的常见原因。

## 不变量

对程序性质 `P`，若对每条转移 `T` 都有

```text
P(s) 成立  =>  P(T(s)) 成立
```

则称 `P` 是关于该程序的不变量。它必须在初始状态成立，并在每次转移后保持。

两点限定：

- 不变量是关于**状态**的性质，不是关于某一行代码的性质。写不变量时不要提到"第 3 行执行之后"。
- 不变量只有在前置条件满足时才被保证。`P` 若依赖"输入非空"，那么空输入不在保证范围内，这是断言的一部分而不是缺陷。

与之相对，**后置条件**只要求在终止状态成立，不要求在中间状态成立。循环中间变量会被反复破坏，所以它们通常不是不变量，只有被小心设计的形式才可能成为不变量。

## 循环不变量

循环是不变量最实用的场景，因为它同时给出正确性论证和终止性论证。

以二分查找的收窄循环为例。令区间为 `[lo, hi)`，候选区间为 `values[lo:hi]`。声明不变量：

```text
INV: 若 target 存在于 values 中，则其下标落在 [lo, hi) 内
```

- **初始化**：`lo = 0`，`hi = len(values)`，候选区间是整个数组，`INV` 成立。
- **保持**：取 `mid = (lo + hi) // 2`。若 `values[mid] < target`，则所有下标 `<= mid` 都不可能是目标，令 `lo = mid + 1`，`INV` 保持；否则目标不可能在 `mid` 右侧（对已排序输入），令 `hi = mid`，`INV` 保持。
- **终止**：`lo == hi` 时候选区间为空，由 `INV` 得 target 不存在。

注意这个论证没有讨论任何具体输入。它同时解释了为什么必须用 `[lo, hi)` 而不是闭区间：半开区间让"空区间"有一个不含特例的表示。

## 用可运行代码观察状态

下面的单元把一个列表按身份共享，然后修改其中一个名字看到的内容。

```python run id="foundations.invariant.alias-demo"
a = [1, 2, 3]
b = a
b.append(4)
print("a =", a)
print("same object:", a is b)
```

`a` 与 `b` 是同一个列表的两个名字。这里可观察的不变量是：只要没有重新绑定 `a` 或 `b`，`a is b` 始终为真，而 `len(a)` 的变化会同时被两个名字看到。

改一个值再运行：把 `b.append(4)` 换成 `b = b + [4]`。`b + [4]` 产生新列表并重新绑定 `b`，于是 `a is b` 变为假。同一个语法层面的"加一个元素"，在状态层面是两种完全不同的转移。

## 边界与失败情形

- **不变量写得太弱**：`INV: lo <= hi` 在任何二分查找里都成立，但它推不出终止时的结论。弱不变量不会导致错误，只会让论证失败——这比看起来像错的更强的不变量更危险，因为它"看起来在起作用"。
- **不变量写得太强**：`INV: target 一定在 [lo, hi) 内` 在 target 不存在时为假，于是循环中途就会破坏它，论证随之失效。正确写法是条件式："若存在，则落在区间内"。
- **前置条件被静默违反**：二分查找依赖输入已排序。输入未排序时 `INV` 的保持步骤为假，程序返回的结果无意义但不会崩溃。
- **非终止**：`INV` 只保证结果正确，不保证循环结束。终止性需要另一个论证，通常是一个随每次迭代严格递减且下有界的量。

## 生产后果

- 代码评审里"这条不变量是什么"比"这段代码好不好看"更能发现问题，因为它可以被反例直接证伪。
- 事务、锁与并发协议的正确性都以不变量表述：数据库的约束就是被持久化并强制执行的不变量，详见 <CrossRef id="db.sql.null-semantics" /> 中对 `NOT NULL` 与 `CHECK` 的处理。
- 调试时先写下你认为成立的不变量，再观察它在哪里第一次被破坏，比在输出里猜测要快得多。
- 生成式工具可以很快写出一个"看起来正确"的循环。能判断它是否正确的唯一办法是写出不变量并检查保持步骤，这正是本课要保留的能力。

## 该委托给工具的部分

具体语言的断言语法、调试器命令、静态分析器选项都可以查文档，不必记忆。需要自己保留的是：**先写不变量，再检查初始化、保持与终止**这一套动作。

## 小结

- 程序是状态机；源代码是转移规则，不是状态。
- 不变量必须在初始状态成立，并在每条转移后保持；它不能提到具体某一步。
- 后置条件只约束终止状态，因此比不变量弱。
- 循环正确性 = 初始化成立 + 保持成立 + 终止时蕴含结论；终止性需要单独论证。
- 不变量太弱会让论证失效，太强会在中途被破坏；两种失败模式都要主动排查。
