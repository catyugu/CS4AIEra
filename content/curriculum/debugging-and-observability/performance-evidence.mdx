有人建议改写一个循环来加速报告生成。报告现在需要一秒，循环占其中一毫秒。即使这个循环完全消失，也只能省下一毫秒。性能诊断首先要确定被优化的工作占多少，再判断改变它能否解决用户的等待。

## 同样的一秒，可以有不同原因

经过时间是用户从操作开始到结束等待的时长，包含计算、排队、输入输出等待和调度等待。CPU 时间统计处理器执行程序所花的时间。多线程并行时，总 CPU 时间甚至可以超过经过时间。

考虑用一个独立进程生成一次报告。这个例子中，报告由单线程执行，进程中也没有其他线程同时工作。两次测量如下：

| 执行 | 经过时间 | 进程 CPU 时间 |
| --- | ---: | ---: |
| A | 1000 毫秒 | 920 毫秒 |
| B | 1000 毫秒 | 20 毫秒 |

A 的时间大部分用于计算，适合先找出主要计算在哪里。B 的时间大部分没有消耗进程 CPU，先查它在等什么。B 的这两个数字不能独自区分磁盘、网络、排队和调度等待；它们只帮助选择继续观察的位置。

Python 的 `perf_counter` 测经过时间，包含等待；`process_time` 测进程 CPU 时间，不包含睡眠，见 [Python time 的计时函数](https://docs.python.org/3/library/time.html#time.perf_counter)。进程 CPU 时间覆盖进程里的工作，在并发服务中不能直接归给某一条请求。

## 先看调用关系，再看最高的数字

继续检查执行 B。为报告生成及其子调用分别计时，得到以下记录；本例调用顺序执行，表中的累计时长包含下层调用。

| 操作 | 由谁调用 | 次数 | 累计时长 |
| --- | --- | ---: | ---: |
| generate_report | 外层调用方 | 1 | 1000 毫秒 |
| load_details | generate_report | 1 | 800 毫秒 |
| fetch_one | load_details | 100 | 800 毫秒 |
| format_row | generate_report | 100 | 1 毫秒 |

`load_details` 的 800 毫秒就是它等待 100 次 `fetch_one` 的区间，已经包含在报告的 1000 毫秒中。把两行 800 毫秒相加，会将同一段工作算两遍。行格式化共一毫秒，暂时解释不了主要等待。

调用次数给出了下一项可检验的问题：报告要读 100 条详情，这 100 次独立读取是否必要？逐次读取、一次批量读取和复用已读取的数据可能有不同成本，也有不同的权限、时效与失败规则。应检查接口是否支持相同结果的批量操作，再用相同输入比较，不能只凭调用次数宣布该用缓存。

<Term id="profiling">性能剖析</Term>（profiling）将执行活动归到函数和调用路径。剖析工具常同时显示自身耗时与累计耗时：自身耗时扣除下层调用，累计耗时包含下层调用。父函数累计高而自身低时，继续看它调用了什么。Python `cProfile` 的这些字段见 [Python 剖析器文档](https://docs.python.org/3/library/profile.html#instant-user-s-manual)。记录全部调用的工具与间歇采样执行位置的工具也有不同开销，剖析结果应结合测量方式阅读。

## 从占比估算收益，再检查前提

若修改只让 `load_details` 的这 800 毫秒缩短一半，其余 200 毫秒保持不变，报告需要 $800/2+200=600$ 毫秒。把某一部分加速两倍，整份报告没有因此加速两倍。

一般地，基线总时间为 $T$，可优化部分占比为 $f$，该部分加速 $s$ 倍，其余不变，则

$$T'=T(1-f)+Tf/s.$$

即使把该部分完全消除，也还需要 $T(1-f)$。这个上限可以排除收益太小的方案。例如只优化占比千分之一的格式化循环，无法把一秒缩短到半秒。

这里假定各阶段顺序执行，负载与其余阶段不受修改影响。如果批量读取减少了调用次数，或并行读取改变了排队和资源争用，原来的时间分配也会改变。公式可以给出初步估算，改动后的全程测量负责核对估算。

## 一次查询快，不等于整个方案快

以下实验比较扫描列表与先建立索引。要求是返回整数在列表中第一次出现的位置；查询值都存在。扫描省去准备工作，索引则先保存每个值的位置，让后续查询直接取得结果。

```python run id="debugging-and-observability.performance-evidence.phases"
from time import perf_counter

values = list(range(4000))
queries = [3999] * 200

started = perf_counter()
positions = []
for wanted in queries:
    for i in range(len(values)):
        if values[i] == wanted:
            positions.append(i)
            break
scan_time = perf_counter() - started

started = perf_counter()
index = {}
for i in range(len(values)):
    if values[i] not in index:
        index[values[i]] = i
build_time = perf_counter() - started

started = perf_counter()
indexed_positions = []
for wanted in queries:
    indexed_positions.append(index[wanted])
query_time = perf_counter() - started

print("scan positions:", positions[:5])
print("indexed positions:", indexed_positions[:5])
print("scan seconds:", scan_time)
print("build seconds:", build_time)
print("indexed query seconds:", query_time)
print("indexed total seconds:", build_time + query_time)
```

`perf_counter()` 返回计时读数，两次差值得到本次经过时间。`[3999] * 200` 建立 200 次相同查询；`positions[:5]` 只显示结果列表的前五项，避免长输出遮住阶段耗时。建立索引时，遇到已保存的值就跳过，因此保存的是第一次出现的位置。

这份输入使每次扫描都走到列表末尾，也让索引能使用很多次。它适合观察重复查询节省的工作，尚不能支持“所有查询都应建立索引”。将 `queries` 改成 `[0]`，只查一次首元素：扫描立即结束，索引仍要先检查 4000 个元素。改成 `[3999]`，仍只有一次查询，但扫描也要检查全部元素。查询的次数和位置都影响比较。

索引方案的全程成本是构建加全部查询；只比较两个查询阶段会遗漏准备工作。若数据在查询之间变化，还要计入更新或重建索引的成本。表示与索引的取舍见 <CrossRef id="data-algorithms-and-scale.representation-preprocessing-and-indexes" />。

计时输出随机器和运行负载变化，短区间尤其容易受测量与调度开销影响。一次极小的差值不足以确定哪种方案稳定更快。先保持结果要求相同，再用能代表实际使用的输入重复比较；计时结果也不能替代关于规模增长的分析。

## 练习

在 `values` 列表末尾再追加一个 3999，保持本次查询不变。若建立索引时删掉 `if values[i] not in index`，它保存的位置会怎样变化？即使计时更短，这项修改能否作为当前要求下的优化？

一份剖析报告显示 `handle` 累计 800 毫秒、`query` 累计 600 毫秒，且 `query` 由 `handle` 调用。有人准备将 `handle` 改写为更短的函数，因为它的累计耗时最大。还需要哪一项耗时或调用证据，才能判断应修改哪个函数？

服务中很多请求共享一个进程。一条请求经过时间为 100 毫秒，同一期间进程 CPU 时间增加 90 毫秒。能否确认这条请求用了 90 毫秒 CPU？提出一种与数字一致的其他执行情况，并选择更合适的观测。
