# CONTENT_GUIDE.md

本文件规定一门课如何写：读者假设、内容分级、论证与示范方式、术语与引用、写作风格。

课程包含什么、模块顺序与完成状态见 `doc/CURRICULUM.md`；产品与运行时如何实现见 `doc/DESIGN.md`；仓库级不变量与验证要求见 `AGENTS.md`。

## 1. 读者

读者可能无正式 CS 前置知识，但具备专业级技术推理能力：能读懂技术定义、跟上代码与形式化论证。

由此得到两条硬要求：

- 前置知识在被依赖之前引入，不用类比替代机制，不为"易懂"降低技术深度；
- 不写面向初学者的鼓励性铺垫、儿童化比喻与 Tutorial 式过渡。

## 2. 内容分级

按"学它的价值"给每个主题定级，再决定篇幅。判据是：**记不住这一点，是否会实质损害推理能力？** 若否，不为它花整页。

| 级别 | 特征 | 处理 |
| --- | --- | --- |
| A Lookup / 可委托 | 语法表、长 API 清单、命令行参数、样板、易变库用法、厂商管理命令、面试题清单；有经验的实践者检索或问 AI 即可得到 | 尽量不进正文；仅在读懂后续示例必需时给紧凑参考。教"如何验证"而不是"如何记住" |
| B Working knowledge | 生产高频细节、读懂普通代码所需的惯例、常见工具操作、浅但处处出现的语言与库行为 | 精确解释，演示一到两次；目标是识别与正确使用，不是死记 |
| C Core model | 语义、不变量、抽象边界、成本模型、数据表示、失败行为、并发顺序、持久化规则、安全与信任边界 | 先定义再依赖，推导后果，给反例，必要时用可执行实验，并在多个语境下反复回顾 |
| D Deep leverage | 反复决定真实系统正确性、性能、可运维性或安全性的概念；API 简单但后果微妙；生成代码看似合理却可能出错 | 覆盖对抗性情形与故障模式；说明什么证据能证伪直觉；连到其他模块 |

课程应在 C、D 两级上不成比例地丰富。各模块对这套分级的默认解释记录在 `doc/CURRICULUM.md` 的模块小节里，不在这里重复。

AI 时代的两个后果：

- **减少记忆负担**：不围绕记忆设计课程。要学的是该问什么、如何识别可信答案、如何验证。
- **强化验证**：生成代码很便宜，正确性论证不便宜。持续追问：前置条件是什么？保持了哪条不变量？哪些状态被共享？哪些操作可能被重排？部分失败时会发生什么？这个 API 承诺了什么，什么只是碰巧如此？

不要把"AI 视角"做成每节课的装饰标签，也不要给每节课塞一段"AI 容易写错什么"。它的作用决定优先级与验证习惯，不构成段落。

## 3. 写一节课

一节课只承担一个核心原理，或一族高度内聚的机制/心智模型。

下面是适用的写作规则，不是必须套用的模板：结构服务于内容，标题与段落划分按内容需要决定，缺少某一项不是缺陷。

| 规则 | 说明 |
| --- | --- |
| 目标只有一处 | 可检验目标写在 frontmatter 的 `objectives` 里，页面渲染成"学习目标"；正文不再用一节复述这一课要干什么 |
| 导入进入问题 | 正文以一到两段导入开头：这一课处理什么情形、依赖哪些前提、结论取什么形式。导入直接进入问题 |
| 先给模型再给后果 | 定义实体、状态、操作、不变量与假设；有形式定义就给出。具体内容需要它时才写生产后果，不挂成每节课末尾的固定栏目 |
| 示例暴露机制 | 示例用于检验模型，不是展示语法能跑通 |
| 实验可对账 | 让读者改代码或查询并运行，把观察结果与模型比对 |
| 边界写进所属机制 | 空输入、重复值、缺失值、溢出、并发修改、部分失败、版本差异在依赖它的段落里交代，不汇总成每节课末尾的清单 |
| 目标用可观察动作表述 | 写在 frontmatter 的 `objectives` 里，用推导、区分、预测、追踪、估算、在约束下选择、构造反例、解释故障模式这类动作；避免"理解 X"，除非给出具体判据 |

### 3.1 课时结构

小节标题按内容命名，不套用统一序列。默认形态通常是：导入段 → 依内容命名的小节（模型、机制、示例，以及随机制交代的边界）→ 内容较长、确有需要时写小结。

### 3.2 标题与锚点

标题文本同时决定页面锚点，同一课时内两个标题规约到同一锚点时构建失败。因此标题要短，不用标点堆叠（`：`、`、` 等字符不进入锚点），也不要在标题里使用行内代码与强调之外的 Markdown 语法。

跨课时引用用 `<CrossRef id="...">` 指向稳定 ID，不要指向锚点。

### 3.3 可见性与阅读顺序

- 新课时先以 `draft` 落盘，在开发服务器下通读并运行全部单元格，再改为 `published`。
- 各状态如何影响路由与导航见 `doc/DESIGN.md` 第 5.4 节；阅读顺序、`order` 的作用域与 slug 规则见 `doc/DESIGN.md` 第 5 节。

## 4. 定义、术语与引用

| 规则 | 说明 |
| --- | --- |
| 先定义后依赖 | 术语即使预期多数读者已熟悉，也须在论证依赖它之前定义 |
| 优先精确定义 | 存在且重要的形式定义必须给出，不用类比替代。例如：函数是*单射*的，当且仅当不同输入总映射到不同输出 |
| 区分规范与实现 | 明确论断针对抽象模型、语言规范、协议标准、具体实现、具体版本还是通行实践。语言语义与实现行为不得混为一谈 |
| 引用有节制 | 需要快速回忆时用 `<Term id="...">`，不给每次出现都加标记；不为每个名词新建词条。只有会跨模块反复引用、短定义有独立价值、或术语文容易产生持续误解时才值得新增词条 |
| 词条不是阐述 | 词条短定义一到两句，精确到不会教出错误模型；正文仍须独立讲清当前需要的概念，术语表只是回忆入口 |
| 中英术语 | 英文代码、论文、标准与文档中常见的术语，首次出现给英文，如 可串行化（serializability）；此后保持中文译名一致，除非英文已成工程惯例 |

机制（`<Term>` 的解析、词条 schema、快速定义浮层、词条页面）由 `doc/DESIGN.md` 第 14 节规定。

## 5. 论证

| 规则 | 要求 |
| --- | --- |
| 声明假设 | 复杂度、分布式与性能论断离开假设就没有意义。复杂度要说明输入度量与操作成本模型；系统要说明失败与时间假设 |
| 推导而非断言 | 结论若来自不变量或递推，就展示推理 |
| 大胆使用反例 | 简短反例常是推翻诱人错误规则的最好方式 |
| 区分经验与演绎 | 基准测试只证明某配置下的行为，不证明渐进律或普遍实现性质 |
| 不以权威代替论证 | 文档与标准是契约证据，不能替代对后果的推理 |

## 6. 代码示例

| 规则 | 要求 |
| --- | --- |
| 每个示例都要有理由 | 至少展示其一：语义、状态转移、表示、故障模式、算法、性能影响、并发行为、接口契约 |
| 最小但不误导 | 去掉无关样板，但不删产生关键行为的行 |
| 让状态可观察 | 打印或返回能暴露模型的量：身份、别名、形状、边界值、成本增长 |
| 确定性 | 不用当前时间、随机源、在线 API、网络与未规定的迭代顺序。以不确定性为课题时，说明允许结果的集合 |
| 资源有界 | 在普通硬件上快速结束，不无意分配无界内存或打印海量行。演示渐进增长时，规模要大到能显现效果、小到能在浏览器里跑完 |
| 假定读者会改 | 解释在邻近情形下仍成立。实验依赖关键条件时显式命名，不藏在任意常量里 |
| 不依赖隐藏状态 | 默认单元格相互隔离；只有共享状态本身有教学价值时才使用具名 session |
| 不依赖富显示 | 输出优先文本、表格或简单图形 |

本仓的约定是：**每节课至少有一种能检验核心论断的证据**。论断能由浏览器实验忠实呈现时，证据就是可执行单元格；不能时必须给出另一种可观察证据——状态轨迹、协议报文、系统调用 trace、查询计划、日志、崩溃前后的状态、形式推导。不为凑单元格把真实行为模拟成玩具示例：操作系统、网络与安全模块的机制大多无法在浏览器运行时里忠实重现，那里的选题不因运行时的能力而被裁剪。

Python 可执行内容适合讲：名称绑定与对象身份、可变性与别名、相等与同一、迭代协议、生成器、闭包与延迟绑定、异常与上下文管理器、数据模型与描述符、算法轨迹、数据结构不变量、解析与序列化。不把单元格的篇幅花在官方文档讲得更好的标准库方法清单上；涉及 CPython 特有行为要标注，且不得暗示课程运行时必然复现 CPython 的全部底层特征。

SQL 可执行内容（夹具设计、数据情形选择、方言标注、查询计划配对）见 `doc/CURRICULUM.md` 的数据库模块小节与 `doc/DESIGN.md` 第 9 节。

## 7. 可执行单元格的声明语法

普通 fenced 代码块是静态的。要成为可执行单元格，必须在信息串中显式写出 `run`，并给出课时内唯一的 `id`：

````md
```python run id="py.names.rebinding"
a = [1, 2]
b = a
b.append(3)
print(a)
```
````

语言只能是 `python` 或 `sql`。`run` 之后可用的选项：

| 选项 | 适用 | 含义 |
| --- | --- | --- |
| `id` | 必填 | 单元格标识，须在课时内唯一 |
| `session` | 可选 | 具名 session；省略表示状态隔离 |
| `timeout` | 可选 | 该单元格的硬超时（毫秒） |
| `packages` | 可选 | 逗号分隔的包名；必须属于固定 Pyodide 发行版 |
| `fixture` | SQL 必填 | 实验夹具 id，对应 `content/labs/<dir>/lab.yaml` 的 `id` |
| `editable` | 可选 | 默认 `true`；`false` 用于不应被修改的演示 |
| `expect` | 可选 | 期望输出快照，仅作文档，不参与判分 |

规则：

- 未知选项、非正整数的 `timeout`、不在固定发行版内的包名都会让构建失败。
- `session="isolated"` 是默认行为，写了会被判为冗余并报错。
- SQL 单元格必须声明 `fixture`；同一 `session` 中后续单元格可以省略，它们复用该连接。同一 session 声明两个不同 fixture 是错误。
- Python 单元格不得声明 `fixture`。
- 课时内 `id` 重复是错误；不同课时可以复用同名 id，因为执行作用域是页面。

读者看到的按钮语义（运行、编辑、恢复代码、停止、重置 session）与超时口径由 `doc/DESIGN.md` 第 11 节规定。

## 8. 练习（无 LMS）

产品不判分，练习依然有价值。优先让学习者：改一个假设并解释后果；构造反例；诊断 bug；估算复杂度或资源占用；在给定约束下二选一；写个小实现并与不变量比对；检视查询计划；在受控模型中复现竞态或故障。

避免主要挑战是"生成样板"的大作业。解答可折叠或放在刻意留白之后，但应解释推理，不只给最终代码。

## 9. 来源与论断

| 规则 | 要求 |
| --- | --- |
| 优先一手来源 | 语言规范、官方语言与运行时文档、RFC 与标准、数据库厂商文档、操作系统手册、算法与分布式系统与安全概念的经典论文 |
| 版本敏感要注明 | 行为可能随运行时、数据库或协议版本变化时，说明版本与适用范围，或引用权威来源 |
| 避免民间说法 | "X 总是更快""Y 是线程安全的""TCP 保证送达"这类表述通常需要限定，要写出真实契约 |
| 出处写在句子里 | 版本敏感或实现相关的论断，在作出它的那一句里给出一手来源：行内 Markdown 链接指向语言参考、标准库文档、PEP、RFC 或厂商文档的具体小节，链接文本写出文档名 |

## 10. 跨模块连接

课程应反复连接跨模块概念：

- 对象身份 ↔ 别名 ↔ 容器可变性 ↔ 共享状态与并发
- 渐进复杂度 ↔ 缓存局部性 ↔ 数据库查询计划
- 文件描述符 ↔ socket ↔ HTTP 服务器
- 重试 ↔ 幂等 ↔ 事务 ↔ 投递语义
- 虚拟内存 ↔ 内存映射 ↔ 数据库缓冲管理
- 不变量 ↔ 测试 ↔ 事务 ↔ 授权规则
- 哈希 ↔ 哈希表 ↔ Git 的内容寻址 ↔ 密码学哈希的安全区别

交叉链接要照亮共享模型，而不只是宣传另一章。一处模型只在它的主场完整讲授，其他位置引用。

## 11. 写作风格

| 规则 | 要求 |
| --- | --- |
| 精确而经济 | 直接陈述加条件，优于激励性铺垫 |
| 直陈优于对比 | 少用"不是 X，而是 Y"句式，把结论直接写成陈述句 |
| 避免假简化 | 后文若依赖地址空间、资源或内核状态，就不要用"进程就是一个运行中的程序"收场 |
| 少用类比 | 类比可以定位，不能承担证明或定义；在重要情形下失效时说明局限或删掉 |
| 机制重要时避免拟人 | 不写"TCP 知道包丢了"，而要说明哪些确认、定时器与信号导致了重传行为 |
| 避免教程填充 | 不用"接下来我们……"式过渡、重复鼓励或显而易见的重述凑篇幅 |
| 记法一致 | 符号就地定义，尽量在章内与跨章保持数学记法稳定 |

## 12. 课时级维护

- 宁可新增一节课，也不无限扩写一个已经异质的页面。
- 按概念依赖拆分，而不是按页面长度。
- 不让新的框架或库决定概念大纲。
- 定期清理过时的"这条命令怎么敲"材料，同时保留耐久模型。
- 行业实践变化时，区分"模型变了"与"当前工具变了"。

稳定 ID、slug、`order` 与可见性的规则见 `doc/DESIGN.md` 第 5 节；课程级的登记与批次流程见 `doc/CURRICULUM.md`。

## 13. 成功的标准

成功的课程让读者在下列情形下仍能推理：忘记 API 名字；实现由 AI 生成；顺利路径的示例被换成边界情形；性能成为约束；多个操作并发发生；系统部分失败；规范与观察到的实现看似矛盾；输出看似合理却可能错误。
