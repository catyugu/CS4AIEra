# CONTENT_GUIDE.md

本文件规定一门课**怎样写**：读者假设、一节课的组织、定义与论证的写法、代码与实验的写法、术语与风格。

教什么、模块顺序与理由见 `doc/CURRICULUM.md`；产品与运行时的设计见 `doc/DESIGN.md`；仓库不变量与完成标准见 `AGENTS.md`。精确的语法——可执行 fence 的合法选项、frontmatter 字段、公式里花括号的转义写法——由 schema 与构建期校验器定义，本文件不复制：非法写法会让构建失败并指出文件与位置，这比让作者先背一份参数手册可靠。

## 读者

读者可能没有正式的 CS 前置知识，但具备专业级技术推理能力：能读懂技术定义，跟得上代码与形式化论证。由此得到两条硬要求：

- 前置知识在被依赖之前引入，不用类比替代机制，不为「易懂」降低技术深度；
- 不写鼓励性铺垫、儿童化比喻与 Tutorial 式过渡。

## 一节课怎样组织

一节课承担一个核心原理，或一族高度内聚的机制。它回答一个问题，而不是走一遍模板。

- **从这一课自己的问题进入。** 第一段给一个具体问题、一个反常的输出或一个必须做出的选择。不从术语清单开场，不从模块依赖图开场（「某课已经建立 X，本课处理 Y」把依赖图当成了教材开头），也不把抽象的 P／拆／合并四层框架摆在第一个实例之前。
- **概念在推理需要它的位置出现。** 「先定义后依赖」要求术语在被依赖之前精确定义，不要求抽象模型先于具体实例；建模条件（有向与无向、自环与平行边、权重定义域）写在表示之后，不挡在第一个例子前面。
- **一个核心例子贯穿全课。** 先把它跑出来，再说它的不变量，再证明它，最后数它的操作——同一份状态在每一步得到更多的解释，而不是每完成一项义务就换一个分析对象。几条平行主线（三种摊还方法配三个例子）会让读者在每个转弯处重建状态。
- **每一节都在回答导入段提出的问题。** 小节标题按内容命名；如果同一组标题在每一节课重复出现（成本类别、边界与失效、小结），作者的必答项就变成了读者的目录。
- **边界写在依赖它的段落里。** 空输入、重复值、缺失值、溢出、并发修改、部分失败、版本差异在用到它的地方交代，不汇总成每节课末尾的清单。
- **框架只在新东西出现时重述。** 契约、表示、表示不变量、成本模型这套分析语言在一个模块的前两三次完整建立；之后每节课只写它真正新增的那一条，并把它作为自己的标题。
- **宁可新增一节课。** 一个页面开始承担异质问题时，按概念依赖拆分，而不是按页面长度拆分，也不无限扩写它。
- **不要 `## 小结` 作为默认收尾。** 只有若干条独立机制必须综合起来才能得到结论时才写，并只写这些结论；把正文重压成一份清单等于让读者读第二遍目录。
- **不按位置指代别的课时。** 不写「上一节」「下一课」「留到某一节」；阅读顺序属于 `doc/CURRICULUM.md`。概念真正发生关联的位置放 `<CrossRef id="..." />`。跨模块连接要照亮共享模型：一处模型只在它的主场完整讲授，别处引用。
- **目标只有一处。** 可检验的目标写在 frontmatter 的 `objectives` 里，用可观察动作表述（推导、区分、预测、追踪、估算、在约束下选择、构造反例、解释故障模式），不要「理解 X」。目标渲染为纯文本：里面不写行内代码与公式。正文不再用一节复述这一课要干什么。
- **活泼靠可操作的问题，不靠比喻。** 「把 `seen.add(v)` 从入队挪到出队，再运行一次：顶点都还能找到，但队列里出现了重复项，被破坏的是每个顶点只进入 frontier 一次这条成本不变量」这种句子比任何口语化修辞都有效。**改一处 → 预测 → 运行 → 解释**是这门课推进的方式。围绕可运行单元格写「先预测再运行」「把结果与模型对账」这类指令不是内容：单元格与它前后的模型说明本身承担了这件事。

## 定义、论证与证据

- **核心概念在正文里定义。** 形式定义、契约、成本模型、正确性论证与成本推导的主线永远留在正文，不因为术语表里有一个词条就外移。
- **推导而非断言。** 结论来自不变量或递推，就展示推理。证明按关键转折切段：一次只说当下需要什么义务、为什么这一点成立、哪条假设在这一步被使用；真正困难的那一步（非负性、轮次、交换）有明确位置，其余标准步骤压缩。
- **大胆使用反例。** 简短反例常是推翻诱人错误规则的最好方式；一节课至少有一个能让错误版本失败的输入。
- **声明假设。** 复杂度论断要说明输入度量与计价单位，系统论断要说明失败与时间假设；基准测试只证明某配置下的行为，不证明渐进律。
- **一手来源写在作出论断的那一句里。** 版本敏感或实现相关的论断给出行内链接，指向语言参考、标准库文档、PEP、RFC 或厂商文档的具体小节，链接文本写出文档名。不用权威代替论证：文档是契约证据，不替代对后果的推理。
- **每节课至少有一种能检验核心论断的证据。** 浏览器运行时能忠实呈现时，证据就是可执行单元格；不能时给出另一种可观察证据：状态轨迹、协议报文、系统调用 trace、查询计划、崩溃前后的状态、形式推导。不为了凑单元格把真实行为模拟成玩具示例。
- **落盘前逐项确认**（这是作者的检查表，不是读者看到的小节顺序）：接受什么输入、承诺什么输出；为什么正确（循环不变量、交换论证或递推）；为什么会结束（variant 怎样单调下降）；复杂度从哪里推出；额外空间（递归深度、辅助数组、显式栈）；结论依赖输入的哪些性质（有序、非负权、分布）；哪一个反例会让它失败。

## 代码与实验

- **每个示例都要有理由。** 至少展示其一：语义、状态转移、表示、故障模式、算法、性能影响、接口契约。
- **一个单元格讲一个现象或一个算法。** 学习者想改一条边或一个权重，却要先读懂五六个辅助函数，实验就已经失败。
- **oracle 属于仓库测试。** 独立 oracle、穷举检查器、复现的不变量断言、全边界扫描与 mismatch 计数是作者的回归证据，放在 `tests/oracles/`，由 `scripts/check-oracles.ts` 在 Node 下用同一份自托管运行时回放。页面上留 4 到 6 个有解释力的输入，其中至少一个能让错误版本现形；读者的实验一次只改一个条件。例外只有一种：当「枚举是慢的、判据是快的」本身就是这一课的内容时，oracle 留在页面上作为对照。
- **单元格规模大致 15 到 30 行核心代码。** 超过时先检查里面是不是混进了验证脚手架。
- **让状态可观察。** 打印或返回能暴露模型的量：身份、别名、形状、边界值、计数、轨迹。
- **确定性。** 不用当前时间、随机源、在线 API、网络与未规定的迭代顺序；以不确定性为课题时，说明允许结果的集合。
- **资源有界**，在普通硬件上快速结束；演示增长时规模要大到能显现效果、小到能在浏览器里跑完。
- **不依赖隐藏状态。** 单元格默认相互隔离；只有共享状态本身有教学价值时才用具名 session，并说明重置时哪些状态被丢弃。
- **fenced 代码块只装代码。** 它有两种用途：可执行单元格，以及不执行的真实代码（递归辅助函数、`async for` 的展开）。契约、输入输出规格、对照清单、不变量、定理与证明写进表格、列表、行间公式或正文——中文说明放进代码块会以等宽字体呈现，读者也分不清哪一段能运行。
- **SQL 课时标注引擎特有行为**，不把某一引擎的语义当作 SQL 的语义。
- **练习不判分，但要能判对错。** 优先让学习者改一个假设并解释后果、构造反例、诊断 bug、估算资源占用、在约束下二选一、写个小实现并与不变量比对。避免主要挑战是生成样板的大作业；给答案时解释推理，不只给最终代码。
- **实现边界降级。** CPython 与浏览器运行时的差异、`RecursionError`、`hash(-1)`、回收与缓存计数器这类实现细节，只在会改变当前结论时留在主推理链上；刚建立一条直觉就连续插入限定会把论证截成一串 caveat，其余的写成段末一句实现边界。

## 术语与术语表

正文负责把一个问题想明白，术语表负责让一个词随时查清楚。同一个词在一节课里扮演哪种角色，决定它由谁解释：

| 词的角色 | 正文怎么写 |
| --- | --- |
| 本课的核心概念 | 在正文里完整定义并依赖它推理 |
| 已经建立、此处只是使用 | 首次重要出现标一次 `<Term id="...">`，此后直接写词 |
| 偶然遇到、只需一句话 | 标一次，只在它直接参与当前论证时补一句 |

- **标记判据是「读者点进去能不能省下正文一句话」，不一定第一次出现就标。** 一节课里一个词标一次。
- **一个很实用的判据**：删掉这句话之后，后面的推理还成立吗？成立，只是有人可能不知道这个词——放术语表；不成立，它是后面论证的前提——留正文。自环、平行边、简单图、frontier、walk 与 path 与 cycle 的辨析、predecessor、spanning forest、decrease-key、stale heap entry、伪多项式这类名词解释适合外移；而「为什么 BFS 要在发现时标记」「为什么 `O(V+E)` 成立」「Dijkstra 为什么要求非负边」「cut 为什么能证明 Kruskal 与 Prim」「状态为什么足够」「交换为什么保持最优」必须留在正文。
- **词条分普通与模型两档**，结构由它在课程里的复用范围决定；机制（标记解析、词条 schema、快速定义浮层）见 `doc/DESIGN.md`。跨课时复用、读者可能回头查的词才值得有词条；实现琐事不因为「写在词条里更整齐」而进入词条。

## 语言与风格

- **精确而经济**：直接陈述加条件，优于激励性铺垫。
- **直陈优于对比**：少用「不是 X，而是 Y」。把结论直接写成陈述句；替换句必须仍然断言原来那句话承载的事实，删掉否定词可能把论断反转。
- **少用类比**：类比可以定位，不能承担证明或定义；在重要情形下失效时说明局限或删掉。
- **机制重要时避免拟人**：写清哪些确认、定时器与信号导致了行为。
- **不写超出语言承载力的承诺**：「等价于」「只在…时」「一律」「必然」「任何」「都」都要先核对严格规则再保留，通常应改写成机制加条件。
- **误解写在会发生的时刻**：先给正确模型，再在读者刚好可能混淆的位置处理错误读法；不写成回答审稿意见的免责声明。
- **记法一致**：符号就地定义，章内与跨章保持稳定。数学写成 `$...$` 与 `$$...$$`，不用特殊字符拼公式，也不把公式写成行内代码；程序标识符用行内代码。
- **中英术语**：英文代码、论文与标准里常见的术语首次出现给英文（如 可串行化（serializability）），此后保持中文译名一致，除非英文已成工程惯例。
- **区分规范与实现**：论断要说明它针对抽象模型、语言规范、协议标准、具体实现还是具体版本。
