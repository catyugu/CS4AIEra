# CONTENT_GUIDE.md

本文件规定一门课**怎样写**：读者假设、一节课的组织、定义与论证的写法、代码与实验的写法、术语与风格。

教什么、模块顺序与每个模块要形成的认知见 `doc/CURRICULUM.md`；产品与运行时的设计见 `doc/DESIGN.md`；仓库不变量与完成标准见 `AGENTS.md`。精确的语法——可执行 fence 的合法选项、frontmatter 字段、公式里花括号的转义写法——由 schema 与构建期校验器定义，本文件不复制：非法写法会让构建失败并指出文件与位置。

## 面向的读者

读者可能没有正式的 CS 前置知识，但具备专业级技术推理能力：能读懂技术定义，跟得上代码与形式化论证。本课程培养的是驱动 Agent 完成开发工作的技术使用者，不是亲手实现全部组件的人，因此一节课的重心默认落在「能解释」与「能判断」上，只在必要时要求动手实现。

- 前置知识在被依赖之前引入，不用类比替代机制，不为「易懂」降低技术深度；
- 不写鼓励性铺垫、儿童化比喻与 Tutorial 式过渡。

## 一节课怎样组织

一节课承担一个核心原理，或一族高度内聚的机制。它回答一个问题，而不是走一遍模板。内尽量复用两三个读者熟悉的案例，减少无关的背景切换。

- **从这一课自己的问题进入。** 可以从具体问题、反常输出、需要做出的选择或直接的定义进入；选择读者理解这一概念所需的起点。不从术语清单开场，不从模块依赖图开场（「某课已经建立 X，本课处理 Y」把依赖图当成了教材开头），也不把抽象的 P／拆／合并四层框架摆在第一个实例之前。
- **概念在推理需要它的位置出现。** 「先定义后依赖」要求术语在被依赖之前精确定义，不要求抽象模型先于具体实例；建模条件（有向与无向、自环与平行边、权重定义域）写在表示之后，不挡在第一个例子前面。
- **检查抽象是否来得太早。** 读者尚不知道概念要解决什么问题时，先给最小实例；直接定义更清楚时就从定义开始。不要为满足固定节奏重复例子，也不要让一般框架挡住理解。
- **每一节都在回答导入段提出的问题。** 小节标题按内容命名；如果同一组标题在每一节课重复出现（成本类别、边界与失效、小结），作者的必答项就变成了读者的目录。
- **边界写在依赖它的段落里。** 空输入、重复值、缺失值、溢出、并发修改、部分失败、版本差异在用到它的地方交代，不汇总成每节课末尾的清单。
- **一个主题出现，不等于它周边的知识都要交代。** 一个主题可能有很多技术细节，但是如果读者此刻却不需要它们就能跟上本课，就暂没必要在这一课交代。不要让大量延伸模糊了主线。
- **主线不要求面面俱到。** 页面上要有可见的层次。这一课只解决它自己的那个主要问题，描述清楚主要观念，它周边的边界情形、变体与完备分类等真正用到时再处理。
- **延伸部分不开第二条主线。** 一个核心内容走完一整课之后，末尾的延伸只做简单变体或应用，或指出进一步学习的去处；不在那里再引入一个从头讲到尾的完整主线，否则一课就有两份互不相干的状态。
- **避免过度拆课。** 目录给读者的第一个信息是「我要学多少东西」，知识图谱可以很细，课程目录不能一样细；一个章节对应一个稳定的认知主题，而不是一个知识点，课时数应尽可能不变。
- **不要 `## 小结` 作为默认收尾。** 只有若干条独立机制必须综合起来才能得到结论时才写，并只写这些结论；把正文重压成一份清单等于让读者读第二遍目录。
- **一课在它的结论处停下，不以补丁式小节收尾。** `## …边界`、`## 深入…`、`## 延伸…` 只写当前论证需要、或改变读者对当前结论预测的内容，不作为默认的收尾段。判据是：删掉这一段，读者是否仍然足以正确理解本课的核心机制、并能继续下一课；答案为是时，它的正确去处是删除，或移到真正依赖它的那一页，而不是留在本页把课程补全。同一机制在基础页与高级页各有一份完整展开时，基础页只保留支撑当前推理所需的最小事实。
- **不按位置指代别的课时。** 不写「上一节」「下一课」「留到某一节」；阅读顺序属于 `doc/CURRICULUM.md`。概念真正发生关联的位置放 `<CrossRef id="..." />`。一处模型只由其中一页完整讲解，别处只引用或直接使用已有结论：这条既管跨模块，也管同一模块里两个页面先后碰到同一个模型的情形（动态数组的容量管理、随机性的量词规则），后者要明确指定由哪一页负责，另一页只负责提出问题和引用。
- **不在正文里清点本课不涉及的主题。** 模块范围由 `doc/CURRICULUM.md` 管理；一节正文以自己的结论收尾，不写「本节不涉及 A、B、C」这类清单——它不推进当前问题，读者也不需要在本页读到边界外的算法名。
- **少用指向写作自身的元话语。**「本课反复用到……这句话」「下面的实验让……」这类话删掉后通常更直接：直接陈述机制，或直接放代码，代码后的段落解释现象。
- **目标只有一处。** 可检验的目标写在 frontmatter 的 `objectives` 里，用可观察动作表述（说明、推导、区分、预测、追踪、估算、在约束下选择、构造反例、解释故障模式、画出边界、定位故障）。目标渲染为纯文本：里面不写行内代码与公式。目标数量由内容决定，两个或三个清楚的目标就足够时，不补齐固定数量。正文不再用一节复述这一课要干什么。

## 定义、论证与证据

- **核心概念在正文里定义。** 形式定义、规约、成本模型、正确性论证与成本推导的主线永远留在正文，不因为术语表里有一个词条就外移。
- **推导而非断言。** 结论来自不变量或递推，就展示推理。证明按关键转折切段：一次只说当下需要证明什么、为什么这一点成立、哪条假设在这一步被使用；真正困难的那一步（非负性、轮次、交换）有明确位置，其余标准步骤压缩。
- **在容易混淆的条件处使用反例。** 存在诱人的错误规则时，优先给最小反例；不为凑数量制造错误实现或虚构一个错误代码。
- **声明假设。** 复杂度论断要说明输入度量与计数单位，系统论断要说明失败与时间假设；基准测试只证明某配置下的行为，不证明渐近律。
- **一手来源写在作出论断的那一句里。** 版本敏感或实现相关的论断给出行内链接，指向语言参考、标准库文档、PEP、RFC 或厂商文档的具体小节，链接文本写出文档名。不用权威代替论证：文档是契约证据，不替代对后果的推理。
- **重要结论要有依据。** 根据结论选用规范来源、推理或可观察证据，不规定每课使用相同的证据形式。 浏览器运行时能忠实呈现时，证据就是可执行单元格；不能时给出另一种可观察证据：状态轨迹、协议报文、系统调用轨迹、查询计划、崩溃前后的状态、形式推导。不为了凑单元格把真实行为模拟成玩具示例。

## 代码与实验

- **每个示例都要有理由。** 至少展示其一：语义、状态转移、表示、故障模式、算法、性能影响、接口契约。
- **一个单元格讲一个现象或一个算法。** 学习者想改一条边或一个权重，却要先读懂五六个辅助函数，实验就已经失败。
- **代码分三类。** 算法本身留在单元格；让状态可观察的极少量插桩代码可以留；只为证明教材没写错而存在的检查器、穷举基线、交叉核对与计数框架属于测试，不进教学单元格。
- **判据比行数硬。** 教学单元格里不应出现只为证明这段代码正确而存在的辅助函数：计数脚手架、一致性核对、穷举最优解等不应存在，留下的辅助函数必须服务于读者接下来要改的那一处。
- **可运行、互动的单元格应该短小，不超过 100 行代码，形态是「算法本体 + 显示关键状态的几行插桩代码」。** 超过时先检查里面是不是混进了验证脚手架、冗余输出，或者混进了第二个算法。
- **输出便于辨认。** 打印数据、计数、轨迹与错误本身；允许 samples: 这类短标签帮助读者辨认，不把整段解释塞进 print。
- **确定性。** 不用当前时间、随机源、在线 API、网络与未规定的迭代顺序；以不确定性为课题时，说明允许结果的集合。
- **资源有界**，在普通硬件上快速结束；演示增长时规模要大到能显现效果、小到能在浏览器里跑完。
- **不依赖隐藏状态。** 单元格默认相互隔离；只有共享状态本身有教学价值时才用具名 session，并说明重置时哪些状态被丢弃。
- **fenced 代码块只装代码或结构图。** 它有三种用途：可执行单元格；不执行的真实代码（递归辅助函数、`async for` 的展开）；以及数据结构的 ASCII 结构图（树、堆、链表、图、连续布局）。结构图标注 `text`，渲染时带 `text` 徽标，与可执行单元格在视觉上区分开，且只画结构、不写说明文字。契约、输入输出规格、对照清单、不变量、定理与证明仍写进表格、列表、行间公式或正文——中文说明放进代码块会以等宽字体呈现，读者分不清哪一段能运行。
- **SQL 课时标注引擎特有行为**，不把某一引擎的语义当作 SQL 的语义。
- **观测到的数字不进正文。** 单元格打印的字节数、容量分档位置、探测长度这类具体数值不应该进入正文；正文只写一般性质。

## 练习

练习的默认目标是判断：给出一个现成实现或一个方案，让读者预测、诊断、比较或审查它。四类形态：

| 形态 | 问题 | 例子 |
| --- | --- | --- |
| 预测 | 这段程序会做什么？ | 给一次调用的输入，写出执行结束时每个名字指向什么 |
| 诊断 | 这里可能出现什么故障？ | 指出共享状态被两个调用方同时修改的位置 |
| 比较 | 两个方案哪个更适合当前约束？ | 同一组操作在两种表示上的成本与前提 |
| 审查 | 这段解释、设计或代码可信吗？ | Agent 说「这样更高效」，判断它依据的是什么 |

- **从零写出完整程序只占很小一部分。**「实现快速排序」「实现一个栈」训练的是实现熟练度；课程要的判断力出现在审阅一个现成实现的位置上。
- **练习由运行验证，正文不作答。** 提问之后不写「判断依据」这类答案段，也不写出这份代码在哪个输入上会得到什么结果、会在哪一行失败。需要交代判断标准时只给一行中性判据，说明用什么标准去看，不点明结论。不写鼓励语，也不写评分口径。
- **待审代码写成可执行单元格。** 读者先读代码作出判断，再运行它核对；换输入、换一处写法就在同一格里改，所以这一格要能单独运行，只装这段情形需要的数据与语句。练习格可以刻意失败，读者要的正是那一次运行结果。
- **练习写在提出它的段落之后**；一节课有多道时收进一个 `## 练习`；没有练习的课时不必补一个。

## 术语与术语表

正文负责把一个问题想明白，术语表负责让一个词随时查清楚。同一个词在一节课里扮演哪种角色，决定它由谁解释：

| 词的角色 | 正文怎么写 |
| --- | --- |
| 本课的核心概念 | 在正文里完整定义并依赖它推理 |
| 已经建立、此处只是使用 | 首次重要出现标一次 `<Term id="..." />`，此后直接写词 |
| 偶然遇到、只需一句话 | 标一次，只在它直接参与当前论证时补一句 |

- **标记判据是「读者点进去能不能省下正文一段话」，不一定第一次出现就标。** 一节课里一个词标一次。
- **一个很实用的判据**：删掉这句话之后，后面的推理还成立吗？成立，只是有人可能不知道这个词——放术语表；不成立，它是后面论证的前提——留正文。
- **三分法是完整的：跨情境可独立查阅的进术语表，当前推理不可缺少的留正文，两者都不是的删掉。** 一个词只出现一次、以后基本不用、对当前推理也不重要时，正解是删掉它，而不是「正文不讲就塞进术语表」——术语表不是知识垃圾场。一页顺手提到的专名在正文里写即可，真正需要区分时再讲；只在某个算法局部说得清的名字在正文局部定义，不建词条。
- **一个词值得有词条，当它离开当前这一课的机制也说得清，或者跨课时反复出现。** 自环、平行边、简单图、割、拓扑序属于前者，不变量、松弛、摊还分析属于后者；只对某一个算法成立、要靠那一段论证才能陈述的名字不建词条。

词条按同一个形态写，不分级：

- **`short` 只回答「它是什么」。** 一句话，最多再补一个最关键的区别；用途、后果以及它与其他算法的关系不写进去。首页列表与浮层只放这一句，读者用它决定要不要点开。`short` 按纯文本渲染：行内代码、公式与强调都会原样打印。
- **完整词条通常 2–4 个自然段。** 第一段给精确定义，第二段处理最容易与它混淆的相邻概念，第三段最多给一个重要后果或一个最有代表性的例子。推导、证明、成本分析、运行时细节与语言实现行为留在正文——词条只负责让一个词查得清。
- **词条不设固定栏目。** 「适用范围 / 判据 / 常见误用」是作者自检清单，不是词条结构，按它写出来的词条连着读几篇就像审稿意见答辩。一条词条超过大约 600 字，或需要四级标题时，先假设其中有内容本来属于正文。
- **词条与引用它的课时是两个深度上的同一件事。** 词条里的界必须与正文一致，也不提前讲解后面某一课才建立的机制：优先队列的词条不讲 `decrease-key`，binary64 的词条不讲 SQL 的数值类型。

## 语言与风格

- **精确而经济**：直接陈述加条件，优于激励性铺垫。
- **直陈优于对比**：少用对比句式、「必须同时……否则……」「这条结论只覆盖……」「不是 X，而是 Y」。把结论直接写成陈述句。
- **少讲技术细节是降低展开深度，不是降低准确性。** 一个机制讲到读者够用为止：写「内存是一种由地址索引的易失性存储，正在运行的进程通过虚拟地址空间访问它」，到此为止，不展开页表、TLB 置换与 NUMA；不写「CPU 像大脑、内存像桌面」这类比喻，它既没有给出机制，也没有划出边界。
- **少用类比**：类比可以定位，不能承担证明或定义；在重要情形下失效时说明局限或删掉。
- **不写超出语言承载力的保证**：「等价于」「只在…时」「一律」「必然」「任何」「都」都要先核对严格规则再保留，通常应改写成机制加条件。
- **误解写在会发生的时刻**：先给正确模型，再在读者刚好可能混淆的位置处理错误读法；不写成回答审稿意见的免责声明。
- **记法一致**：符号就地定义，章内与跨章保持稳定。数学写成 `$...$` 与 `$$...$$`，不用特殊字符拼公式，也不把公式写成行内代码；程序标识符用行内代码。
- **中英术语**：英文代码、论文与标准里常见的术语首次出现给英文（如 可串行化（serializability）），此后保持中文译名一致，除非英文已成工程惯例。
- **区分规范与实现**：论断要说明它针对抽象模型、语言规范、协议标准、具体实现还是具体版本。
- **有成熟中文译名就用中文。** 首次出现写成「中文（English）」交代一次（割（cut）、安全边（safe edge）、游走（walk）、记账法（accounting method）），此后只用中文；同一概念不在两种译名之间随机切换，只有英文已成工程惯例时才长期保留裸英文。
- **少用作者的连接词与元话语。**「一个 Agent 交来……」「回到开头那份……」「判据是……」「这条路径没有被任何一个结构接住」「成本落在 append 上」「这一层 / 这一侧 / 这一档降不下来」「最好值涨上来」「暴露出来」这类说法单独看都通顺，连读十几课就成了一份模板。改写时点出具体对象与动作——`append` 在末尾追加、记忆化后每个状态只算一次——没有具体对象可点，就删掉这层框架。
- **不搬运英文写作习惯的隐喻。** accounting、ownership、consumption、tie-breaking、exposure、freezing 这类隐喻要还原成机制：写清谁做、作用于什么、结果是什么，而不是「记账」「拥有」「消费」「打破平局」「暴露」「冻结」。
