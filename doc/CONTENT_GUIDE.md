# CONTENT_GUIDE.md

本文件规定课程内容的取材、结构、论证、演示与维护方式。

读者可能无正式 CS 前置知识，但假定具备专业级技术推理能力。作者须显式补足前置知识，不得稀释定义、隐去关键限定或用类比替代机制。目标是把注意力集中到能提升推理、验证、调试、设计与生产判断力的知识上，把易检索的细节降级为参考。

## 1. 目的与读者

本指南面向作者与评审者，回答：哪些内容值得花篇幅、一节课必须包含什么、如何论证与演示。

读者默认能专业推理、读懂技术定义、跟上代码与形式化论证。前置知识须在被依赖之前引入；不得为"易懂"降低技术深度，不用儿童化类比。

## 2. AI 时代的内容分级

写任何小节前，先按"学它的价值"定级：

| 级别 | 特征 | 处理 |
| --- | --- | --- |
| A Lookup | 语法表、长 API 清单、命令行参数、样板、低解释价值的实现冷知识、易变库用法 | 尽量不进正文；仅在读懂后续示例必需时给紧凑参考；教"如何验证"而非"如何记住" |
| B Working knowledge | 生产中高频细节、读懂普通代码所需的惯例、常见工具操作、不深但处处出现的语言与库行为 | 精确解释，演示一到两次；目标是识别与正确使用，不是死记 |
| C Core model | 语义、不变量、抽象边界、成本模型、数据表示、失败行为、并发顺序、持久化规则、安全与信任边界 | 严格讲授：先定义再依赖，推导后果，给反例，必要时用可执行实验，多语境反复回顾 |
| D Deep leverage | 反复决定真实系统正确性、性能、可运维性或安全性的概念；API 简单但后果微妙；生成代码看似合理却可能出错 | 超越配方：覆盖对抗性情形与生产故障模式；说明什么证据能证伪直觉；连到其他模块 |

判断标准：**记不住这一点是否会实质损害推理能力？** 若否，不必为它花整页。

D 级示例：别名与可变性、摊还分析、存储层次与虚拟内存、竞态与同步、TCP 与应用层重试的交互、事务隔离与可串行化、查询计划与索引、幂等与投递语义、共识与失败模型、认证与授权的区别、密码学误用与信任边界。

课程应在 C、D 两级上不成比例地丰富。

## 3. AI 改变了什么

**减少记忆负担**：不围绕记忆设计课程。精确方法名、命令行选项、库样板、长语法例外表、安装步骤都不该成为主线。要学的是：该问什么、如何识别可信答案、如何验证。

**强化验证**：生成代码很便宜，正确性论证不便宜。教读者提问：前置条件是什么？保持了哪条不变量？哪些状态共享？复杂度和主导资源是什么？部分失败时会发生什么？哪些操作可能被重排？什么在何时持久？这个 API 承诺了什么，又只是碰巧如此？什么是被信任的？我如何检验假设？

**保留实现素养**：当理解机制是调试、评审、优化或加固生成代码的前提时，"AI 能写这段代码"不构成省略理由。

**不要 AI 表演**：不给每节课硬塞"AI 视角"。AI 时代的视角决定优先级与验证习惯，不是装饰性标签。

## 4. 一节课的必备结构

不要求每节课用相同标题，但完整技术课通常包含：

| 要素 | 要求 |
| --- | --- |
| 目的 | 本课要解决的问题、该模型为何重要 |
| 学习目标 | 用可观察的推理动作表述：推导、区分、预测、论证、追踪、估算、在给定约束下选择、构造反例、解释故障模式。避免"理解 X"，除非给出具体判据 |
| 精确模型 | 引入实体、状态、操作、不变量与假设；有形式定义就给出 |
| 示例 | 暴露机制，而非只展示能跑通的语法 |
| 实验 | 让读者改代码或查询、运行，并把结果与模型对账 |
| 边界与失败情形 | 每个重要抽象在边界受检：空输入、重复值、NULL 或缺失、溢出与资源耗尽、并发修改、部分失败、非法输入、对抗性输入、版本与实现差异 |
| 生产后果 | 该模型改变了真实系统的什么：正确性、延迟、吞吐、可运维性、安全、成本、可维护性、调试 |
| 小结 | 重述不变量与决策规则，而非重复小标题 |

"目的"写法对照：

> 差：本节课我们学习字典。
>
> 好：本节课解释基于哈希表的映射、Python 通过 `dict` 暴露的语义，以及平均常数时间查找背后的不变量与成本假设。

### 4.1 标题与锚点

标题文本同时决定页面锚点。同一课时内两个标题若规约到同一个锚点，构建失败。因此标题要短，不要用标点堆叠（`：`、`、` 一类字符不进入锚点），也不要在标题里使用行内代码与强调之外的 Markdown 语法。

跨课时引用使用 `<CrossRef id="...">` 指向稳定 ID，不要指向锚点；锚点只在页面内部有效。

### 4.2 可见性与阅读顺序

- 只有 `status: published` 的课时进入站点与导航；`draft` 与 `review` 只在开发服务器下可见，用于自查；`archived` 永不出现。
- 阅读顺序是课程树的深度优先遍历：一节自己的课时排在它的子章节之前，同级之间按 `order` 排序。`order` 是同级内的局部序号，不是全局序号。
- 新课时先以 `draft` 写出，在开发服务器下通读并运行示例，再改为 `published`。

## 5. 定义与术语

| 规则 | 说明 |
| --- | --- |
| 先定义后依赖 | 即使预期多数读者已熟悉，术语也须在论证依赖它之前定义 |
| 优先精确定义 | 存在且重要的形式定义必须给出，不得用类比替代。例：函数是*单射*的，当且仅当不同输入总映射到不同输出，即对所有 `x1 != x2` 都有 `f(x1) != f(x2)` |
| 区分规范与实现 | 明确论断针对抽象模型、语言规范、协议标准、具体实现、具体版本还是通行实践。Python 语言语义与 CPython 实现细节不得混为一谈 |
| 术语表引用有节制 | 需要快速回忆时用 `<Term id="...">`，不给每次出现都加标记。短定义一到两句，精确到不会教出错误模型；多义时说明适用范围；例子不得比定义更长。正文仍给更深定义 |
| 中英术语 | 英文代码、论文、标准与文档中常见的术语，首次出现给英文，如 可串行化（serializability）；此后保持中文译名一致，除非英文已成工程惯例 |

## 6. 论证与证明

| 规则 | 要求 |
| --- | --- |
| 声明假设 | 复杂度、分布式行为与性能论断离开假设就没有意义。复杂度要说明输入度量与操作成本模型；系统要说明相关的失败与时间假设 |
| 推导而非断言 | 结论若来自不变量或递推，就展示推理 |
| 大胆使用反例 | 简短反例常是推翻诱人错误规则的最好方式 |
| 区分经验与演绎 | 基准测试只证明某配置下的行为，不证明渐进律或普遍实现性质 |
| 不以权威代替论证 | 文档与标准是契约证据，不能替代对后果的推理 |

## 7. 代码示例

| 规则 | 要求 |
| --- | --- |
| 每个示例都要有理由 | 至少展示其一：语义、状态转移、表示、故障模式、算法、性能影响、并发行为、接口契约、测试策略 |
| 最小但不误导 | 去掉无关应用样板，但不删产生关键行为的行 |
| 让状态可观察 | 打印或返回能暴露模型的量。数据结构在相关时展示身份、别名与形状；SQL 选择能暴露关系行为的列 |
| 确定性 | 可执行示例应确定，除非不确定性本身是课题：随机数设种子、用固定夹具、不用当前时间、不调在线 API、不依赖网络与未规定的迭代顺序。以不确定性为课题时，说明允许结果的集合 |
| 资源有界 | 示例要在普通硬件上快速结束，不无意分配无界内存、打印上百万行或要求巨大依赖。演示渐进增长时，输入规模大到能显现效果、小到能在浏览器里跑完 |
| 单元格可编辑 | 假定读者会改任意值或语句，解释在邻近情形下仍成立。实验依赖关键条件时显式命名，不藏在任意常量里 |
| Reset 语义 | 除非单元格有意共享具名 session，课程不得依赖隐藏执行历史；默认单元格相互隔离 |
| 输出 | 不依赖 notebook 特有的花哨富显示，优先文本、表格或简单图形 |

### 7.1 Python 可执行内容

用可运行 Python 讲：名称绑定与对象身份；可变性与别名；相等与同一；迭代协议；生成器；闭包与延迟绑定；异常与上下文管理器；观察有帮助时的描述符与数据模型；算法轨迹；数据结构不变量；Pyodide 中可行的异步调度演示；解析与序列化；测试示例。

不把可执行单元格的篇幅花在官方文档讲得更好的标准库方法长清单上。涉及 CPython 特有行为要标注，且不得暗示 Pyodide 必然复现 CPython 运行时的全部底层特征。

### 7.2 SQL 可执行内容

**夹具设计**：夹具小到可检视、又足以暴露目标语义。优先带真实约束的模式：主键、外键、唯一性、概念上正确的 `NOT NULL`、有教学意义时的 `CHECK`。不为写短查询造不真实的模式。

**数据情形**：数据要能暴露缺失与 `NULL`、一对多与多对多、看起来重复但身份不同的值、没有匹配连接对象的行、相关边界日期与数值。

**方言标注**：可执行基线是 SQLite。行为在不同引擎间有差异时显式说明方言。不得暗示 SQLite 的并发、类型亲和性、查询计划器行为或 DDL 语义普遍成立。

**查询计划**：讲索引与优化时，把逻辑 SQL 与引擎计划输出配对，强调优化器依实现与统计信息而定。

**变更与事务**：对 `INSERT`、`UPDATE`、`DELETE` 与事务示例，用前后查询显式呈现状态转移；Reset 必须精确还原夹具。

### 7.3 可执行单元格的声明语法

普通 fenced 代码块是静态的。要成为可执行单元格，必须在信息串中显式写出 `run`，并给出页面内唯一的 `id`：

````md
```python run id="py.names.rebinding"
a = [1, 2]
b = a
b.append(3)
print(a)
```
````

语言只能是 `python` 或 `sql`。信息串中 `run` 之后的选项如下：

| 选项 | 适用 | 含义 |
| --- | --- | --- |
| `id` | 必填 | 单元格标识，须在课时内唯一 |
| `session` | 可选 | 具名 session；省略表示状态隔离 |
| `timeout` | 可选 | 该单元格的硬超时（毫秒） |
| `packages` | 可选 | 逗号分隔的包名；必须属于固定 Pyodide 发行版 |
| `fixture` | SQL 必填 | 实验夹具 id，对应 `content/labs/<dir>/lab.yaml` 的 `id` |
| `editable` | 可选 | 默认 `true`；`false` 用于不应被修改的演示 |
| `expect` | 可选 | 期望输出快照，仅作文档，不参与判分 |

规则：

- 未知选项、非正整数的 `timeout`、不在固定发行版内的包名都会让构建失败。
- `session="isolated"` 是默认行为，写了会被判为冗余并报错。
- SQL 单元格必须声明 `fixture`；同一 `session` 中后续单元格可以省略，它们复用该连接。同一 session 声明两个不同 fixture 是错误。
- Python 单元格不得声明 `fixture`。
- 一个课时内的 `id` 重复是错误；不同课时可以复用同名 id，因为执行作用域是页面。

### 7.4 读者看到的单元格

单元格在页面加载时是一段高亮代码，不含编辑器、不加载运行时：

- **运行**：执行代码区当前内容。读者尚未进入编辑时，执行的就是作者源码。
- **编辑**：点击代码区才创建编辑器；只读代码的读者不下载编辑器，也不下载运行时。
- **恢复代码**：把代码区还原为作者源码，并清除"已修改"标记。
- **停止**：终止并重建运行时。硬超时与"停止"走同一条路径。
- **重置 session**：仅对声明了 `session` 的单元格出现；重建该 session 的状态（SQL 会重新应用夹具）。

超时从单元格开始执行算起，不含解释器加载。首次运行时页面会下载并启动 Pyodide，这一步在慢连接上可能明显耗时，此时"停止"仍然可用。

`expect` 只作为作者留下的期望输出快照，不参与判分，也不影响运行时行为。

## 8. 练习（无 LMS）

产品不判分，练习依然有价值。优先让学习者：改一个假设并解释后果；构造反例；诊断 bug；估算复杂度或资源占用；在给定约束下二选一；写个小实现并与不变量或测试判据比对；检视 SQL 查询计划；在受控模型中复现竞态或故障。

避免主要挑战是"生成样板"的大作业。解答可折叠、可链接或放在刻意留白之后，但应解释推理，不只给最终代码。

## 11. 跨模块连接

课程应反复连接跨模块概念：

- Python 对象身份 ↔ 别名 ↔ 数据结构可变性 ↔ 并发共享状态
- 渐进复杂度 ↔ 缓存局部性 ↔ 数据库查询计划
- OS 文件描述符 ↔ socket ↔ HTTP 服务器
- 重试 ↔ 幂等 ↔ 事务 ↔ 分布式投递语义
- 虚拟内存 ↔ 内存映射文件 ↔ 数据库缓冲管理
- 不变量 ↔ 测试 ↔ 事务 ↔ 授权规则
- 哈希 ↔ 哈希表 ↔ Git 的内容寻址 ↔ 密码学哈希的安全区别

交叉链接要照亮共享模型，而不只是宣传另一章。

## 12. 写作风格

| 规则 | 要求 |
| --- | --- |
| 精确而经济 | 直接陈述加条件，优于激励性铺垫 |
| 直陈优于对比 | 少用"不是 X，而是 Y"句式；把结论直接写成陈述句，避免先立一个错误模型再纠正 |
| 避免假简化 | 后文若依赖地址空间、资源、凭据或内核状态，就不要用"进程就是一个运行中的程序"收场；开篇一句可以有，但必须立刻被真正的模型修正 |
| 少用类比 | 类比可以定位，但不能承担证明或定义；若类比在重要情形下失效，说明其局限或删掉 |
| 机制重要时避免拟人 | 不写"TCP 知道包丢了"，而要说明哪些确认、定时器与信号导致了重传行为 |
| 避免教程填充 | 不用"接下来我们……"式过渡、重复鼓励或显而易见的重述凑篇幅 |
| 记法一致 | 符号就地定义，尽量在章内与跨章保持数学记法稳定 |

## 13. 发布前检查

1. 核心模型或不变量是什么？
2. 各部分属于 A、B、C、D 哪一级？
3. 是否把本该只作参考的材料写进了正文？
4. 所有前置知识是否真的引入过？
5. 形式术语是否在使用前定义？
6. 规范级论断是否与实现和版本细节分开？
7. 每个代码示例是否暴露机制或故障模式？
8. 可执行示例是否确定且有界？
9. 读者修改示例时会不会撞上隐藏状态？
10. SQL 示例是否标注了 SQLite 特有行为？
11. 复杂度与性能论断是否显式说明假设？
12. 是否覆盖失败与边界情形？
13. 生产相关性是否具体而非激励性？
14. 这里 AI 能否生成看似合理却错误的代码？若能，是否教了如何发现错误？
15. 引用与术语标记是否显式且正确？
16. 小结是否重述决策规则与不变量，而非小标题？

## 14. 课程级维护

- 宁可新增一节课，也不无限扩写一个已经异质的页面。
- 按概念依赖拆分，而不是按页面长度。
- 移动或改标题时保持稳定 ID。
- 不让新的框架或库决定概念大纲。
- 运行时升级时复查版本敏感的示例。
- 定期清理过时的"这条命令怎么敲"材料，同时保留耐久模型。
- 行业实践变化时，区分"模型变了"与"当前工具变了"。
- 示例要小到能在 Git 里评审、不运行也能读懂。

## 15. 成功的标准

成功的课程让读者在下列情形下仍能推理：忘记 API 名字；实现由 AI 生成；顺利路径的示例被换成边界情形；性能成为约束；多个操作并发发生；系统部分失败；规范与观察到的实现看似矛盾；输出看似合理却可能错误。

课程应优化这种持久能力，而不是对当下工具表面的记忆。
