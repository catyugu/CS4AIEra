# CONTENT_GUIDE.md

本文件说明课程怎样写：读者假设、课时组织、定义与论证、代码与实验、练习、术语和表达风格。

教学范围与模块设计见 `doc/CURRICULUM.md`，产品与运行时设计见 `doc/DESIGN.md`，仓库约束与完成标准见 `AGENTS.md`。元数据、引用和可执行代码块的精确语法以 schema、Markdown 管线与内容校验器为准；构建会定位并报告格式错误。

## 面向的读者

读者可能从零开始学习计算机科学，同时具备理解专业问题的推理能力。课程帮助他们解释程序行为、判断方案，并驱动 Agent 完成开发工作。实现练习围绕理解机制和检验判断安排。

在使用前建立必要的前置知识，用具体过程解释机制。技术深度随当前问题展开，表达保持平实，尊重成年自学者的理解能力。

## 一节课怎样组织

一节课围绕一个核心问题，或一组紧密相关的机制展开。起点可以是具体需求、一段输出、需要作出的选择，也可以是清楚的定义；选择取决于读者理解这个问题需要什么。

先给出足以理解问题的信息，再在推理需要的位置引入概念、条件和抽象。实例承担解释作用，语境提供真实约束；案例复用以节省理解成本为准。每个小节推进主要问题，标题说明具体内容，篇幅随难点分配。

空输入、缺失值、并发、部分失败和版本差异等条件，放在依赖这些条件的论证旁边。正文讲清当前判断所需的机制，进一步的变体在实际使用它们的课时展开。课时边界对应稳定的认知主题。

课程在问题得到回答处收尾。多个机制需要结合才能得到新结论时，可以安排综合段落。延伸内容选择与当前结论直接相关的应用，深入学习的去处通过引用提供。

跨课关联使用 `<CrossRef id="..." />` 指向稳定内容 ID。每个模型由一页完整讲解，其他页面引用该页，并保留当前推理所需的事实。教学范围由 `doc/CURRICULUM.md` 统一说明。

可检验的学习目标集中写在 frontmatter 的 `objectives` 中，以预测、追踪、解释、估算、比较、选择或构造反例等可观察动作表述。目标数量由课时内容决定，使用适合纯文本显示的语言。

## 定义、论证与证据

核心概念的定义、规约与推理保留在正文。结论来自不变量、递推或执行过程时，展示关键步骤，交代每一步使用的条件。用具体机制、推导和可检验的证据支撑判断。

复杂度论断说明输入规模与计数单位；系统论断说明执行、时间与失败假设；测量说明环境、输入和观察范围。区分事实、推论、待验证解释与建议，结论的确定程度与证据相称。

反例用于检验实际提出的规则或推论。选择能说明问题的最小情形，并解释它使哪一步推理失效。概念辨析围绕读者当前确实需要区分的对象展开。

版本敏感或实现相关的论断，在相应语句旁链接到语言参考、标准库文档、PEP、RFC 或厂商文档的具体位置，链接文本说明来源。规范给出契约，正文解释契约怎样影响当前问题。

证据形式由结论决定。浏览器能忠实呈现的行为可用单元格检验；其他行为可用状态轨迹、协议报文、查询计划、故障前后状态或形式推导说明。构造示例、模型推演与实际测量分别交代来源。

## 代码与实验

可执行单元格应让读者通过运行或修改输入观察机制。一个单元格围绕一个现象或算法，保留理解和修改它所需的数据、实现与少量观察代码。教材自身的交叉核对、穷举基线和验证框架放在测试中。

根据问题选择代码、公式、表格或执行轨迹。解释递归时追踪调用与返回，解释共享状态时追踪读取与修改，解释算法成本时在实际计算中观察工作量。代码长度以读者能看清过程、找到修改位置为准。

新语法和库调用在首次需要时就地解释，范围以读懂当前代码为准。静态片段说明所属语言、运行环境，以及它是一份完整程序还是其中一部分。

输出展示数据、计数、轨迹或错误，短标签帮助识别结果，机制解释写在正文。示例使用固定输入和明确的顺序；以不确定性为主题时，说明允许出现的结果及其条件。实验规模应能在普通硬件的浏览器中及时完成。

单元格默认独立运行。共享状态有教学价值时使用具名 session，并说明状态如何建立、使用和重置。让读者能从明确的初始状态重复实验。

代码块承载代码、协议报文、机器可读数据或结构图，并标注相应语言。解释、契约、定理和证明使用正文、表格、列表或公式。SQL 示例标明引擎，涉及引擎特有行为时给出具体依据。

输入与规则确定的结果可以写入正文供核对。运行测得的耗时、空间和容量变化附上环境与适用范围。

## 练习

练习主要训练预测、诊断、比较和审查。给读者足够的信息作出判断，把结论留给读者推导和验证。题目可以引入新的输入、执行历史或约束，帮助读者把机制用到另一种情形。

| 形态 | 需要作出的判断 | 示例 |
| --- | --- | --- |
| 预测 | 程序会怎样执行 | 根据输入追踪结束时的状态 |
| 诊断 | 故障由哪些条件触发 | 找到导致更新丢失的读写交错 |
| 比较 | 方案如何满足当前约束 | 比较两种表示的成本与适用条件 |
| 审查 | 证据是否支持结论 | 检查性能报告的输入与测量方法 |

待审代码在运行环境支持时写成可独立执行的单元格，读者先判断，再运行、修改和重置。刻意失败的练习保留可观察的错误；判断标准说明需求和成功条件。涉及系统故障或部署的练习可通过轨迹、状态表和方案比较验证推理。

练习放在相关论证之后，多道练习可以集中组织。数量和位置由学习需要决定；从头实现程序用于确有必要通过实现理解机制的情形。

## 术语与术语表

正文负责解释当前问题，术语表提供可以独立查阅的定义。本课的核心概念在正文中完整定义；已建立的概念在首次重要使用处标记 `<Term id="..." />`，同页后续直接使用译名。

当前推理依赖的内容留在正文，跨情境仍有查阅价值的概念进入术语表。局部使用的名称就地解释；正文和词条都围绕各自的阅读目的选择信息。

词条的 `short` 用纯文本简洁回答“它是什么”，必要时补充最关键的区别。完整词条从精确定义开始，按需要解释相邻概念、后果或典型例子。段落数量与组织随概念决定，推导和完整机制由课程正文承担。

词条与正文使用一致的条件和术语，解释深度以读者能独立理解定义为准。

## 语言与风格

直接陈述事实、机制、推理和结论，优先用肯定句表达。句子写清具体对象、动作及其结果，用自然、平实的语言保持信息密度。

否定、转折、澄清和限制用于真实的语义需要：纠正已有错误、区分容易混淆的概念，或说明影响结论的条件。使用前确认它回应的是正文、示例或读者当前推理中的具体问题。可以正面说明的内容，直接说明。

过渡、强调与总结承担明确的逻辑功能。段落通过因果、条件、顺序或问题本身连接，保留能推进论证的语句。开头进入主题，代码前交代阅读所需的信息，代码后解释观察到的现象。

结构随问题复杂度展开。简单问题简洁回答，复杂问题充分推导；列表用于并列、步骤或比较，标题帮助定位，强调用于标识确需关注的信息。每个段落围绕一个意思展开，并与前后推理衔接。

判断保持独立，依据充分时明确下结论，证据有限时准确交代已知与待验证部分。评价具体方案时说明理由，限定条件聚焦于会影响当前判断的因素。

通俗表达以清楚的机制为基础。技术细节展开到足以理解和检验当前结论；类比用于辅助定位，定义与论证由实际机制承担。使用“必然”“任意”“等价”等严格表述时核对其成立条件。

符号就地定义并保持一致。数学使用 `$...$` 或 `$$...$$`，程序标识符使用行内代码。有成熟中文译名的术语优先使用中文，首次出现时按需给出英文，后续译名保持一致；工程惯用英文可保留原名。论断明确针对抽象模型、规范还是具体实现。

交稿前通读全文：检查每句话的信息增量、段落间的联系、对比和限定的实际用途，以及结论与证据是否相称。合并重复解释，删去空洞铺垫、写作过程的自述和预设争论，保留技术含义、条件与确定程度。
