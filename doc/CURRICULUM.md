# CURRICULUM.md

本文件是课程地图：课程要形成的判断力、模块顺序、每个模块教什么、模块之间怎样分工。它描述**教学意图**，不描述清单。

精确的课程树——子章节、课时 `id`、标题、顺序与发布状态——由各目录的 `_section.yaml` 与课时 frontmatter 表达，那是唯一的权威来源：新增一节课、拆分一个章节或推进发布状态都不应该要求修改本文件。写作方法见 `doc/CONTENT_GUIDE.md`；产品与运行时的设计见 `doc/DESIGN.md`；仓库不变量与完成标准见 `AGENTS.md`。

## 毕业目标

课程不培养「没有 AI 也能从零实现一切」的初级程序员，而是培养知道软件世界如何运作、因而能够正确提出问题、判断设计、发现风险并验证 Agent 工作成果的技术使用者。

课程结束时，读者应当能独立回答这些问题：

- 这个需求在技术上大致可不可行？
- 这件事应该放在浏览器、客户端、服务器还是数据库里完成？
- 数据存在哪里，什么时候会丢？
- 为什么一个程序在本机能跑、部署后却跑不起来？
- 为什么「把这个函数改快一点」可能毫无意义？
- 为什么一个 API 不能假设调用一定成功？
- 为什么并发修改会产生错误？
- 为什么缓存既解决问题又制造问题？
- 哪些操作可以重试，哪些不能简单重试？
- 一个 Agent 改了二十个文件，应该检查什么，而不是逐行重写一遍？
- 一个程序出了 bug，应该查输入、状态、日志、调用栈、网络、数据库还是环境？
- 一个 Agent 说「这样更高效」「这样更安全」「这样更可扩展」，它的依据是什么？

支撑这些问题的是同一项能力，它也是本课程的特色：**画边界**。遇到任何系统先问：什么在哪里运行？状态在哪里？谁调用谁？数据以什么形式越过边界？哪个组件信任哪个组件？哪一步可能失败？

大量软件问题最终都归到四类错误：边界放错了、状态放错了、职责放错了、信任关系弄错了——或者把可能失败的边界当成了可靠的函数调用。

## 组织原则

- **按心智模型的依赖关系组织，不按学科分类。** 顺序是：一个程序如何表达计算 → 程序如何组织状态与数据 → 它有多贵、能撑多大 → 程序如何被计算机执行 → 多个程序如何通过接口协作 → 机器之间如何通信 → 数据如何持久保存 → 一个应用怎样由这些东西组合起来 → 系统为什么会慢、会错、会失效 → 怎样开发、测试、观察、修改和验证这样的系统 → 怎样有效驱动 Agent。
- **准入判据是判断力，不是惯例。** 一个知识点如果不知道它也不会妨碍读者理解软件或判断 Agent 的方案，就不进主线，哪怕传统 CS 课程都会讲。已经写好不构成保留的理由：课程定位变化后，删减本身就是设计工作。
- **删减的判据是一句话**：读者永远不会亲自实现它，但需要用这段内容判断 Agent 给出的方案是否合理——这段内容还有价值吗？答案为否，它就不占据主线篇幅。状态与副作用、接口与契约、数据表示、不变量、时间与空间成本、哈希与索引为什么能加速查询、树与图各自表达什么关系、缓存为什么有效与什么时候失效、搜索空间为什么会爆炸、预计算与空间时间怎样交换、平均与最坏情形为什么可能不同、「能运行」为什么不等于「设计合理」，属于留在主线的例子。
- **课程不是操作性教程。** Linux 命令、编辑器、Git 命令、Python 环境安装、Agent 软件的操作技巧与部署步骤不属于任何模块的教学目标；它们最多以附录或外部链接出现，不进入课程主干。
- **三种掌握层次，越往后越克制。**

| 层次 | 要求 | 例 |
| --- | --- | --- |
| 必须能解释 | 用自己的话说明机制与它的边界 | 什么是进程；索引为什么能加速查询 |
| 必须能判断 | 面向具体情形作出并说明理由 | 这份数据能不能只放在内存里；这个操作能不能安全重试 |
| 能够亲自实现 | 动手做过最小的一种，其余只理解保证 | 写出循环、函数、简单数据结构操作、HTTP 调用、简单 SQL、基本测试 |

顺序由依赖关系决定，不由学科惯例决定。「程序如何工作」建立工作语言；「如何组织数据与计算」先把数据的组织方式与方案的可行性判断讲清楚；「成本与规模」给出全课程共用的成本语言；「程序如何运行」把程序接到机器与内核上，使后面的运行时、持久性与通信有机制可依；「程序如何协作」先把契约讲在进程之内，「网络与 Web」再把它扩展到机器之间；「数据持久化」处理状态跨进程、跨时间的问题；「真实软件系统」把前七个模块组合成一个应用，并给出失败模型；「正确性与故障」在此之上讨论什么证据说明它是对的、出错时往哪里查；「安全」需要具体机制才能建立威胁模型；「软件演化」讨论怎样长期安全地改变这些系统；「Agent 协作」最后收束，同时它也是一条横贯前面的线。

## 程序如何工作——以 Python 为例（`python`）

**定位**：课程的第一章，回答「程序是什么，它是怎样工作的」。Python 在这里是用于观察程序行为的可执行语言，本模块不要求系统掌握它；本模块建立此后所有模块直接使用的程序语义模型，使它们可以直接给出 Python 实验而不必再解释语言。

**教学主线**：数据是什么 → 程序如何改变数据 → 如何决定下一步做什么 → 如何把复杂行为拆成可推理的小块 → 如何控制变化与错误。共十课：程序如何执行；程序如何选择下一步；数据怎样组织；名字、对象与状态；函数是一个边界；失败也是程序行为；模块与接口；对象作为状态边界；表示会泄漏到行为中；怎样验证自己的理解。语言自带的语法顺序（变量、字符串、列表、条件、循环、函数、类、模块）不作为组织依据。

**核心主题**：表达式、语句与执行；值、类型与表示；名字、对象与状态——别名与共享状态是本模块的核心内容；条件、循环与提前返回；函数作为边界：输入是什么、输出是什么、会不会修改外部状态、什么输入合法、失败时怎么办；容器的选择；就地修改与副作用；失败作为正常路径：异常传播、处理位置与清理；模块与公开接口；类所提供的状态边界；浮点近似与文本编码；判断一段程序是否可信的最小手段（边界输入、断言、最小实验）。

要求是把「能写出程序」推进到「能精确预测程序的行为，并知道自己什么时候预测不了」：给定一段陌生的 Python，能预测它的状态变化、控制流与失败行为；不能预测时知道该构造什么实验来验证；面对一个陌生的函数，先问它修改什么、要求什么、返回什么、怎样失败。

**边界与去处**：语言自带的语法体系不产生课程内容——数值与字符串运算清单、参数种类分类（位置-only、keyword-only、`*args`/`**kwargs`）、装饰器技巧、属性查找与描述符、魔术方法大全、继承与方法解析顺序、迭代器协议与生成器内部机制、上下文管理器协议不进正文；类只讲到「把一组状态和围绕状态的操作放进一个边界」所需的程度。协作式异步、线程与并发模型归 `program-execution`；完整契约与不变量的论述归 `program-composition`；测试判据设计与剖析归 `correctness-and-failure`，本模块只给「这段程序能不能信」的最小检查手段；全课程共用的成本语言归 `cost-and-scale`。

## 如何组织数据与计算——算法、数据结构与可行性判断（`data-and-computation`）

**定位**：让读者能判断数据应该怎样组织，以及一个计算方案是否靠谱。本模块回答三个问题：这个方案在逻辑上为什么正确？数据规模增大以后还能不能运行？为什么这种数据表示或算法设计比另一种更合适？本模块只保留做设计判断所需的成本语言——看出成本的形状；形式化的成本模型、渐近记号定义、摊还、平均与尾延迟、I/O 与局部性、容量估算由 `cost-and-scale` 建立。

**教学主线**：从需求变成计算问题 → 正确意味着什么 → 规模改变以后发生什么 → 数据表示与工作负载 → 序列、集合与映射 → 查找、排序与预处理 → 栈、队列与优先级 → 树：层次、索引与高度 → 图：关系、遍历与依赖 → 搜索空间为什么会爆炸 → 避免重复计算 → 不必搜索所有可能 → 综合设计审查，随机化作为延伸。这条链是判断顺序，算法只是在需要它的位置出现的案例。

**核心主题**：从需求写出输入、输出、条件与规模；循环不变量、终止与反例；成本随规模增长的形状（固定、线性、减半、相乘、分支展开）；表示与工作负载的匹配；查找、去重与按键定位为什么能便宜，以及代价是什么；预处理怎样换取后续查询的加速；处理顺序的选择（后进先出、先进先出、优先级）；层次结构的高度为什么决定成本；关系、可达性与依赖为什么要求没有环；搜索空间为什么随决策数爆炸；什么时候值得复用已算结果（动态规划）、什么时候值得丢弃整块搜索空间（分支定界与剪枝）；随机化换取了什么。要求是能给出一个结构的成本论断，并为一个数据模型选择表示。

**边界与去处**：经典算法的实现细节不占主线——三种排序的实现、heapsort、比较排序下界、KMP 前缀函数、主定理、AVL 旋转、Bellman–Ford、最小生成树割论证、并查集摊还分析、编辑距离状态设计、Freivalds 验证的概率推导都不进正文，需要时降为深入阅读；分支定界与剪枝只讲「界是否合法、是否够紧、算得是否便宜」这一层判断；动态规划只讲「同一个子问题被反复求解」这条主线与它的代价。Python 只是演示用的语言，本模块不是 Python 容器教程。缓存局部性背后的存储层次归 `program-execution`；B 树、外部存储结构与查询计划在引擎中的形态归 `persistence`；并发数据结构归 `program-execution`；成本语言的形式化部分归 `cost-and-scale`。

## 成本与规模（`cost-and-scale`）

**定位**：把「能运行」和「能实际使用」分开。本模块给出全课程共用的成本语言，此后所有性能与容量论断都用它表述；`data-and-computation` 只用到其中「看出成本形状」的部分，形式化的建立与验证在这里。

**核心主题**：时间复杂度与空间复杂度；输入度量与多参数规模；成本模型怎样选；渐近记号的形式定义与增长率；摊还分析；平均情形、最坏情形与尾延迟；I/O 与缓存局部性为什么常常主导总成本；查找、搜索与索引；搜索空间为什么会随决策数爆炸；预计算、空间与时间之间怎样交换；延迟与容量的量级估算；数据量增长时哪些量先崩；基准测试纪律；什么时候「优化」是无效的。

**边界与去处**：从证据定位瓶颈归 `correctness-and-failure`；索引与缓存的实现形态归 `persistence`；分布式容量估算与背压归 `software-systems`。本模块不做常数因子对比表，不复制某个算法的实现细节。

## 程序如何运行（`program-execution`）

**定位**：解释代码下面发生了什么。C 在这里按需进入，作用是把内存、地址、编译与链接变得可观察，而不是一门完整的语言课；操作系统机制在这里与程序接上，使「服务器重启后内存状态为什么消失」这类现象可以回到机制。

**核心主题**：字节、定宽整数、溢出回绕与字节序；读懂少量 C——对象、指针、数组、结构体、`malloc`/`free` 的生命周期——目的是理解内存、地址、值与引用的区别，以及程序为什么可能越界；源文件、目标文件、符号与链接、动态库；指令、寄存器、load/store、调用与返回、栈帧；存储层次与访问模式；为什么 Python 调用 NumPy 最后执行的是 C/C++ 代码；进程与线程；地址空间与虚拟内存（地址转换、缺页）；系统调用与内核边界；文件与描述符；调度与阻塞；同步、竞态与死锁；内核边界的代价。

**边界与去处**：概念产生语言需求，语言目录不产生课程内容——C 的语法只讲到能读懂上面这些现象为止，宏在介绍「编译之前还发生了什么」时出现。逻辑门、ALU 电路、流水线微架构、页表四级结构、TLB 置换、NUMA、调度器参数与发行版管理命令不进正文。文件系统的持久性语义与事务归 `persistence`；进程间协作的契约形态归 `program-composition`；并发与部分失败在分布式系统中的形态归 `software-systems`。

## 程序如何协作（`program-composition`）

**定位**：系统边界与接口。这是「画边界」的第一次正式训练：同一台机器上的多个部分怎样通过接口协作。

**核心主题**：模块与信息隐藏；依赖方向；库、包与版本；API 作为契约——成功路径与失败路径都必须在契约里；序列化与线格式（文本与二进制、schema 演化、向后与向前兼容）；协议与状态机；进程内与进程间的边界；错误在边界处的传播与翻译；超时是契约的一部分。

**边界与去处**：HTTP 与 TLS 的协议细节归 `networks-and-web`；依赖管理、版本与迁移归 `software-evolution`；完整 API 清单与厂商 SDK 用法不进正文。

## 网络与 Web（`networks-and-web`）

**定位**：现代应用怎样通信，以及协议保证与运维后果之间的距离。本模块从「浏览器里的程序怎样让另一台机器替它完成工作」进入，而不是从方法名清单进入。

**核心主题**：分层与分组交换的必要概念；IP 与 DNS；TCP 与 UDP 的实际保证；延迟构成与尾延迟；HTTP 的 request/response 模型、URL、method、headers、body 与 status code；TLS 建立的信任；同源模型与 CORS；缓存语义；连接生命周期与连接池；超时、重试与幂等的相互作用。读者应当能把「端口被占用」「localhost 能访问而别人不能」「刷新之后状态没了」「POST 超时之后能不能重试」这类现象落到机制上。

**边界与去处**：字节级头部记忆、端口号表与厂商 CLI 语法不进正文；认证与授权归 `security`；状态保存在哪里归 `persistence`；服务如何组合归 `software-systems`。

## 数据持久化（`persistence`）

**定位**：状态放在哪里，什么时候会丢。文件、数据库、索引、事务与缓存共同构成持久状态的选择面。

**核心主题**：文件与描述符的持久性边界、缓冲与刷盘；关系模型与键；SQL 的多重集语义与三值逻辑；约束作为完整性规则；连接作为关系组合；变更语句与状态转移；B 树索引、访问路径、查询计划与基数估计；索引的写入代价；事务与日志、隔离级别、MVCC 与锁、崩溃恢复；两个请求同时修改一条记录会怎样；缓存作为解法与问题；缓存失效与一致性；对象存储与二进制内容。核心模型是「声明式语句与它实际触发的执行之间的距离」。

**边界与去处**：分布式一致性权衡与复制拓扑归 `software-systems`；文件系统的内核机制归 `program-execution`；完整 SQL 语法、厂商管理命令与 ORM 方法清单不进正文。

**夹具**：关系语义、`NULL`、聚合、连接与约束，带主键、外键、唯一约束与 `CHECK`；索引与查询计划需要更大规模的行与多个索引；事务与隔离需要可并发访问的夹具。

## 真实软件系统（`software-systems`）

**定位**：一个应用怎样由前面这些东西组合起来。本模块是课程的中轴：把浏览器、客户端、服务器、数据库、缓存、队列与第三方服务放到一张图上，并从失败模型推导行为。

**核心主题**：职责划分——同一件事放在浏览器、客户端、服务器还是数据库里做，代价与后果分别是什么；有状态与无状态服务；任务队列与异步工作；缓存的位置与代价；对象存储；第三方服务与它们各自的失败方式；部署形态——进程、端口、环境变量、文件系统与网络边界，以及「本机能跑、部署后不能跑」的原因；容量与背压；失败模型与部分失败；时钟、顺序与超时；复制与一致性的最少必要模型；幂等与投递语义；恢复与对账；降级与限流。

**边界与去处**：单机并发原语归 `program-execution`；事务与索引语义归 `persistence`；协议细节归 `networks-and-web`。重点是画出结构并从失败模型推导行为，而不是罗列产品与架构模式。

## 正确性与故障（`correctness-and-failure`）

**定位**：系统为什么会错，以及出错时应该往哪里查。本模块把前面模块的机制放进诊断路径。

**核心主题**：测试作为判据设计——覆盖真实的失败模式，而不是行数或覆盖率数字；确定性与隔离；基于属性与不变量的测试；日志、指标与追踪各自回答什么问题；异常、调用栈与错误传播；超时与重试的语义——哪些操作可以重试、哪些不能简单重试，以及重试放大；并发修改与竞态；部分失败与降级；剖析与从证据定位瓶颈；从输入、状态、日志、调用栈、网络、数据库与环境这些观察面定位问题，而不是猜。

**边界与去处**：断言 API 与工具参数清单不进正文；成本模型与基准测试纪律归 `cost-and-scale`，I/O 机制归 `program-execution`；安全相关的失效归 `security`；变更流程与 CI 归 `software-evolution`。

## 安全（`security`）

**定位**：对抗性场景下的系统推理。从资产、对手与信任边界开始，把前面模块的机制放进威胁模型，再讨论具体控制。

**核心主题**：威胁建模与信任边界；认证、授权与会话；口令与密钥的生命周期；TLS 与哈希的正确使用；输入验证与输出编码；注入与解析歧义；XSS、CSRF 与同源模型；secret 放在哪里——为什么前端不能直接保存数据库密码；权限与最小授权；沙箱与隔离；依赖与供应链；审计与隐私的取舍。

**边界与去处**：先建威胁模型再谈控制——不理解机制就背漏洞缩写、没有威胁模型的检查表、密码学参数表不进正文。要识别「已加密」「已签名」这类表述并不等于所需性质。

## 软件演化（`software-evolution`）

**定位**：怎样安全地修改一个持续演化的项目。前面模块讲系统如何工作，本模块讲如何改动它们，以及什么证据支持「改动正确」这一结论。

**核心主题**：仓库工作流与 Git 对象模型——读懂历史、回退、分支与合并；接口与依赖方向从「改动」的角度重看；兼容、弃用与迁移；依赖声明、锁文件与可复现构建；配置与环境；部署与发布；CI 作为验证管道；版本与回滚。

**边界与去处**：Git 参数含义与命令清单不进正文；测试判据设计与诊断归 `correctness-and-failure`。重点始终是「什么证据支持改动正确」，而不是工具用法。

## Agent 协作（`agent-collaboration`）

**定位**：把前面模块的判断力用在 Agent 辅助开发上。它是课程的收束，同时也是一条横贯全课程的线。

**核心主题**：把需求、约束与验收标准写成可检验的要求；比较 Agent 提出的方案——依据是什么、失败模式在哪里；review 一个 diff——一个 Agent 改了二十个文件时，应该检查边界、状态、职责与信任关系是否被改动，而不是逐行重写；要求 Agent 给出验证证据，并判断证据是否覆盖真实的失败模式；哪些判断不能外包；Agent 输出的常见失败模式——无脑重试、把可能失败的调用当成可靠函数、把状态放到错误的层、用缓存掩盖正确性问题。

**边界与去处**：本模块不教具体工具的产品用法——工具会变，判断力不会。产品不集成 AI 辅导，Agent 协作是课程主题而不是产品功能（见 `doc/DESIGN.md`）。

## Agent 协作这条线

Agent 协作不在最后集中成一章，而是每一部分都要回答：Agent 可以替你做什么，你不能把什么判断外包给它。

| 模块 | Agent 可以代劳 | 读者不可外包的判断 |
| --- | --- | --- |
| 程序如何工作 | 写出函数、循环与容器操作的实现 | 这段程序在做什么、会怎样失败 |
| 如何组织数据与计算 | 实现数据结构与查找 | 规模与操作模式、表示选择 |
| 成本与规模 | 做基准测试与剖析 | 瓶颈在哪里、哪一步优化才有意义 |
| 程序如何运行 | 写构建脚本与少量 C | 进程、内存与边界的心智模型 |
| 程序如何协作 | 搭模块骨架与序列化代码 | 接口契约与失败路径由谁负责 |
| 网络与 Web | 写 endpoint 与客户端调用 | 认证、状态与失败处理 |
| 数据持久化 | 写 SQL 与迁移 | 数据关系、事务边界与索引需求 |
| 真实软件系统 | 写容器与部署配置 | 进程、端口、环境变量、文件系统与网络边界 |
| 正确性与故障 | 生成测试与日志 | 测试是否覆盖真实失败模式 |
| 安全 | 加校验与配置 | 信任边界与权限模型 |
| 软件演化 | 提交、分支与 CI 配置 | 什么改动可以做、什么证据支持它 |
| Agent 协作 | 生成、修改与解释代码 | 需求、约束、方案取舍与验收 |
