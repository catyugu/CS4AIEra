# CURRICULUM.md

本文件是课程地图：课程要形成的判断力、模块顺序、每个模块教什么、模块之间怎样分工。它描述**教学意图**，不描述清单。

精确的课程树——子章节、课时 `id`、标题、顺序与发布状态——由各目录的 `_section.yaml` 与课时 frontmatter 表达，那是唯一的权威来源：新增一节课、拆分一个章节或推进发布状态都不应该要求修改本文件。写作方法见 `doc/CONTENT_GUIDE.md`；产品与运行时的设计见 `doc/DESIGN.md`；仓库不变量与完成标准见 `AGENTS.md`。

## 毕业目标

课程不培养「没有 AI 也能从零实现一切」的初级程序员，而是培养知道软件世界如何运作、因而能够正确提出问题、判断设计、发现风险并验证 Agent 工作成果的技术使用者。

课程结束时，读者应当能独立回答这些问题：

- 这个需求在技术上大致可不可行？
- 这件事应该放在浏览器、客户端、服务器还是数据库里完成？
- 数据存在哪里，什么时候会丢？
- 为什么一个程序在本机能跑、部署后却跑不起来？
- 为什么「把这个函数改快一点」可能毫无意义？
- 为什么一个 API 不能假设调用一定成功？
- 为什么并发修改会产生错误？
- 为什么缓存既解决问题又制造问题？
- 哪些操作可以重试，哪些不能简单重试？
- 一个 Agent 改了二十个文件，应该检查什么，而不是逐行重写一遍？
- 一个程序出了 bug，应该查输入、状态、日志、调用栈、网络、数据库还是环境？
- 一个 Agent 说「这样更高效」「这样更安全」「这样更可扩展」，它的依据是什么？

支撑这些问题的是同一项能力，它也是本课程的特色：**画边界**。遇到任何系统先问：什么在哪里运行？状态在哪里？谁调用谁？数据以什么形式越过边界？哪个组件信任哪个组件？哪一步可能失败？

大量软件问题最终都归到四类错误：边界放错了、状态放错了、职责放错了、信任关系弄错了——或者把可能失败的边界当成了可靠的函数调用。

## 组织原则

- **按心智模型的依赖关系组织，不按学科分类。** 顺序是：一个程序如何表达计算 → 程序如何组织状态与数据 → 它有多贵、能撑多大 → 程序如何被计算机执行 → 多个程序如何通过接口协作 → 机器之间如何通信 → 数据如何持久保存 → 一个应用怎样由这些东西组合起来 → 出错时怎样定位与观察 → 怎样安全地修改、审查与验证一个持续演化的系统。正确性与 Agent 协作都不是最后才第一次出现：每一部分都要给出结论的证据，Agent 协作集中在综合案例、调试与修改审查中讨论，不作为每课的叙事框架。
- **章节名是导航，不是教学意图。** 导航名取短而稳定的主题名（如应用系统），让读者扫一遍课程树就得到一张知识地图；一个模块的教学目的、边界与取舍写在它自己的 `summary` 与本文件的定位段。名称不写成「怎样…」「为什么…」「…如何…」的问句式，也不写成覆盖面过宽的复合短语——相邻模块看起来没有区别时，读者只能靠点开才知道这一章讲什么。
- **准入判据是判断力，不是惯例。** 一个知识点如果不知道它也不会妨碍读者理解软件或判断 Agent 的方案，就不进主线，哪怕传统 CS 课程都会讲。已经写好不构成保留的理由：课程定位变化后，删减本身就是设计工作。对课时用同一个判据，问法更具体：**删掉这一课以后，读者会在哪一种真实的软件设计判断中明显变差？**回答不出来，它就不该作为独立主线课时，最多是某一课里的一节或一段延伸阅读。
- **删减的判据是一句话**：读者永远不会亲自实现它，但需要用这段内容判断 Agent 给出的方案是否合理——这段内容还有价值吗？答案为否，它就不占据主线篇幅。状态与副作用、接口与契约、数据表示、不变量、时间与空间成本、哈希与索引为什么能加速查询、树与图各自表达什么关系、缓存为什么有效与什么时候失效、搜索空间为什么会爆炸、预计算与空间时间怎样交换、平均与最坏情形为什么可能不同、「能运行」为什么不等于「设计合理」，属于留在主线的例子。
- **课程不是操作性教程。** Linux 命令、编辑器、Git 命令、Python 环境安装、Agent 软件的操作技巧与部署步骤不属于任何模块的教学目标；它们最多以附录或外部链接出现，不进入课程主干。
- **三种掌握层次，越往后越克制。**

| 层次 | 要求 | 例 |
| --- | --- | --- |
| 必须能解释 | 用自己的话说明机制与它的边界 | 什么是进程；索引为什么能加速查询 |
| 必须能判断 | 面向具体情形作出并说明理由 | 这份数据能不能只放在内存里；这个操作能不能安全重试 |
| 能够亲自实现 | 动手做过最小的一种，其余只理解保证 | 写出循环、函数、简单数据结构操作、HTTP 调用、简单 SQL、基本测试 |

## 模块顺序

模块沿着程序逻辑、数据与算法、计算机执行机制、组件接口、网络、持久化、应用系统、调试测试、安全、修改审查的依赖关系展开。实际导航名称和阅读顺序见课程树。

顺序由依赖关系决定，不由学科惯例决定。「程序逻辑与状态」建立工作语言与执行模型；「数据、算法与规模」把「怎样做」与「做起来有多贵」放进同一条判断链，先建立成本语言，再将表示选择、预处理与索引放在同一个操作成本问题中讨论；「计算机如何执行程序」把程序接到机器与内核上，使后面的运行时、持久性与通信有机制可依；「软件组件与接口」先把契约讲在进程之内，「网络与 Web」再把它扩展到机器之间；「持久化与数据库」处理状态跨进程、跨时间的问题；「应用系统」把前面的六个模块组合成一个应用，并给出失败模型；「调试、测试与可观测性」在此之上讨论出错时往哪里查、什么证据说明它是对的；「安全与信任边界」需要具体机制才能建立威胁模型；「修改与审查软件」收束，把前面的模型用在一次具体改动上。

## 程序逻辑与状态（`program-logic-and-state`）

**定位**：课程的第一章，回答「程序是什么，它是怎样工作的」。Python 在这里是用于观察程序逻辑与状态的可执行语言，本模块不要求系统掌握它；本模块建立此后直接使用的执行、绑定、控制流和调用模型。后续实验可以沿用这些概念；新出现的库接口、具名参数和资源管理语法，仍要在使用处解释到能够读懂当前代码，不把“学过 Python 基础”当成认识所有写法。

**教学主线**：执行顺序 → 名字、对象与状态变化 → 容器操作 → 条件与循环 → 函数的参数、返回值与副作用 → 异常传播与清理 → 类与实例 → 模块与导入。名字与对象的关系用列表建立，从共享、重新赋值与独立追加推进到浅拷贝；读取和替换列表位置在需要追踪内部对象时就地解释。容器选择随后只比较各自保留的信息，控制流据此逐项处理数据。类先展示多个实例如何各自保存状态并复用操作，再讨论类上共享的状态；模块另行解释名字的组织与导入。练习尽可能选择状态追踪、边界诊断、契约比较或副作用审查，不统一成预测结果；系统测试与改动审查由后续模块负责。

**核心主题**：值、类型、表达式、语句与执行；名字、对象与状态——别名与共享状态是本模块的核心内容；条件、循环、提前返回与循环为什么停下来；序列、集合与映射表达什么、允许哪些操作、修改后会发生什么；就地修改与副作用；函数作为边界：输入是什么、输出是什么、会不会修改外部状态、什么输入合法、失败时怎么办；失败作为正常路径：传播、处理位置与最小清理；函数、模块与对象这三种组织手段各自把什么收进一个边界；判断一段程序是否可信的最小手段（边界输入、断言、最小实验、反例）。

**语法按需引入**：本模块不设独立的语法知识点，语言构造在第一次需要它的推理出现时引入——值、类型、名字、赋值、表达式与调用随第一个执行模型进入，`if`、`for`、`while` 随控制流进入，`def` 与 `return` 随函数边界进入，`try` 随失败路径进入，`import` 与最简单的 `class` 随状态与行为的组织进入。这条规则同时防住两件事：把模块写成语法目录，以及正文默认读者已经会 Python。

要求是把「能写出程序」推进到「能精确预测程序的行为，并知道自己什么时候预测不了」：给定一段陌生的 Python，能预测它的状态变化、控制流与失败行为；不能预测时知道该构造什么实验来验证；面对一个陌生的函数，先问它修改什么、要求什么、返回什么、怎样失败。

**边界与去处**：语言自带的语法体系不产生课程内容——数值与字符串运算清单、参数种类分类（位置-only、keyword-only、`*args`/`**kwargs`）、装饰器技巧、属性查找与描述符、魔术方法大全、继承与方法解析顺序、迭代器协议与生成器内部机制、上下文管理器协议不进正文；类只讲实例、属性、方法与共享状态的最低必要模型。表示选择与操作成本归 `data-algorithms-and-scale`，本模块只讲容器语义与操作。浮点表示连同内存、地址与字节一起在 `program-execution` 建立；文本、字节与编码在 `program-composition` 的序列化与线格式处建立；模块公开什么、依赖方向与接口的兼容性成本归 `program-composition` 与 `change-and-review`，本模块只建立模块对象、模块命名空间和导入的基本模型。协作式异步、线程与并发模型归 `program-execution`；测试判据设计与剖析归 `debugging-and-observability`，本模块只给「这段程序能不能信」的最小检查手段；成本语言与表示选择归 `data-algorithms-and-scale`。

## 数据、算法与规模（`data-algorithms-and-scale`）

**定位**：把需求变成一项正确、合适、而且在目标规模下做得完的计算。这是「怎样做」与「做起来有多贵」合成的一章：表示与计算方法的选择本来就无法脱离操作成本讨论——选字典而不是列表、建索引、用优先队列、复用已算结果、不穷举，理由都落在各类操作的成本分布上。成本语言因此在本模块正式建立，成为表示与算法设计共用的一套东西，不再分成「先建立定性直觉、再正式建立复杂度」两章。本模块要回答的问题是一句话：怎样把一个需求变成合理的计算？

**教学主线**：问题是什么 → 结果怎样才算正确 → 计算需要多少工作 → 为重复操作维护什么结构 → 规模变大怎么办。先把需求写成输入、输出、约束与规模；再给出最小的正确性语言（规约、反例、不变量、终止）；接着建立成本随规模增长的语言（固定、线性、对数、线性对数、平方、指数，以及上界与渐近紧确界的区别）；然后统一比较表示、排序、预处理与索引，按操作频率权衡构建、查询、更新和空间成本，避免重复讲解维护额外结构的理由；然后处理顺序、层次与依赖（队列、优先级、树、图，只到软件判断需要的模型）；最后处理候选太多时的情形（状态复用、组合爆炸、剪枝、近似，以及重新表述问题）。组合搜索作为拓展主线，只要求估算空间、判断剪枝是否误删候选，以及比较计算界的成本，不展开完整的分支定界实现。综合案例只使用已建立的概念审查方案。课时边界由「读者需要作出的判断」决定，不由经典算法与数据结构的目录决定。

**核心主题**：把需求写成输入、输出、必须满足的条件与规模；反例、关键不变量与终止条件作为正确性证据——循环不变量在这里是一种推理工具，不发展成算法证明课；工作负载决定的表示选择（要不要保持次序、允不允许重复、按位置取还是按成员或键取、读多还是写多）；成本随规模的增长率（固定、线性、对数、线性对数、平方、指数）、渐近记号与输入度量；平均情形与最坏情形的区别；摊还成本只给足以理解连续操作的简短说明，完整分析留给实现机制；按键定位为什么通常很快，以及这种速度依赖什么、维护它要付出什么；用一次性成本换重复查询（排序、预处理、索引）；处理顺序（后进先出、先进先出、优先级）——它们合起来只回答一件事：下一项由什么决定；层次与深度为什么决定一次操作的路径长度；关系、可达性与依赖，以及依赖图里的环意味着不存在满足全部依赖先后关系的线性顺序；同一个计算状态被反复求解时复用已算结果的条件与代价——状态必须包含决定后续结果所需的全部信息，总工作量随不同状态的数量乘以每个状态的处理成本增长；候选本身太多时，利用约束排除整块候选、接受近似，或者重新表述问题；成本论断怎样用测量检验，以及什么时候「优化」是无效的。要求是能给出一个结构的成本论断，并为一个数据模型选择表示。

**边界与去处**：经典算法的实现细节不占主线——三种排序的实现、heapsort、比较排序下界、KMP 前缀函数、主定理、平衡树的旋转、Bellman–Ford 与 Dijkstra 的完整推导、最小生成树割论证、并查集摊还分析、编辑距离状态设计、Freivalds 验证的概率推导都不进正文，需要时降为深入阅读；连续布局与链式结构的对照同样不进正文，链式结构最多作为附加阅读。栈、队列与优先队列不各自成为算法主题，它们合起来只讲「下一项由什么决定」。树与图不发展成图论入门——树表达单一父属层次，图表达一般关系，依赖图里的环说明不存在满足全部依赖的先后顺序，这已经够支撑后面各模块。动态规划、广度优先遍历与分支定界在对应机制处给出标准名称，方便读者识别技术交流中的说法；不因此展开传统算法实现。状态复用与剪枝只留两条一般判断：同一个计算状态反复出现时结果可以复用，且缓存键必须包含决定结果的全部状态；候选数指数增长时利用约束排除整块候选、接受近似，或者重新表述问题。哈希只讲到保证这一层——按键定位通常很快、这种速度依赖键的分布与具体实现、维护它要付出空间与更新代价；开放寻址、链地址与负载因子阈值不进核心。排序稳定性只在需要它的那一句里解释。带权最短路不进这条教学主线。剪枝只讲「一块区域能不能被证明没有希望、这个界是否合法、够紧、算得便宜」。随机化不占主线：效果与代价留在素材里，在抽样、随机退避、随机标识这类真实场景中引用。递归与记忆化用真正的重复子问题建立模型，复用后的成本从状态数与每个状态的工作推导；不以只递增计数器的循环代替算法。树与图以小结构解释层次、可达性和依赖顺序，展示算法时先固定边的含义与方向。综合审查分别估算扫描、排序和更新，不能把不同操作的计数直接当作耗时比例。Python 只是演示用的语言，本模块不是 Python 容器教程。存储层次与访问局部性的机制归 `program-execution`；B 树、外部存储结构与查询计划在引擎中的形态归 `persistence`；并发数据结构归 `program-execution`；从证据定位瓶颈与剖析归 `debugging-and-observability`；尾延迟、容量与背压的估算归 `networks-and-web` 与 `software-systems`。

## 计算机如何执行程序（`program-execution`）

**定位**：解释代码下面发生了什么。与 `program-logic-and-state` 的分工：那一章建立程序的可观察行为模型——执行、状态、控制流、函数、副作用与异常；本章解释这些行为由什么机制实现——内存与地址、机器代码、进程与线程、以及操作系统提供的边界。C 在这里按需进入，作用是把内存、地址、编译与链接变得可观察，而不是一门完整的语言课；操作系统机制在这里与程序接上，使「服务器重启后内存状态为什么消失」这类现象可以回到机制。

**核心主题**：围绕四个问题展开：一个值实际存在哪里；源代码怎样变成正在运行的程序；运行中的程序可以访问哪些资源；多件工作交错时怎样影响共享状态。字节与定宽表示解释范围和舍入，地址与生命周期解释共享和失效，编译与装载解释构建产物和运行环境，进程与内核解释私有内存和受控资源访问，线程与事件循环解释计算和等待，同步解释怎样保持一次更新的条件。

**教学衔接**：Python 中的值先作为抽象值使用，再通过“把数写入有限格式”引出机器表示。C 只在表示、指针和构建需要可观察写法时进入；片段明确是完整程序、函数还是函数内语句。进程先从多次启动各自持有状态进入，再解释地址空间和内核边界。并发先追踪读写交错，实验装置作为可选验证，不承担模型的首次解释。

**边界与去处**：访问局部性只用于解释相同工作量为何可能耗时不同；具体容器布局、数组视图和性能实验归 `debugging-and-observability` 的深入分析。文件读取接口作为资源契约的阅读示例，不要求记忆 POSIX 类型和函数。C 的语法只讲到能读懂当前现象，ABI 只用于识别部署产物需要匹配。逻辑门、ALU 电路、流水线微架构、页表结构、TLB 置换、NUMA、调度器参数与发行版管理命令不进正文。文件系统的持久性语义与事务归 `persistence`；进程间协作的契约归 `program-composition`；并发与部分失败在分布式系统中的形态归 `software-systems`。

## 软件组件与接口（`program-composition`）

**定位**：系统边界与接口。这是「画边界」的第一次正式训练：同一台机器上的多个部分怎样通过接口协作——模块、API、序列化与进程边界。

**核心主题**：模块与信息隐藏；依赖方向；库、包与版本；API 作为契约——成功路径与失败路径都必须在契约里；序列化与线格式（文本与二进制、schema 演化、向后与向前兼容）；协议与状态机；进程内与进程间的边界；错误在边界处的传播与翻译；超时是契约的一部分。

**边界与去处**：HTTP 与 TLS 的协议细节归 `networks-and-web`；依赖管理、版本与迁移归 `change-and-review`；完整 API 清单与厂商 SDK 用法不进正文。

## 网络与 Web（`networks-and-web`）

**定位**：现代应用怎样通信，以及协议保证与运维后果之间的距离。本模块从「浏览器里的程序怎样让另一台机器替它完成工作」进入，而不是从方法名清单进入。

**核心主题**：分层与分组交换的必要概念；IP 与 DNS；TCP 与 UDP 的实际保证；延迟构成与尾延迟；HTTP 的 request/response 模型、URL、method、headers、body 与 status code；TLS 建立的信任；同源模型与 CORS；缓存语义；连接生命周期与连接池；超时、重试与幂等的相互作用。读者应当能把「端口被占用」「localhost 能访问而别人不能」「刷新之后状态没了」「POST 超时之后能不能重试」这类现象落到机制上。

**边界与去处**：字节级头部记忆、端口号表与厂商 CLI 语法不进正文；认证与授权归 `security`；状态保存在哪里归 `persistence`；服务如何组合归 `software-systems`。

## 持久化与数据库（`persistence`）

**定位**：状态放在哪里，什么时候会丢。文件、数据库、索引、事务与缓存共同构成持久状态的选择面。

**核心主题**：文件与描述符的持久性边界、缓冲与刷盘；关系模型与键；SQL 的多重集语义与三值逻辑；约束作为完整性规则；连接作为关系组合；变更语句与状态转移；B 树索引、访问路径、查询计划与基数估计；索引的写入代价；事务与日志、隔离级别、MVCC 与锁、崩溃恢复；两个请求同时修改一条记录会怎样；缓存作为解法与问题；缓存失效与一致性；对象存储与二进制内容。核心模型是「声明式语句与它实际触发的执行之间的距离」。

**边界与去处**：分布式一致性权衡与复制拓扑归 `software-systems`；文件系统的内核机制归 `program-execution`；完整 SQL 语法、厂商管理命令与 ORM 方法清单不进正文。

**夹具**：关系语义、`NULL`、聚合、连接与约束，带主键、外键、唯一约束与 `CHECK`；索引与查询计划需要更大规模的行与多个索引；事务与隔离需要可并发访问的夹具。

## 应用系统（`software-systems`）

**定位**：一个应用怎样由前面这些东西组合起来。本模块是课程的中轴：把浏览器、客户端、服务器、数据库、缓存、队列与第三方服务放到一张图上，并从失败模型推导行为。

**核心主题**：职责划分——同一件事放在浏览器、客户端、服务器还是数据库里做，代价与后果分别是什么；有状态与无状态服务；任务队列与异步工作；缓存的位置与代价；对象存储；第三方服务与它们各自的失败方式；部署形态——进程、端口、环境变量、文件系统与网络边界，以及「本机能跑、部署后不能跑」的原因；容量与背压；失败模型与部分失败；时钟、顺序与超时；复制与一致性的最少必要模型；幂等与投递语义；恢复与对账；降级与限流。

**边界与去处**：单机并发原语归 `program-execution`；事务与索引语义归 `persistence`；协议细节归 `networks-and-web`。重点是画出结构并从失败模型推导行为，而不是罗列产品与架构模式。

## 调试、测试与可观测性（`debugging-and-observability`）

**定位**：出错时应该往哪里查，以及什么证据说明一个结论是对的。正确性、失败与测试贯穿前面每个模块——每个模块都已经在回答「这个结论有什么证据」；本模块把前面模块的机制放进诊断路径，并把测试、日志、指标与追踪作为产生证据的手段集中讲清楚。

**核心主题**：测试作为判据设计——覆盖真实的失败模式，而不是行数或覆盖率数字；确定性与隔离；基于属性与不变量的测试；日志、指标与追踪各自回答什么问题；异常、调用栈与错误传播；超时与重试的语义——哪些操作可以重试、哪些不能简单重试，以及重试放大；并发修改与竞态；部分失败与降级；剖析与从证据定位瓶颈；从输入、状态、日志、调用栈、网络、数据库与环境这些观察面定位问题，而不是猜。

**边界与去处**：断言 API 与工具参数清单不进正文；成本语言与基准测试纪律归 `data-algorithms-and-scale`，I/O 机制归 `program-execution`；安全相关的失效归 `security`；变更流程与 CI 归 `change-and-review`。

## 安全与信任边界（`security`）

**定位**：对抗性场景下的系统推理。从资产、对手与信任边界开始，把前面模块的机制放进威胁模型，再讨论具体控制。

**核心主题**：威胁建模与信任边界；认证、授权与会话；口令与密钥的生命周期；TLS 与哈希的正确使用；输入验证与输出编码；注入与解析歧义；XSS、CSRF 与同源模型；secret 放在哪里——为什么前端不能直接保存数据库密码；权限与最小授权；沙箱与隔离；依赖与供应链；审计与隐私的取舍。

**边界与去处**：先建威胁模型再谈控制——不理解机制就背漏洞缩写、没有威胁模型的检查表、密码学参数表不进正文。要识别「已加密」「已签名」这类表述并不等于所需性质。

## 修改与审查软件（`change-and-review`）

**定位**：怎样安全地改动一个已经存在、并且会继续演化的系统，以及怎样判断一次改动是否可信。前面模块讲系统如何工作，本模块讲改它们：接口与依赖方向从「改动」的角度重看，兼容、弃用与迁移，仓库工作流与可复现构建，CI 作为验证管道，部署、版本与回滚。审查是同一件事的另一半——一份 diff、一份设计说明或一段 Agent 生成的实现，要检查什么，以及什么证据支持「这个改动正确」。改动最常见的执行者之一就是 Agent，而改一个已有系统与审查一次改动需要的是同一条判断力：边界、状态、职责与信任关系有没有被改坏。

**核心主题**：仓库工作流与 Git 对象模型——读懂历史、回退、分支与合并；接口与依赖方向从「改动」的角度重看；兼容、弃用与迁移；依赖声明、锁文件与可复现构建；配置与环境；部署与发布；CI 作为验证管道；版本与回滚；把需求、约束与验收标准写成可检验的要求；比较一个方案——依据是什么、失败模式在哪里；review 一个 diff——一次改动碰了二十个文件时，检查边界、状态、职责与信任关系是否被改动，而不是逐行重写一遍；要求给出验证证据，并判断证据是否覆盖真实的失败模式；哪些判断不能外包；Agent 输出的常见失败模式——无脑重试、把可能失败的调用当成可靠函数、把状态放到错误的层、用缓存掩盖正确性问题。

**综合判断**：需求、迁移、依赖、验证与发布分别建立自己的模型，改动审查再把它们连接起来。练习要带入新的历史、状态或失败条件，避免把正文结论换成问句再问一次。

**边界与去处**：本模块不教具体工具的产品用法——工具会变，判断力不会；Git 参数含义与命令清单不进正文。测试判据设计与诊断归 `debugging-and-observability`；接口本身的形态归 `program-composition`。产品不集成 AI 辅导，Agent 是课程的使用情境而不是产品功能（见 `doc/DESIGN.md`）。

## Agent 协作这条线

读者用这些知识判断 Agent 提供的实现与方案。各模块先把机制讲清楚，综合案例、调试和改动审查再讨论如何分配实现工作与判断责任，无须每课都安排一个 Agent 场景。下表说明这种分工，不是各课必须重复的教学模板。

| 模块 | Agent 可以代劳 | 读者不可外包的判断 |
| --- | --- | --- |
| 程序逻辑与状态 | 写出函数、循环与容器操作的实现 | 这段程序在做什么、会怎样失败 |
| 数据、算法与规模 | 实现数据结构与查找、做基准测试 | 规模与操作模式、表示选择、瓶颈在哪里 |
| 计算机如何执行程序 | 写构建脚本与少量 C | 进程、内存与边界的心智模型 |
| 软件组件与接口 | 搭模块骨架与序列化代码 | 接口契约与失败路径由谁负责 |
| 网络与 Web | 写 endpoint 与客户端调用 | 认证、状态与失败处理 |
| 持久化与数据库 | 写 SQL 与迁移 | 数据关系、事务边界与索引需求 |
| 应用系统 | 写容器与部署配置 | 进程、端口、环境变量、文件系统与网络边界 |
| 调试、测试与可观测性 | 生成测试与日志 | 测试是否覆盖真实失败模式 |
| 安全与信任边界 | 加校验与配置 | 信任边界与权限模型 |
| 修改与审查软件 | 生成、修改与解释代码，提交、分支与 CI 配置 | 什么改动可以做、什么证据支持它、需求与验收 |
