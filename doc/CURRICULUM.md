# CURRICULUM.md

本文件说明课程面向谁、希望形成哪些能力，以及选择和组织内容的原则。各章的具体范围、课时标题和顺序由课程目录的 `_section.yaml`、课时 frontmatter 与正文维护，本文件不另列章节说明。

写作方法见 `doc/CONTENT_GUIDE.md`；产品与运行时设计见 `doc/DESIGN.md`；仓库约束与完成标准见 `AGENTS.md`。

## 课程宗旨

这是一套面向非计算机专业自学者的计算机科学入门课程。读者可以没有编程基础，但愿意阅读代码、追踪过程并理解技术概念。

课程帮助读者理解程序、计算机和应用怎样工作，在 AI 工具辅助开发时能够提出具体需求、理解方案、定位问题并验证结果。读者既需要理解正常过程，也需要掌握分析错误的基本方法。

## 学习成果

学完课程，读者应能：

- 阅读短程序，追踪控制流、状态变化和失败路径。
- 根据数据规模和操作频率，比较表示与算法的成本。
- 解释源码、运行时、进程、内存和操作系统之间的关系。
- 追踪组件之间的数据与调用，理解接口的输入、输出和失败约定。
- 说明一个 Web 应用的组成，辨认常见技术在开发和运行中的职责。
- 为数据选择保存方式，理解查询、约束、事务和并发修改。
- 分析后台处理、容量不足和组件故障怎样影响用户操作。
- 识别身份、权限、不可信输入和第三方代码带来的具体安全问题。
- 把需求写成验收标准，通过测试和代码审查判断一次修改。

这些能力建立在对机制的理解上。读者应当能够自己解释一次执行或请求的过程，再用运行结果检验解释。

## 内容取舍

主线选择能帮助读者理解常见软件、判断方案和诊断问题的知识。一个主题是否成为独立课时，取决于它能否形成清楚且有用的认识；传统教材目录和已经写好的篇幅都不构成保留理由。

先讲完整的正常过程，再引入会改变当前判断的失败条件。专业细则、产品配置和少见边界情况按实际需要取舍，通过来源链接提供继续学习的入口。删去的细节不必逐项改成补充单元。

使用具体代码、数据、报文和状态轨迹解释机制。原理与技术名称应当相互对应：读者既能说明发生了什么，也能识别技术交流中的常用术语。

## 整体组织

课程按理解上的依赖关系推进：从可观察的程序行为进入，逐步连接到执行机制、组件协作、网络通信、数据管理和完整应用，再讨论安全与持续维护。相邻章节通过已经建立的概念衔接。

课时围绕一个概念或一组紧密相关的机制组织，按理解上的依赖关系安排顺序。程序与算法基础之后，结合实际应用说明概念在哪个环节起作用、影响什么行为，以及它和已经讲过的机制如何配合。案例可以跨课复用，每次只引入理解当前概念所需的背景。

一个核心模型在适合的位置完整建立，后文在需要时引用，并说明新场景增加了什么。跨场景复用案例应带来新的认识，避免反复铺陈同一种超时、缓存或审查结论。

章与课时采用简洁、明确的主题名称，优先使用通行中文术语。学习目标写在 frontmatter，具体问题可以用于正文引入，标题不承担整段教学目标。

## 练习与验证

练习让读者追踪执行、解释现象、修改输入、构造失败条件、比较方案和检验结果。题型随主题变化，既训练理解和操作，也训练审查。

可运行例子使用明确的初始数据和可核对的结果。系统故障等不适合在浏览器里真实重现的过程，用明确假设下的状态表解释。模型推演、真实运行和性能测量分别标明。

## AI 辅助开发

读者可以让 Agent 实现、修改和解释代码，准备实验与收集结果。需求、允许的行为和验收标准仍需由使用者判断。

正文先讲清知识本身，在综合案例中再讨论怎样分配工作、检查实现和验证结论。无需为每节课另设 Agent 场景。
